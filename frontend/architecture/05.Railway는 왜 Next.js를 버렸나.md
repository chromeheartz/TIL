# Railway는 왜 Next.js를 버렸나

> **원문**: [Moving Railway's Frontend Off Next.js](https://blog.railway.com/p/moving-railways-frontend-off-nextjs) — Victor Ramirez (Railway)

Railway가 프로덕션 프론트엔드 전체를 Next.js에서 `Vite + TanStack Router`로 옮겼다는 글. 대시보드, 캔버스, railway.com까지 전부다. 그것도 PR 두 개, 다운타임 0으로. 요즘 "Next.js 탈출" 글이 종종 보이는데 이건 실제 수백만 유저 서비스 사례라 꼼꼼히 읽어봤다.

### Next.js가 잘 맞았던 시절, 그리고 아니게 된 시점

Next.js 덕에 railway.com이 0에서 월 수백만 유저 서비스까지 컸다는 건 저자도 인정한다. 프레임워크가 나쁜 게 아니라, **제품에 더 이상 맞지 않게 된 것**이 문제였다.

#### 빌드 10분, 그중 6분이 Next.js

프론트 빌드가 10분을 넘겼고, 그중 6분이 순수 Next.js 몫이었다. 절반은 `finalizing page optimization` 단계에 멈춰 있었다고. 하루에 여러 번 배포하는 팀 입장에서 이건 사소한 불편이 아니라 **모든 이터레이션마다 내는 비싼 세금**이다.

#### 서버 우선 프레임워크 vs 클라이언트 중심 제품

Railway 앱은 압도적으로 클라이언트 사이드다. 대시보드는 상태가 많은 리치 UI, 캔버스는 실시간, 웹소켓이 사방에 깔려 있다. Next.js의 서버 우선 프리미티브는 거의 쓰지 않았고, 오히려 Pages Router 위에 레이아웃·라우팅용 자체 추상화를 얹어서 쓰고 있었다.

#### Pages Router의 레이아웃 문제

여전히 Pages Router였고, 공유 레이아웃은 전부 해키한 우회책이었다. App Router로 가면 일부는 해결되겠지만, App Router는 서버 우선 패러다임에 강하게 기대고 있다. 의도적으로 클라이언트 주도인 제품을 **필요도 없는 패러다임에 맞춰 다시 짜는** 건 말이 안 된다고 판단했다.

### 왜 TanStack Start + Vite인가

원하는 스택의 조건은 세 가지였다. 명시적일 것, 클라이언트 우선일 것, 이터레이션이 빠를 것. 그리고 솔직히 "쓰는 게 즐겁다"는 점도 컸다고.

- **타입 안전 라우팅이 기본** — 라우트 파라미터와 search params가 추론되고, 라우트 트리 전체에서 자동완성이 된다. 라우트는 파일 시스템에서 생성.
- **레이아웃이 일급 시민** — pathless layout route가 기존의 모든 핵을 대체했다. 조합 가능하고 예측 가능.
- **생각을 안 해도 되는 dev loop** — 즉시 HMR, 거의 0에 가까운 시작 시간. 코드 바꾸고 결과 보는 사이의 피드백 사이클이 사실상 사라졌다.
- **SSR은 필요한 곳에만** — 마케팅 페이지, 체인지로그, 채용 페이지만 SSR. 나머지는 순수 클라이언트. 이득 없는 화면에 서버 렌더링을 강제하지 않겠다는 것. (편집자 주: 정작 이 블로그는 아직 TanStack이 아니라고 하하)
- **명시적인 모델** — 프레임워크 매직이 적고, 내부에서 뭐가 돌아가는지 더 통제할 수 있다.

팀원 몇 명이 연휴 동안 TanStack Start를 써봤고 반응이 만장일치였다고 한다. 벤치마크만큼이나 "빌드하는 게 좋다"는 감각이 중요하다는 말이 인상적이다.

### PR 두 개, 다운타임 0

수백만 유저에 200개 넘는 라우트를 가진 프로덕션 프론트를 옮기는 건 보통 몇 달간 병렬 운영 + 점진적 컷오버로 하는 일이다. 데드라인이 있어서 PR 두 개로 끝냈다. (스쿼시 전엔 커밋이 수백 개였다고.)

#### PR 1: Next.js 의존성 제거 (프레임워크는 그대로)

`next/image`, `next/head`, `next/router` 같은 Next.js 전용 API를 전부 브라우저 네이티브 API 또는 프레임워크 무관 대안으로 교체. **이 PR은 프레임워크 자체를 건드리지 않는다.** 의존성만 걷어내서 PR 2가 깔끔한 스왑이 되도록 준비하는 단계.

#### PR 2: 프레임워크 스왑

- 200개 이상 라우트 마이그레이션. 먼저 page 파일에서 라우팅과 무관한 모든 것을 개별 React 컴포넌트로 뽑아낸 뒤, 원래 page 트리로부터 라우트를 생성했다.
- 서버 레이어로 `Nitro` 추가. `next.config.js`를 Nitro 설정으로 교체하면서 리다이렉트(500개 이상), 보안 헤더, 캐싱 규칙을 한 곳에 모았다.
- Next.js가 폴리필해주던 Node.js API(`Buffer`, `url.parse` 등)를 브라우저 네이티브로 교체. 부수효과로 코드가 더 깔끔해졌다.

일요일 이른 아침에 머지. 팀이 바로 Discord 워룸에서 dogfooding했고, 같은 날 수정 사항이 줄줄이 들어갔다. 다운타임 없음.

### 포기한 것들

빠르고 명시적인 스택을 얻었지만 트레이드오프가 없진 않다.

| 포기한 것 | 대체 |
|---|---|
| 내장 이미지 최적화 (`next/image`) | `<img>` 태그 + Fastly 엣지 이미지 최적화 |
| 생태계 일부 (`next-seo`, `next-sitemap`) | 작은 자체 구현. 만들기 쉽고 의존성 추가 없음 |
| 성숙도 | TanStack Start는 신생이라 거친 부분이 있음. 방향이 맞고 메인테이너가 빠르게 반응하니 감수. Railway는 Vite와 TanStack 둘 다 후원 중 |

### Railway 프론트는 Railway 위에서 돈다

유저들이 쓰는 방식 그대로 운영한다. PR마다 프리뷰 배포, 헬스체크, 무중단 롤아웃. 빌드 시스템과 프레임워크를 통째로 갈아끼웠는데 **인프라는 전혀 건드리지 않았다.** 코드 바꾸고 푸시하면 끝.

#### 엣지 캐싱 + Vite 에셋 모델

Fastly가 트래픽 대부분을 엣지에서 직접 서빙한다. 마케팅 페이지는 캐시, 동적 페이지는 필요한 곳에 ISR. 그 결과 프론트 서버는 대부분 놀고 있다.

여기서 Vite의 에셋 모델이 특히 잘 맞는다. 모듈마다 콘텐츠 해시가 붙은 청크로 나뉘니까, billing 쪽 변경을 배포하면 **그 청크만 무효화**된다. 재방문 유저는 메가바이트가 아니라 킬로바이트만 받는다.

저자가 생각하는 프론트 배포의 이상형은 이렇다. 빌드는 빠르고, 에셋은 불변이며 캐시 친화적이고, 인프라가 롤아웃·프리뷰·라우팅을 알아서 처리해서 신경 쓸 필요가 없는 것. 프레임워크는 이터레이션 속도에 최적화돼야 하고, 인프라는 그 이터레이션을 배포하는 과정을 투명하게 만들어야 한다.

### 왜 지금인가

프론트엔드 이터레이션 속도는 그 어느 때보다 중요하다. 10분 넘던 빌드가 2분 미만으로. dev 서버는 즉시 시작. 라우트 변경은 경계에서 타입 체크. 레이아웃은 우회책 없이 조합.

코드를 쓰는 시점과 유저 앞에 도달하는 시점 사이의 간극이 병목이다. 프레임워크 스왑, 엣지 캐싱, 에셋 모델 전부 그 간극을 좁히기 위한 것.

### 📌 정리

`프레임워크는 제품의 성격에 맞아야 한다. 클라이언트 중심 앱에 서버 우선 프레임워크의 세금을 계속 낼 이유는 없다.`

#### 핵심

> Railway는 Next.js를 Vite + TanStack Router로 교체했다. 이유는 빌드 10분(그중 6분이 Next.js), 안 쓰는 서버 우선 프리미티브, Pages Router의 레이아웃 핵. 마이그레이션은 "Next.js 의존성 제거 PR → 프레임워크 스왑 PR" 두 단계로 나눠 다운타임 없이 끝냈고, 빌드는 2분 미만으로 줄었다. 대가는 `next/image`·`next-seo` 같은 편의 기능과 생태계 성숙도.

#### ⭐️ 앞으로 기억할 것

1. 프레임워크 선택 기준은 "제품이 어디서 도는가"
Next.js가 나쁜 게 아니다. Railway 앱은 웹소켓·실시간 캔버스·상태 많은 대시보드라 서버 우선 프리미티브가 쓸모없었을 뿐. 내 제품이 마케팅 사이트인지, 로그인 뒤 SPA인지부터 먼저 따지자. App Router로 가기 전에 "서버 우선 패러다임이 나한테 필요한가"를 묻는 게 먼저다.

2. 큰 마이그레이션은 "의존성 제거 → 스왑" 2단계로
프레임워크 전용 API(`next/image`, `next/head`, `next/router`)를 먼저 네이티브/프레임워크 무관 대안으로 바꾸는 PR을 따로 뺀다. 이 PR은 기존 프레임워크 위에서 그대로 검증 가능하다. 그 다음 PR이 순수 스왑이 되니 리스크가 분리된다.
```tsx
// ❌ PR 2에서 한꺼번에: 프레임워크도 바꾸고 API도 바꾸고
import Image from 'next/image'
import { useRouter } from 'next/router'

// ✅ PR 1에서 먼저 걷어내기: 아직 Next.js 위지만 의존은 없음
// <img>는 그대로 브라우저 네이티브, 라우팅은 추상화 뒤로
import { useAppRouter } from '@/lib/router' // 내부 어댑터
```

3. page 파일은 라우팅만, 나머지는 컴포넌트로
Railway는 스왑 전에 page 파일에서 라우팅과 무관한 로직을 전부 개별 컴포넌트로 뽑아냈다. 그래야 라우트 트리를 기계적으로 다시 생성할 수 있다. 평소에도 page/route 파일은 얇게 유지하는 게 나중에 뭘 하든 유리하다.

4. Pathless layout으로 레이아웃 핵 없애기
TanStack Router의 pathless layout route는 URL 세그먼트 없이 레이아웃만 공유한다. Pages Router에서 `getLayout` 같은 우회책 쓰던 걸 프레임워크 프리미티브로 대체.
```
routes/
  _dashboard.tsx          # 언더스코어 → URL에 안 나오는 레이아웃
  _dashboard/
    projects.tsx          # /projects (대시보드 레이아웃 안)
    settings.tsx          # /settings (대시보드 레이아웃 안)
  index.tsx               # / (레이아웃 밖)
```

5. 설정은 한 곳에 (Nitro)
리다이렉트 500개, 보안 헤더, 캐싱 규칙을 `next.config.js`에서 Nitro 설정 하나로 통합. 흩어진 설정은 마이그레이션 때 가장 먼저 발목 잡는다.

6. Node 폴리필 의존을 걷어내면 코드가 좋아진다
`Buffer`, `url.parse` 같은 걸 Next.js가 몰래 폴리필해주고 있었다. 브라우저 네이티브(`TextEncoder`, `new URL()`)로 바꾸니 번들도 코드도 깔끔해졌다는 게 부수효과.
```ts
// ❌ Node API (폴리필 필요)
import { parse } from 'url'
const { pathname } = parse(href)

// ✅ 브라우저 네이티브
const { pathname } = new URL(href, location.origin)
```

7. 콘텐츠 해시 청크 = 부분 무효화
Vite는 모듈별로 콘텐츠 해시가 붙은 청크를 만든다. 한 기능만 바꾸면 그 청크만 캐시가 깨진다. 엣지 캐시(Fastly 등)랑 조합하면 재방문 유저 다운로드가 KB 단위로 떨어진다. 캐시 전략은 빌드 에셋 모델과 같이 설계해야 한다.

8. 포기할 걸 미리 적어둔다
이미지 최적화, SEO/sitemap 헬퍼, 생태계 성숙도. Railway는 각각 엣지 이미지 최적화·자체 구현·후원으로 대응했다. 마이그레이션 제안서엔 "얻는 것"만큼 "잃는 것 + 대체안" 표가 있어야 설득력이 생긴다.

> 📌 결론  
> ▎ Next.js 탈출의 진짜 이유는 빌드 시간이 아니라 "제품과 프레임워크의 패러다임 불일치"였다.  
> ▎ 클라이언트 중심 앱이면 Vite + TanStack Router가 충분히 프로덕션급 선택지다.  
> ▎ 마이그레이션은 의존성 제거 PR과 프레임워크 스왑 PR을 분리하는 게 핵심 전략.  
> ▎ 빌드 10분 → 2분 미만. 이터레이션 속도가 곧 제품 속도다.  
> ▎ ⭐️ 실무 적용 포인트: 지금 프로젝트에서 `next/*` import가 몇 군데인지 세어보자. 그게 탈출 비용의 첫 번째 지표다.  
> ▎ ⭐️ 실무 적용 포인트: page/route 파일은 얇게, 로직은 컴포넌트로. 프레임워크 바꿀 일 없어도 이게 맞다.
