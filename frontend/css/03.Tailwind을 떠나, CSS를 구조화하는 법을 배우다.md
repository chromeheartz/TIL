# Tailwind을 떠나, CSS를 구조화하는 법을 배우다

> **원문**: https://jvns.ca/blog/2026/05/15/moving-away-from-tailwind--and-learning-to-structure-my-css-/
> **번역 출처**: https://velog.io/@tap_kim/moving-away-from-tailwind-and-learning-to-structure-my-css-

![post-thumbnail](https://velog.velcdn.com/images/tap_kim/post/d9c3309a-595c-415b-844e-eba8310d89ae/image.png)

Julia Evans(jvns.ca)가 오랫동안 쓰던 Tailwind을 떠나 vanilla CSS로 돌아가면서, "CSS를 어떻게 구조화할 것인가"를 정리한 글이다. 솔직히 Tailwind 까는 글일 줄 알고 클릭했는데, 정작 내용은 "Tailwind이 나한테 가르쳐준 게 정말 많다"로 시작한다. 안티-Tailwind가 아니라, **Tailwind이 내장하고 있던 시스템(reset / color / font scale)을 vanilla CSS로 옮겨오는** 실전 회고에 가깝다. CSS 구조 잡는 게 막막했던 사람한테 좋은 지도 같은 글.

### Tailwind은 사실 나에게 많은 걸 가르쳐줬다

CSS 구조화가 막막했던 이유는 "정답 구조"가 없어 보여서였다. 근데 블로그 글들을 읽으면서 깨달은 핵심 세 가지:

1. **모든 CSS 코드베이스는 여러 관심사가 섞여 있다** (원래 지저분한 게 정상)
2. **시스템과 가이드라인이 그 혼돈을 막아준다**
3. **Tailwind은 이미 따라 할 만한 시스템을 갖고 있다** — reset, 컬러 팔레트, 폰트 스케일

그래서 이 시스템들을 그대로 vanilla CSS로 이식했다.

#### 내가 다룰 CSS 시스템들

저자가 잡은 9개 영역: **reset / components / colors / font sizes / utilities / base / spacing / responsive / build system**. 아래 하나씩.

---

### ① Reset

Tailwind의 CSS 파일에서 preflight 스타일 **약 200줄을 그대로 복사**했다.

재밌는 포인트: Tailwind을 쓰면서 **무의식적으로 의존하고 있던 기본값**들이 있었다는 것.

```css
* {
  box-sizing: border-box;
}
```

`html { line-height: 1.5; }` 같은 것도 그렇다. Tailwind이 깔아주던 걸 "내가 안 깔았는데도 당연히 되던" 거였고, reset을 통째로 빼면 적응 비용이 크다. → 그래서 일부러 가져왔다.

### ② Components

핵심 원칙: **CSS를 컴포넌트 단위로 구조화한다.** Vue/React 컴포넌트처럼 머릿속에서 매핑.

**3가지 룰:**
1. 각 컴포넌트는 **고유한 클래스**를 가진다
2. 한 컴포넌트의 CSS가 **다른 컴포넌트를 덮어쓰지 않는다**
3. 각 컴포넌트는 **자기 CSS 파일**을 가진다

```html
<figure class="zine horizontal">
    <img src="whatever.jpg">
</figure>
```

```css
.zine {
  ...
  &.horizontal {
    ...
  }
  &.vertical {
    ...
  }
  &:hover {
    ...
  }
}
```

이점: 어떤 컴포넌트의 100줄을 수정할 때 **그 100줄만 생각하면 된다.** 인지 부하가 확 줄어든다. (BEM의 "한 컴포넌트는 격리" 철학과 통함)

### ③ Colors

`colours.css` 파일 하나에 **모든 색을 CSS 변수로** 정의하고, 사이트의 모든 색은 반드시 여기 등장하도록 강제한다.

```css
:root {
  --pink: #fea0c2;
  --pink-light: #F9B9B9;
  --red: #f91a55;
  --orange: rgb(222, 117, 31);
  ...
}
```

> 색은 어렵다. 중앙 팔레트 하나로 모아두면 일관성이 유지된다.

### ④ Font Sizes

Tailwind이 좋았던 점: **단위(em/px/rem) 고민을 없애줬다.** 그 장점만 변수로 가져왔다.

```css
--size-xs: 0.75rem;
--line-height-xs: 1rem;

--size-sm: 0.875rem;
--line-height-sm: 1.25rem;
```

```css
h3 {
  font-size: var(--size-lg);
  line-height: var(--line-height-lg);
}
```

Tailwind의 `text-lg`보다 길긴 하지만(verbose), 받아들일 만한 수준.

### ⑤ Utilities

여러 컴포넌트에 걸쳐 반복되는 작은 패턴만 모으는 영역. Tailwind의 `.sr-only`(스크린리더 전용) 클래스를 복사해 왔다.

⚠️ 이 영역은 여러 컴포넌트에 영향을 주므로 **조심해서 바꾼다.**

### ⑥ Base

요소를 직접 선택해서(`section`, `a` 등) 사이트 전역에 적용하는 스타일. 확신이 낮아서 **최대한 적게** 유지한다.

```css
/* 각 <section> 가운데에 950px 컬럼 배치 */
section {
  --inner-width: 950px;
  padding: 3rem max(1rem, (100% - var(--inner-width))/2);
}

a {
  color: var(--orange);
}
```

접근법은 **bottom-up**: 거의 빈 base에서 시작 → 패턴이 보이면 컴포넌트 스타일을 위로 끌어올린다. (처음부터 전역 규칙 깔지 않기)

### ⑦ Spacing

아직 미완이지만 Tailwind 때보다는 원칙적이다(예전엔 padding/margin을 닥치는 대로 붙였음).

전략: **바깥 레이아웃 컴포넌트가 간격을 관리**하고, 인접 형제 결합자(sibling combinator)로 일관성을 준다.

```css
/* the owl selector */
section > * + * {
  margin-top: 1rem;
}
```

이른바 **owl selector(`* + *`)** 패턴. "바깥 여백 금지(no outer margin)" 원칙과 함께 씀 — 각 요소가 자기 위쪽 여백을 형제 관계로만 만든다.

### ⑧ Responsive Design — Grid를 더 쓰자!

- ❌ 예전(Tailwind): 미디어 쿼리 떡칠 (`md:text-xl` 같은 거 남발)
- ✅ 지금: 유연한 **CSS Grid** 레이아웃 → 브레이크포인트가 거의 필요 없어짐

```css
display: grid;
grid-template-columns: repeat(auto-fit, minmax(min(100%, 400px), max-content));
justify-content: center;
```

`auto-fit` + `minmax`로 "알아서 줄바꿈"이 된다. 추가로 `grid-template-areas`를 적극 써서 미디어 쿼리 없이 레이아웃을 짠다.

### ⑨ Build System — esbuild

개발 중엔 **빌드 시스템 자체가 필요 없다.** 이제 CSS가 네이티브로 import와 중첩 선택자를 지원하니까.

```css
@import "reset.css";
@import "typography.css";
@import "colors.css";
```

```css
.page {
  h2 { ... }
}
```

배포용 번들링은 선택적으로 esbuild 사용:

```bash
esbuild style.css --bundle --loader:.svg=dataurl --loader:.woff2=file --outfile=/tmp/out.css
```

esbuild를 허용한 이유: **표준 기반**이고 **정적 Go 바이너리**라 가볍다.

---

### 왜 Tailwind을 떠났나

- Tailwind v3+는 **빌드 시스템 의존이 심하다.** 저자는 수년간 v2를 썼는데, 신버전은 빌드 툴 없이는 못 쓸 것 같았다.
- 빌드 시스템을 안 쓰니 **2.8MB짜리 tailwind.min.css(gzip 270K)**를 통째로 싣고 있었다 → 낭비.
- 그동안 **본인 CSS 실력이 크게 늘었다.**
- Tailwind엔 본질적 한계가 있다. 커스텀 CSS가 필요한 "이상한 작업(weird stuff)"은 Tailwind을 버리지 않으면 불가능.
- **Tailwind/vanilla 혼합 프로젝트는 유지보수가 어려웠다.**
- 시맨틱 HTML을 직접 써보고 싶은 호기심.

### 궁금했던 CSS 기능들 (앞으로 배울 것)

`@layer` · `@scope` · 컨테이너 쿼리(container queries) · 서브그리드(subgrid).

### 떠나는 마지막 이유 — CSS를 존중하기

"Tailwind and the Femininity of CSS"라는 글을 읽고 생각이 바뀌었다. **"CSS는 쉬운 건데"라고 가정했다가 현실이 안 맞으면 좌절하는 태도** — 그게 문제였다.

- 과거의 좌절(가운데 정렬 불가능 등)은 사실 **CSS에서 오래전에 해결됐다.**
- CSS가 어려운 건 진짜 어려운 문제를 풀기 때문이다.
- 최근 기능(grid, container queries…)으로 사용성이 크게 좋아졌다.
- **CSS 전문성을 키운 건 진짜 가치 있었다.**

> 더 깊은 우려: Tailwind은 CSS 전문성을 평가절하하는 데 일조한다. **LLM 시대일수록 사람의 전문성(specialization)이 더 중요하다.**

---

### 📌 정리
`Tailwind 안티가 아니라 — Tailwind이 가르쳐준 "시스템"을 vanilla로 이식한 회고`

#### 핵심
> CSS 구조화의 핵심은 "관심사를 시스템으로 나누는 것". Julia Evans는 Tailwind이 내장하던 reset/color/font-scale을 그대로 CSS 변수와 컴포넌트 파일로 옮겨, **컴포넌트 단위 격리 + 중앙 팔레트 + 변수 기반 스케일 + Grid 우선 반응형**이라는 구조를 만들었다. 빌드리스(@import·중첩 선택자)로도 충분하고, Tailwind을 떠난 진짜 이유는 번들 낭비 + 커스텀 한계 + "CSS 전문성을 존중하자"는 철학이다.

#### ⭐️ 앞으로 기억할 것
- 1. **컴포넌트 3룰**: 고유 클래스 / 남의 CSS 안 덮음 / 파일 분리
  → 100줄 고칠 때 그 100줄만 생각하면 됨 (인지 부하 ↓)
- 2. **색은 무조건 `colours.css` 변수로** 모은다. 일관성의 핵심.
- 3. **폰트도 변수 스케일**로. Tailwind의 장점(단위 고민 제거)만 흡수.
  ```css
  h3 { font-size: var(--size-lg); line-height: var(--line-height-lg); }
  ```
- 4. **owl selector로 간격 관리** — 닥치는 대로 margin 붙이지 말 것
  ```css
  section > * + * { margin-top: 1rem; }
  ```
- 5. **반응형은 미디어 쿼리보다 Grid 먼저**
  ```css
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 400px), max-content));
  ```
- 6. **빌드리스 CSS가 가능해졌다** — `@import` + 중첩 선택자 네이티브 지원. 배포만 esbuild 옵션.
- 7. **base는 bottom-up으로 최소화** — 전역 규칙부터 깔지 말고, 패턴 생기면 위로 끌어올리기.

📌 결론
▎ "CSS 구조화 = 관심사를 9개 시스템(reset/component/color/font/util/base/spacing/responsive/build)으로 나누기".
▎ Tailwind을 써봤다면, 그 안의 시스템을 vanilla로 베껴오는 게 좋은 출발점이다.
▎ ⭐️ 실무 적용 포인트
▎ - 신규 프로젝트면 → 컴포넌트별 CSS 파일 + `colours.css`/폰트 변수부터 깐다.
▎ - 미디어 쿼리가 늘어난다 싶으면 → `auto-fit minmax` / `grid-template-areas`로 대체 검토.
▎ - "Tailwind이냐 vanilla냐"는 종교전쟁이 아니라 — **둘 다 시스템이 필요하다**는 게 진짜 교훈.
