# 쿼리 캐시에 미리 데이터 채워 넣기 (React Query)

> 원문: [Seeding the Query Cache](https://tkdodo.eu/blog/seeding-the-query-cache) — TkDodo (Dominik Dorfmeister)
> 번역/정리 출처: [번역글 — eunbinn](https://velog.io/@eunbinn/seeding-the-query-cache)

React Query를 쓰다 보면 "로딩 스피너를 어떻게 줄이지?"가 결국 "캐시에 데이터를 얼마나 일찍 채워두느냐"로 귀결된다. 이 글은 그 캐시 시딩(seeding) 전략을 폭포(waterfall) 문제부터 시작해 prefetch, 그리고 리스트 캐시로 디테일 캐시를 채우는 pull / push 두 방식까지 정리한다. 핵심은 "데이터를 늦게 받지 말고, 가능한 한 일찍 채워라"다.

### Fetch Waterfall(폭포) 문제

폭포는 요청들이 병렬로 나가지 않고 **하나가 끝나야 다음이 시작**될 때 생긴다. 의존 쿼리(앞의 결과가 있어야 다음을 요청)면 어쩔 수 없지만, **서로 독립적인 데이터인데 순차로 나가면 낭비**다.

![fetch waterfall](https://velog.velcdn.com/images/eunbinn/post/72fa12e9-b65e-41f4-b278-4c77c9477232/image.png)

독립 데이터는 병렬로 받자. React Query는 두 가지 방법을 준다.

```javascript
// 1. useQuery를 두 번 사용
const issues = useQuery({ queryKey: ["issues"], queryFn: fetchIssues });
const labels = useQuery({ queryKey: ["labels"], queryFn: fetchLabels });

// 2. useQueries 훅 사용
const [issues, labels] = useQueries([
  { queryKey: ["issues"], queryFn: fetchIssues },
  { queryKey: ["labels"], queryFn: fetchLabels },
]);
```

![parallel](https://velog.velcdn.com/images/eunbinn/post/b8269686-8b96-450f-bbec-6193ee37c7ce/image.png)

### Suspense와 숨은 폭포

Suspense는 promise의 세 상태(pending / fulfilled / rejected)를 React가 처리하게 해준다. 컴포넌트 안에서 로딩·에러 분기를 직접 안 써도 된다.

```javascript
function Issues() {
  // 👓 캐시에서 데이터를 읽어온다
  const { data } = useQuery({
    queryKey: ["issues"],
    queryFn: fetchIssues,
    // ⬇️ 실험 기능인 서스펜스 모드 활성화
    suspense: true,
  });

  // 🎉 로딩/에러 상태를 직접 관리할 필요 없음

  return (
    <div>
      {data.map((issue) => (
        <div>{issue.title}</div>
      ))}
    </div>
  );
}

function App() {
  // 🚀 로딩/에러는 Suspense + ErrorBoundary가 처리
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <ErrorBoundary fallback={<div>On no!</div>}>
        <Issues />
      </ErrorBoundary>
    </Suspense>
  );
}
```

⚠️ 함정: 한 컴포넌트 안에 `suspense: true` 쿼리가 여러 개 있으면, 첫 쿼리에서 컴포넌트가 멈춰버려서 두 번째 쿼리가 **순차적으로** 나간다. 의도치 않은 폭포가 생긴다.

![suspense waterfall](https://velog.velcdn.com/images/eunbinn/post/f48f804c-120d-4b20-9e21-c914af86e6b1/image.png)

### Prefetching: 더 일찍 받으면 더 빨리 끝난다

병렬화로도 부족하면 **렌더 전에 미리 받기**. 방법들:
- 서버 사이드 렌더링에서 서버가 미리 fetch
- 라우터 로더(loader)에서 prefetch
- 컴포넌트 렌더 전에 `prefetchQuery`

```javascript
const issuesQuery = { queryKey: ["issues"], queryFn: fetchIssues };

// ⬇️ 컴포넌트가 렌더되기 전에 페칭 시작
queryClient.prefetchQuery(issuesQuery);

function Issues() {
  const issues = useQuery(issuesQuery);
}
```

![prefetch](https://velog.velcdn.com/images/eunbinn/post/cc224d0b-5b09-4ae9-a94d-0768529facc5/image.png)

## 리스트 캐시로 디테일 캐시 시딩하기

리스트(`["todos", "list"]`)를 이미 받아왔다면, 디테일 화면(`["todos", "detail", id]`)에서 그 데이터를 재활용해 스피너를 없앨 수 있다. 두 방향이 있다: **pull(당겨오기)** vs **push(밀어넣기)**.

### Pull 방식 — 디테일에서 리스트 캐시를 당겨온다

`initialData`에서 리스트 캐시를 찾아 해당 item을 초기값으로 쓴다.

```typescript
const useTodo = (id: number) => {
  const queryClient = useQueryClient();
  return useQuery({
    queryKey: ["todos", "detail", id],
    queryFn: () => fetchTodo(id),
    initialData: () => {
      // ⬇️ 리스트 캐시에서 해당 아이템을 찾는다
      return queryClient
        .getQueryData(["todos", "list"])
        ?.find((todo) => todo.id === id);
    },
  });
};
```

문제: `initialData`는 "방금 받은 fresh 데이터"로 취급돼서, 리스트가 한참 전에 받은 낡은 데이터여도 디테일이 새로 fetch를 안 할 수 있다. → `initialDataUpdatedAt`로 **리스트가 마지막으로 받아진 시각**을 알려주면, staleTime 계산이 그 시각 기준으로 맞춰진다.

```typescript
const useTodo = (id: number) => {
  const queryClient = useQueryClient();
  return useQuery({
    queryKey: ["todos", "detail", id],
    queryFn: () => fetchTodo(id),
    initialData: () => {
      return queryClient
        .getQueryData(["todos", "list"])
        ?.find((todo) => todo.id === id);
    },
    initialDataUpdatedAt: () =>
      // ⬇️ 리스트가 마지막으로 페칭된 시각을 가져온다
      queryClient.getQueryState(["todos", "list"])?.dataUpdatedAt,
  });
};
```

| Pull | 내용 |
|------|------|
| ✅ | 캐시를 채우는 타이밍이 정확함 (디테일이 필요할 때만) |
| ❌ | staleness(신선도)를 따로 챙겨줘야 함 (`initialDataUpdatedAt`) |

### Push 방식 — 리스트가 디테일 캐시에 밀어넣는다

리스트를 받아온 직후, 각 item을 디테일 캐시에 `setQueryData`로 미리 심는다.

```typescript
const useTodos = () => {
  const queryClient = useQueryClient();
  return useQuery({
    queryKey: ["todos", "list"],
    queryFn: async () => {
      const todos = await fetchTodos();
      todos.forEach((todo) => {
        // ⬇️ 각 아이템에 대한 디테일 캐시를 만든다
        queryClient.setQueryData(["todos", "detail", todo.id], todo);
      });
      return todos;
    },
  });
};
```

| Push | 내용 |
|------|------|
| ✅ | staleTime이 자동 적용됨 (`setQueryData`가 신선도까지 세팅) |
| ⚠️ | 적절한 콜백이 없음 |
| ⚠️ | 안 볼 디테일까지 불필요한 캐시 항목이 잔뜩 생길 수 있음 |
| ❌ | 데이터가 너무 빨리 GC(가비지 컬렉션)됨 |

### 주의: 구조가 같을 때만 가능

pull/push 둘 다 **리스트와 디테일의 데이터 구조가 호환될 때만** 통한다. 디테일이 리스트보다 필드가 많거나 구조가 다르면, `initialData`(완전한 데이터로 취급) 대신 `placeholderData`(임시 표시용, 백그라운드 fetch 유지)를 쓰는 게 맞다.

### 📌 정리
`스피너를 줄이려면 캐시를 일찍 채워라 — 단, 신선도를 챙겨서`

#### 핵심
> 로딩을 줄이는 본질은 "데이터를 얼마나 일찍 캐시에 넣느냐"다. ① 독립 데이터는 병렬(useQuery 여러 개/useQueries)로, ② 가능하면 렌더 전에 prefetch, ③ 이미 가진 리스트 캐시로 디테일을 시딩(pull: initialData로 당겨오기 / push: setQueryData로 밀어넣기). pull은 타이밍이 정확하지만 신선도(initialDataUpdatedAt)를 챙겨야 하고, push는 신선도는 자동이지만 불필요한 캐시·빠른 GC가 단점. 구조가 다르면 initialData 말고 placeholderData.

#### ⭐️ 앞으로 기억할 것
- 1. 독립 데이터는 절대 순차로 받지 말 것
  서로 안 의존하면 useQuery 여러 개 또는 useQueries로 병렬. 폭포는 의존 쿼리에서만 어쩔 수 없는 것.
- 2. Suspense 여러 쿼리 = 숨은 폭포 주의
  한 컴포넌트에 `suspense: true` 쿼리가 여러 개면 순차 실행됨. 병렬이 필요하면 useQueries나 컴포넌트 분리/prefetch.
- 3. initialData는 "fresh"로 취급된다
  리스트 캐시를 initialData로 쓰면 디테일이 재fetch를 안 할 수 있다. `initialDataUpdatedAt`로 리스트의 dataUpdatedAt을 넘겨 staleTime 기준을 맞춰라.
  ```ts
  initialDataUpdatedAt: () => queryClient.getQueryState(["todos","list"])?.dataUpdatedAt,
  ```
- 4. pull vs push
  - pull(디테일에서 initialData로 당김): 필요할 때만 채움, 신선도 수동.
  - push(리스트에서 setQueryData로 밀어넣음): 신선도 자동, 대신 불필요 캐시·빠른 GC.
- 5. 구조 다르면 placeholderData
  디테일 ≠ 리스트 구조면 initialData(완전 데이터)가 아니라 placeholderData(임시 표시 + 백그라운드 fetch).

📌 결론
▎ "로딩 줄이기 = 캐시 일찍 채우기." 병렬화 → prefetch → 리스트로 디테일 시딩 순으로 고민.
▎ pull은 정확하지만 신선도 직접 관리, push는 자동이지만 캐시 낭비/빠른 GC.
▎ 리스트·디테일 구조 호환되면 initialData, 다르면 placeholderData.
▎ ⭐️ 실무 적용 포인트
  - 리스트→디테일 네비게이션 UX는 pull(initialData + initialDataUpdatedAt)이 무난.
  - prefetchQuery는 라우터 로더/링크 hover 시점에 걸면 체감 로딩이 확 준다.
  - setQueryData 남발은 캐시 쓰레기를 만든다 — 정말 곧 볼 데이터에만.
