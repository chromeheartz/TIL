# TanStack Query는 언제 GET을 보내나

> **원문**: [Important Defaults][important-defaults] (TanStack Query 공식 문서)
> **함께 읽은 글**: [React Query as a State Manager][tkdodo-state-manager] (TkDodo)

`useQuery`를 쓰면 컴포넌트가 렌더링될 때마다 조회하는 건지 헷갈렸다. 결론부터 말하면 아니다. 리렌더는 조회 기준이 아니고, **캐시 상태**와 **어떤 이벤트가 일어났는지**로 정해진다. 그 기준을 정리해 둔다. (콜백이 없어진 얘기는 [`v5 쿼리 콜백 노트`][callbacks-note]에 따로 있다)

### 1. 먼저 보는 것: 캐시 상태

| 캐시 상태 | 의미 | GET을 보내나 |
|---|---|---|
| 없음 | 이 `queryKey`로 받은 적이 없거나, `gcTime`(기본 5분)이 지나 지워짐 | 보낸다. `isPending`으로 로딩 화면 |
| stale (오래됨) | 받은 지 `staleTime`이 지남 | 아래 이벤트가 일어나면 보낸다. 캐시를 먼저 보여 주고 뒤에서 다시 받는다 |
| fresh (신선함) | 받은 지 `staleTime`이 안 지남 | 안 보낸다. 캐시만 쓴다 |

여기서 제일 중요한 게 **`staleTime` 기본값이 0**이라는 거다. 받자마자 stale이 된다. 그래서 기본 설정이면 아래 이벤트가 생길 때마다 다시 조회한다. "TanStack Query가 요청을 너무 자주 보낸다"는 말이 나오는 이유가 사실 이거다.

#### `staleTime`과 `gcTime`은 다른 시계다

| 옵션 | 기본값 | 재는 것 | 지나면 |
|---|---|---|---|
| `staleTime` | `0` | 받은 뒤로 얼마나 지났나 | stale이 된다 (데이터는 그대로 있음) |
| `gcTime` | 5분 | 그 쿼리를 쓰는 컴포넌트가 **하나도 없게 된 뒤로** 얼마나 지났나 | 캐시에서 삭제된다 |

`gcTime`은 v4까지 `cacheTime`이라는 이름이었다. 이름 때문에 "캐시가 유지되는 시간 = 다시 안 받는 시간"으로 오해하기 쉬웠는데, 다시 받을지는 `staleTime`이 정한다.

### 2. stale일 때 GET을 보내는 이벤트

| 이벤트 | 옵션 (기본값) |
|---|---|
| 그 쿼리를 쓰는 컴포넌트가 **마운트**될 때 | `refetchOnMount: true` |
| 브라우저 탭으로 **다시 돌아올** 때 | `refetchOnWindowFocus: true` |
| 네트워크가 **다시 연결**될 때 | `refetchOnReconnect: true` |
| 정해진 주기마다 | `refetchInterval` (기본 꺼짐. 이건 fresh여도 보낸다) |

캐시 상태와 상관없이 보내는 경우도 있다.

- **`queryKey`가 바뀔 때**: `['user', 1]`이 `['user', 2]`가 되면 다른 쿼리다. 그 키의 캐시 상태로 다시 판단한다
- **`invalidateQueries`를 부를 때**: stale로 만들고, 지금 화면에 있는 쿼리는 바로 다시 받는다
- **`refetch()`를 직접 부를 때**

```tsx
// mutation 성공 후 목록을 다시 받게 하는 전형적인 패턴
const mutation = useMutation({
  mutationFn: addTodo,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['todos'] }),
})
```

### 3. 보내지 않는 경우

#### `enabled: false`

자동 조회를 막는다. 값이 준비된 뒤에 조회할 때 쓴다.

```tsx
// ❌ userId가 undefined인데도 요청이 나간다
useQuery({ queryKey: ['user', userId], queryFn: () => fetchUser(userId) })

// ✅ userId가 생긴 뒤에만 조회
useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUser(userId!),
  enabled: !!userId,
})
```

#### 같은 키는 한 번만

같은 키를 쓰는 컴포넌트 3개가 동시에 마운트돼도 GET은 1번이다. 진행 중인 요청을 같이 기다린다. 그래서 `useUser()` 같은 커스텀 훅을 여러 곳에서 불러도 걱정 안 해도 된다.

#### 리렌더

부모 state가 바뀌어 다시 그려지는 건 마운트가 아니다. 조회 안 한다.

### 📌 예시 흐름 (기본 설정)

```
0s    목록 페이지 마운트        캐시 없음 → GET ①, 로딩 화면
0.3s  응답 도착                캐시 저장, 바로 stale (staleTime 0)
10s   상세로 이동              목록 언마운트, 캐시는 남음 (gcTime 5분 카운트 시작)
20s   목록으로 돌아옴           stale + 마운트 → 캐시 즉시 표시 + GET ② (백그라운드)
60s   다른 탭 갔다가 돌아옴      stale + 포커스 → GET ③
6분   (목록을 떠난 지 5분 넘음)  캐시 삭제 → 다시 오면 처음처럼 로딩 화면
```

`staleTime: 60_000`으로 두면 20초, 60초 시점 둘 다 fresh라서 GET ②, ③이 안 나간다.

```tsx
// 전역 기본값을 바꾸고, 쿼리마다 필요하면 덮어쓴다
const queryClient = new QueryClient({
  defaultOptions: {
    queries: { staleTime: 60_000 }, // 1분 동안은 다시 안 받는다
  },
})

useQuery({
  queryKey: ['exchange-rate'],
  queryFn: fetchRate,
  staleTime: 0,             // 환율처럼 자주 바뀌는 건 항상 최신으로
  refetchInterval: 10_000,  // 10초마다 폴링
})
```

---

### 📌 정리
`리렌더가 아니라 캐시 상태 + 이벤트로 조회한다`

#### 핵심
> `useQuery`는 렌더링마다 조회하지 않는다. 캐시가 없으면 받고, fresh면 안 받고, stale이면 마운트·포커스·재연결 같은 이벤트 때 다시 받는다. 기본 `staleTime`이 0이라 기본 설정에서는 이벤트마다 다시 받는다.

#### ⭐️ 앞으로 기억할 것
1. 요청이 너무 많으면 `staleTime`부터 본다
   데이터가 얼마나 자주 바뀌는지에 맞춰 정한다. 전역은 `defaultOptions`, 예외는 쿼리마다.
   ```tsx
   new QueryClient({ defaultOptions: { queries: { staleTime: 60_000 } } })
   ```
2. `staleTime`은 "다시 받을지", `gcTime`은 "캐시를 지울지"
   둘은 다른 시계다. `gcTime`은 쓰는 컴포넌트가 없어진 뒤부터 잰다.
3. 조건부 조회는 `enabled`
   값이 없을 때 요청이 나가지 않게 `enabled: !!id`를 건다.
4. 데이터를 바꾼 뒤엔 `invalidateQueries`
   직접 `refetch`를 여기저기 부르지 말고, 키 단위로 stale 처리해서 화면에 있는 것만 다시 받게 한다.

> 📌 결론  
> ▎ 리렌더는 조회 조건이 아니다  
> ▎ 캐시 없음 → 받음, fresh → 안 받음, stale → 이벤트 때 받음  
> ▎ 기본 `staleTime`은 0, 기본 `gcTime`은 5분  
> ▎ 같은 키는 동시에 여러 곳에서 불러도 요청 1번  
> ▎ ⭐️ 요청이 많다 싶으면 `staleTime`부터 조정한다
