# TanStack Query v5는 왜 useQuery의 onSuccess를 없앴나

> **원문**: [Breaking React Query's API on purpose][tkdodo-breaking] (TkDodo)
> **RFC**: [Remove callbacks on useQuery][rfc-5279] (TanStack/query Discussion #5279)

react-query 시절에 공부할 땐 `useQuery`에 `onSuccess`, `onError`를 붙여서 받아온 데이터를 `setState`로 옮기는 코드를 당연하게 썼다. 그런데 v5로 올라가면서 이게 통째로 사라졌다. 이름이 TanStack Query로 바뀐 게 v4라서 둘을 한 번에 기억하고 있었는데, 콜백이 없어진 건 v5(2023년 10월)다. 왜 없앴는지, 대신 뭘 쓰는지 정리해 둔다.

### 버전별로 뭐가 바뀌었나

| 버전 | 패키지 | 쿼리 콜백 |
|---|---|---|
| v1 ~ v3 | `react-query` | `useQuery`에 `onSuccess`, `onError`, `onSettled` 있음 |
| v4 | `@tanstack/react-query` (이름 변경) | 그대로 있음 |
| v5 | `@tanstack/react-query` | `useQuery`에서 **제거**. `useMutation`은 그대로 |

v4에서 바뀐 건 콜백이 아니라 쿼리 키 배열 강제, `idle` 상태 제거, `networkMode` 추가 같은 것들이다.

### 왜 없앴나: 콜백이 생각한 대로 안 불린다

`onSuccess`는 "데이터가 오면 한 번 불린다"처럼 보인다. 근데 실제로는 그렇지 않았다. 문제가 세 가지다.

#### 1. 캐시에서 꺼낼 때는 안 불린다

`staleTime` 안이라 fetch를 안 하면 `onSuccess`도 안 불린다. 콜백에서 로컬 state를 맞추고 있었다면 그 state는 빈 값으로 남는다.

#### 2. observer마다 따로 불린다

콜백은 쿼리 하나당이 아니라 **훅을 호출한 곳(observer)마다** 실행된다. `useTodos()`를 쓰는 컴포넌트가 화면에 3개면 에러 토스트도 3개 뜬다.

#### 3. 상태를 두 벌 갖게 된다

서버 상태를 로컬 state로 복사하면 렌더가 한 번 더 일어난다. 그 사이 한 번은 `data`는 있는데 복사본은 비어 있는, 어긋난 화면이 그려진다.

솔직히 1번이 제일 무섭다. 개발 중엔 매번 새로 fetch하니까 잘 되다가, `staleTime`을 늘리는 순간 조용히 깨진다.

### v4에서 v5로 이렇게 바꾼다

#### 데이터를 state로 복사하던 코드

```tsx
// ❌ v4: onSuccess에서 setState
function Profile() {
  const [name, setName] = useState('')

  useQuery(['user'], fetchUser, {
    onSuccess: (data) => setName(data.name), // 캐시 히트면 안 불림
  })

  return <input value={name} onChange={(e) => setName(e.target.value)} />
}
```

```tsx
// ✅ v5: 보여주기만 할 거면 data에서 바로 계산
function Profile() {
  const { data } = useQuery({ queryKey: ['user'], queryFn: fetchUser })
  return <p>{data?.name}</p>
}

// ✅ 폼 초기값처럼 편집이 필요하면, 데이터가 온 뒤에 폼을 마운트한다
function ProfilePage() {
  const { data } = useQuery({ queryKey: ['user'], queryFn: fetchUser })
  if (!data) return <Spinner />
  return <ProfileForm initialName={data.name} />
}

function ProfileForm({ initialName }: { initialName: string }) {
  const [name, setName] = useState(initialName) // 초기값으로 한 번만 받는다
  return <input value={name} onChange={(e) => setName(e.target.value)} />
}
```

#### 에러 토스트

```tsx
// ❌ v4: 쿼리마다 onError. observer 수만큼 토스트가 뜬다
useQuery(['todos'], fetchTodos, {
  onError: (err) => toast.error(err.message),
})
```

```tsx
// ✅ v5: QueryCache에서 쿼리당 한 번만
const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error, query) => {
      // 메시지를 띄울 쿼리만 meta로 표시해 둔다
      if (query.meta?.errorMessage) toast.error(String(query.meta.errorMessage))
    },
  }),
})

useQuery({
  queryKey: ['todos'],
  queryFn: fetchTodos,
  meta: { errorMessage: '할 일 목록을 불러오지 못했습니다' },
})
```

#### 그래도 부수효과가 필요하면

```tsx
// ✅ v5: useEffect로 data를 지켜본다
const { data } = useQuery({ queryKey: ['user'], queryFn: fetchUser })

useEffect(() => {
  if (data) analytics.track('user_loaded', { id: data.id })
}, [data])
```

### useMutation 콜백은 왜 남았나

위 세 가지 문제가 mutation에서는 안 생긴다.

| 문제 | useQuery | useMutation |
|---|---|---|
| 캐시 때문에 안 불림 | fresh면 fetch를 건너뛰어 `onSuccess`도 건너뜀 | 결과를 캐시에서 꺼내 쓰지 않는다. `mutate()`마다 실제 요청 |
| 여러 번 불림 | 같은 키를 쓰는 컴포넌트마다 한 번씩 | 인스턴스끼리 공유 안 함. `mutate()` 한 번에 콜백 한 번 |
| 실행 시점 | 마운트, 포커스, 재연결, 주기 refetch 등 라이브러리가 정함 | 내가 `mutate()`를 부른 순간에만 |

결국 성격 차이다. 쿼리는 서버 데이터를 화면에 맞춰 두는 **선언적 동기화**라 "fetch 끝나면 이거 해"의 시점이 믿을 게 못 된다. mutation은 "저장 눌렀다" 같은 **명령 한 번**이라 "끝나면 이거 해"가 분명하다. invalidate, 이동, 토스트를 붙이는 게 원래 용도다.

#### 콜백을 둘 수 있는 곳이 두 군데다

```tsx
const mutation = useMutation({
  mutationFn: updateUser,
  // 훅 옵션: 컴포넌트가 언마운트돼도 실행된다
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['user'] }),
})

mutation.mutate(form, {
  // mutate 옵션: 요청이 끝나기 전에 컴포넌트가 사라지면 실행 안 된다
  onSuccess: () => navigate('/profile'),
})
```

- 캐시 invalidate처럼 **꼭 실행돼야 하는 로직**은 훅 옵션
- 이동, 모달 닫기처럼 **그 화면이 있을 때만 의미 있는 UI 동작**은 `mutate` 쪽

---

### 📌 정리
`쿼리 콜백은 믿을 수 있는 시점이 없어서 뺐다`

#### 핵심
> v5는 `useQuery`의 `onSuccess`, `onError`, `onSettled`를 일부러 없앴다. 캐시 히트면 안 불리고, observer마다 여러 번 불리고, 서버 상태를 로컬 state로 복사하는 안티패턴을 부추겼기 때문이다. 시점이 분명한 `useMutation` 콜백은 그대로 남았다.

#### ⭐️ 앞으로 기억할 것
1. 서버 데이터는 state로 복사하지 않는다
   표시용이면 `data`에서 바로 계산하고, 편집용이면 데이터가 온 뒤 폼을 마운트해서 초기값으로 넘긴다.
   ```tsx
   const name = data?.name ?? ''
   ```
2. 전역 에러 처리는 `QueryCache`의 `onError` 한 곳에서
   쿼리별 메시지는 `meta`로 넘긴다. 쿼리당 한 번만 불린다.
3. mutation 콜백은 두 층으로 나눈다
   꼭 돌아야 하는 건 `useMutation` 옵션, 화면에 묶인 UI 동작은 `mutate()` 옵션.

> 📌 결론  
> ▎ 이름 변경은 v4, 콜백 제거는 v5  
> ▎ 쿼리는 선언적 동기화라 "끝나면 해라"를 걸 시점이 없다  
> ▎ mutation은 명령 한 번이라 콜백이 남았다  
> ▎ ⭐️ `onSuccess`에서 `setState` 하고 있으면 그게 바로 v5가 없애려던 코드다
