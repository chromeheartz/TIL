# Remix는 무엇이고 Next.js와 어떻게 다른가

> **원문**: https://www.smashingmagazine.com/2022/07/look-remix-differences-next/ (Facundo Giuliani)
> **번역 출처**: https://velog.io/@eunbinn/look-remix-differences-next

Next.js만 쓰다 보니 Remix가 정확히 뭐가 다른지 늘 헷갈렸다. 둘 다 React 풀스택 프레임워크인데, Remix는 "웹 표준(Web Standards) + 엣지 우선"을 내세운다. 이 글은 Remix의 핵심 개념을 짚고 Next.js와 항목별로 비교한다. 코드보다 "철학 차이"가 핵심이라 그 관점으로 정리했다.

### Remix란?

공식 소개로는 React와 JS로 클라이언트/서버 렌더링을 모두 지원하는 **"엣지 우선(edge-first) 풀스택 프레임워크"**. **Fetch API** 위에 만들어져서 어디서든(노드, Cloudflare Workers, Deno Deploy 등) 돌아가고, 서버에서 HTML을 렌더해 **클라이언트로 보내는 JS를 최소화**하는 걸 지향한다.

> 참고: Remix는 원래 유료 구독 프레임워크였는데 1년도 안 돼 오픈소스로 전환됐다.

### Remix의 핵심 기능

- **라우트(Routes)**: 파일 시스템 기반 라우팅. JS/TS 파일에 핸들러 함수를 둔다. 내부적으로 React-Router를 활용.
- **중첩 컴포넌트(Nested Routes)**: 라우트 파일 옆에 같은 이름의 폴더를 만들어 페이지를 중첩 관리.
- **에러 처리**: 특정 중첩 컴포넌트에서 에러가 나도 다른 영역엔 영향이 없다 → **캡슐화된(부분) 에러 처리**.
- **폼(Forms)**: JS가 아니라 기본 HTTP 메서드(POST/PUT/DELETE/PATCH)를 쓴다 → 웹 표준 강조.
- **loader / action**: 서버 사이드 동적 처리를 담당하는 두 함수.
  - `loader`: GET 요청 / 데이터 페칭
  - `action`: POST·PUT·DELETE·PATCH / 데이터 변경

이해를 돕는 표준 형태 (원문엔 코드 없음, 보조 예시):

```jsx
// app/routes/posts.tsx
import { json } from "@remix-run/node";
import { useLoaderData, Form } from "@remix-run/react";

// GET → 데이터 읽기
export async function loader() {
  const posts = await db.post.findMany();
  return json({ posts });
}

// POST/PUT/DELETE → 데이터 변경 (JS 없이 <Form>이 트리거)
export async function action({ request }) {
  const form = await request.formData();
  await db.post.create({ data: { title: form.get("title") } });
  return redirect("/posts");
}

export default function Posts() {
  const { posts } = useLoaderData();
  return (
    <Form method="post">
      <input name="title" />
      <button type="submit">추가</button>
    </Form>
  );
}
```

> 한 파일 안에 클라이언트(`<Form>`)와 서버(`loader`/`action`) 코드가 같이 있고, 상태 관리·Context 없이 폼이 동작한다. PHP 시절 "폼 submit → 서버 처리"의 단순함으로 돌아간 느낌.

## Remix vs Next.js 항목별 비교

| 항목 | Remix | Next.js |
|------|-------|---------|
| React 의존 | React 위에 있지만 **추상화 지향** (Vue/Angular/Svelte 실험 있음) | React 의존 |
| SSR | ✅ | ✅ |
| SSG | ❌ 없음 | ✅ (+ ISR, On-Demand ISR) |
| 캐싱 전략 | **SWR**(stale-while-revalidate) 중심 | `getServerSideProps`의 cache-control 헤더로 구현 가능 |
| prefetch | `<link rel="prefetch">` — **모든 페이지** 가능 | `<Link>` — **SSG 페이지만**(동적 페이지 X) |
| 엣지 | **엣지 우선**, 기본 내장 | 12.2+에서 선택적 엣지 런타임 |
| 서버 코드 | `loader`/`action` + `<Form>`, 표준 HTTP | JS로 상태·API·갱신 관리, API Routes 분리 |
| 런타임 의존 | **Fetch API** (노드 불필요) | 주로 **Node.js** (12.2+ 엣지 선택 가능) |

### React 기반이지만 방향이 다르다

둘 다 React를 쓰지만, Remix는 **React 의존을 추상화**하려는 방향(커뮤니티에서 Vue/Angular/Svelte 구현 탐색). Next.js는 React에 단단히 묶여 있다.

### SSR은 둘 다, SSG는 Next만

둘 다 SSR로 서버에서 마크업을 만들어 보내고 클라이언트에서 hydration한다. **차이는 SSG**: Next.js는 빌드 타임에 정적 페이지를 미리 생성(SSG)할 수 있다. Remix엔 SSG가 없다.

- SSG 장점: 사용자 방문 전에 콘텐츠가 미리 만들어져 있음(빠름).
- SSG 단점: 콘텐츠가 바뀌면 재빌드 필요 → 프로젝트가 커질수록 빌드 시간 폭증. Next는 이를 **ISR / On-Demand ISR**로 완화.

### Remix는 SWR(stale-while-revalidate)로 푼다

정적 콘텐츠를 미리 만드는 대신, **트래픽이 들어오면 캐시를 준비**한다. 페이지는 캐시에서 즉시 제공하고 백그라운드에서 재검증(revalidate). Next도 `getServerSideProps`의 cache-control 헤더로 비슷하게 구현 가능.

### 클라이언트 내비게이션(prefetch)

- **Next.js**: `<Link>`가 뷰포트에 들어온 페이지를 prefetch — 단 **SSG 페이지만**, 동적 페이지는 안 됨.
- **Remix**: HTML `<link rel="prefetch">` 사용 → **캐시 의존 없이 어떤 페이지든** prefetch 가능.

### 엣지 우선 아키텍처

Remix는 엣지 컴퓨팅을 토대에 내장 — 분산 서버에서 사용자 근처에서 동적 코드를 실행. Next.js는 12.2+에서 Node.js 기본 위에 **선택적으로** 엣지 런타임을 고를 수 있다.

### 서버 코드 다루는 방식

- **Remix**: `<Form>` + `action`/`loader`로 표준 HTTP 메서드를 써서 폼을 처리. 클라이언트·서버 코드가 한 파일에. Context/상태관리 복잡성이 적다.
- **Next.js**: JS가 상태·API 호출·재검증·UI 갱신을 관리. 서버 기능은 API Routes로 별도 파일에 분리.

### Node.js 의존성

- **Remix**: Fetch API 기반이라 Node 없이도 다양한 플랫폼(Cloudflare Workers, Deno Deploy, 일반 서버)에서 실행.
- **Next.js**: 주로 Node.js 의존. 12.2+에서 프로젝트 전체 엣지 런타임 선택 가능.

### 📌 정리
`Remix = 웹 표준 + 엣지 우선 + Fetch API, Next = SSG/ISR + Node 생태계`

#### 핵심
> Remix와 Next.js는 둘 다 React 풀스택이지만 철학이 다르다. Remix는 **웹 표준(HTTP 폼, Fetch API)**, **엣지 우선**, **loader/action으로 서버 코드를 같은 파일에** 두는 단순함을 추구하고 Node에 묶이지 않는다. Next.js는 **SSG/ISR**, 풍부한 생태계, JS 중심 상태/데이터 관리가 강점이고 주로 Node 기반(12.2+ 엣지 선택). SSG가 필요하면 Next, 엣지·웹 표준·다양한 런타임이 중요하면 Remix.

#### ⭐️ 앞으로 기억할 것
- 1. SSG는 Next만 있다
  빌드타임 정적 생성 + ISR이 필요하면 Next. Remix는 SSG 대신 SWR(요청 시 캐시 + 백그라운드 재검증).
- 2. Remix의 데이터는 loader/action
  GET=`loader`(읽기), 변경=`action`(POST/PUT/DELETE). `<Form>`이 JS 없이 action을 트리거.
  ```jsx
  export async function loader() { /* GET */ }
  export async function action({ request }) { /* mutate */ }
  ```
- 3. prefetch 범위가 다르다
  Next `<Link>`는 SSG 페이지만, Remix `<link rel=prefetch>`는 모든 페이지.
- 4. 런타임 의존성
  Remix=Fetch API(엣지/Deno/CF Workers 자유), Next=주로 Node(12.2+ 엣지 옵션).
- 5. 서버 코드 위치
  Remix는 한 라우트 파일에 클라이언트+서버, Next는 페이지/API Routes 분리 + JS 상태관리.

📌 결론
▎ "JS를 덜 보내고 웹 표준으로 돌아가자"가 Remix, "정적 생성·생태계·JS 제어"가 Next.
▎ 폼/데이터 흐름은 Remix가 단순(HTTP 표준), 정적 콘텐츠·블로그류는 Next(SSG/ISR)가 유리.
▎ ⭐️ 실무 적용 포인트
  - 콘텐츠 위주(마케팅/블로그) + SEO + 빌드타임 정적화 → Next.
  - 폼·뮤테이션 많은 앱, 엣지 배포, 다양한 런타임 → Remix.
  - 지금은 Next App Router가 Remix식 데이터/엣지 개념을 상당 부분 흡수 중이라, 둘의 경계는 계속 좁아지는 중(원문은 2022년 기준).
