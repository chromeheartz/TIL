# 리액트는 언제 컴포넌트를 렌더링하나

> **원문**: https://www.zhenghao.io/posts/react-rerender (Zhenghao)
> **번역 출처**: https://velog.io/@eunbinn/when-does-react-render-your-component

"왜 이 컴포넌트가 또 렌더되지?"는 리액트 디버깅 단골 질문이다. 이 글은 리액트 소스(beginWork의 bailout 조건)까지 들여다보며 "재렌더 규칙"을 명확히 정리한다. 막연히 "부모 렌더되면 자식도 렌더"로 알던 걸 4가지 제외 조건으로 정확히 잡아준다.

### TL;DR — 리액트가 재렌더하는 경우

1. 컴포넌트에 **예약된 state 업데이트**가 있을 때 (커스텀 훅 포함)
2. **부모가 렌더**됐고, 자식이 아래 **4가지 제외 조건을 전부 동시에** 만족하지 못할 때:
   - 이전에 렌더된 적 있음(이미 마운트됨)
   - props가 (참조 기준) 안 바뀜
   - context 값 변화 없음
   - 예약된 state 업데이트 없음

> 성능 최적화는 **실제로 성능 문제가 생긴 뒤에만** 하라.

### "렌더"가 정확히 무슨 뜻인가

표현부터 정확히: "컴포넌트가 렌더한다"가 아니라 **"리액트가 컴포넌트를 렌더한다"**. 컴포넌트는 리액트가 UI 업데이트를 스케줄링하려고 호출하는 함수일 뿐. 리액트가 UI 스케줄링·업데이트를 완전히 통제한다. 그래서:
- state 업데이트 1번 ≠ 렌더 1번 (배칭으로 묶임)
- React 17에선 promise resolve/async 콜백이 배칭을 우회 (18에서 해결)
- 렌더 패스가 쪼개질 수 있음 (concurrent mode)
- **렌더한다고 화면(DOM)이 반드시 바뀌는 건 아님**

### 두 종류의 렌더

**능동(active) 렌더** — 스스로 state 업데이트를 예약:
- 클래스: `this.setState`
- 함수: `useState`/`useReducer`의 `dispatchAction`
- `ReactDOM.render` 직접 호출

**수동(passive) 렌더** — 부모가 렌더됐는데 자식이 제외 조건을 못 채울 때.

### 구현: Fiber와 reconciliation

모든 업데이트 예약은 결국 reconciler의 `scheduleUpdateOnFiber`를 호출한다. 여기서 "Fiber"(React 16 도입, 작업 단위를 나타내는 자료구조) 노드를 관리한다.

> 핵심 구분: `ReactElement` 객체는 **불변**이라 렌더마다 새로 생성되고, **Fiber 노드는 가변**이라 컴포넌트를 건너뛸 때 재사용된다.

### 모든 자식이 똑같이 취급되진 않는다

```jsx
export default function App() {
  return (
    <Parent lastChild={<ChildC />}>
      <ChildB />
    </Parent>
  );
}

function Parent({ children, lastChild }) {
  return (
    <div className="parent">
      <ChildA />
      {children}
      {lastChild}
    </div>
  );
}

function ChildA() { return <div className="childA"></div>; }
function ChildB() { return <div className="childB"></div>; }
function ChildC() { return <div className="childC"></div>; }
```

`Parent`가 업데이트되면 **`ChildA`만 재렌더**된다. `ChildB`/`ChildC`는 **props로 전달**돼서(그 JSX가 Parent 안에서 재평가되지 않음) 제외 조건을 만족한다.

관찰용 강제 렌더 훅:

```jsx
function useForceRender(interval) {
  const render = useReducer(() => ({}))[1];
  useEffect(() => {
    const id = setInterval(render, interval);
    return () => clearInterval(id);
  }, [interval]);
}
```

### Context: Provider가 렌더되면 consumer도 렌더된다

```jsx
const Context = createContext();

export default function App() {
  return (
    <Parent lastChild={<ChildC />}>
      <ChildB />
    </Parent>
  );
}

function Parent({ children, lastChild }) {
  useForceRender(2000);
  const contextValue = {}; // 매 렌더마다 새 객체!
  console.log("Parent is rendered");
  return (
    <div className="parent">
      <Context.Provider value={contextValue}>
        <ChildA />
        {children}
        {lastChild}
      </Context.Provider>
    </div>
  );
}

function ChildC() {
  console.log("ChildC is rendered");
  const value = useContext(Context); // consumer
  return <div className="childC"></div>;
}
```

`Parent`가 렌더될 때마다 `contextValue`가 **새 참조**가 되어, 값이 의미상 안 바뀌어도 consumer인 `ChildC`가 재렌더된다.

### bailout 조건 (소스 레벨)

```javascript
// beginWork 발췌
// 보류 중인 업데이트나 context 변경이 없음 → 여기서 bail out
didReceiveUpdate = false;
return attemptEarlyBailoutIfNoScheduledUpdate(current, workInProgress, renderLanes);
```

여기 도달하려면 **모든 조건이 true**:
- `current !== null` (이미 마운트됨)
- `oldProps === newProps` (props 참조 안 바뀜)
- `hasLegacyContextChanged() === false`
- `hasScheduledUpdateOrContext === false`

### props를 안 바꾸는 법

props 없이 그냥 `<Child />`를 쓰면, 매 부모 렌더마다 `props` 객체가 새로 생긴다.

```jsx
function Parent() {
  return (
    <div>
      <Child /> {/* 매 렌더마다 새 props 객체 */}
    </div>
  );
}
```

이건 `React.createElement(Child, null)` → `{type: Child, props: {}}`로 매번 새로 만들어진다. 리액트는 `===` 비교라 새 객체는 "다름"으로 본다.

**해법: children으로 넘긴다** (위 ChildB/ChildC처럼):

```jsx
function App() {
  return (
    <Parent>
      <Child />
    </Parent>
  );
}

function Parent({ children }) {
  return <div>{children}</div>;
}
```

이제 `Child` JSX가 `Parent` 안에서 재평가되지 않아 새 props 객체가 안 생긴다.

### props 비교 규칙 바꾸기

기본은 `===`. `PureComponent`나 `React.memo`를 쓰면 모든 props를 **얕은 비교**한다 (개념상 `Object.keys(prev).some(k => prev[k] !== next[k])`).

> Dan Abramov: props 비교 비용도 공짜가 아니다. 보통 더 나은 대안(구조 변경)이 있다.

### context 값을 안 바꾸는 법

context 값이 참조로 바뀌면 모든 consumer가 재렌더된다. → `useMemo`로 메모이즈:

```jsx
function Parent({ children, lastChild }) {
  const contextValue = {};
  const memoizedCxtValue = useMemo(() => contextValue, [contextValue]);
  return (
    <div className="parent">
      <Context.Provider value={memoizedCxtValue}>
        <ChildA />
        {children}
        {lastChild}
      </Context.Provider>
    </div>
  );
}
```

> 예외: Provider가 트리 최상단(부모 없음)이면 수동 재렌더가 없으니 메모이즈 불필요.

### 모든 건 한 가지 암묵적 가정 위에 있다

제외(bailout)는 컴포넌트가 **트리에서 같은 위치**에 머문다는 전제다. 아래는 서브트리를 통째로 파괴/재생성한다 → 단순 재렌더가 아니라 **state 손실**:
- 같은 위치에서 다른 컴포넌트로 교체
- 같은 컴포넌트를 다른 위치에 렌더
- `key`를 의도적으로 변경

### 무엇을 배워야 하나

리액트는 여러 이유로 재렌더한다. 그러니 컴포넌트는 **여러 번 렌더돼도 괜찮게(idempotent)** 만들어야 한다 — 한 번 렌더하든 여러 번 하든 (성능 빼고) 동일한 UI. 다만 과도한 재렌더는 지연을 일으키니 "어디를 보고 어떻게 최적화할지"는 알아야 한다.

### 📌 정리
`재렌더 = 부모 렌더 + (마운트됨·props동일·context동일·업데이트없음) 4조건 미충족`

#### 핵심
> 리액트는 ① state 업데이트가 예약됐거나 ② 부모가 렌더됐는데 자식이 4가지 제외 조건(이미 마운트 / props 참조 동일 / context 동일 / 예약 업데이트 없음)을 **전부** 만족하지 못할 때 재렌더한다. 핵심 함정 둘: `<Child/>`를 직접 쓰면 매번 새 props 객체가 생기고(→ children으로 넘겨 회피), context value를 인라인 객체로 주면 매 렌더마다 새 참조라 모든 consumer가 렌더된다(→ useMemo). 최적화는 문제 생긴 뒤에.

#### ⭐️ 앞으로 기억할 것
- 1. "컴포넌트가 렌더"가 아니라 "리액트가 렌더한다"
  렌더 ≠ DOM 업데이트. state 1번 ≠ 렌더 1번(배칭).
- 2. props로 넘긴 JSX는 부모 렌더에 안 휩쓸린다
  `<Parent>{children}</Parent>` 형태면 children은 Parent 재렌더 때 재평가 안 됨 → 재렌더 회피.
  ```jsx
  <Parent lastChild={<ChildC />}><ChildB /></Parent> // B, C는 bailout
  ```
- 3. 인라인 context value는 모든 consumer를 깨운다
  `value={{}}`는 매 렌더 새 참조. `useMemo`로 고정. (단 최상단 Provider는 불필요)
- 4. memo/PureComponent는 얕은 비교 + 비용
  공짜 아님. 구조 변경(lift content up)이 먼저.
- 5. key 변경/위치 변경은 재렌더가 아니라 state 손실
  같은 위치 가정이 깨지면 서브트리 파괴·재생성.
- 6. 컴포넌트는 idempotent하게
  여러 번 렌더돼도 같은 UI가 나오도록. 그게 기본기, 최적화는 그다음.

📌 결론
▎ 재렌더 규칙은 "부모 렌더 + 4가지 제외조건"으로 외운다.
▎ 두 고전 함정: 새 props 객체(→children), 새 context value(→useMemo).
▎ ⭐️ 실무 적용 포인트
  - 재렌더 디버깅은 Profiler로 "누가, 왜"부터 확인 (props/context/state 중 무엇).
  - 무지성 React.memo 도배 전에 "props로 children 끌어올리기"가 더 깔끔한 경우 많음.
  - context는 값 메모이즈 + 필요하면 분리(자주 바뀌는 값/안 바뀌는 값 Provider 나누기).
