# GitHub는 diff 라인을 어떻게 빠르게 만들었나

> **원문**: [The uphill climb of making diff lines performant][ref-src] - GitHub Blog  
> **번역 출처**: [(번역) diff 라인 성능 개선이라는 험난한 오르막길][ref-tr] - Ricki Lee

![GitHub diff 라인 성능 개선 대표 이미지](https://cdn-images-1.medium.com/max/1024/0*ATrr_tmrT-aclGmN)

수천 줄짜리 리스트를 리액트로 렌더링하면 어디서부터 무거워질까. GitHub가 PR의 Files changed 탭을 리액트로 다시 만들면서 겪은 성능 문제와 해결 과정을 정리한 글이다. 한 줄 요약은 "더 나은 성능은 단순함에서 나온다".

### 문제: 큰 PR에서 페이지가 멈춘다

Files changed 탭을 새 리액트 기반으로 바꿨는데(지금은 모두에게 기본값), 대부분의 PR에선 괜찮았지만 큰 PR에서 성능이 확 떨어졌다. 극단적인 경우 이 정도였다고 한다.

- JS 힙 1GB 초과
- DOM 노드 400,000개 이상
- 인터랙션이 아주 느리거나 아예 못 쓸 수준
- [`INP(Interaction to Next Paint)`][ref-inp-webdev]가 허용 수준 초과. 사용자가 입력 지연을 체감함

### 해결책은 하나가 아니다

처음부터 "만능 해결책은 없다"고 판단했다. 브라우저 기본 동작(페이지 내 검색 등)을 다 살리는 기법은 극단적인 PR에서 한계가 오고, 최악의 경우를 막는 기법은 평범한 리뷰에서 손해가 된다. 그래서 PR 크기별로 전략을 나눴다.

| 전략 | 대상 | 목표 |
|---|---|---|
| diff 라인 컴포넌트 집중 최적화 | 대부분의 PR (중형, 대형 포함) | 페이지 내 검색 같은 기본 동작 유지하면서 빠르게 |
| 가상화로 우아한 성능 저하 | 가장 큰 PR | 렌더링량을 제한해서 응답성과 안정성 우선 |
| 기반 컴포넌트, 렌더링 개선 | 모든 크기 | 어떤 모드든 효과가 복리로 쌓이게 |

목표는 세 가지였다.

1. 메모리와 JS 힙 크기 줄이기
2. DOM 노드 수 줄이기
3. 평균 [`INP`][ref-inp-mdn] 줄이고 p95, p99 크게 개선하기

방법은 단순화. <strong>더 적은 상태, 더 적은 요소, 더 적은 JS, 더 적은 리액트 컴포넌트</strong>.

### v1: 라인 하나가 너무 비쌌다

Rails 뷰에서 리액트로 처음 옮긴 v1은 "작고 재사용 가능한 컴포넌트를 많이, DOM 구조는 그대로"가 방향이었다. 당시엔 타당했다.

![v1 diff 라인의 리액트 컴포넌트 구조와 DOM 트리](https://cdn-images-1.medium.com/max/960/0*9TDSQCg8z9TxjKee)

근데 라인 하나에 들어가는 비용을 세어보면 이렇다.

| 항목 (라인당) | 통합 뷰 | 분할 뷰 |
|---|---|---|
| DOM 요소 (구문 강조 전) | 약 10개 | 약 15개 |
| 리액트 컴포넌트 (최소) | 8개 | 13개 |
| 리액트 이벤트 핸들러 | 20개 이상 | 20개 이상 |

구문 강조가 붙으면 `<span>`이 더 늘고, 댓글, 호버, 포커스 같은 UI 상태가 붙으면 컴포넌트도 더 는다. 작은 컴포넌트마다 이벤트 핸들러가 5~6개씩 붙어 있었으니, 라인 하나에 20개 넘는 핸들러가 생기고 수천 라인이면 그게 몇 배로 곱해진다.

성능뿐 아니라 코드 복잡도도 올라갔다. 처음 설계는 깔끔했는데 데이터 요구가 끝없이 늘면서 한계가 드러나는, 다들 아는 그 시나리오다.

### v2: 작은 것부터 다 줄였다

#### 사소한 노드도 곱하면 크다

라인 번호 셀에 있던 불필요한 `<code>` 태그를 뺐다. 라인당 DOM 노드 2개. 사소해 보이지만 10,000라인이면 20,000개다.

![v1 diff 라인 HTML](https://cdn-images-1.medium.com/max/720/0*ooUrj4vt7u1Bk_74)

![v2 diff 라인 HTML](https://cdn-images-1.medium.com/max/704/0*TkhlfcM0KSeBUyI_)

#### 공용 래퍼 대신 뷰별 전용 컴포넌트

컴포넌트 구조로 보면 차이가 더 확실하다.

![v1 diff 라인 컴포넌트 구조](https://cdn-images-1.medium.com/max/681/0*VFKF-jiVojd-H10R)

![v2 diff 라인 컴포넌트 구조](https://cdn-images-1.medium.com/max/667/0*W1WEEJF9_NrO5oTb)

라인당 컴포넌트가 <strong>8개 → 2개</strong>. v1 컴포넌트 대부분은 분할 뷰와 통합 뷰가 코드를 공유하게 해주는 얇은 래퍼였다. 문제는 한 번에 한 뷰만 렌더링되는데도 각 래퍼가 두 뷰의 로직을 다 들고 있었다는 것. v2는 뷰마다 전용 컴포넌트를 줬다. 코드가 좀 중복되지만 데이터 접근이 단순해지고 더 빨라졌다.

```tsx
// ❌ v1 느낌: 두 뷰를 다 아는 얇은 래퍼가 층층이
<DiffLine view={view}>
  <LineNumberCell view={view} />
  <LineContentWrapper view={view}>
    <LineContent view={view} />
  </LineContentWrapper>
</DiffLine>

// ✅ v2 느낌: 뷰별 전용 컴포넌트 (중복은 감수)
{view === 'split' ? <SplitDiffLine line={line} /> : <UnifiedDiffLine line={line} />}
```

(위 코드는 구조를 이해하려고 내가 단순화한 예시. 실제 컴포넌트 이름은 원문 이미지 참고)

#### 이벤트 핸들러는 위에 하나만

라인마다 핸들러를 다는 대신, <strong>최상위 핸들러 하나</strong>가 `data-attribute`를 보고 처리한다. 예를 들어 여러 라인을 클릭 드래그로 선택할 때, 라인마다 `mouseenter`를 두지 않고 최상위 핸들러가 이벤트 대상의 `data-attribute`를 읽어서 어느 라인을 강조할지 정한다. 이벤트 위임(event delegation)이다.

```tsx
// ❌ 라인마다 핸들러 (라인 수 × 핸들러 수)
{lines.map((line) => (
  <tr key={line.id} onMouseEnter={() => highlight(line.number)}>...</tr>
))}

// ✅ 최상위 핸들러 하나 + data-attribute
<table
  onMouseOver={(e) => {
    const row = (e.target as HTMLElement).closest<HTMLElement>('[data-line]')
    if (row) highlight(Number(row.dataset.line))
  }}
>
  {lines.map((line) => (
    <tr key={line.id} data-line={line.number}>...</tr>
  ))}
</table>
```

#### 복잡한 상태는 조건부 자식으로

v1 → v2에서 <strong>가장 효과가 컸던 변화</strong>다. 댓글이나 컨텍스트 메뉴가 실제로 열리는 라인은 극히 일부인데, 모든 라인이 복잡한 댓글 상태를 들고 있을 이유가 없다. 그래서 댓글 상태를 각 라인 안의 중첩 컴포넌트(필요할 때만 렌더링되는)로 내렸다. diff 라인 컴포넌트의 책임은 "코드 렌더링" 하나만 남는다. [`단일 책임 원칙`][ref-srp]에도 더 맞다.

```tsx
// ❌ 모든 라인이 댓글 상태를 들고 있음
function DiffLine({ line }: DiffLineProps) {
  const [draft, setDraft] = useState('')
  const [isMenuOpen, setIsMenuOpen] = useState(false)
  // ...
}

// ✅ 라인은 렌더링만, 상태는 열릴 때만 생기는 자식이 가짐
function DiffLine({ line, hasOpenThread }: DiffLineProps) {
  return (
    <>
      <tr data-line={line.number}>...</tr>
      {hasOpenThread && <CommentThread line={line} />}
    </>
  )
}
```

#### O(1) 조회와 useEffect 제한

v1에는 공유 저장소와 컴포넌트 상태 곳곳에 O(n) 조회가 쌓여 있었고, 라인 트리 여기저기 흩어진 `useEffect`가 불필요한 리렌더링을 만들었다. v2에서 한 일은 두 가지다.

1. `useEffect`는 diff 파일 최상위에서만 쓴다. 라인 컴포넌트에 `useEffect`가 못 들어오게 [`린트 규칙`][ref-eslint]까지 만들었다. 덕분에 라인 컴포넌트 메모이제이션이 정확해지고 동작이 예측 가능해졌다.
2. 전역 상태와 diff 상태 머신을 [`Map`][ref-map] 기반 O(1) 조회로 재설계했다. 라인 선택, 댓글 관리 같은 공통 작업용 셀렉터가 빠르고 일관돼졌다.

이제 라인은 파일 경로와 라인 번호로 바로 조회한다.

```ts
// 해당 라인에 댓글이 있는지 O(1)로 확인
commentsMap['path/to/file.tsx']['L8']
```

### 결과 (v1 vs v2)

분할 diff 설정, 10,000라인 변경 PR 기준이다.

![v1과 v2 성능 지표 비교표](https://cdn-images-1.medium.com/max/1024/1*cV9r6nqKFc1-g-W5DkGdbw.png)

| 지표 | v1 | v2 | 개선 |
|---|---|---|---|
| 전체 코드 라인 수 | 2,800 | 2,000 | 27% 감소 |
| 고유 컴포넌트 타입 수 | 19 | 10 | 47% 감소 |
| 렌더링된 전체 컴포넌트 수 | ~183,504 | ~50,004 | 74% 감소 |
| 전체 DOM 노드 수 | ~200,000 | ~180,000 | 10% 감소 |
| 전체 메모리 사용량 | ~150-250 MB | ~80-120 MB | ~50% 감소 |
| 대형 PR INP (M1 MacBook Pro, 4배 슬로다운) | ~450 ms | ~100 ms | ~78% 빨라짐 |

재밌는 건 DOM 노드는 10%밖에 안 줄었는데 렌더링된 컴포넌트는 74%, 메모리는 절반, INP는 78%나 줄었다는 점이다. 비용의 대부분이 DOM이 아니라 <strong>리액트 컴포넌트, 상태, 핸들러</strong> 쪽에 있었다는 얘기다.

### 초대형 PR은 가상화로

p95+ PR(diff 라인과 주변 컨텍스트 라인이 10,000개 이상)은 컴포넌트를 아무리 가볍게 해도 수만 개를 한 번에 그리면 못 버틴다. 여기서 [`윈도우 가상화(window virtualization)`][ref-virtual-list]를 꺼냈다.

화면에 보이는 부분만 DOM에 두고, 스크롤하면 요소를 갈아 끼운다. 데이터 위를 움직이는 "창"이 있다고 생각하면 된다. 화면 밖 콘텐츠 때문에 브라우저가 느려지지 않는다.

[`TanStack Virtual`][ref-tanstack]을 diff 뷰에 붙였고 효과는 이랬다.

- p95+ PR에서 JS 힙과 DOM 노드 <strong>10배 감소</strong>
- 대형 PR INP가 약 275~700ms 이상에서 40~80ms로

(번역본에는 "275700ms 이상에서 4080ms"로 나오는데, 범위 표기의 물결이 빠진 걸로 보인다. 원문 기준 275~700ms+ → 40~80ms)

이게 표의 "전략 2: 가상화로 우아한 성능 저하"다. 가상화하면 화면 밖 라인이 DOM에 없으니 브라우저 페이지 내 검색(Cmd+F) 같은 기본 동작은 포기해야 한다. 그래서 모든 PR이 아니라 초대형 PR에만 쓰는 것.

### 그 밖의 최적화

| 영역 | 한 일 | 효과 |
|---|---|---|
| 리액트 | 불필요한 리렌더링 줄이고 상태 관리 정리 | UI 업데이트 빨라지고 인터랙션 부드러워짐 |
| CSS | 무거운 셀렉터(`:has(...)` 등) 교체 | 스타일 계산 비용 감소 |
| 드래그/리사이즈 | GPU 변환(`transform`)으로 재설계 | 강제 레이아웃(forced layout) 제거 |
| 모니터링 | 인터랙션 단위 INP 추적, diff 크기별 세분화, 메모리 태깅 → Datadog 대시보드 | 병목을 문제 되기 전에 발견 |
| 서버 렌더링 | 보이는 diff 라인만 하이드레이션 | TTI 단축, 메모리 억제 |
| 로딩 | 점진적 diff 로딩 + 백그라운드 페치 | 전체 로딩 기다리지 않고 바로 보고 인터랙션 |

### 마무리

DOM 노드 줄이기, 컴포넌트 트리 단순화, 복잡한 상태를 조건부 자식으로 내리기, O(1) 데이터 접근, 상태 관리 규칙 강화. 크고 오래된 코드베이스에서도 이런 목표 지향 리팩터링이 큰 효과를 낸다는 걸 보여준다. 때로는 작고 단순한 개선이 가장 큰 영향을 미친다.

### 📌 정리
`리스트 성능은 아이템 하나의 비용 × 개수다`

#### 핵심
> 큰 PR에서 GitHub diff 뷰가 느렸던 이유는 라인 하나가 너무 비쌌기 때문이다. 라인마다 컴포넌트 8~13개, 이벤트 핸들러 20개 이상, 모든 라인이 댓글 상태를 들고 있었다.  
> v2는 단순화로 풀었다. 뷰별 전용 컴포넌트(8개 → 2개), 최상위 이벤트 핸들러 + `data-attribute`, 복잡한 상태는 열릴 때만 렌더링되는 자식으로, `useEffect`는 최상위에만, 데이터는 `Map`으로 O(1) 조회.  
> 그래도 안 되는 초대형 PR만 TanStack Virtual로 가상화했다. 결과는 메모리 약 50% 감소, INP 약 78% 개선.

#### ⭐️ 앞으로 기억할 것

1. 리스트 아이템은 곱셈으로 생각한다
아이템 하나에 노드 2개, 핸들러 1개 더 붙이는 게 1만 개면 2만 개, 1만 개다. 큰 리스트의 아이템 컴포넌트는 "재사용성"보다 "개당 비용"이 먼저다.

2. 공용 래퍼보다 전용 컴포넌트가 나을 때가 있다
`view` prop으로 분기하는 얇은 래퍼가 층층이 쌓이면, 각 층이 안 쓰는 로직까지 들고 다닌다. 중복을 조금 감수하고 분리하는 게 빠르고 읽기도 쉽다.

3. 핸들러는 위임한다
아이템마다 `onClick`, `onMouseEnter`를 다는 대신 부모 하나에서 `closest('[data-*]')`로 대상을 찾는다.
```tsx
<ul onClick={(e) => {
  const item = (e.target as HTMLElement).closest<HTMLElement>('[data-id]')
  if (item) select(item.dataset.id)
}}>
```

4. 가끔 쓰는 상태는 가끔 렌더링되는 자식에게
편집 중, 메뉴 열림, 댓글 초안 같은 상태는 그 UI가 열렸을 때만 마운트되는 자식 컴포넌트가 갖게 한다. 리스트 아이템 자체는 props만 받아 그리는 순수 컴포넌트로 두면 `memo`도 잘 먹힌다.

5. 배열 `find` 대신 `Map` 셀렉터
아이템마다 `array.find`로 자기 데이터를 찾으면 전체가 O(n²)이 된다. 키로 바로 꺼내 쓰게 정규화한다.
```ts
// ❌ 라인마다 O(n)
const comment = comments.find((c) => c.path === path && c.line === line)

// ✅ O(1)
const comment = commentsMap.get(path)?.get(line)
```

6. 가상화는 마지막 카드
가상화하면 Cmd+F, 스크린 리더 탐색, 앵커 이동 같은 브라우저 기본 동작이 깨진다. 아이템 비용을 먼저 줄이고, 그래도 안 되는 크기에만 쓴다.

7. 규칙은 린트로 박는다
"리스트 아이템에선 `useEffect` 쓰지 말자"를 구두로 정하면 언젠가 깨진다. GitHub처럼 린트 규칙으로 막아야 유지된다.

> 📌 결론  
> ▎ 큰 리스트의 성능은 아이템 하나의 비용 × 개수로 결정된다  
> ▎ DOM보다 리액트 컴포넌트, 상태, 핸들러 쪽 비용이 더 컸다 (DOM 10% 감소, INP 78% 개선)  
> ▎ 단순화가 답이었다: 전용 컴포넌트, 이벤트 위임, 조건부 자식 상태, Map O(1) 조회  
> ▎ 가상화는 기본 동작을 포기하는 대가가 있으니 초대형 케이스에만 쓴다  
> ▎ ⭐️ 실무 적용 포인트: 긴 리스트 아이템에서 핸들러는 부모로 위임하고, 가끔 쓰는 상태는 조건부 자식으로 내리고, 데이터는 Map으로 꺼내 쓴다
