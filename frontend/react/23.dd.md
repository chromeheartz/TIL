# 참조 안정성을 타입으로 만들기

> **원문**: [Making Referential Stability a Type](https://www.jovidecroock.com/blog/referential-stability-types/) — Jovi De Croock
> **번역 출처**: [[번역] 참조 안정성을 타입으로 만들기](https://www.yeongseo-blog.site/blog/referential-stability-types) — yeongseo-blog

`React.memo` 걸어둔 자식이 계속 리렌더링돼서 보면, 결국 부모에서 인라인 배열이나 화살표 함수를 넘기고 있던 경우가 대부분이었다. 리뷰에서 매번 눈으로 잡는 게 지겨웠는데, "그 안정성 자체를 타입으로 강제하면 어떨까?"라는 글이 있어서 읽고 정리해둔다.

### 타입은 '모양'만 말해준다

`items: Item[]`라는 타입은 배열이라는 것만 알려주지, **다음 렌더에서도 같은 참조가 오는지**는 전혀 말해주지 않는다. 그래서 메모이제이션이 깨지는 버그는 타입 체크를 그냥 통과하고, 성능 이슈로만 조용히 드러난다.

저자의 아이디어는 단순하다. "참조를 유지하겠다는 의도"를 타입의 일부로 만들자는 것.

```ts
// 런타임에는 존재하지 않는 브랜드 심볼
declare const stableBrand: unique symbol

// 객체·배열·함수만 브랜딩, 원시값은 어차피 값 비교라 그대로 통과
type Stable<T> = T extends object ? T & { readonly [stableBrand]: true } : T
```

핵심은 `unique symbol`이다. 일반 코드로는 이 키를 가진 객체를 만들 수 없으니, 구조적 타이핑으로 "우연히" 만족시키는 게 불가능하다. 즉 `Stable<T>`는 **증명이 붙은 값**만 가질 수 있다.

참고로 이건 불변성(immutability) 얘기가 아니다. "관련 없는 렌더에서는 참조가 살아남고, 원천(state, 의존성)이 바뀔 때만 바뀐다"는 **identity 보존 계약**이다.

#### props에서 요구하기

```ts
type ItemListProps = {
  items: Stable<Item[]>                     // 호출자가 안정성을 증명해야 함
  onSelect: Stable<(id: string) => void>
  title: string                             // 원시값은 그냥 둠
}
```

❌ 이제 부모에서 이렇게 넘기면 타입 오류

```tsx
<ItemList items={data.filter(isActive)} onSelect={(id) => select(id)} title="목록" />
```

✅ 메모이제이션을 거쳐야 통과

```tsx
const items = useMemo(() => data.filter(isActive), [data])
const onSelect = useCallback((id: string) => select(id), [select])

<ItemList items={items} onSelect={onSelect} title="목록" />
```

### 모듈 보강 말고 별도 진입점

처음엔 `declare module 'react'`로 기존 훅 타입을 보강하려 했다고 한다. 근데 문제가 있었다. 의존성이 증명되지 않으면 TS가 **원래 리액트의 느슨한 오버로드로 조용히 fallback** 해버려서 오류가 안 난다. 증명이 사라졌는데 아무도 모르는 상황.

그래서 최종적으로는 `stableref/react`라는 별도 진입점에서 엄격한 시그니처의 훅을 제공한다. 훅 사용법은 그대로, **import 경로만 바꾸면** 된다.

```ts
// ❌ 기존
import { useMemo, useCallback } from 'react'

// ✅ 엄격한 버전
import { useMemo, useCallback } from 'stableref/react'
```

### 리액트가 이미 보장하는 것들은 타입에 그대로

사실 리액트는 이미 몇 가지 안정성을 보장하고 있다. 그걸 타입에 담아주기만 하면 된다.

| API | 안정성 |
|-----|--------|
| `useState` | state와 setter 모두 `Stable` 브랜드 |
| `useRef` | 반환된 ref 객체 자체가 `Stable` |
| `useReducer` | `dispatch`가 `Stable` |
| 초기화 함수 (`useState(() => ...)`) | 한 번만 호출되니 증명 불필요 |

#### 의존성 배열 검사

`stableref/react`의 `useMemo`/`useCallback`/`useEffect`는 의존성 배열에 증명 안 된 값이 들어가면 **그 자리에서** 오류를 낸다. 재밌는 건 오류 메시지 자체가 해결법이라는 점.

```ts
const rawFilter = (x: Item) => x.active   // 매 렌더 새로 생기는 함수

useMemo(() => source.filter(rawFilter), [source, rawFilter])
// ❌ Type 'Function' is not assignable to type
//    'This dependency is not Stable<T>: ...' ← 여기에 고치는 방법이 문자열로 나옴
```

고치는 방법은 대략 네 가지:
- `useMemo`/`useCallback`으로 감싸기
- `useState`에서 가져오기
- `useRef` 컨테이너에 담기
- 모듈 상수라면 `stable()`로 감싸기

#### `stable()` — 모듈 스코프 상수용

```ts
// 런타임에선 그냥 x => x, 타입에만 증명을 붙임
export const EMPTY_ITEMS = stable([] as Item[])
```

모듈 최상단 상수는 원래 안정적이니까, "여기는 진짜 안정적이다"라는 주장을 그 값이 정의된 곳에 딱 한 번만 하게 해준다. 이게 좋은 점이다. 주장이 흩어지지 않는다.

### 컨텍스트에서 효과가 제일 크다

Context는 value 참조가 바뀌면 구독자가 전부 리렌더링된다. `createStableContext`로 만들면 Provider가 `Stable<T>`만 받는다.

```tsx
const ThemeContext = createStableContext<ThemeValue | null>(null)

// ❌ 매 렌더 새 객체 → 타입 오류
<ThemeContext.Provider value={{ mode, toggle }}>

// ✅ Provider 쪽에서 메모이제이션 책임을 짐
const value = useMemo(() => ({ mode, toggle }), [mode, toggle])
<ThemeContext.Provider value={value}>
```

메모이제이션 책임이 트리 깊숙한 소비자들한테 흩어지지 않고 **Provider 한 곳**에 모인다는 게 포인트.

### Preact도 같은 방식

`stableref/preact` 진입점이 있고, 원래 Preact 훅을 그대로 쓰면서 시그니처만 엄격하게 바꾼다. 증명 메커니즘 자체는 프레임워크에 묶여 있지 않다.

### 이걸로 해결 못 하는 것

- **타입 단언으로 우회 가능** — `value as Stable<typeof value>` 하면 끝이다. 저자는 이걸 명시적인 탈출구로 보고, 린트보다는 **코드 리뷰에서 잡는 팀 규약**으로 관리하자고 한다. 솔직히 `as`가 보이면 리뷰어 눈에 띄기라도 하니까 인라인 화살표 함수보단 낫다.
- **React Compiler와는 역할이 다름** — 컴파일러는 메모이제이션을 *자동으로 해주는* 구현 쪽 얘기고, `Stable<T>`는 *소비자가 요구할 수 있는* 타입 계약이다. 둘은 같이 쓸 수 있다.

### 에이전트용 가드레일로서의 타입 오류

이 부분이 꽤 와닿았다. 코딩 에이전트가 만든 코드에서 메모된 자식에 불안정한 참조를 넘기는 실수가 정말 자주 나온다. 리렌더링이 한 번 더 되는 건 눈에 안 보이는 버그라 아무도 못 잡는다.

근데 타입 오류는 빌드를 멈춘다. 그리고 에이전트는 이미 타입 오류에 반응하도록 동작한다. 사람이 다 읽을 수 없을 만큼 코드가 빨리 생성되는 상황에서, **버티는 가드레일은 결국 빌드를 깨는 것뿐**이라는 주장.

### 더 넓은 아이디어

메모이제이션은 하나의 예시일 뿐이다. 지금 주석, 린트 룰, 팀 내 암묵지로만 남아 있는 보장들을 타입 시스템이 실어 나를 수 있다. 컴포넌트는 안정성을 *요구*하고, 훅은 *제공*하고, 컨텍스트는 서브트리 전체에 *유지*한다. 런타임에선 원래 다 일어나던 일이고, 빠져 있던 건 그 보장이 타입 그래프를 따라 전파되게 하는 것이었다.

### 📌 정리
`"참조가 안 바뀐다"를 주석이 아니라 타입으로 증명하게 하자`

#### 핵심
> `unique symbol` 브랜드로 `Stable<T>`를 만들고, 엄격한 훅 진입점(`stableref/react`)으로 의존성·props·컨텍스트에서 증명을 강제한다.
> 증명 안 된 참조는 그 자리에서 타입 오류 → 메모이제이션 누락이 런타임 성능 버그가 아니라 빌드 실패가 된다.

#### ⭐️ 앞으로 기억할 것
- 1. 브랜드 타입은 `unique symbol`로 만든다
일반 객체 리터럴로 위조할 수 없어야 브랜드가 의미 있다. 문자열 키(`__brand: 'x'`)는 구조적으로 흉내 낼 수 있다.
```ts
declare const brand: unique symbol
type UserId = string & { readonly [brand]: 'UserId' }
```
- 2. 모듈 보강은 오버로드 fallback에 주의
기존 라이브러리 타입을 `declare module`로 좁히려 해도, 원래의 느슨한 오버로드가 살아있으면 TS가 조용히 그쪽으로 빠진다. 강제하고 싶으면 별도 진입점으로 래핑하는 게 확실하다.
- 3. Context value는 Provider에서 메모이제이션
소비자 쪽에서 아무리 `memo`해도 value 참조가 바뀌면 의미 없다. 책임은 Provider 한 곳에.
```tsx
const value = useMemo(() => ({ mode, toggle }), [mode, toggle])
```
- 4. 안정적인 상수는 모듈 스코프로 뺀다
`[]`, `{}` 기본값을 컴포넌트 안에서 만들지 말 것. 모듈 상수로 빼면 공짜로 안정적이다.
```ts
// ❌ function List({ items = [] }) — 매 렌더 새 배열
// ✅
const EMPTY: Item[] = []
function List({ items = EMPTY }) {}
```
- 5. `as`는 "증명 포기" 선언이다
`as Stable<...>` 같은 단언은 리뷰에서 반드시 이유를 물어볼 것.

> **📌 결론**
> ▎ 타입은 데이터 모양뿐 아니라 "참조가 유지된다" 같은 계약도 실어 나를 수 있다.
> ▎ 리액트가 이미 보장하는 것(`useState` setter, `useRef`, `dispatch`)을 타입에 그대로 반영하면 된다.
> ▎ 컴파일러는 자동화, `Stable<T>`는 계약 — 경쟁이 아니라 보완 관계.
> ▎ ⭐️ 실무 적용 포인트: 당장 라이브러리를 도입 안 하더라도, `memo`된 컴포넌트·Context Provider에 넘기는 값은 "이게 다음 렌더에도 같은 참조인가?"를 먼저 묻는 습관. 에이전트가 짠 코드 리뷰할 때 특히.
