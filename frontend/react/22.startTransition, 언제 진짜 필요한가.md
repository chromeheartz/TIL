# startTransition, 언제 진짜 필요한가

> **원문**: [When Do You Really Need startTransition?](https://tigerabrodi.blog/when-do-you-really-need-starttransition) — Tiger Abrodi
> **번역 출처**: [[번역] startTransition은 언제 정말로 필요할까요?](https://imnotadevleoper.tistory.com/383) — 유승완

`startTransition`은 들어본 적은 다들 있는데, 실제로 뭘 하는지 설명해보라고 하면 막히는 API다. 나도 "우선순위 낮추는 거"까지는 알았는데 정확히 리액트 내부에서 뭐가 달라지는지, 그리고 디바운스랑 뭐가 다른지는 흐릿했다. 이 글이 기초부터 딱 정리해줘서 노트로 남긴다.

### startTransition 없이 리액트가 렌더링하는 방식

먼저 기본 동작. `setState`를 부르면 리액트는 렌더링을 예약한다. 컴포넌트 함수를 실행하고, 새 엘리먼트 트리를 만들고, 이전 트리와 비교해서 차이만 DOM에 적용한다. 이게 재조정(reconciliation)이다.

중요한 건 이거다. **기본적으로 모든 상태 업데이트는 긴급(urgent)하다.** 리액트는 업데이트를 전부 똑같이 취급하고, 순서대로, 하나가 끝나야 다음을 시작한다.

검색창을 생각해보자. 키 하나 누를 때마다 `setState`가 불리고, 그 컴포넌트가 10,000개짜리 리스트를 필터링하고 있으면 키 입력마다 10,000개 전체 렌더링이 돈다. 다음 키 입력을 처리하려면 이 렌더링이 끝나야 한다.

"hello" 입력 → 키 입력 5회 → 렌더링 5회 → 각각 10,000개 처리. 리액트가 리스트 렌더링하느라 바쁜 동안 입력 필드가 멈추고, 글자가 한 글자씩이 아니라 덩어리로 튀어나온다. 이게 **쟁크(jank)**다. 메인 스레드가 너무 긴 작업에 막혀서 UI가 끊기는 현상.

### startTransition이 실제로 하는 일

`startTransition`은 리액트에게 "이 업데이트는 긴급하지 않다"고 알려주는 것이다. 그러면 리액트는 이걸 백그라운드에서 처리하고, **더 중요한 작업이 들어오면 중단할 수 있다.**

멘탈 모델은 레인(lane) 두 개다.

| 레인 | 대상 | 특징 |
|---|---|---|
| 긴급 레인 (urgent) | 입력, 클릭, 키 입력 | 즉시 반영 안 되면 앱이 고장 난 것처럼 느껴짐 |
| 전환 레인 (transition) | 필터링된 리스트, 큰 차트, 검색 결과 | 중요하지만 몇 프레임 늦어도 사용자가 못 알아챔 |

`setState`를 `startTransition`으로 감싸면 그 업데이트를 전환 레인으로 보내는 것.

```tsx
import { useState, useTransition } from 'react'

function Search() {
  const [query, setQuery] = useState('')
  const [results, setResults] = useState([])
  const [isPending, startTransition] = useTransition()

  function handleChange(e) {
    // 긴급: 입력 필드는 즉시 갱신
    setQuery(e.target.value)

    // 긴급하지 않음: 리액트가 여유 있을 때 리스트 갱신
    startTransition(() => {
      setResults(filterItems(e.target.value))
    })
  }

  return (
    <div>
      <input value={query} onChange={handleChange} />
      {isPending && <span>필터링 중...</span>}
      <ItemList items={results} />
    </div>
  )
}
```

이제 "hello"를 치면 이렇게 된다.

- "h" 입력 → 입력 필드에 "h" 즉시 표시 → 전환 레인에서 "h" 필터링 시작
- 필터링 중에 "e" 도착 → **"h" 필터링을 버린다** → 입력 필드에 "he" 즉시 표시 → "he" 필터링 시작
- 사용자는 타이핑이 즉시 반영되는 걸 보고, 리액트가 숨 돌릴 틈이 생기면 리스트가 갱신된다

핵심 단어는 **버린다(abandon)**. 새 업데이트가 오면 진행 중인 전환 렌더링을 완료하지 않고 폐기할 수 있다. 이게 중단 가능한 렌더링(interruptible rendering)이고, `startTransition` 없이는 불가능하다. 시작한 렌더링은 무조건 끝내야 하니까.

### 리액트는 언제 중단할지 어떻게 아나

리액트 18 이전에는 렌더링이 동기였다. 시작하면 끝날 때까지 안 멈추고, 그동안 메인 스레드는 막혀 있고, 사용자 이벤트도 처리 못 했다.

리액트 18의 동시 렌더링(concurrent rendering)은 렌더링 작업을 작은 단위로 쪼갠다. 단위 하나 처리할 때마다 "더 급한 거 있나?" 확인하고, 있으면 현재 작업을 멈추고 급한 걸 먼저 한다.

`startTransition`은 "이 업데이트는 멈춰도 안전하다"는 표시다. 리액트는 긴급 업데이트는 절대 안 멈추고, **전환만** 멈춘다.

`useTransition`이 주는 `isPending`은 전환이 진행 중인지 알려준다. 백그라운드에서 무거운 작업이 도는 동안 로딩 표시를 띄우는 용도.

### 실제로 필요한 경우

#### AI 스트리밍

토큰이 초당 10~30개씩 들어온다. 토큰마다 마크다운 문자열이 늘어나고, 블록 단위로 쪼개서 다시 렌더링한다.

`startTransition` 없으면 토큰마다 동기 렌더링이 돈다. 렌더링이 30ms 걸리고 토큰이 33ms마다 오면 렌더링이 쌓이고, 브라우저가 화면 그릴 틈이 없어서 페이지가 멈춘다.

```tsx
useEffect(() => {
  const newBlocks = splitIntoBlocks(content)
  startTransition(() => {
    setBlocks(newBlocks)
  })
}, [content])
```

토큰 1 도착 → 전환 레인에서 렌더링 시작 → 33ms 뒤 토큰 2 도착 → 토큰 1 렌더링 버리고 토큰 2로 새로 시작 → 토큰 3 → 또 버림 → 토큰이 잠시 멈추면 가장 최근 상태로 렌더링 완료. 사용자는 중간 상태를 못 보고 항상 최신만 본다. UI는 내내 반응한다.

#### 대규모 리스트 필터링·검색

제일 대표적인 예. 위에서 본 검색창 그대로다. 입력은 긴급, 필터링은 전환.

#### 무거운 콘텐츠가 있는 탭 전환

탭을 클릭하면 새 탭에 차트, 표, 대량 데이터가 있다. `startTransition` 없으면 새 콘텐츠가 다 렌더링될 때까지 클릭한 탭이 강조 표시조차 안 된다. 클릭이 씹힌 것처럼 느껴진다.

```tsx
function Tabs({ tabs }) {
  const [activeTab, setActiveTab] = useState(0)
  const [content, setContent] = useState(tabs[0].content)
  const [isPending, startTransition] = useTransition()

  function handleClick(index) {
    setActiveTab(index) // 긴급: 탭 강조는 즉시
    startTransition(() => {
      setContent(tabs[index].content) // 전환: 콘텐츠는 준비되면
    })
  }

  return (
    <div>
      <div className="tabs">
        {tabs.map((tab, i) => (
          <button key={i} onClick={() => handleClick(i)} className={i === activeTab ? 'active' : ''}>
            {tab.label}
          </button>
        ))}
      </div>
      {isPending ? <Spinner /> : <TabContent data={content} />}
    </div>
  )
}
```

탭은 즉시 강조되고 콘텐츠는 잠시 뒤에 나타난다.

#### SPA 라우팅

링크를 클릭하면 즉각 반응하는 것처럼 느껴져야 하는데 새 페이지 로딩은 시간이 걸린다. 경로 업데이트를 `startTransition`으로 감싸면 기존 페이지가 그대로 보이는 채로 새 페이지가 백그라운드에서 렌더링된다. 화면이 비는 순간이 없다. React Router와 Next.js는 이미 내부적으로 이렇게 하고 있다.

### 필요 없는 경우

대부분의 상태 업데이트는 `startTransition`이 필요 없다.

- **렌더링이 16ms 미만이면** 필요 없다. 브라우저가 프레임 드롭 없이 처리한다. 빠른 업데이트에 붙이면 이득 없이 복잡도만 는다.
- **사용자 입력을 직접 제어하는 상태**는 감싸지 마라. 입력은 즉시 반영돼야 한다. 대신 업데이트를 분리한다. 입력값은 긴급, 그 하류 효과는 전환.
- **업데이트가 하나뿐이고 작으면** 오버헤드만 생긴다. 스케줄링은 공짜가 아니다. 사소한 업데이트는 그냥 동기 렌더링이 더 빠르다.

```tsx
// ❌ 입력 자체를 전환으로 감싸면 타이핑이 늦게 보인다
startTransition(() => {
  setQuery(e.target.value)
})

// ✅ 입력은 긴급, 파생 결과만 전환
setQuery(e.target.value)
startTransition(() => {
  setResults(filterItems(e.target.value))
})
```

### startTransition vs 디바운싱

같은 문제를 디바운스로 푸는 경우가 많다. "300ms 동안 입력이 멈추면 리스트를 갱신한다." 동작은 하지만 **인위적인 지연**이 생긴다. 리액트가 더 빨리 렌더링할 수 있어도 마지막 키 입력 후 300ms를 무조건 기다려야 한다.

`startTransition`은 지연을 추가하지 않는다. 즉시 시작하되 중단 가능하게 할 뿐이다. 다음 키 입력 전에 렌더링이 끝나면 사용자는 결과를 바로 본다.

| | 디바운싱 | startTransition |
|---|---|---|
| 작업 시작 | 지연시킴 | 즉시 |
| 중단 | 불가 (타이머 리셋만) | 가능 |
| 최소 대기 | 항상 N ms | 0 |

둘을 같이 쓸 수도 있다. **네트워크 요청**처럼 키 입력마다 날리면 안 되는 건 디바운스, 그 뒤에 오는 **렌더링**은 `startTransition`.

### startTransition vs requestIdleCallback

이름이 비슷해서 자주 비교되는데 완전히 다르다. `requestIdleCallback`은 "브라우저가 유휴일 때 이 함수를 실행해라"는 브라우저 API로, 리액트 렌더링과 아무 연동이 없다. 리액트는 이걸 인식 못 하고, 이걸로 리액트 렌더링을 중단시킬 수도 없다.

`startTransition`은 리액트 자체 기능이고 reconciler와 연동된다. 리액트가 전체 프로세스를 제어하니까 중단하고 재개할 수 있다.

| | 용도 |
|---|---|
| `requestIdleCallback` | 분석, 로깅 같은 리액트와 무관한 작업 |
| `startTransition` | 비용 큰 렌더링을 유발하는 리액트 상태 업데이트 |

### 한 문장으로

`startTransition`은 리액트에게 "이 업데이트는 중요하지만 잠시 미뤄도 된다"고 알리는 것이다. 긴급 업데이트가 들어오면 전환 렌더링을 중단해서 UI 반응성을 지킨다. 상태 업데이트가 비싼 렌더링을 일으키는데, 그게 끝날 때까지 사용자를 막으면 안 될 때 쓴다.

---

### 📌 정리
`startTransition은 "미루기"가 아니라 "버려도 되게 만들기"다`

#### 핵심
> 리액트는 기본적으로 모든 업데이트를 긴급으로 보고 시작한 렌더링을 반드시 끝낸다. `startTransition`은 특정 업데이트를 전환 레인으로 보내서, 더 급한 업데이트가 오면 **진행 중인 렌더링을 폐기**할 수 있게 한다. 지연을 넣는 게 아니라 즉시 시작하되 중단 가능하게 하는 것. 그래서 디바운스와 다르다.

#### ⭐️ 앞으로 기억할 것
- **1. 입력값과 파생값을 분리하는 게 전부다**
입력을 제어하는 상태는 절대 감싸지 않는다. 그 값에서 파생되는 무거운 결과만 감싼다.
```tsx
setQuery(value)                                  // 긴급
startTransition(() => setResults(filter(value))) // 전환
```

- **2. 16ms 기준**
렌더링이 한 프레임 안에 끝나면 안 쓴다. 스케줄링 오버헤드 때문에 오히려 느려진다. 프로파일러로 재고 결정.

- **3. 디바운스는 요청에, 전환은 렌더링에**
둘은 대체재가 아니라 다른 층을 다룬다. API 호출은 디바운스로 줄이고, 응답을 받은 뒤 렌더링은 전환으로.
```tsx
const debouncedFetch = useDebounce(fetchResults, 300)
// 응답 도착 후
startTransition(() => setResults(data))
```

- **4. 스트리밍 UI는 전환이 기본값**
토큰이 렌더링보다 빨리 들어오면 중간 상태는 어차피 못 보여준다. 전환으로 감싸면 항상 최신만 렌더링된다.

- **5. `isPending`은 "느려짐"의 시각화**
전환이 진행 중일 때만 true. 탭 전환이나 필터링에 스피너를 붙이는 용도.

- **6. `requestIdleCallback`은 다른 물건**
리액트 렌더링과 무관한 로깅·분석용. 리액트 상태에는 `startTransition`.

> **📌 결론**
> ▎ 리액트 18 이전엔 렌더링이 동기라 중단이 불가능했다. 동시 렌더링이 작업을 쪼개고, `startTransition`이 "이건 멈춰도 된다"를 표시한다.
> ▎ 긴급 레인(입력·클릭)은 절대 안 멈추고, 전환 레인만 멈춘다. 그래서 입력은 감싸면 안 된다.
> ▎ 디바운스는 시작을 늦추고, 전환은 즉시 시작하되 버릴 수 있게 한다. 사용자 체감이 다르다.
> ▎ 대부분의 업데이트에는 필요 없다. 비싼 렌더링 + 사용자를 막으면 안 되는 상황, 이 둘이 동시에 있을 때만.
> ▎ ⭐️ 실무 적용 포인트 — 검색 필터, 무거운 탭, 스트리밍 응답 세 곳부터 점검. 이미 디바운스가 있으면 지우지 말고 렌더링 쪽에 전환을 추가한다. `startTransition`을 붙이기 전에 React DevTools Profiler로 렌더링 시간이 16ms를 넘는지 먼저 확인.
