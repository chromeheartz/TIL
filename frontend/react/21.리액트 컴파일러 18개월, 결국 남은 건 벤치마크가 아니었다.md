# 리액트 컴파일러 18개월, 결국 남은 건 벤치마크가 아니었다

리액트 컴파일러가 2024년 말 리액트 19와 같이 공개 베타로 나왔고, 2025년 10월에 1.0이 됐다. 그 사이 우리 프로젝트에도 켤까 말까를 몇 번 고민만 하다 말았는데, 마침 18개월 회고 글이 있어서 읽어봤다. 저자도 대규모 마이그레이션을 직접 해본 건 아니고 공개 문서·RFC·초기 도입 사례를 모아서 정리한 글이라, 나도 같은 시점에서 정리해둔다.

> 컴파일러의 가장 큰 유산은 벤치마크 숫자가 아니라, "useCallback 의존성 배열 하나 빠졌네요" 같은 대화가 사라졌다는 것이다.

### 18개월의 흐름

발표 → 프레임워크 통합 → 도구 성숙 → 논쟁. 큰 플랫폼 변화가 늘 밟는 순서 그대로였다.

#### 출시와 초기 통합

리액트 19 직후 몇 달은 "설정"이 전부였다. Next.js, Expo, TanStack Start, Vite 계열 프레임워크가 각자 빌드 파이프라인에 컴파일러를 붙였다. 새 프로젝트는 "기본 켜짐, 필요하면 끔"이 기본값이 됐고, 기존 프로젝트는 ESLint 플러그인이 "지금 도입해도 되는지"를 판단하는 지표가 됐다.

#### 조용했던 중간

기대에 비해 조용했다. 초기 도입 팀들이 보고한 성과도 화려하지 않았다. 코드 리뷰에서 잡히는 불필요한 리렌더링 버그가 줄고, "왜 여기 느리지?" 류의 이슈가 줄고, 코드베이스에 메모이제이션 코드가 계속 쌓이는 게 멈췄다는 정도. 극적인 벤치마크 글이 안 나온 이유가 여기 있다. 컴파일러의 가치는 숫자를 보여주는 게 아니라 **애초에 버그가 안 생기게 하는 것**이기 때문이다.

#### 생태계 현실 점검

2025년 말이 되자 질문이 "도입할까?"에서 "**컴파일러랑 안 맞는 라이브러리는 어쩌지?**"로 바뀌었다. Rules of React는 원래 있던 규칙인데 이제 빌드 시점에 강제 검증되니까, 생태계 상당수가 그 규칙을 조용히 어기고 있었다는 게 드러났다. 오래된 상태 관리 라이브러리, 레거시 폼 라이브러리, 일부 DnD 구현체, 다들 좋아하던 유틸 훅 몇 개. 컴파일러가 이걸 망가뜨린 게 아니라, 원래 문제였던 걸 **드러냈을 뿐**이다.

한 줄로 요약하면 이렇다. **그린필드는 끝난 문제, 브라운필드는 아직 프로젝트.**

### 컴파일러가 하는 일

빌드 타임 변환이다. 컴포넌트를 읽고, 코드가 Rules of React를 따른다고 가정한 뒤, 도움이 되는 위치에 메모이제이션을 자동으로 넣는다. 런타임 비용은 없다. 결과물은 그냥 평범한 리액트 코드다.

그리고 사람보다 **더 잘게** 메모한다. 손으로 쓴 `useMemo`는 보통 파생 객체 전체를 한 덩어리로 묶는데, 컴파일러는 그 안의 개별 표현식 단위로 메모할 수 있다. 객체의 한 필드만 바뀌면 나머지는 무효화되지 않는다.

```tsx
// ❌ 컴파일러 이전: 셋 다 손으로
const DashboardRow = memo(({ entity, onSelect }: Props) => {
  const formatted = useMemo(
    () => ({
      label: formatLabel(entity),
      total: entity.items.reduce((sum, i) => sum + i.value, 0),
      status: entity.state === 'active' ? 'green' : 'red',
    }),
    [entity], // entity 객체 통째로 의존
  )
  const handleClick = useCallback(() => onSelect(entity.id), [entity.id, onSelect])

  return (
    <Row onClick={handleClick}>
      <Label color={formatted.status}>{formatted.label}</Label>
      <Total>{formatted.total}</Total>
    </Row>
  )
})
```

```tsx
// ✅ 컴파일러 켠 코드베이스: 그냥 쓴다
function DashboardRow({ entity, onSelect }: Props) {
  const label = formatLabel(entity)
  const total = entity.items.reduce((sum, i) => sum + i.value, 0)
  const status = entity.state === 'active' ? 'green' : 'red'

  return (
    <Row onClick={() => onSelect(entity.id)}>
      <Label color={status}>{label}</Label>
      <Total>{total}</Total>
    </Row>
  )
}
```

`memo`, `useMemo`, `useCallback`이 전부 사라진다. 사용자 체감으로 제일 큰 변화는 **리렌더링 비용이 커지는 방식 자체**가 바뀐다는 점이다. 대표적인 실패 케이스가 리스트다. 부모의 `useCallback` 의존성 하나만 틀려도 타이핑할 때마다 모든 행이 리렌더링되고, 비용은 리스트 크기에 비례해서 커지다가 결국 입력 지연으로 터진다. 컴파일러는 이 구조를 없앤다. props 안 바뀐 행은 리스트가 아무리 커도 그대로다.

#### 비용도 있다

| 항목 | 영향 |
|---|---|
| 빌드 시간 | 공개 벤치마크 기준 수십 % 증가 가능. 증분 빌드는 거의 영향 없음 |
| 번들 크기 | 인라인된 메모 헬퍼 때문에 한 자릿수 초반 % 소폭 증가 |

물론 프로젝트마다 다르니까 직접 재기 전엔 어떤 숫자도 믿지 말 것.

> 컴파일러는 **리렌더링 문제만** 해결한다. 네트워크 워터폴, 과도한 데이터 요청, 번들 크기, 느린 초기 JS 실행은 그대로다. 앱이 느리면 무조건 측정부터. 컴파일러 켜고 나서야 진짜 병목이 딴 데 있었다는 걸 알게 되는 경우가 많다.

### 컴파일러가 손 안 대는 경우

18개월치 마이그레이션 후기에서 공통으로 나온 패턴들이다.

#### 1. 렌더링 중에 props나 클로저를 변경

```tsx
function Row({ entity }: Props) {
  entity.lastSeen = Date.now() // ❌ 렌더링 중 변경
  return <span>{entity.name}</span>
}
```

컴파일러가 변환 안 한다. 코드를 고쳐야 한다.

#### 2. 렌더링 중에 ref를 읽기

```tsx
function Tooltip() {
  const ref = useRef<HTMLDivElement>(null)
  const width = ref.current?.offsetWidth // ❌ 렌더링 중 ref 읽기
  return <div ref={ref}>{width}px</div>
}
```

이펙트나 `useLayoutEffect`로 옮겨야 한다. 컴파일러는 표시만 해주지 대신 고쳐주진 않는다.

#### 3. 레거시 클래스 컴포넌트

아예 컴파일 안 된다. `React.Component` 상속한 게 남아 있으면 그냥 지금까지처럼 동작한다. 새 프로젝트엔 상관없지만 오래된 코드베이스면 알아둘 것.

#### 4. 멀쩡해 보이는 컴포넌트 안의 미지원 문법

이게 사람들이 제일 놀라는 실패 모드다. 컴파일러가 추론 못 하는 문법을 만나면 **그 함수에서 그냥 빠져나간다.** 린트 규칙을 안 켜놨으면 이게 **조용히** 일어난다.

```tsx
// ❌ 구조 분해한 props를 재할당
function Field({ value }: Props) {
  value = value ?? defaultValue // 컴파일러가 이 함수를 통째로 건너뜀
  return <input defaultValue={value} />
}

// ❌ try/catch 안에서 조건문·옵셔널 체이닝·null 병합
async function load(url: string) {
  try {
    const res = await fetch(url)
    const data = ((await res.json()) as Data | undefined) ?? {}
    if (data.ok) setResult(data) // 여기도 컴파일 대상에서 제외
  } catch (e) {
    logError(e)
  }
}
```

둘 다 컴파일되고 실행된다. 런타임 에러도 없다. 문제는 주변 컴포넌트가 **조용히 메모 대상에서 빠진다**는 것. 그리고 대부분 아무도 안 보던 리렌더링 성능 회귀가 터진 뒤에야 알아차린다.

막는 방법은 `react-hooks/unsupported-syntax` 규칙이다. `eslint-plugin-react-hooks` v6부터 들어 있다(`eslint-plugin-react-compiler`는 2025년 말에 이 패키지로 통합됨). v7부터 `recommended`에 기본 포함인데 **심각도가 warning**이라, CI가 error만 실패 처리하면 그냥 지나간다. 조용한 스킵을 빌드 실패로 만들고 싶으면 `error`로 올려야 한다.

#### 5. `"use no memo"` 탈출구

컴파일러 판단이 틀렸거나, 당장 컴파일러 친화적으로 고칠 여력이 없을 때 함수 단위로 끌 수 있다.

```tsx
function ComplicatedLegacyThing() {
  'use no memo'
  // 컴파일러가 이 함수를 건너뛰고 평범한 컴포넌트로 취급
}
```

> 모든 `"use no memo"`는 코드베이스에 숨어 있는 **성능 절벽**이다. 영구 표시가 아니라 TODO로 취급하고, 왜 아직 호환이 안 되는지 주석을 남길 것. 이 지시어 개수를 주기적으로 grep하는 게 코드베이스 건강 지표가 된다.

### 대부분의 팀이 따르는 마이그레이션 순서

공식 문서 + Next.js·Expo·TanStack Start 가이드를 종합하면 순서는 단순하다.

📌 1단계: 리액트 19 이상으로 올린다.

📌 2단계: ESLint 플러그인 적용하고 심각도를 조정한다. `eslint-config-next` v16 이상 같은 프레임워크 프리셋을 쓰면 v7 플러그인이 이미 딸려오고 `recommended`도 켜져 있어서 설치할 건 없다. 진짜 할 일은 **warn을 error로 올리는 것**, 특히 `unsupported-syntax`. 컴파일러 설정 건드리기 전에 여기서 나온 문제부터 고친다.

📌 3단계: annotation-driven 모드로 켠다. 리프 컴포넌트 한두 개부터 적용하고 관찰.

📌 4단계: inference 모드로 전환. 어떤 파일을 컴파일할지 컴파일러가 스스로 판단하게 맡긴다. 테스트 돌리고 실제 인터랙션 프로파일링.

📌 5단계: 컴파일러가 대신 처리하는 수동 메모이제이션을 제거. `useMemo`·`useCallback`·`React.memo`를 대량 삭제.

📌 6단계: 코드베이스가 충분히 정리됐으면 strict mode. 규칙 위반이 조용히 스킵되는 대신 즉시 에러.

5단계로 바로 점프하는 팀은 대개 몇 주째 열려 있는 거대 PR을 만들게 된다. 반면 1·2단계는 독립적으로 적용 가능하고 그 자체로 코드 품질이 좋아진다.

### "규칙을 켠다"는 게 실제로 뭘 의미하나

규칙 목록만 읽어선 체감 안 되는 부분이다. 저자가 제시하는 `eslint.config.mjs` strict 출발점.

```js
{
  rules: {
    // recommended에 warn으로 있는 것 → error로 승격
    'react-hooks/unsupported-syntax': 'error',
    'react-hooks/exhaustive-deps': 'error',
    'react-hooks/incompatible-library': 'error',
    // 기본 비활성인 컴파일러 규칙들
    'react-hooks/todo': 'error',
    'react-hooks/syntax': 'error',
    'react-hooks/capitalized-calls': 'error',
    'react-hooks/rule-suppression': 'error',
    'react-hooks/no-deriving-state-in-effects': 'error',
    'react-hooks/void-use-memo': 'error',
    'react-hooks/automatic-effect-dependencies': 'error',
    'react-hooks/memoized-effect-dependencies': 'error',
    'react-hooks/hooks': 'error',
  },
}
```

#### `react-hooks/todo`가 제일 많이 잡는다

기본 비활성이고 react.dev에 문서화도 안 돼 있는데, 컴파일러 내부의 lowering 실패(컴파일러가 아직 처리법을 못 배운 패턴)를 가장 넓게 드러낸다. 실제 코드베이스에서 자주 나오는 두 가지.

```tsx
// ❌ .map() 람다 안에서 캡처된 카운터를 변경
let globalIndex = 0
return (
  <>
    {groupA.map((row, i) => render(row, i, globalIndex++))}
    {groupB.map((row, i) => render(row, i, globalIndex++))}
  </>
)

// ❌ 이펙트 안에서 동적 import()
useEffect(() => {
  void import('heavy-lib').then(({ default: lib }) => { /* ... */ })
}, [])
```

둘 다 컴파일되고 실행되지만 주변 컴포넌트를 조용히 제외시킨다. 고치는 건 기계적이다.

```tsx
// ✅ 카운터 → 미리 계산한 오프셋
{groupB.map((row, i) => render(row, i, offsetB + i))}

// ✅ 동적 import → 모듈 레벨에서 캐시된 프로미스로 끌어올리기
const heavyLib = import('heavy-lib')
useEffect(() => {
  void heavyLib.then(({ default: lib }) => { /* ... */ })
}, [])
```

`todo`는 `unsupported-syntax`보다 시끄럽다는 건 감안하고 켜둘 만하다.

#### 조용한 스킵은 연쇄된다

한 컴포넌트가 컴파일 대상에서 빠지면, 그 컴포넌트에 대해 하위 규칙들이 진단을 못 내는 경우가 있다. 분석이 첫 실패 지점에서 멈추기 때문. 그래서 상위 스킵 원인을 고치면 바로 두 번째 문제가 튀어나온다. **린트 정리는 한 번에 끝나는 게 아니라 반복 작업이다.** 첫 실행은 개수를 알려주고, 이후 실행이 진짜 상태를 보여준다.

나머지 기본 비활성 규칙들(`syntax`, `capitalized-calls`, `rule-suppression`, `no-deriving-state-in-effects`, `void-use-memo`, effect deps 계열)은 평범한 리액트 관용구를 따르는 코드베이스에선 대체로 조용하다. 그래도 켜두는 게 좋다. 오탐이 낮고, 이 규칙들이 잡는 영역은 조용히 방치하면 안 되는 영역이다.

### 여전히 논쟁 중인 것들

#### Rules of React를 강제 계약으로 볼 것인가

컴파일러 이전에도 규칙은 있었지만 권장 사항에 가까웠다. 컴파일러는 이걸 빌드 타임 경계로 바꿨다. 위반하면 조용히 메모 대상에서 빠진다. "원래 약속보다 엄격한 모델을 사실상 강요한다"는 쪽과 "규칙은 애초에 선택이 아니었고 결과를 보이게 했을 뿐"이라는 쪽. 둘 다 일리 있고, 이 긴장은 규칙이 명문화되기 전에 만들어진 오래된 라이브러리에서 제일 뚜렷하다.

#### `"use no memo"`는 영구 기술 부채인가

너무 쉽게 쓸 수 있어서 `@ts-ignore`나 `// eslint-disable`처럼 수년간 쌓일 거라는 우려. 반대로 전체 리팩터링 없이 배포할 수 있게 해주니 실질적 가치가 있고, 영구 표시로 쓰는 건 기능이 아니라 사용 방식의 문제라는 반론. 확실한 건 하나, **개수를 건강 지표로 보는 것엔 이제 아무도 이견이 없다.**

#### 컴파일러 vs 런타임 최적화 도구

대부분은 컴파일러로 충분하다. 하지만 트레이딩 대시보드, 로그 뷰어, 스프레드시트처럼 리스트 중심 UI에선 Million.js 같은 블록 기반 리컨실러가 여전히 눈에 띄는 이점을 준다. 둘은 다른 문제를 푼다.

| 계층 | 푸는 문제 |
|---|---|
| 컴파일러 | 컴포넌트가 **얼마나 자주** 리렌더링되는가 |
| 런타임 최적화 도구 | 각 리렌더링을 **얼마나 빠르게** 처리하는가 |

같이 쓰는 팀도 있고 실제로 잘 동작하는데, 상호작용을 제대로 정리한 문서는 아직 없다.

### 앞으로의 방향

리액트 팀 발언, Meta 엔지니어링 글, 진행 중인 RFC를 종합한 다섯 가지. 확정이 아니라 **신호**로 받아들일 것.

- **더 세밀한 컴파일 제어** — 지금은 켜기/끄기/annotation 모드가 전부. 특정 컴포넌트는 공격적으로, 다른 건 보수적으로, 레거시는 제외하고 싶다는 요구가 많다. 새 지시어가 나올 가능성이 높다.
- **서버 컴포넌트와의 통합** — RSC는 이미 클라이언트 아일랜드에 메모 친화적 결과물을 만든다. 다음은 직렬화 경계 최적화. 컴파일러가 "이 값은 브라우저로 안 가도 된다"를 증명할 수 있으면 하이드레이션 페이로드 자체가 줄어든다. 사실 리렌더링 횟수보다 **하이드레이션 비용**이 초기 로딩 체감엔 더 중요할 수 있다.
- **`useEvent`** — 최신 상태를 읽으면서 안정적인 콜백을 주는 API. 오래 논의됐는데 컴파일러의 순수성 분석이 있어야 검증 가능해서 진전이 없었다. 가까운 미래에 어떤 형태로든 나올 듯.
- **리액트 네이티브** — 네이티브 뷰 diffing은 웹 재조정보다 비싸서 자동 메모의 효과가 더 크다. Expo는 이미 지원, RN 자체는 더딤.
- **DevTools** — 지금 제일 부족한 것. 컴파일러가 각 컴포넌트에 뭘 했고 왜 했는지 보여주는 패널. 지금은 ESLint가 "건너뛰었다"만 알려준다. 공식 로드맵엔 없지만 커뮤니티 플러그인으로 먼저 나올 수도.

### 저자의 결론

컴파일러가 남길 유산은 벤치마크가 아니다. "`useCallback` 의존성 빠졌네요"가 더 이상 대화 주제가 아니게 된 것. "이 컴포넌트 메모해야 하나?"도 마찬가지. 답은 항상 "그렇다"이고 컴파일러가 대신 한다.

더 흥미로운 질문은 Rules of React가 이제 **빌드 타임 계약**이 된 상황에서 이 규칙들이 어떤 의미를 갖느냐다. 앞으로 1년의 핵심은 컴파일러 자체보다 생태계가 얼마나 컴파일러 친화적으로 재편되느냐에 달렸다.

새 프로젝트면 그냥 켜라. 기존 프로젝트면 오래된 코드를 직접 고칠지, `"use no memo"`를 유예 장치로 받아들일지 결정해야 한다. 둘 다 합리적이고, 중요한 건 **의도적으로** 결정하는 것.

> 2026년에 `useMemo`나 `useCallback`을 본다면, 현대 JS에서 손으로 쓴 `for` 루프를 보는 것처럼 생각해도 된다. 대부분 문제없고, 가끔 여전히 필요하고, 많은 경우 더 나은 도구가 나오기 전에 쓰인 코드라는 신호다.

### 📌 정리
`컴파일러는 성능 도구가 아니라 "메모이제이션 실수"라는 버그 클래스를 없애는 도구다`

#### 핵심
> 컴파일러는 빌드 타임에 Rules of React를 전제로 자동 메모를 넣는다. 규칙을 어기면 에러가 아니라 **조용히 그 함수를 건너뛴다.** 그래서 컴파일러 설정보다 ESLint 심각도 설정이 먼저다. 그린필드는 그냥 켜면 되고, 브라운필드는 린트 → annotation → inference → 수동 메모 삭제 순서로 간다.

#### ⭐️ 앞으로 기억할 것
- **1. 실패는 조용하다. 린트를 error로 올려야 보인다**
`react-hooks/unsupported-syntax`는 v7 `recommended`에 있지만 warning이다. CI가 error만 막으면 그냥 통과한다. 최소 이 세 개는 error로.
```js
'react-hooks/unsupported-syntax': 'error',
'react-hooks/exhaustive-deps': 'error',
'react-hooks/incompatible-library': 'error',
```

- **2. 컴파일러를 건너뛰게 만드는 흔한 코드 4가지**
렌더링 중 props 변경, 렌더링 중 `ref.current` 읽기, 구조 분해한 props 재할당, try/catch 안의 조건문·`?.`·`??`. 전부 런타임 에러 없이 조용히 빠진다.
```tsx
// ❌ 이 한 줄 때문에 컴포넌트 전체가 메모 대상에서 제외
function Field({ value }: Props) {
  value = value ?? defaultValue
  ...
}
// ✅ 새 변수로
function Field({ value }: Props) {
  const resolved = value ?? defaultValue
  ...
}
```

- **3. `"use no memo"`는 TODO다**
왜 못 고쳤는지 주석 필수. 개수를 grep해서 추적하면 코드베이스 건강 지표가 된다.
```bash
grep -rn '"use no memo"\|'"'"'use no memo'"'"'' src | wc -l
```

- **4. 린트 정리는 반복이다**
스킵은 연쇄된다. 첫 번째 원인을 고치면 두 번째가 드러난다. 첫 실행 결과는 "개수"이지 "전체 상태"가 아니다.

- **5. 컴파일러가 안 푸는 문제를 구분할 것**
리렌더링 횟수만 줄인다. 네트워크 워터폴, 번들 크기, 하이드레이션, 초기 JS 실행은 그대로. 느리면 측정부터.

- **6. 이펙트 안 동적 import는 모듈 레벨로**
`react-hooks/todo`가 잡는 대표 패턴. 컴포넌트 본문에서 `import()` 표현식을 빼면 된다.
```tsx
// ✅
const heavyLib = import('heavy-lib')
useEffect(() => { void heavyLib.then(...) }, [])
```

> **📌 결론**
> ▎ 컴파일러의 가치는 벤치마크가 아니라 "의존성 배열 빠졌네요" 리뷰 코멘트가 사라지는 것이다.
> ▎ 규칙 위반은 에러가 아니라 조용한 스킵이다. 그래서 컴파일러 설정보다 ESLint 심각도가 먼저다.
> ▎ 그린필드는 그냥 켜라. 브라운필드는 린트 → annotation → inference → 수동 메모 삭제, 순서대로.
> ▎ `"use no memo"`는 영구 표시가 아니라 주석 달린 TODO다.
> ▎ ⭐️ 실무 적용 포인트 — 지금 프로젝트에 컴파일러를 안 켰더라도 2단계(ESLint v7 + `unsupported-syntax`를 error)는 독립적으로 적용 가능하고 그 자체로 코드 품질이 올라간다. 여기서부터 시작하면 된다.
