# 죽은 프레임워크 이론: LLM 시대에 리액트가 플랫폼이 된 이유

> **원문**: [Dead Framework Theory](https://aifoc.us/dead-framework-theory) — Paul Kinlan
> **번역 출처**: [(번역) 죽은 프레임워크 이론 (dead framework theory)](https://handhand.tistory.com/entry/dead-framework-theory) — handhand (Korean FE Article)

"LLM이 프레임워크 선택을 추상화할 것"이라는 예측을 저자 본인이 1년 전에 했다가 틀렸다고 인정하며 시작하는 글이다. 현실은 반대였다. 리액트는 다른 프레임워크와 경쟁하는 게 아니라 **플랫폼**이 됐고, 지금 새 프레임워크나 브라우저 기능을 만든다면 리액트가 아니라 LLM 학습 데이터·시스템 프롬프트·개발자 생성 코드 사이의 자기 강화 루프와 싸워야 한다는 얘기. Claude Code로 코드를 뽑을 때마다 "왜 자꾸 리액트로 시작하지?" 싶었던 나한텐 꽤 설득력 있었다.

### 도구들은 프레임워크를 추상화하지 않았다

Replit, Bolt 같은 도구가 뭘 하는지 보면 프레임워크를 감추려는 게 아니다. 오히려 [`시스템 프롬프트에 리액트를 명시적으로 하드코딩`]하고 있다. 그래야만 하기 때문이다. 개발자가 유지보수할 수 있는 코드를 줘야 하는데, 대다수 웹 개발자에게 "유지보수할 수 있는 코드"는 곧 리액트다.

탐지 방식 오류, 데이터셋 크기, 측정 정의가 다 달라서 걸러 봐야 하지만, 추세는 부인하기 어렵다. Angular 같은 경쟁자가 정체하는 동안 리액트는 계속 성장한다.

#### 성장을 견인한 건 LLM

저자의 해석은 지난 12~18개월 동안 LLM 도구들이 리액트 코드를 선호해서 생성했기 때문이라는 것. OpenRouter의 토큰 증가 곡선이 리액트 배포 증가와 시기적으로 겹친다.

![OpenRouter 토큰 사용량](https://blog.kakaocdn.net/dna/bK2udm/dJMcahbQyoc/AAAAAAAAAAAAAAAAAAAAAOm6kxSSLOUHiv8gC7nobwVZ9pgcB73pj8p4lxIS1WBr/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1790780399&allow_ip=&allow_referer=&signature=sN8hzPb4m3f3nbJaB5xHyN%2Bt1T8%3D)

상관관계가 인과는 아니고, 전체 그림은 도구 제작자만 볼 수 있다. 그래도 타이밍이 절묘하다.

### 두 개의 피드백 루프

**데이터 루프**

1. 리액트가 기존 웹을 지배한다 (12개월에 1,300만 사이트)
2. LLM은 기존 웹으로 학습한다
3. LLM은 기본적으로 리액트를 생성한다
4. LLM으로 만든 새 사이트는 리액트다
5. 미래 학습용 리액트 사이트가 더 많아진다
6. 2번으로

**도구 루프**

1. 리액트가 개발자 생태계를 지배한다
2. IDE와 도구는 개발자 선호에 맞춰 리액트를 우선 생성한다
3. 도구는 LLM에게 기본적으로 리액트를 요청한다
4. 새 사이트는 리액트다
5. 리액트 사이트가 많아져서 리액트 생성 수요가 는다
6. 1번으로

저자는 이게 좋은지 나쁜지 판단하지 않는다. 웹에 사이트가 늘고 품질도 꽤 높다. 다만 새 프레임워크·도구·플랫폼 기능에는 **장벽**이 생긴다.

### 새 프레임워크가 넘어야 할 것

기술적으로 우수하더라도 이걸 다 해야 한다.

- LLM 학습 데이터에 진입 (최소 12~18개월 지연)
- 도구 제작자를 설득해서 시스템 프롬프트 수정 (채택이 선행돼야 함)
- 포괄적인 라이브러리 생태계 구축 (수년)
- 개발자 관성을 극복하고 스스로 요구하게 만들기

1단계 끝날 때쯤이면 리액트 생태계는 사이트 1,000만 개를 더 만들어놨을 거다. 순서를 뒤집어서 인식 점유율 캠페인을 하거나, 라이브러리 생태계에 유료로 통합하거나, 심지어 **도구 제공자에게 돈을 내고 시스템 프롬프트에 자기 프레임워크를 넣는 비즈니스 모델**이 생길 수도 있다고 본다. 그래도 리액트 라이브러리와 학습 데이터 양쪽에 뿌리내린 패턴과 싸우는 건 마찬가지.

리액트가 최고라거나 LLM에 적합한 모델이라는 얘기가 아니다. 저자는 그럴 근거를 못 찾았다고 한다. 그냥 **네트워크 효과가 대안을 존속시키기 어렵게 만드는 지점을 이미 넘었다**는 것.

#### 저자가 직접 겪은 사례

Chrome 내장 Prompt API로 익스텐션을 만들려고 Claude를 썼는데, 6개월 전 API인 `self.ai.languageModel`을 썼다. 현재 API는 `LanguageModel.create()`인데 아직 학습 데이터에 없었던 것.

여기에 상호 운용성 작업이 수년 걸려서 "Baseline Newly Available"이 되고, 다시 30개월 지나야 "Widely Available"이 된다는 사실을 더하면, 그때쯤 생태계는 이미 다른 데 가 있다.

**LLM 학습 데이터에 없으면 존재하지 않는 것이다.** 최소 12~18개월, 다음 학습 주기까지, 그리고 통계적으로 의미 있을 만큼 예시가 쌓이기 전까지는.

| 대상 | 학습 마감 전 실사용 기간 |
|---|---|
| 웹 플랫폼 API | 0~6개월 |
| 새 프레임워크 | 0~6개월 |
| 리액트 패턴 | 10년 이상 |

### 플랫폼 기능도 같은 역학에 걸린다

프레임워크 기능을 대체하려는 새 웹 API의 흔한 패턴.

1. 브라우저 팀이 프레임워크에서 흔한 패턴을 식별 (Sass 대신 CSS Nesting)
2. 수년간 표준화
3. 브라우저에 배포
4. 개발자들은... 계속 프레임워크 패턴을 쓴다

왜냐하면 LLM은 오래된 패턴으로 학습했고(Sass 15년 vs CSS Nesting 1~2년), 프레임워크가 이미 돌아가고, 생태계가 이미 있고, **전환할 동기가 없다.** 새 플랫폼 기능이 사용자에게 사이트를 더 좋게 만들진 않으니까.

- CSS Nesting은 거의 출력되지 않는다. 전처리 패턴이 데이터에 더 흔하고, 리액트 개발자는 이미 LLM이 출력할 줄 아는 CSS-in-JS를 갖고 있다.
- 캐러셀을 플랫폼 기본 기능으로 만들자는 의견이 있어도, 학습 데이터에 이미 있는 캐러셀 라이브러리가 수없이 많다.

저자 본인도 CSS Nesting을 좋아한다. 읽고 유지보수하기 쉬우니까. 그런데 그게 **사이트를 쓰는 사람의 경험을 바꾸진 않는다.** 성능도 접근성도 안 바뀐다. 작성자만 편해진다.

정말 중요한 새 플랫폼 기능은 사용자 영역에서 못 만드는 것들뿐이다.

- 다중 페이지 View Transitions (새로운 탐색)
- WebGPU (근본적으로 새로운 연산 접근)
- WebAuthn과 Passkeys (보안 기본 요소)

나머지는 전부 리액트 라이브러리와 학습 데이터에 뿌리내린 패턴과 경쟁한다.

### 세 개의 시장

| 그룹 | 규모 | 특징 |
|---|---|---|
| 핵심(head) | 상위 1,000~100만 | 트래픽·수익 대부분. 안정된 팀, 기술 전환 어려움. LLM은 속도용으로만 쓰고 프레임워크는 안 바꿈 |
| 중간(middle) | 다음 1,000만 | 소규모 팀·개인. LLM으로 사이트를 통째로 만들고, 별도 프롬프트 없으면 **도구의 기본값** 사용 |
| 긴 꼬리(long tail) | 그 이후 | 정규 개발자가 아님. Lovable, Replit, 채팅 앱에서 직접. 코드를 볼 필요조차 없을 수 있음 |

중간과 긴 꼬리가 웹사이트 성장의 주역인데, 이들은 Passkeys, Web Components, CSS Nesting, View Transitions 같은 새 기능을 모르는 도구로 사이트를 만든다. 그냥 원하는 기능이 돌아가는 사이트를 원할 뿐이다.

그리고 **일반 사용자는 도구에 관심이 없다.** 페이지가 빠른가, 인터랙션이 부드러운가, 필요한 기능이 되는가. 그게 전부다.

### 각자에게

**프레임워크 제작자에게.** 새 프레임워크를 만드는 건 LLM이 최소 12~18개월 동안 안 내놓을 제품, 즉 라이브러리 생태계도 없고 개발자도 모르고 기업도 안 쓸 제품을 만드는 것이다. 리액트의 기술적 장점과 경쟁하는 게 아니라 모든 학습 데이터에서 리액트가 차지하는 **통계적 우위**와 경쟁하는 것.

**플랫폼 개발자에게.** 개발자 경험용 기능(문법 설탕, 편의 API)은 대부분 채택되지 않을 것이다. 사용자 영역에서 못 만드는 근본적인 기능에 집중하고, 개발자가 아닌 **사용자에게 주는 이점**을 면밀히 검토해야 한다. 그 관점에서 웹 컴포넌트부터 문법 변화까지 많은 플랫폼 기능이 앞으로 몇 년간 사이트를 만들 대다수에게 필요 없을 것이다.

**도구 제작자에게.** 기본적으로 리액트를 생성하지 않으면 시장이 제한된다. 경쟁자는 현재 수요를 채우고 있다. 프레임워크 다양성에 원칙을 고수할 여유가 없다.

### 죽은 프레임워크 이론

프레임워크가 사라진다는 얘기가 아니다. 리액트가 플랫폼이 된 세상에서, 적어도 사람이 코드를 유지보수해야 하는 한, **새 프레임워크는 도착과 동시에 죽어 있다(dead on arrival)**는 것.

업계는 계속 혁신해야 한다. 다만 작동하는 역학을 인식하고, 결과물을 학습 데이터·시스템 프롬프트·개발자 마음에 심을 명확한 전략이 있어야 한다.

이대로 가면 LLM이 리액트와 학습 데이터에 뿌리내린 소수 라이브러리로 웹을 만드는 세상이 된다. 프레임워크 혁신은 정체되고, 리액트는 보이지 않고 변경 불가능한 **인프라**가 된다.

#### 낙관적인 시나리오

LLM 사용이 계속 늘면 도구 벤더들은 동질화된 생태계 안에서 경쟁해야 한다. 모두가 리액트를 내놓으면 프레임워크 선택으로는 차별화가 안 되니까 **코드 생성 품질**로 경쟁하게 된다. 시장의 힘이 개발자 경험에서 사용자 경험으로 초점을 옮긴다.

어느 시나리오든 사용자 결과물을 두고 경쟁해야 한다. 저자는 Core Web Vitals가 성능에 했던 것처럼 **품질 결과물에 대한 벤치마크**가 등장하길 바란다.

그리고 성공한다면, 장기적으로 모델이 충분히 좋아져서 사람이 말만으로 사이트를 조작하고 LLM 제공자가 자체 프레임워크나 튜닝으로 더 나은 결과를 내면 [`프레임워크는 무의미해진다`]. 전달 기술은 사용자 요구를 충족하는 최적화된 컴파일 출력이 되고, 그게 리액트든 뭐든 상관없어진다.

### 📌 정리
`새 프레임워크의 경쟁 상대는 리액트가 아니라 리액트가 학습 데이터에서 차지하는 통계적 우위다`

#### 핵심
> LLM은 웹으로 학습하고 웹은 리액트로 만들어지니, LLM은 리액트를 내놓고 그게 다시 웹이 된다. 도구 제작자는 개발자가 유지보수할 수 있는 코드를 줘야 해서 시스템 프롬프트에 리액트를 하드코딩한다. 이 두 루프 때문에 새 프레임워크와 개발자 편의용 플랫폼 기능은 학습 데이터에 없다는 이유만으로 최소 12~18개월간 존재하지 않는 것과 같다. 살아남는 플랫폼 기능은 사용자 영역에서 못 만드는 것뿐이고, 경쟁의 축은 개발자 경험에서 사용자 경험으로 옮겨간다.

#### ⭐️ 앞으로 기억할 것
- **1. LLM이 뽑는 API는 6~18개월 전 것이다**
새 브라우저 API나 라이브러리 최신 버전을 쓸 땐 문서를 컨텍스트에 직접 넣어야 한다. 저자도 Claude가 6개월 전 Prompt API를 써서 당했다.
```
// 프롬프트에 최신 문서 링크나 스니펫을 명시
"LanguageModel.create()를 써라. self.ai.languageModel은 폐기됐다."
```

- **2. 기본값이 곧 시장이다**
중간과 긴 꼬리 그룹은 도구가 내놓는 기본값을 그대로 쓴다. 프레임워크·라이브러리를 만든다면 "LLM이 프롬프트 없이 이걸 내놓게 하려면?"이 채택 전략의 핵심 질문.

- **3. 플랫폼 기능은 "사용자에게 뭐가 좋아지나"로 평가**
CSS Nesting, Web Components 같은 개발자 편의 기능은 채택이 더디다. View Transitions, WebGPU, Passkeys처럼 사용자 영역에서 못 만드는 것만 확실히 살아남는다.

- **4. 데이터셋 출처를 항상 확인**
builtwith 4억 도메인 vs HTTP Archive 1,600만 origin. 같은 "리액트 점유율"이 정의에 따라 몇 배 차이 난다. 추세 방향만 믿고 절대값은 걸러서.

- **5. 프레임워크 선택으로는 더 이상 차별화가 안 된다**
모두가 리액트를 내놓으면 남는 경쟁 축은 코드 생성 품질과 사용자 결과물. Core Web Vitals 같은 품질 벤치마크가 다음 전장이 될 가능성이 높다.

- **6. 리액트 외 스택은 의도적 선택이어야 한다**
SvelteKit, Solid, 신규 프레임워크를 쓰면 LLM 도구 지원, 라이브러리 생태계, 채용 풀 모두에서 12~18개월 뒤처진 상태로 시작한다. 그래도 쓸 이유가 있으면 쓰되, 그 비용을 알고 결정할 것.

> **📌 결론**
> ▎ 리액트는 프레임워크가 아니라 플랫폼이 됐다. 학습 데이터 루프와 도구 루프가 이걸 되돌릴 수 없게 만든다.
> ▎ 학습 데이터에 없으면 존재하지 않는다. 새 API·프레임워크는 최소 12~18개월간 LLM의 눈에 안 보인다.
> ▎ 개발자 경험용 플랫폼 기능은 대부분 채택되지 않는다. 사용자 영역에서 못 만드는 근본 기능만 살아남는다.
> ▎ 프레임워크가 동질화되면 경쟁은 사용자 경험으로 이동한다. 그게 오히려 낙관적인 시나리오다.
> ▎ ⭐️ 실무 적용 포인트 — 새 API를 LLM 도구로 쓸 땐 최신 문서를 컨텍스트에 직접 넣는 걸 습관화. 프로젝트 스택을 정할 때 "LLM 도구가 이 스택을 얼마나 잘 내놓나"를 기술 평가 항목에 추가. 그리고 프레임워크 논쟁에 쓸 시간을 사용자 지표(LCP, INP, 접근성)로 돌리는 게 이 글이 말하는 방향이다.
