# "상태 관리" 라이브러리는 상태를 관리하지 않는다

> **원문**: [The Absolute State of Management][origin] — Alex Russell
> **번역 출처**: [[번역] 상태 관리의 참담한 현주소][translation] — imnotadevleoper

Zustand, Jotai, Redux, TanStack Store... 매번 "상태 관리 뭐 쓰세요?"라는 질문이 나오는데, Alex Russell은 아예 그 단어 자체가 틀렸다고 말한다. 리액트도, 그 위에 얹는 라이브러리들도 상태를 "관리"하는 게 아니라는 주장. 처음엔 말장난 같았는데 읽고 나니 꽤 뼈아팠다. 정리해둔다.

### 1루수가 누구야

저자가 컨설팅하면서 반복적으로 겪는 대화가 있다. 대충 이런 식이다.

- "이 UI는 하는 일에 비해 너무 무거운데, 리액트 없이 가는 건 고려해봤나요?"
- "그럼 상태 관리는 어떻게 하죠?"
- "다른 대안들도 반응형으로 잘 돌아가는데요?"
- "리액트가 우리 앱의 상태를 관리하잖아요."
- "그럼 여러분이 같이 쓰는 그 상태 관리 라이브러리들은 뭘 하는 건데요?"
- "아... 걔네가 상태를 관리하죠."

실제로 라이브러리들의 자기소개를 모아보면 전부 "상태 관리"를 내세운다.

| 라이브러리 | 자기소개 |
|---|---|
| [MobX][mobx] | 간단하고 확장 가능한 상태 관리 |
| [Satchel][satchel] | 뷰 업데이트를 쉽게 해주는 옵저버블 상태 |
| [Recoil][recoil] | 리액트를 위한 상태 관리 라이브러리 |
| [Jotai][jotai] | 리액트를 위한 원시적이고 유연한 상태 관리 |
| [XState][xstate] | JS/TS 앱을 위한 상태 관리 및 오케스트레이션 |
| [Apollo][apollo] | GraphQL 상태 관리 라이브러리 |
| [Redux][redux] | 예측 가능한 상태 컨테이너 |
| [TanStack Store][tanstack-store] | 프레임워크 독립적인 상태 프리미티브 |
| [Zustand][zustand] | 리액트 상태 관리를 위한 최소한의 필수 요소 |

그런데 [리액트 공식 문서도 "Managing State"에 꽤 긴 분량을 할애][react-managing-state]하고 있다. 그러면 셋 중 하나는 참이어야 한다.

- 리액트가 상태 관리 시스템이다 → 위 라이브러리들은 중복 의존성이니 지워도 된다.
- 리액트가 불완전한 상태 관리 시스템이다 → 상태 관리의 애매한 일부만 리액트에 맡기는 걸 그만둬야 한다.
- 리액트는 애초에 상태 관리 시스템이 아니다 → 그런 척하는 걸 그만둬야 한다.

저자의 결론은 간단하다. **이 도구들 중 상태를 관리하는 건 하나도 없다. 리액트도 포함해서.**

### 그럼 얘네는 뭘 하는 건데

캡슐화는 한다. 업데이트를 필터링하거나 변환도 한다. 하지만 하는 일의 본질은 `상태 변경 알림을 국소적으로 전파`하는 것이고, 거기에 약간의 후처리와 캐시가 붙은 정도다. 표현력 면에서 이벤트 버스나 Pub/Sub와 동일하다. 그러니까 "상태 관리"가 아니라 `메시지 백플레인`이라고 부르는 게 정확하다는 것.

각주에 더 신랄한 얘기가 있는데, 이들은 캐시 비슷한 역할을 하긴 하지만 데이터베이스는 아니다. 질의(query)도 안 되고 로컬 영속성도 제대로 없다. 인덱스도 메타데이터도 없는 얇은 스냅샷 하나를 범용 데이터 접근 계층처럼 쓰면 최선이 O(n²)다. 실제로 Redux 스토어를 JSON으로 직렬화해뒀다가 부팅 시 읽으려다 실패하는 큰 서비스도 봤다고 한다. 하하, 이거 남 얘기 같지 않다.

### 상태 전파 vs 상태 관리, 차이는 '시간'

이 글의 핵심이 여기다. `상태 전파(state propagation)`와 `상태 관리(state management)`를 가르는 건 **시간이라는 차원**이다.

리액트식 "상태 관리" 라이브러리들이 시간을 다루는 방식은 멀티스레드 C++랑 비슷하다. 즉, 독자가 알아서 하라고 남겨둔다. 순서도 타임스탬프도 없는 업데이트들을 조합해서 하나의 상태를 만들 수는 있다. 하지만 그걸 "관리"라고 부르는 건 희망 사항이다. 상태를 관리한다는 건 시간에 따라 발생하는 변경을 올바른 순서로 적용하고, 충돌을 해결한다는 뜻이기 때문이다.

```ts
// ❌ 전파만 있는 세계. 어느 업데이트가 먼저인지 시스템은 모른다
store.setState({ title: 'A' }) // 탭 1에서, 오프라인이었다가 복귀
store.setState({ title: 'B' }) // 탭 2에서, 방금
// 결과는 "마지막에 도착한 놈"이고, 그게 맞는지는 아무도 보장 안 함

// ✅ 관리가 있는 세계. 변경에 순서 메타데이터가 붙는다
doc.transact(() => { text.insert(0, 'A') }) // 벡터 클록 유사 메타데이터로 순서 확정
// 다른 클라이언트의 동시 변경과 충돌해도 결정적으로 병합됨
```

### 그때, 지금, 그리고 앞으로

리액트 + Redux로 비대해진 코드에서 터지는 문제들은 대부분 같은 뿌리다. 들어오는 업데이트는 출처도, 빈도도, 범위도 제각각인데, 순수 전파 시스템은 "이벤트 버스"라는 추상화 하나로 그 결과를 다 처리하려다 부수적 복잡성에 깔려 무너진다.

본질적으로 이건 **여러 컴퓨터에 걸쳐 데이터를 관리하는 문제**와 같다. 과거 → 현재 → 미래를 가로질러 데이터를 관리하는 문제.

이 관점이 왜 중요하냐면, "지금 메모리에 있는 앱"과 "나중에 다시 켠 같은 앱"을 구분하게 해주기 때문이다. 미래의 어느 시점에 실행되는 앱 인스턴스는 개념적으로 **다른 컴퓨터에서 도는 같은 앱**과 다를 게 없다. 이걸 받아들이는 순간 "상태 관리 라이브러리 뭐 쓰지"라는 질문이 "시간에 걸친 데이터 일관성을 어떻게 보장하지"로 바뀐다.

진짜로 상태를 관리하는 시스템은 내부에 [벡터 클록][vector-clock] 비슷한 메커니즘이 있다. 변경마다 시간·순서 메타데이터를 같이 기록해야 전체 시스템에서 순서를 일관되게 결정할 수 있고, 그게 없으면 충돌 해결 자체가 불가능하다. 이 기준으로 보면 앞서 나온 라이브러리 중 상태를 관리하는 건 없다. 리액트도 마찬가지.

### 진지하게 바라보기

그렇다고 용어 쓰는 사람들을 비난만 할 건 아니다. 진짜 상태를 관리하는 시스템은 아직 널리 안 쓰이고, 대부분의 팀이 [CRDT][crdt], [Operational Transform][ot], [Prolly Tree][prolly] 같은 걸 접해본 적이 없다. 프론트엔드 커뮤니티에서 활발한 주제도 아니다.

다행히 이론과 실무의 간극은 생각보다 작다. 이미 쓸 수 있는 구현체들이 있다.

- [`Y.js`][yjs]: CRDT를 텍스트 편집에 적용한 대표 주자. 자료구조 성능이 좋아져서 몇 년 전엔 비현실적이던 "완전 CRDT" 접근이 이제 실용적이다.
- [`Zero`][zero]: Replicache의 후속. 데이터 동기화를 넘어 실시간 협업까지 목표. 셀프호스팅도 되고 호스팅 서비스도 있다. 저자가 지금 새 프로젝트를 시작한다면 1순위로 꼽는 선택지.
- [`Fluid Framework`][fluid]: Microsoft의 오픈소스 협업·동기화 시스템. OT 아이디어 기반.

이런 시스템의 아름다운 점은, 시간과 충돌을 시스템 차원에서 다루기 때문에 **'지금'의 양쪽 경계를 모두 자연스럽게 처리**한다는 것이다. 실시간 협업(미래 쪽)도, [오프라인 우선][offline-first](과거 쪽)도 별도 기능이 아니라 그냥 따라오는 효과가 된다. Y.js나 Replicache처럼 로컬 우선(local-first)까지 가능하게 하는 것도 있다.

각주에서 덜 구조적인 대안들도 언급한다.

| 도구 | 평가 |
|---|---|
| [PouchDB][pouchdb] | 고전. 아직 개선되지만 충돌 해결 전략이 너무 단순해서 새 프로덕션엔 비추 |
| [RxDB][rxdb] | 충돌 해결을 개발자에게 맡기는 게 아쉬움. CRDT 통합 구조가 있으니 그걸 쓰라 |
| [Replicache][replicache] | 완전한 동기화 + 좋은 충돌 제어. 오픈소스지만 Rocicorp 지원이 줄어든 상태. Y.js가 무겁다면 좋은 선택 |
| Google Docs API | 사실상 Docs를 돌리는 OT 시스템의 외부 진입점. 비공개·셀프호스팅 불가라 비추 |

### 그래도 작은 컴포넌트엔 필요 없잖아?

가장 흔한 반론. 맞는 말이기도 하다. 많은 UI 컴포넌트의 내부 상태는 시간에 따른 이력을 관리할 만큼 복잡하지 않다. 토글, 모달 열림 여부, 입력 포커스. 이런 건 시간 개념 없는 상태 머신으로 충분하고 그게 합리적이다.

문제는 그 작은 범위를 벗어난 뒤에도 **앱 전체의 충돌을 같은 방식으로 처리할 수 있다고 믿는 것**이다. 이 둘은 근본적으로 다른 문제다. 모든 걸 컴포넌트의 무한 재귀로 보고 횡단 관심사는 없다고 여기는 리액트식 사고는, 정작 리액트 커뮤니티의 실무만 봐도 성립하지 않는다. 저자 표현으로는 "Redux는 도움을 요청하는 비명"이다.

대부분의 팀은 실시간 협업 기능을 붙여야 하는 순간에야 더 나은 접근이 있다는 걸 깨닫는다. 그 전까지 Apollo나 Redux를 데이터 동기화 엔진처럼 억지로 굴리느라 쏟는 노력이 안타깝다는 것.

### 용어 오용에 대한 덤

각주 1이 재밌는데, 저자가 꼽는 리액트 문화의 가장 심각한 용어 오용은 `서버 사이드 렌더링`, `순수 함수`, `동시성`이다. 오래 연구된 개념을 가져다 훨씬 느슨하게 재정의한 뒤, 원래 개념의 권위를 빌려 모조품을 정당화했다는 비판. "상태 관리"도 그 계보에 있다는 얘기다. 더 나은 이름 후보로 "이벤트 블렌더", "상태 체(strainer)", "혼란 캐시" 같은 걸 던지는데, 솔직히 "메시지 백플레인"이 제일 정직한 것 같다.

### 📌 정리
`"상태 관리"는 이벤트 전파다. 진짜 관리는 시간과 충돌을 다룬다`

#### 핵심
> Redux, Zustand, Jotai, 그리고 리액트의 `useState`까지, 이들이 하는 일은 **상태 변경 알림을 전파**하는 것이다. Pub/Sub와 표현력이 같다. 진짜 "관리"는 **시간과 순서**를 내장해서 과거(오프라인)와 미래(다른 클라이언트의 동시 편집)에서 오는 변경을 올바르게 병합하고 충돌을 해결하는 것이고, 그건 CRDT/OT 기반 시스템(Y.js, Zero, Fluid)의 영역이다. 작은 컴포넌트엔 전파로 충분하지만, 앱 전체의 데이터 일관성을 전파 시스템으로 해결하려는 순간 복잡성에 깔린다.

#### ⭐️ 앞으로 기억할 것
- 1. 상태 전파 ≠ 상태 관리
구분 기준은 "시간"이다. 업데이트에 순서·출처 메타데이터가 없으면 전파다. 라이브러리 고를 때 "이게 충돌을 어떻게 해결하지?"를 먼저 물어보자. 대답이 "마지막 setState가 이김"이면 전파 시스템이다.
- 2. "나중에 다시 켠 앱"은 "다른 컴퓨터의 앱"이다
localStorage에 스토어 직렬화해두고 부팅 시 복원하는 패턴은 사실 분산 시스템 문제를 맨손으로 푸는 것이다. 데이터가 커지면 무조건 터진다.
```ts
// ❌ Redux 스토어 통째로 직렬화. 큰 서비스에서 실제로 부팅 실패한 사례
localStorage.setItem('store', JSON.stringify(store.getState()))

// ✅ 영속성·동기화·충돌을 아는 계층에 맡김
const doc = new Y.Doc()
new IndexeddbPersistence('my-app', doc) // 로컬 우선
new WebsocketProvider(url, 'my-app', doc) // 실시간 협업은 덤
```
- 3. 스토어는 DB가 아니다
질의도, 인덱스도, 영속성도 없다. 스토어에서 `Object.values(state.items).filter(...)`를 여기저기서 돌리고 있다면 O(n²)로 가는 중이다. 데이터 접근 계층이 필요한 시점이 온 것.
- 4. 작은 컴포넌트는 시간이 필요 없다
토글, 모달, 폼 로컬 상태는 `useState`나 시간 없는 상태 머신으로 충분하다. 그걸 앱 전체 데이터 모델로 확장하려는 게 문제다. 범위를 의식하자.
- 5. 협업·오프라인 요구가 생기면 Redux를 늘리지 말고 바꿔라
실시간 협업이나 오프라인 지원이 요구사항에 등장하면, 그건 전파 시스템에 기능을 덧붙일 신호가 아니라 **Y.js / Zero / Fluid 같은 관리 시스템으로 데이터 모델을 옮길 신호**다. 두 요구는 같은 시스템에서 공짜로 따라온다.
- 6. 용어에 속지 말기
"서버 사이드 렌더링", "순수 함수", "동시성", "상태 관리". 리액트 생태계가 느슨하게 재정의한 단어들이다. 원래 의미를 알고 쓰자.

> **📌 결론**
> ▎ 리액트와 그 위의 "상태 관리" 라이브러리들은 상태를 전파할 뿐, 관리하지 않는다.
> ▎ 관리의 조건은 시간·순서 메타데이터와 충돌 해결. 벡터 클록, CRDT, OT가 그 도구다.
> ▎ 작은 UI 상태엔 전파로 충분하다. 앱 전체 데이터 일관성에 전파를 쓰면 무너진다.
> ▎ 진짜 관리 시스템을 쓰면 오프라인 우선과 실시간 협업이 별도 기능이 아니라 부산물이 된다.
> ▎ ⭐️ 실무: 스토어 전체를 JSON으로 영속화하는 코드가 있다면 그게 첫 번째 경고등이다.
> ▎ ⭐️ 실무: "협업 기능 추가" 티켓이 오면 Redux 미들웨어가 아니라 Y.js/Zero부터 검토한다.
