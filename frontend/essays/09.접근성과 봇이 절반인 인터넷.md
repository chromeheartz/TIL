# 접근성과 봇이 절반인 인터넷

> **원문**: [Accessibility and the new model of the internet](https://cassidoo.co/post/accessibility-and-the-internet) (Cassidy Williams)  
> **번역 출처**: [(번역) 접근성과 인터넷의 새로운 모델](https://handhand.tistory.com/entry/accessibility-and-the-internet) (HandHand)

요즘 에이전트 붙일 일이 많아서 그런지 제목에 끌려서 읽었다. 접근성 글인 줄 알았는데 읽고 나면 인터넷 돈벌이 얘기까지 가 있다. 짧은 글인데 뒷맛이 꽤 남는다.

### 접근성은 늘 뒷순위였다

글쓴이는 GitHub에서 일하는데, 회사가 접근성을 진지하게 다뤄줘서 고맙다는 말로 시작한다. 뒤집어 말하면 업계 전체는 그렇지 않았다는 얘기다. "내가 신경 쓰는 만큼 상사도 접근성에 신경 쓰게 하려면 어떡해요?"라는 질문을 수도 없이 들었다고 한다.

솔직히 이 질문은 나도 낯설지 않다. 접근성은 다들 중요하다고 말하면서 일정 잡을 때 제일 먼저 빠지는 항목이니까. 글쓴이는 접근성이 왜 필요한지는 굳이 논증하지 않겠다고 선을 긋는다. 당연한 걸 또 설득하지 않겠다는 태도가 좋았다.

### 그런데 요즘은 대접이 달라졌다

접근성이 일급 시민처럼 느껴진다는 게 글의 출발점이고, 이유는 두 가지다.

#### 1. 구현이 쉬워졌다

에이전트한테 WCAG 지키라고 시키면 (팀에서 쓰는 다른 기준이어도) 예전보다 훨씬 빠르게 맞춰준다. 귀찮아서 미뤘던 일의 비용이 내려간 셈이다.

#### 2. 에이전트도 접근성이 필요하다

여기가 재밌다. 사람이 탐색 못 하는 사이트는 에이전트도 탐색을 못 할 수 있다. 그래서 에이전트가 잘 쓰라고 접근성을 챙기는 팀이 늘었다는 것이다.

결과만 보면 사람에게도 에이전트에게도 좋은 일이다. 다만 글쓴이는 여기서 살짝 씁쓸해한다. "다른 사람한테 더 좋으니까"로는 안 움직이던 업계가 봇 때문에 움직였다는 거다. 글쓴이 표현으로는 돌아서 온 길(the scenic route). 하하, 맞는 말이라 더 씁쓸하다.

### 인터넷의 사업 모델이 흔들린다

구독료를 안 내면 인터넷은 공짜고, 대신 우리는 주의력으로 값을 치른다. 광고 산업이 커진 것도, 낚시 제목이 표준이 된 것도, 기술 크리에이터들이 분노 유발 콘텐츠에 빠진 것도 전부 여기서 나왔다는 진단이다. 리소토 재료 하나 보려고 레시피에 얽힌 인생사를 끝까지 스크롤해야 하는 것도 마찬가지고.

문제는 이 모델이 방문자가 사람일 때만 돌아간다는 점이다. 글에 따르면 [`Cloudflare의 Bot vs. Human 지표`][cloudflare]에서 인터넷 트래픽의 절반 이상이 자동화된 봇으로 나왔다. 봇은 광고를 안 누르고, 뭘 사겠다고 결정하는 일도 드물고, 필요 이상으로 머물지도 않는다.

사람을 위해 만든 인터넷이 점점 봇 위주로 돌아가면 뭐가 될까? 글쓴이는 이 질문을 던져놓는다.

### 그래도 낙관한다

글쓴이의 답은 낙관 쪽이다. 봇이 많아져서 앱이 간결해지고, 열린 표준이 나아지고, 접근성이 기본값이 된다면 사람은 주의를 뺏는 경험 대신 질 좋은 경험을 얻는다. 봇은 그 아래에서 조용히 돌아다니고, 사람은 뭘 계속 팔려고 들지 않는 플랫폼을 쓰는 그림이다.

마지막 문장은 "아니면 다 같이 나가서 풀이나 만지거나". 이렇게 끝나는 것도 좋았다.

### 📌 정리
`접근성은 이제 사람과 에이전트가 같이 쓰는 인터페이스다`

#### 핵심
> 접근성의 대접이 나아진 이유는 AI로 구현 비용이 내려갔고, 에이전트도 접근성 있는 화면이 있어야 일을 하기 때문이다.  
> 그 방향으로 가면 주의력을 파는 광고 모델은 흔들린다. 봇은 광고를 보지 않는다.

#### ⭐️ 앞으로 기억할 것
1. 사람 눈에만 버튼이면 버튼이 아니다
보조 기술이든 에이전트든 화면을 픽셀이 아니라 역할과 이름으로 읽는 경우가 많다. `div`에 `onClick`만 달면 그쪽에서는 그냥 글자 없는 상자다.
```tsx
// ❌ 눈에는 버튼인데 역할도 이름도 키보드 포커스도 없다
<div className="btn" onClick={save}><SaveIcon /></div>

// ✅ 네이티브 요소를 쓰면 역할과 포커스가 따라오고, 아이콘 버튼은 이름만 붙여주면 된다
<button type="button" aria-label="저장" onClick={save}><SaveIcon /></button>
```
2. 테스트 셀렉터를 접근성 점검으로 겸한다
`getByRole`로 안 잡히는 요소는 접근성 트리에서도 뭔가 빠져 있다는 신호다. 테스트 짜면서 공짜로 점검이 된다.
```ts
// ❌ 클래스가 바뀌면 깨지고, 접근성에 대해 알려주는 것도 없다
await page.locator('.btn-primary').click()

// ✅ 사람이 인식하는 역할과 이름으로 찾는다
await page.getByRole('button', { name: '저장' }).click()
```
3. "에이전트한테 WCAG 지키라고 했음"으로 끝내지 않는다
구현이 쉬워진 건 맞는데 맞게 됐는지는 별개다. 자동 검사가 못 잡는 영역이 있으니 탭 키로 한 바퀴 돌아보고 스크린 리더로 주요 흐름은 직접 들어본다.
4. 동기가 뭐든 결국 사람을 위한 일이라는 걸 잊지 않는다
에이전트 때문에 시작해도 된다. 다만 에이전트가 읽기 좋게 만드는 것과 사람이 쓰기 좋게 만드는 건 완전히 같지 않다. 글쓴이가 씁쓸해한 지점도 사실 이거다.

> 📌 결론  
> ▎ 접근성이 대접받기 시작한 이유는 구현 비용 하락과 에이전트의 필요다.  
> ▎ 사람이 못 쓰는 화면은 에이전트도 못 쓸 수 있다.  
> ▎ 트래픽의 절반 이상이 봇이면 주의력을 파는 광고 모델은 전제부터 흔들린다.  
> ▎ 봇 덕분에 접근성이 나아지는 건 좋은 일이지만, 돌아서 왔다는 건 기억해둘 만하다.  
> ▎ ⭐️ 실무: 시맨틱 태그와 `getByRole`을 기본값으로 두면 접근성과 에이전트 대응을 한 번에 챙긴다.  
> ▎ ⭐️ 실무: AI가 짠 접근성 코드는 키보드와 스크린 리더로 직접 확인한다.
