# AEO — AI 에이전트를 위한 문서 최적화 (Agentic Engine Optimization)

> 원문: [Agentic Engine Optimization (AEO)](https://addyosmani.com/blog/agentic-engine-optimization/) — Addy Osmani

SEO를 사람·검색 크롤러 기준으로 해왔는데, 이제 **문서를 읽는 주체가 점점 AI 코딩 에이전트(Claude Code, Gemini CLI, Cursor, Copilot)** 로 바뀌고 있다는 게 이 글의 출발점이다. Addy Osmani(Google Cloud AI 디렉터)가 "에이전트는 사람과 완전히 다르게 문서를 소비하는데, 아직도 사람만 위해 최적화하면 점점 늘어나는 audience가 네 분석 도구엔 안 보이게 된다"고 짚는다. 우리가 하는 SEO의 다음 버전 같은 얘기라 흥미로웠다.

> ⚠️ 저자 디스클로저: Addy는 Google Cloud AI 소속이고, **Google Search는 `llms.txt`를 공식 표준으로 권장하지 않는다.** 이 글은 "개발자 대상 문서"라는 특정 렌즈로 봐야 하는, 한 실무자의 관점이지 구글 전사 권장이 아니다.

### 문제 제기: 에이전트는 거기 있었지만 분석엔 안 잡힌다

엔지니어가 Claude Code에 스펙 구현을 시키고 엔터. 에이전트가 네 문서를 fetch → HTML 벗기고 → raw text 파싱 → 토큰 세고 → 컨텍스트에 쓰거나, 토큰 초과면 **조용히 버린다.**

이때 네 analytics엔 **아무 유용한 것도 안 남는다.** scroll depth 0, time-on-page 400ms, 링크 클릭·튜토리얼 완료·UI 인터랙션 전부 없음. 수년간 최적화한 퍼널이 텅 비어 보인다. **근데 에이전트는 분명히 거기 있었고 문서를 읽었다.** 문서 구조에 따라 작업을 성공하거나, 토큰이 너무 무겁고·구조가 나쁘고·`robots.txt`가 막아서 **할루시네이션**을 했거나.

### AEO란?

**Agentic Engine Optimization = AI 코딩 에이전트가 실제로 사용할 수 있게 기술 콘텐츠를 구조화·포맷·서빙하는 실천.** SEO와 같은 아이디어, 소비자만 다름(검색 크롤러+사람 → 자율적으로 fetch·파싱·추론하는 AI 에이전트). 중요한 건 꽤 구체적이다:

- **Discoverability** — JS 렌더 없이 문서를 찾을 수 있나?
- **Parsability** — 시각 레이아웃 해석 없이 기계가 읽을 수 있나?
- **Token efficiency** — 잘림 없이 에이전트 컨텍스트 윈도우에 들어가나?
- **Capability signaling** — API를 *어떻게 호출*하는지 말고 *무엇을 하는지* 알려주나?
- **Access control** — `robots.txt`가 AI 트래픽을 실제로 통과시키나?

하나라도 실패하면 에이전트는 콘텐츠를 통째로 스킵하거나 미묘하게 틀린 출력을 낸다. **무서운 건 너는 그걸 영영 모른다 — analytics 이벤트가 안 뜨니까.**

### 사람 vs 에이전트, 읽는 패턴이 다르다

- **사람:** 홈 → 섹션 이동 → 헤딩 훑기 → 문단 읽기 → 콘솔에서 코드 실행 → 내부 링크 2~3개 → 4~8분 세션. analytics가 다 잡음.
- **에이전트:** [연구](https://arxiv.org/html/2604.02544v1)(9개 주요 코딩 에이전트의 HTTP 트래픽 분석)에 따르면 **여러 페이지 내비게이션을 1~2개 HTTP 요청으로 압축.** 사람이 몇 분 클릭할 걸 단일 `GET`으로 전체 페이지 받고 끝. **"user journey" 개념 자체가 단일 서버사이드 이벤트로 붕괴.** → scroll·time·click 등 모든 클라이언트 사이드 이벤트가 안 보이게 됨.

#### AI 트래픽의 지문(fingerprint)
서버 로그에서 에이전트를 식별할 수 있는 시그니처:

| Agent | HTTP 런타임 | 시그니처 |
|---|---|---|
| Aider | Headless Chromium (Playwright) | Full Mozilla/Safari UA |
| Claude Code | Node.js / Axios | `axios/1.8.4` |
| Cline | curl (+OpenAPI/Swagger sweep) | `curl/8.4.0` |
| Cursor | Node.js / got (HEAD → GET) | got (sindresorhus/got) |
| Junie | curl (순차 멀티페이지 GET) | `curl/8.4.0` |
| OpenCode | Headless Chromium | Full Mozilla/Safari UA |
| VS Code | Electron / Chromium | Electron 마커 |
| Windsurf | Go / Colly | `colly` |

+ ChatGPT·Claude·Gemini·Perplexity 같은 AI 어시스턴트도 유저가 URL 공유하면 자체 서버사이드 fetch를 트리거.

### 토큰 문제 — 네 문서가 에이전트에 안 보일 수도

가장 과소평가된 부분 = **토큰 이코노미.** 에이전트는 무한 컨텍스트가 없다(대개 100K~200K 토큰). 논문 예시: Cisco Secure Firewall API Quick Start Guide가 **193,217 토큰(약 71.8만 자)** — 단일 문서가 대부분 에이전트의 가용 컨텍스트를 통째로 먹거나 초과한다.

문서가 너무 길면 — 전부 안 좋다:
- 조용히 truncate(중요 정보 잘림)
- 더 짧은 걸 찾아 통째로 스킵
- chunking 시도(지연·에러 표면↑)
- parametric knowledge로 폴백 = **지어냄**

→ **토큰 수는 이제 일급(first-class) 문서 메트릭이다.** 페이지별 토큰을 안 추적하면, 에이전트가 "읽기를 시도할지 말지" 결정에 쓰는 신호를 놓치는 것.

**토큰 가이드:** quick start < 15K / 개별 API 레퍼런스 < 25K / 전체 API 레퍼런스는 제품이 아니라 리소스·엔드포인트별로 chunk / 개념 가이드 < 20K(세부는 embed 말고 link).

## AEO 스택 — 실제로 뭘 만드나 (6 레이어)

#### Layer 1: 접근 제어 `robots.txt`
에이전트의 첫 정거장. 잘못 설정해 AI 크롤러를 막으면 **조용히** 문서 접근 전체가 차단됨(트래픽·에러·신호 없음). → AI UA에 대한 의도치 않은 차단 감사, 알려진 AI 패턴(Anthropic/OpenAI/Google/Perplexity) 명시 허용 고려, 세밀한 제어는 `agent-permissions.json`(허용 인터랙션·rate limit·선호 엔드포인트 선언).

#### Layer 2: 발견 `llms.txt`
**AI 에이전트용 sitemap.** `yourdomain.com/llms.txt`에 두는 플랫한 Markdown 파일로, 설명까지 붙은 문서 디렉터리를 제공해 에이전트가 전체 크롤 없이 관련 콘텐츠를 찾게 함.
```markdown
# YourProduct Documentation

## Getting Started
- [Quick Start Guide](/docs/quickstart): Install and make your first API call in 5 minutes
- [Authentication](/docs/auth): OAuth 2.0 and API key authentication patterns

## API Reference
- [Users API](/docs/api/users): CRUD operations for user management (12K tokens)
- [Events API](/docs/api/events): Event streaming and webhook configuration (8K tokens)
```
좋은 `llms.txt`: **페이지 이름이 아니라 "뭘 찾게 될지" 설명**, 페이지별 토큰 수, **제품 위계가 아니라 task 기준 구성**, 자기 자신은 5K 토큰 이하 유지(인덱스가 예산을 잡아먹으면 안 됨).

#### Layer 3: 능력 신호 `skill.md`
`llms.txt`가 "어디 있나"라면 `skill.md`는 **"네 제품이 뭘 할 수 있나"**. 에이전트가 산문에서 능력을 추론하게 하지 말고 선언적으로 노출 — intent를 엔드포인트·리소스에 매핑.
```markdown
---
name: auth-service
description: Handles user authentication, OAuth 2.0 flows, and session management
---
## What I can accomplish
- Authenticate users via OAuth 2.0 (authorization code, client credentials, PKCE)
- Issue and validate JWT tokens
## Required inputs
- Client ID and Client Secret, Redirect URI (pre-registered), scopes
## Constraints
- Rate limit: 1000 token requests per minute per application
- Token expiry: access 1hr, refresh 30 days
## Key documentation
- [OAuth 2.0 Guide](/docs/oauth), [Token Reference](/docs/tokens)
```
→ 에이전트가 전체 문서를 읽는 데 컨텍스트를 쓰기 **전에**, "이 API가 유저 의도를 충족할 수 있나"를 판단하게 해줌.

#### Layer 4: 에이전트 파싱용 콘텐츠 포맷
- **HTML 말고 Markdown 서빙.** URL에 `.md` 붙이면 raw Markdown 주는 식. HTML보다 토큰 오버헤드가 극적으로 낮음(태그·네비·푸터 노이즈 없음).
- **읽기가 아니라 스캔용으로 구조화.** 일관된 헤딩 위계(H1→H2→H3 건너뛰기 금지), 섹션을 배경 아닌 **결과(outcome)로 시작**, 코드 예시는 주장 바로 뒤에, 파라미터는 산문 말고 **테이블**(압축 잘 됨).
- **네비 노이즈 제거.** 사이드바·브레드크럼·푸터는 Markdown/텍스트에선 그냥 노이즈. 파싱 경로에서 빼라.
- **유용한 걸 앞에(front-load).** 페이지 첫 500토큰이 "이게 뭐고, 뭘 할 수 있고, 시작하려면 뭐가 필요한가"에 답해야. 에이전트는 서론에 인내심 없음.

#### Layer 5: 토큰 노출(surfacing)
문서 페이지에 **토큰 수를 노출** — `llms.txt` 인덱스에도, 페이지 자체(메타/헤더)에도. 그러면 에이전트가 똑똑하게 결정: "8K → 전체 포함 가능 / 150K → 관련 섹션만 / 윈도우 초과 → llms.txt 요약으로 대체." 구현은 단순: 서버사이드 글자 수 ÷ ~4로 토큰 추정 → meta 태그/HTTP 헤더로 노출.

#### Layer 6: "Copy for AI" 버튼
인프라보단 UX 브릿지. 개발자가 IDE의 AI에 문서를 컨텍스트로 넣을 때 현재는 렌더된 HTML(네비·푸터 노이즈 포함)을 복붙. **깨끗한 Markdown을 클립보드에 복사하는 버튼**은 작지만 에이전트가 받는 컨텍스트 품질을 의미 있게 개선. Anthropic·Cloudflare 등 이미 출시. 저비용 고신호.

### AGENTS.md — 떠오르는 기본값
`README.md`가 사람용 진입점이듯, **`AGENTS.md`는 AI 에이전트의 진입점.** 코딩 에이전트가 프로젝트를 열면 루트의 `AGENTS.md`를 찾아 이후 모든 작업에 instruction으로 끌어옴. 좋은 `AGENTS.md`: 프로젝트 구조·핵심 파일 위치, 관련 API/서비스 문서 직링크, 사용 가능한 dev 샌드박스·테스트 환경, rate limit·제약, 코드베이스 선호 패턴·컨벤션, MCP 서버 링크. (Cisco DevNet은 오픈소스 GitHub 템플릿 기본 파일로 이미 채택.)

### AI 리퍼럴 트래픽 모니터링 (지금 당장 가능)
주시할 리퍼럴 소스: `claude.ai/referral`, `chatgpt.com/organic`, `platform.openai.com/referral`, `gemini.google.com/referral`, `copilot.microsoft.com/referral`, `labs.perplexity.ai/referral` 등. + 리퍼러 없이 오는 직접 에이전트 트래픽은 앞의 HTTP 지문(`axios/1.8.4`, `curl/8.4.0`, `got`, `colly`)으로 포착. → AI 트래픽 세그먼트를 만들면 이 작업이 효과 있는지 선행 지표가 생김.

### 더 큰 함의 — DX의 전제가 깨진다
웹 역사 내내 개발자 포털은 **사람 인지 패턴**(점진적 공개, 시각 위계, 인터랙티브 예제, 가이드 튜토리얼)으로 설계됐다. 에이전트 중심 세계에선:
- **시각 위계 무의미** — 에이전트는 레이아웃 아닌 텍스트를 읽음
- **점진적 공개가 장애물** — 에이전트는 한 번에 전부 원함
- **인터랙티브 예제 가치↓** — static/API 등가물이 없으면
- **user journey 붕괴** — 멀티 챕터 튜토리얼이 단일 컨텍스트 로드로

사람 중심 설계가 안 중요해지는 게 아니라, 사람도 점점 **AI 어시스턴트의 컨텍스트 안에서** 문서를 읽는다 → 에이전트가 직접 소비자, 사람은 최종 수혜자. **앞으로 최고의 문서는 둘 다 동시에** — 사람에겐 스캔 가능·잘 구조화, 에이전트에겐 기계 가독·토큰 효율.

### 📌 정리
`SEO의 다음 챕터 = AI 에이전트가 실제로 쓸 수 있게 문서를 구조화·서빙하기`

#### 핵심
> AI 코딩 에이전트(Claude Code/Cursor/Copilot…)는 사람과 완전히 다르게 문서를 소비한다 — 멀티페이지를 단일 GET으로 압축하고, 토큰 예산 안에서 파싱하고, 안 맞으면 조용히 버리거나 할루시네이션한다(analytics엔 안 잡힘). **AEO**는 이를 위해 ① `robots.txt`로 접근 허용 ② `llms.txt`로 발견성 ③ `skill.md`로 능력 신호 ④ Markdown·스캔용 구조로 파싱성 ⑤ 토큰 수 노출 ⑥ "Copy for AI" — 6레이어 스택을 갖추는 실천. 코드 리포엔 `AGENTS.md`. 토큰 수가 일급 문서 메트릭이 됐다는 게 핵심 전환.

#### ⭐️ 앞으로 기억할 것
- 1. **토큰 수 = 일급 문서 메트릭**
  100K~200K 윈도우. 너무 길면 truncate/skip/할루시네이션. 목표: quick start <15K, API 레퍼런스 <25K, 개념 가이드 <20K. 페이지에 토큰 수 노출(글자수÷4).
- 2. **`llms.txt` = AI용 sitemap (가장 먼저 추가할 것)**
  task 기준 구성 + "뭘 찾게 될지" 설명 + 페이지별 토큰. 자기 자신 5K 이하.
- 3. **`skill.md` = "어떻게"가 아니라 "무엇을 하는가"**
  capabilities / required inputs / constraints / key docs. 에이전트가 full read 전에 적합성 판단.
- 4. **HTML 말고 Markdown을 서빙 (`.md` URL 컨벤션)**
  태그·네비·푸터 노이즈 제거 → 토큰 급감. 첫 500토큰에 "뭐고/뭘 하고/뭐 필요한가" front-load.
- 5. **`robots.txt`가 AI를 조용히 막고 있을 수 있다**
  10분 감사로 silent lockout 방지. 세밀 제어는 `agent-permissions.json`.
- 6. **`AGENTS.md` = 에이전트의 README**
  리포 루트에 두면 코딩 에이전트가 모든 작업에 끌어씀(구조·문서 링크·샌드박스·제약·컨벤션).
- 7. **AI 트래픽은 지문으로 식별**
  `axios/1.8.4`(Claude Code), `curl/8.4.0`(Cline/Junie), `got`(Cursor), `colly`(Windsurf) + 리퍼럴 소스. 세그먼트 만들어 효과 측정.

📌 결론
▎ 에이전트는 이미 문서 트래픽의 크고 빠르게 느는 비중인데, 대부분 포털은 아직 사람만 위해 설계됨.
▎ 일찍 움직이는 팀이 유리 — 에이전트가 추천·통합·재방문하는 API가 됨. 안 하면 "문서 품질 ↔ 에이전트 작업 성공률" 격차가 벌어지는 silent failure.
▎ 좋은 소식: 에이전트용으로 잘 만들면 사람에게도 더 나은 문서가 된다(두 분야는 발산보다 수렴).
▎ ⭐️ 실무 적용 순서 (주말이면 됨)
▎ 1) robots.txt 감사(10분) → 2) llms.txt 추가(몇 시간) → 3) 토큰 수 측정·노출(주말) → 4) 상위 3개 API에 skill.md → 5) "Copy for AI" 버튼 → 6) AI 트래픽 모니터링.
