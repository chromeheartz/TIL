# 페이지는 사라지고 컴포넌트가 남는다

> **원문**: [Components Will Kill Pages](https://bitsandbytes.dev/posts/components-will-kill-pages) — bitsandbytes.dev (2026.02.11)
> **번역 출처**: [(번역) 페이지는 사라지고, 컴포넌트가 살아남을 것입니다](https://handhand.tistory.com/entry/components-will-kill-pages) — handhand.log

요즘 뭘 찾을 때 검색창보다 ChatGPT를 먼저 여는 내 모습을 보다가, 이 제목을 보고 바로 읽어봤다. 짧은 칼럼인데 FE 입장에서 꽤 찔리는 질문을 던진다. **사용자가 더 이상 우리 페이지를 안 돌아다니면, 우리는 뭘 만들어야 하나?**

### 웹 탐색 방식이 바뀌고 있다

지난 20년 동안 웹은 "사이트 → 페이지 → 다음 페이지"로 돌아다니는 구조였다. 그런데 채팅형 AI가 들어오면서 흐름이 바뀌었다.

- 입력창에 질문하면 **나한테 맞춘 답**이 바로 나온다
- 숏폼에 익숙해진 사용자는 **즉각적인 결과**를 원하고, AI가 딱 그걸 준다
- 그러니 웹사이트를 직접 방문할 이유가 줄어든다

봇은 여전히 페이지를 크롤링하겠지만, 사람은 점점 안 들어온다는 얘기.

#### FE가 고민하던 문제가 흔들린다

FE는 지금까지 **사용자 여정** 단위로 문제를 풀어왔다. 페이지와 기능 사이를 어떻게 옮겨 다니게 할지 최적화하는 일.

- 가입 퍼널에 어떤 단계를 넣을까?
- 사용자를 핵심 가치까지 얼마나 빨리 데려갈까?

그런데 가입을 사람이 아니라 AI가 대신 해준다면? 솔직히 이 질문들 중 상당수가 의미를 잃을 수도 있다.

### AI 앱은 링크를 내보내고 싶지 않다

여기서 글쓴이가 짚는 포인트가 재밌다. AI 채팅 앱 입장에서는 사용자를 **외부 사이트로 내보내는 게 손해**다.

- X(트위터)가 링크 달린 게시글 노출을 줄이는 것
- 모바일 앱이 앱 밖으로 링크를 거의 안 거는 것

다 같은 이유다. 사용자를 자기 앱 안에 붙잡아 두고 싶은 것. 그렇다면 남는 질문은 이거다. **채팅 안에서 브랜드의 UI를 직접 보여줄 수 있다면?**

### 예시: Cloudflare Workflow 시각화

글에서 드는 예시. Cloudflare에 배포한 Workflow들이 어떻게 돌아가는지 AI한테 보여달라고 하면, 단계·재시도·try/catch까지 얽혀서 텍스트로 설명하기엔 꽤 복잡하다.

만약 채팅 앱이 Cloudflare가 제공하는 컴포넌트를 이해하고 **응답 안에서 바로 렌더링**할 수 있다면?

| 관점 | 얻는 것 |
|------|---------|
| 사용자 | 앱 밖으로 안 나가도 제대로 된 UI를 본다 |
| AI 채팅 앱 | 사용자를 붙잡아 둔다 |
| 브랜드 | 자기 제품을 **어떻게 보여줄지** 주도권을 지킨다 |

셋 다 이득인 구조다.

### UI를 JSON으로 표현하기

이걸 가능하게 하는 도구로 두 가지를 소개한다.

- [`json-render`][json-render] — UI 컴포넌트를 JSON으로 표현. AI가 어떤 컴포넌트가 자식을 받는지, 어떤 props가 있는지, 어떻게 조합하는지 이해할 수 있게 해준다
- [`Kumo`][kumo] — Cloudflare의 컴포넌트 라이브러리. 앱이 쓸 수 있는 컴포넌트 목록을 제공한다

흐름은 대략 이렇다.

```text
사용자: "내 Workflow 시각화해줘"
  ↓
AI: Kumo 컴포넌트 목록 확인 → FlowDiagram 있음
  ↓
AI: json-render 스펙에 맞춰 props/children 조합한 JSON 생성
  ↓
채팅 앱: JSON을 렌더링 → Cloudflare 브랜딩된 인터랙티브 Workflow 뷰어
```

AI가 만드는 건 HTML이 아니라 **"어떤 컴포넌트를 어떤 props로 쓸지"에 대한 설명**이다. 이게 생성형 UI(generative UI)의 핵심인 듯.

### 5년 뒤의 사용자

글쓴이의 질문. 5년 뒤 사용자가 페이지 다섯 단계를 들어가서 필터 걸고 정렬해서 직접 답을 찾을까? 아마 아닐 거다.

- 몇 마디 말로 **액션을 트리거**하고
- 몇 초 만에 **결과**를 받는다

그래서 글쓴이는 질문하면 답이 나오는 **퍼스트파티 경험**을 직접 만들라고 한다. AI는 인터넷의 새 운전대가 되고, 페이지를 돌아다니는 방식은 아닐 거라는 것.

결론은 단순하다. **지금이 고품질 컴포넌트에 투자할 때.** AI 우선 컴포넌트 라이브러리를 안 쓰고 있거나, AI가 내 브랜딩으로 UI를 어떻게 만들지 고민 안 하고 있다면 지금 시작하라고. 아직 늦지는 않았지만, 매달 바뀌는 시기라 앞서가는 게 최선이라고.

### 📌 정리

`페이지 설계에서 컴포넌트 계약 설계로`

#### 핵심

> 사용자는 페이지를 돌아다니는 대신 AI한테 묻고, AI 앱은 사용자를 밖으로 내보내고 싶어 하지 않는다.
> 그래서 브랜드 UI가 **채팅 안에서 렌더링되는 컴포넌트**로 살아남을 가능성이 크다.
> `json-render`, `Kumo`처럼 UI를 JSON으로 기술해 AI가 조합할 수 있게 만드는 쪽에 투자할 때다.

#### ⭐️ 앞으로 기억할 것

- 1. 이건 칼럼이다
"페이지가 죽는다"는 예측이지 사실이 아니다. 검색·SEO·직접 방문은 아직 크다. 흐름은 체크하되 당장 페이지를 버릴 이유는 없다.

- 2. 컴포넌트 API가 곧 계약이다
AI가 조합하려면 props가 명확하고 설명 가능해야 한다. 지금 하는 "props 타입 제대로 잡기"가 그대로 투자가 된다.
```ts
// ❌ AI도 사람도 뭘 넣을지 모름
interface ChartProps {
  data: any;
  options?: Record<string, unknown>;
}

// ✅ 스키마로 설명 가능한 props
interface ChartProps {
  /** x축 라벨과 값 */
  data: { label: string; value: number }[];
  variant: 'bar' | 'line';
}
```

- 3. 스키마는 Zod로 한 곳에
TS 타입만 있으면 런타임에 AI가 준 JSON을 검증할 수 없다. 스키마 하나로 타입 추론 + 검증 + (필요하면) JSON Schema 변환까지.
```ts
import { z } from 'zod';

const chartPropsSchema = z.object({
  data: z.array(z.object({ label: z.string(), value: z.number() })),
  variant: z.enum(['bar', 'line']),
});

type ChartProps = z.infer<typeof chartPropsSchema>;

// AI가 만든 JSON은 신뢰하지 말고 검증 후 렌더링
const props = chartPropsSchema.parse(aiOutput);
```

- 4. 디자인 시스템이 브랜드를 지킨다
채팅 안에서 렌더링돼도 "우리 제품처럼" 보이려면 토큰·컴포넌트가 정리돼 있어야 한다. 페이지 단위로 CSS 땜빵해온 프로젝트는 여기서 막힌다.

- 5. 퍼널 지표가 바뀔 수 있다
"몇 페이지 만에 가입했나"보다 "질문 한 번에 원하는 결과를 받았나"가 중요한 지표가 될 수 있다.

> **📌 결론**
> ▎ 사용자는 페이지 대신 AI한테 묻기 시작했다
> ▎ AI 앱은 사용자를 밖으로 내보내지 않으려 한다
> ▎ 브랜드 UI는 채팅 안의 컴포넌트로 들어갈 가능성이 크다
> ▎ UI를 JSON으로 기술하는 `json-render`, `Kumo` 같은 흐름이 그 길이다
> ▎ ⭐️ 실무 적용 포인트: 컴포넌트 props를 명확한 타입/스키마로 정리하고 디자인 시스템을 다듬는 것부터. 이건 AI가 아니어도 손해 볼 일이 없다
