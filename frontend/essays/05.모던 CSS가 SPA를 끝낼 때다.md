# 모던 CSS가 SPA를 끝낼 때다

> **원문**: [It's time for modern CSS to kill the SPA](https://www.jonoalderson.com/conjecture/its-time-for-modern-css-to-kill-the-spa/) — Jono Alderson
> **번역 출처**: [[번역] 이제 모던 CSS가 SPA를 끝낼 때입니다](https://devowen.com/524) — 오웬의 개발 이야기

"앱처럼 느껴지게 해주세요" 한마디로 SPA가 결정되는 장면을 나도 여러 번 봤다. 그런데 이 글의 주장은 그 근거가 이미 무너졌다는 것이다. 네이티브 CSS 트랜지션이 클라이언트 사이드 라우팅의 가장 강력한 이유를 조용히 없애버렸는데, 사람들은 여전히 성능 좋은 사이트 대신 무거운 앱을 만들고 있다는 얘기. 도발적인 제목이지만 기술적 근거가 구체적이라 정리해둔다.

### 앱처럼 보여야 한다는 착각

기획 단계 어딘가에서 CMO든 브랜드 매니저든 누군가 "앱처럼"을 꺼내고, 그 한마디로 아키텍처가 정해진다. SPA, 아마 리액트, Vercel 배포, 헤드리스 CMS, GraphQL까지 세트로.

그런데 이 결정은 사실 아키텍처나 성능이나 확장성에 관한 게 아니었다. 그냥 **인터랙션**, 클릭할 때 어떤 느낌인지에 관한 것이었다. 가정은 단순하다. 매끄러운 내비게이션 = 앱을 만들어야 한다. 이 가정이 이제 낡았다는 게 글의 출발점이다.

### SPA의 거짓 약속

SPA가 기본 선택지가 된 건 더 뛰어나서가 아니다. 한동안 페이지 사이에 하얗게 번쩍이는 화면 없이 부드러운 느낌을 줄 수 있는 **유일한** 방법이었기 때문이다.

그런데 실제 대부분의 SPA가 주는 건 이렇다.

- 매끄러워 보이지만 사실 로딩 상태 두 개 사이를 페이드하는 것뿐인 전환
- 깨진 스크롤 복원
- 일관성 없는 포커스 동작
- 리하이드레이션 동안 지연되는 내비게이션
- 레이아웃 시프트, 뜬금없이 나타나는 콘텐츠, 전체 페이지 스켈레톤
- 효과 대비 터무니없는 성능 저하

Next.js, Gatsby, Nuxt로 만든 사이트 대부분이 네이티브 내비게이션을 흉내 내려고 킬로바이트, 종종 메가바이트 단위 JS를 보낸다. 라우팅 로직, 하이드레이션, 스피너. 전부 브라우저가 이미 할 줄 알던 걸 다시 짜깁기하는 것이다.

매끄러움 대신 **시뮬레이션**을 얻는다. "빠르게 느껴지게" 하려고 JS를 쌓다가 모든 걸 더 느리게 만들었다.

### 웹은 그 사이에 성장했다

우리가 JS로 내비게이션을 재발명하는 동안 플랫폼이 조용히 문제를 풀어버렸다. 크로미움 기반 브라우저는 이제 **네이티브 선언적 페이지 트랜지션**을 지원한다. View Transitions API로 JS 한 줄 없이 두 문서 사이, 즉 전체 페이지 내비게이션까지 애니메이션할 수 있다.

여기서 "모던 CSS"는 View Transitions, Speculation Rules, 그리고 내비게이션·인터랙션·레이아웃을 처음부터 처리하도록 설계된 네이티브 기능으로 돌아가는 것을 통칭한다.

이제 가능한 것들.

- 페이지 간 페이드 전환
- 공유 요소 애니메이션 (섬네일 → 상품 상세)
- 헤더나 내비게이션 바 같은 지속 요소 유지
- 실제 URL, 실제 페이지 로드, JS 라우팅 꼼수 없이

#### 🔄 기본 크로스 페이지 페이드

현재 페이지와 도착 페이지 **양쪽**에 이걸 넣으면 끝이다.

```css
/* 문서 간 내비게이션에 뷰 트랜지션 활성화 */
@view-transition {
  navigation: auto;
}

/* 나가는 페이지와 들어오는 페이지 스냅샷에 애니메이션 */
::view-transition-old(root),
::view-transition-new(root) {
  animation: fade 0.3s ease both;
}

@keyframes fade {
  from { opacity: 0; }
  to   { opacity: 1; }
}
```

| 조각 | 역할 |
|---|---|
| `@view-transition { navigation: auto }` | 같은 출처 문서 간 내비게이션을 뷰 트랜지션으로 처리하겠다는 선언 |
| `::view-transition-old(root)` | 떠나는 페이지의 스냅샷 |
| `::view-transition-new(root)` | 도착하는 페이지의 스냅샷 |

클라이언트 라우팅도, 하이드레이션도, 스피너도 없다.

#### 🔁 공유 요소 트랜지션

섬네일이 다음 페이지의 큰 상품 이미지로 날아가는 애니메이션. JS 없이 양쪽 요소에 같은 `view-transition-name`만 주면 된다.

```html
<!-- 목록 페이지 -->
<a href="/product/red-shoes">
  <img src="/images/red-shoes-thumb.jpg" style="view-transition-name: product-image;" />
</a>
```

```html
<!-- 상세 페이지 -->
<img src="/images/red-shoes-large.jpg" style="view-transition-name: product-image;" />
```

브라우저가 내비게이션 사이의 요소를 매칭해서 위치, 스케일, 불투명도, 레이아웃까지 애니메이션한다.

#### 🤖 JS로 트리거해야 한다면

페이지 안에서 수동으로 트랜지션을 시작할 수도 있다. 탭 토글이나 테마 전환에 딱이다.

```js
document.startViewTransition(() => {
  document.body.classList.toggle('dark-mode')
})
```

프레임워크도 하이드레이션 레이어도 필요 없다.

#### 🔮 Speculation Rules: JS 없는 즉각 내비게이션

View Transitions는 매끄러움을 준다. 그럼 **빠르게**는? Speculation Rules다. 링크에 호버하거나 터치하는 사용자 행동을 기반으로, 클릭 전에 브라우저가 전체 페이지를 프리로드하거나 프리렌더한다.

```html
<script type="speculationrules">
{
  "prerender": [
    {
      "where": {
        "selector_matches": "a"
      }
    }
  ]
}
</script>
```

결과는 즉각적인 내비게이션. 대기도 로딩도 스피너도 없다.

#### ⚠️ 주의

Speculation Rules는 **성능 배율기**다. 가벼운 사이트에서는 모든 게 즉각적으로 느껴지지만, 페이지가 느리거나 JS가 무거우면 그 비용을 **앞당겨 지불**하게 만들 뿐이다. 사용자가 방문조차 안 할 페이지를 위해 CPU, 대역폭, 모바일 배터리를 태운다.

빠른 사이트에서는 마법, 느린 사이트에서는 함정.

### 브라우저는 돕고 싶어한다, 허락한다면

대표 예시가 [`bfcache`]다. 뒤로가기·앞으로가기 때 전체 페이지 스냅샷을 즉시 복원한다. 사실상 공짜 성능인데, "잘 작동하는" 페이지에서만 된다. 제멋대로인 JS 없고, 가로챈 내비게이션 없고, 생명주기 혼란이 없어야 한다.

잘 구조화된 MPA와는 자연스럽게 어울리지만 대부분의 SPA에서는 아예 못 쓴다. SPA를 정의하는 패턴들, 즉 가로챈 라우팅, 클라이언트 렌더링, 복잡한 상태 관리가 bfcache의 전제를 깨기 때문이다.

이게 더 큰 그림의 축소판이다. **브라우저는 단순함과 회복탄력성에 보상하는 방향으로 진화하고 있고, SPA는 점점 이질적인 존재가 되고 있다.**

### 📊 SPA vs MPA 성능 현실 점검

| | 평균적인 Next.js 마케팅 사이트 | 모던 MPA + View Transitions + Speculation Rules |
|---|---|---|
| JS 번들 | 1~3MB | 0KB (선택적 향상만) |
| TTI | ~3.5~5초 | ~1초 |
| 라우트 전환 | 시뮬레이션 | 실제, 네이티브 |
| SEO | 복잡하고 취약 | 간단 |
| 스크롤/포커스/히스토리 | 불안정 | 브라우저 기본값, 완벽 |

저자의 주장은 모던 CSS가 SPA의 동작을 대체하는 게 아니라 **능가**한다는 것. 수치는 저자 추정치니 참고만.

### 웹사이트를 앱처럼 만들지 마라

대부분의 웹사이트는 앱이 아니다. 공유 상태도, 클라이언트 라우팅도, 모든 화면의 인터랙티브 컴포넌트도 필요 없다. 그런데 어느 순간 이 구분을 그만뒀다. 실시간 협업 UI용으로 설계된 스택으로 이커머스, 문서 포털, 마케팅 사이트, 블로그를 만들고 있다.

콘텐츠 블록 여섯 개와 문의 폼 하나 있는 홈페이지에 하이드레이션, 서스펜스 바운더리, 렌더링 전략은 필요 없다. 빠른 마크업, 깔끔한 URL, 어쩌면 약간의 인터랙티비티면 된다.

그런데 매 프로젝트에서 이 순서가 반복된다.

1. 이해관계자: "앱처럼 느껴지게"
2. 개발팀이 Next.js나 Nuxt를 꺼낸다
3. 라우팅이 클라이언트로 넘어간다
4. 성능이 곤두박질친다
5. 엣지 함수, 스트리밍, ISR, 로딩 전략, 디버깅 계획이 필요해진다
6. 그런데도 일반 링크 클릭 + CSS 애니메이션보다 여전히 느리다

프레임워크 반대가 아니다. **의도적으로 선택하자**는 것. 리액트든 Tailwind든 Vite든 쓰고 싶으면 쓰되, 필요 없으면 브라우저에 다 보내지 말라는 얘기.

### 우리가 가진 웹을 위해 만들자

SPA는 일시적인 한계에 대한 영리한 해결책이었다. 그 한계는 이제 없다. 실제 페이지 간 네이티브 트랜지션, Speculation Rules 프리렌더링, 우아한 점진적 저하, 깔끔한 마크업과 실제 URL, 그리고 허락하면 도와주는 플랫폼.

여전히 "매끄러움"을 위해 SPA를 만들고 있다면 브라우저가 이미 푼 문제를 풀고 있는 것이고, 그 대가를 복잡성·성능·유지보수성으로 치르는 것이다. 2018년 Gatsby 데모에 갇히지 말고 2025년답게 만들자는 게 결론.

---

### 📌 정리
`"매끄러운 전환 = SPA"라는 등식은 View Transitions가 깼다`

#### 핵심
> SPA를 선택하는 진짜 이유는 대부분 "페이지 전환 느낌"인데, 그건 이제 CSS 몇 줄과 `view-transition-name` 속성으로 MPA에서도 된다. 속도는 Speculation Rules가 채운다. 그러면 남는 건 하이드레이션·클라이언트 라우팅·상태 관리라는 비용뿐이고, 그 비용은 bfcache 같은 브라우저 최적화까지 막는다. 콘텐츠 사이트라면 MPA + 네이티브 기능이 기본값이어야 한다.

#### ⭐️ 앞으로 기억할 것
- **1. 크로스 문서 View Transition은 양쪽 페이지 모두에 선언**
`@view-transition { navigation: auto }`를 출발·도착 페이지 CSS 둘 다에 넣어야 동작한다. 한쪽만 있으면 그냥 일반 내비게이션.
```css
@view-transition { navigation: auto; }
```

- **2. 공유 요소는 이름만 맞추면 된다**
양쪽 페이지에서 같은 `view-transition-name`을 가진 요소를 브라우저가 알아서 매칭한다. 한 페이지 안에서 같은 이름이 두 개면 트랜지션이 깨지니 유일해야 한다.
```html
<img style="view-transition-name: product-image;" />
```

- **3. Speculation Rules는 가벼운 사이트에서만**
프리렌더는 비용을 앞당기는 것이다. 페이지가 무거우면 방문도 안 할 페이지에 배터리를 쓰게 된다. `selector_matches: "a"` 전체 적용보다 주요 링크만 골라서 시작.
```html
<script type="speculationrules">
{ "prerender": [{ "where": { "selector_matches": ".nav a" } }] }
</script>
```

- **4. bfcache를 깨는 것들**
`unload` 이벤트, 열린 연결(WebSocket 등), `Cache-Control: no-store`. SPA의 가로챈 라우팅도 마찬가지. DevTools → Application → Back/forward cache에서 확인 가능.

- **5. "앱처럼"을 들으면 되물을 것**
그게 공유 상태가 필요하다는 뜻인지, 전환 애니메이션이 필요하다는 뜻인지. 후자면 SPA가 답이 아니다.

- **6. 브라우저 지원 확인**
크로스 문서 View Transitions와 Speculation Rules는 2025년 기준 크로미움 중심. 점진적 향상으로 접근하면 미지원 브라우저는 그냥 일반 내비게이션이 되니 손해는 없다.

> **📌 결론**
> ▎ SPA가 기본이 된 건 뛰어나서가 아니라 한때 매끄러운 전환의 유일한 방법이었기 때문이다. 그 전제는 사라졌다.
> ▎ View Transitions가 매끄러움을, Speculation Rules가 속도를, bfcache가 뒤로가기를 네이티브로 준다. 셋 다 JS 0KB.
> ▎ 브라우저는 단순하고 선언적인 구조에 보상한다. SPA 패턴은 그 보상을 스스로 차단한다.
> ▎ 프레임워크 반대가 아니라 의도적 선택. 콘텐츠 사이트에 협업 앱용 스택을 쓰지 말자.
> ▎ ⭐️ 실무 적용 포인트 — 마케팅·블로그·문서 성격의 페이지가 있다면 `@view-transition` 3줄부터 시험해볼 것. 이미 Next.js라면 라우트 전환 대신 `document.startViewTransition`으로 테마·탭 전환부터 대체하고, DevTools에서 bfcache 통과 여부를 확인하는 게 첫 단계다.
