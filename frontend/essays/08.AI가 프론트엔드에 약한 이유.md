# AI가 프론트엔드에 약한 이유

> 원문: [Why AI Sucks At Front End](https://nerdy.dev/why-ai-sucks-at-front-end) — Adam Argyle

Adam Argyle(`nerdy.dev`, 크롬/CSS 쪽에서 유명한 그분) 글이다. 백엔드 짤 때는 AI가 그렇게 잘 도와주는데 왜 프론트만 시키면 이상해질까 — 사실 나도 늘 느끼던 거라 읽게 됐다. 결론부터 말하면 "AI가 프론트에 약한 건 모델이 멍청해서가 아니라, 프론트라는 문제 자체가 LLM이 제일 못하는 종류의 문제이기 때문"이라는 얘기다.

### AI가 잘하는 영역 (The Good)

AI는 지루한 걸 사랑한다. 평범함 속에서 번성한다. 솔직히 못한다고만 하면 거짓말이고, 잘하는 데는 확실히 잘한다.

- **스캐폴딩** — 봐온 패턴을 그대로 게워내기, OK
- **토큰** — 토큰 마이그레이션/매핑 같은 노가다, 아침밥처럼 먹어치움
- **기능 뼈대(outline)** — 제네릭한 리스트 ✅
- **태연하게 거짓말하기** — 자신만만하게 똥덩어리를 은쟁반에 담아줌. 스니펫 던져주고 "다 했어요" 하는데, _사실 안 끝났다._

한 줄 요약:

> "If it's a well-worn pattern, AI is there to help you copy-paste faster."
> 닳고 닳은 패턴이면, AI는 네가 더 빨리 복붙하게 도와준다.

즉 **이미 수백만 번 작성된 코드**일수록 잘한다. 학습 데이터에 차고 넘치니까. 그리고 프로그래밍의 꽤 많은 부분이 실제로 그렇다 — 이 영역에선 진짜 쓸모 있다.

### AI가 무너지는 영역 (The Bad)

픽셀 퍼펙션 & 맞춤형 솔루션? 그게 뭔데? 비포장도로(독창성)로 한 발 내딛는 순간 바로 고꾸라진다(faceplant).

- **맞춤형 인터랙션** — 스크롤 기반 애니메이션, 커스텀 마이크로 인터랙션 시켜보면 IE6 시절에도 없던 CSS 문법을 발명해온다 ㅋㅋ
- **레이아웃 & 간격** — intrinsic/extrinsic 속성 예측? 수학 자체로 만들어진 녀석이 정작 동적 계산은 틀린다. 대칭 간격? 수학에 약해서 못 맞춤
- **복합 상태(combined states)** — 복잡한 컴포넌트 상태를 어디서 고쳐야 할지 짚는 순간 운다
- **접근성** — `aria-hidden="true"`를 벽에다 던지고 붙길 바람
- **성능** — 명시적으로 안 시키면 제일 무겁고 버벅이는(jankiest) 해법을 줌
- **테스트** — 좋은 테스트? 노. 많은 테스트? 예스 (양만 많음)

압권은 이거다. **컴포넌트가 복잡해질수록 프론트 도움은 더 느려지고 더 멍청해진다.** 괜찮은 디자인/컴포넌트를 원샷으로 뽑아놓고, 후속 요청에서 숨막혀 함. 뭘 잘하는지를 그대로 보여준다.

## 📌 왜 그럴까 (Why?) — 4가지 근본 원인

#### 1. 낡은 쓰레기로 학습했다 (It trained on ancient garbage)
모던 학습 데이터가 없다. 인터넷이 표준 템플릿으로 가득하니 거기에 과하게 의존한다. 모던 CSS(컨테이너 쿼리, `:has()`, subgrid, `@layer`, nesting…)? 거의 모른다.

#### 2. 말 그대로 '못 본다' (It literally cannot see)
핵심 문장.

> "It's an LLM, not a rendering engine!"
> 이건 LLM이지 렌더링 엔진이 아니다!

화면을 실제로 렌더해서 보는 게 아니라 **어둠 속에서 찌르는(stabbing in the dark)** 중이다. 간격이 떴는지, 정렬이 깨졌는지, 대비가 충분한지 — 시각적 판단이 필요한 문제에서 약할 수밖에 없다.

#### 3. '왜(why)'를 모른다 (Missing intent)
이 디자인 시스템이 왜 이렇게 설계됐는지, 이 아키텍처 결정의 의도가 뭔지 이해 못 한다. 확률적으로 그럴듯한 출력을 뱉을 뿐, 설계 철학과 분리돼 있다. 그래서 "코드는 도는데 우리 컨벤션/의도랑 안 맞는" 결과가 나온다.

#### 4. 환경을 통제할 수 없다 (No environmental control)
백엔드는 런타임/버전을 핀(pin)으로 고정할 수 있다. 프론트는? 못 한다.

- 브라우저 종류·버전 무한대
- 뷰포트 크기 무한대
- 입력 수단(마우스/터치/키보드/펜)
- 유저 설정(`prefers-reduced-motion`, `prefers-color-scheme`, 폰트 크기…)

"이걸 깨뜨리는 백만 가지 방법"이 존재한다. **움직이는 표적(moving target)이고, LLM은 움직이는 표적에 약하다.**

### 그리고 진짜 빌런 — 사람

결국 가장 예측 불가능한 변수는 **사람**이다. 취향도, 기기도, 맥락도 계속 바뀐다. 이게 `LLM combinatorial explosion`(조합 폭발)을 만든다. 프론트엔드는 본질적으로 계속 움직이는 표적이라, 패턴 기반 AI가 끝까지 맞히기 어려운 분야라는 것.

### 📌 정리
`AI는 '흔한 프론트'에 강하고 '우리만의 프론트'에 약하다`

#### 핵심
> AI가 프론트에 약한 건 모델 성능 문제가 아니라 **문제의 성질** 문제다. 프론트엔드 = 낡은 학습 데이터 + 시각 불가 + 의도 부재 + 통제 불가능한 환경(+사람). LLM이 제일 못하는 4박자가 다 모인 분야다. 그래서 "흔한 패턴 복붙"은 맡기되, "맞춤·시각·성능·접근성"은 사람이 잡아야 한다.

#### ⭐️ 앞으로 기억할 것
- 1. **잘하는 일만 시켜라**
  스캐폴딩·보일러플레이트·토큰 매핑·반복 노가다 → AI. bespoke 인터랙션·레이아웃 수학·a11y·성능 → 사람이 검수.
- 2. **AI는 화면을 못 본다는 걸 전제로 프롬프트**
  "이건 LLM이지 렌더링 엔진이 아니다." 결과를 항상 실제 브라우저에서 눈으로 확인. 픽셀/정렬/대비는 사람 책임.
  ```text
  ❌ "이쁘게 만들어줘"          // AI는 '이쁨'을 못 봄
  ✅ "8px 그리드, 카드 간격 16px, 대비 4.5:1 이상으로"  // 수치로 박아주기
  ```
- 3. **a11y는 무조건 사람이 다시 본다**
  AI가 `aria-hidden`이나 role을 아무 데나 던지는 경향. 생성 후 키보드 탭 순서·스크린리더로 검증.
  ```html
  <!-- ❌ AI가 종종 이렇게 가려버림 -->
  <button aria-hidden="true">메뉴</button>
  ```
- 4. **성능 제약을 말 안 하면 안 챙긴다**
  명시 안 하면 무거운 코드가 기본값. 번들·리렌더·이미지 최적화 같은 제약을 프롬프트에 못 박기.
- 5. **'왜'는 내가 채운다**
  디자인 시스템 의도·아키텍처 결정 이유는 AI가 모름. 컨벤션/의도를 프롬프트나 룰 파일로 떠먹여 주기.
- 6. **테스트는 양 말고 질**
  AI는 테스트를 '많이' 짠다. 진짜 깨지는 시나리오(엣지 케이스·상태 조합)는 내가 골라서 보강.

📌 결론
▎ AI는 "흔한 프론트"엔 강하고 "우리만의 프론트"엔 약하다 — 능력 차가 아니라 문제 성질 차.
▎ 약한 4가지 이유: 낡은 학습 데이터 / 못 봄 / 의도 모름 / 환경 통제 불가.
▎ 거기에 '사람'이라는 조합 폭발이 더해져 프론트는 영원히 움직이는 표적.
▎ ⭐️ 실무 적용 포인트
▎ → 복붙성 작업은 AI에 위임하고, 시각·접근성·성능·의도는 사람이 게이트키핑.
▎ → 추상적 요구("이쁘게") 대신 수치·제약·컨벤션을 명시해서 '안 보이는 AI'의 약점을 메운다.
