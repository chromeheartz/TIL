# async가 약속한 것, 그리고 실제로 준 것

> 원문: [What Async Promised and What it Delivered](https://causality.blog/essays/what-async-promised/) — Josh Segall

비동기를 다루는 방식이 callbacks → promises → async/await로 진화해온 역사를 훑으면서, **"각 파도(wave)가 직전 파도의 최악의 문제를 고쳤지만, 동시에 새로운 문제를 만들었다"** 는 한 줄로 꿰는 글이다. 매일 `await` 쓰면서도 "이게 왜 이렇게 됐지?"를 생각해본 적 없었는데, 그 누적된 비용(특히 함수 컬러링)을 정면으로 짚어줘서 좋았다.

### 출발점: C10K 문제

OS 스레드는 비싸다. 스택용 가상 주소 공간을 잡고, 생성에 수십 마이크로초가 들고, 컨텍스트 스위칭은 커널에서 일어나 CPU를 태운다. `select`/`poll` 같은 O(n) 준비도 폴링도 규모가 커지면 누적된다. **커넥션마다 스레드 하나**를 쓰면 수천 개 스레드가 메모리를 먹고 스케줄링을 두고 경쟁한다. 시스템이 유용한 일 대신 스레드 관리에 시간을 쓰는 것.

이게 1999년 Dan Kegel이 이름 붙인 **C10K 문제**다. 동시 커넥션이 많은 서버/채팅을 만들려면 "커넥션당 스레드" 없이 동시성을 다룰 방법이 필요했다. 그 답이 파도처럼 왔다.

### 1파도 — Callbacks

첫 답은 단순했다. **스레드를 블록하지 마라.** i/o 완료를 기다리는 대신, 끝나면 호출될 함수를 등록하고 다음 일로 넘어가라. 이벤트 루프(`select`/`poll`/`epoll`/`kqueue`)가 수천 커넥션을 소수의 스레드에 다중화하고, 콜백이 그 기계장치의 인터페이스였다. Node.js가 이 모델로 생태계를 통째로 지었고, Nginx의 이벤트 기반 구조가 Apache를 밀어낸 큰 이유였다.

성능 문제는 잘 풀었는데, 대가가 있었다.

- **제어 흐름이 뒤집힌다.** "A 하고, B 하고, C 해"를 세 문장으로 못 쓰고, "A 하고 끝나면 이 함수 불러, 걔가 B 하고 끝나면 저 함수 불러…" 식으로 의도가 중첩 클로저에 흩어진다. → `callback hell`.
- **에러 처리가 깨진다.** 콜백마다 자기 에러 경로가 필요. 호출 스택이 없으니(콜백은 등록된 곳과 다른 컨텍스트에서 실행) 에러가 자연스럽게 위로 전파 못 됨.
- **취소(cancellation) 개념이 없다.** 시작한 비동기 작업의 결과가 더는 필요 없어져도 멈출 일반적 방법이 없다. 콜백은 결국 실행되고, 내 코드는 "결과 필요 없어진 경우"를 처리해야 함.

**콜백은 리소스 문제(스레드 과다)를 풀면서 ergonomics 문제(쓰기·읽기·맞게 짜기 어려운 코드)를 만들었다.**

### 2파도 — Promises / Futures

다음 파도의 아이디어: 콜백을 넘기는 대신, **비동기 작업이 "곧 생길 결과를 나타내는 객체"를 즉시 반환**하면 어떨까? 이게 promise(JS) / future(Java, Rust…). 개념은 1977년 Baker & Hewitt까지 거슬러 가지만, 2010년대 C10K 압박이 이걸 주류로 밀어올렸다(JS는 ES2015 네이티브 Promise, Java 8 `CompletableFuture`).

```js
// 콜백: 중첩, 매 단계마다 에러 처리
getUser(userId, (err, user) => {
    if (err) return handleError(err);
    getOrders(user.id, (err, orders) => {
        if (err) return handleError(err);
        render(user, orders);
    });
});

// 프로미스: 체이닝, 에러 처리 통합
getUser(userId)
    .then(user => getOrders(user.id).then(orders => [user, orders]))
    .then(([user, orders]) => render(user, orders))
    .catch(handleError);
```

장점: ① **합성 가능** — `.then(f).then(g)`는 피라미드가 아니라 파이프라인으로 읽힘 ② **에러 통합** — 끝에 `.catch()` 하나면 어느 단계 실패든 처리 ③ **값이다** — 저장·전달·반환 가능. "이 값은 아직 안 끝난 계산에 의존한다"를 표현할 수 있게 됨.

근데 또 자기 문제를 만들었다:
- **one-shot.** 프로미스는 딱 한 번 resolve. 스트림·이벤트·반복 메시지를 못 모델링한다. WebSocket의 메시지 스트림은 "나중에 생길 하나의 값"에 안 맞음 → request-response는 프로미스, 나머지는 다른 것(이벤트 에미터, 옵저버블, 또 콜백)으로 쪼개짐.
- **합성이 투박하다.** `user`와 `orders`를 마지막 `.then()`에 다 넣으려면 중첩이나 `Promise.all` 곡예 필요. 조건 분기·루프·조기 종료는 점점 복잡한 콤비네이터 패턴이 필요한데, 명령형 언어에 함수형 관용구를 이식한 거라 자연스럽지 않다.
- **에러가 조용히 사라진다.** `.catch()` 없이 reject된 프로미스는 원래 에러를 그냥 삼켰다. 콜백엔 없던 새로운 종류의 silent failure를 만든 것(나중에 Node는 unhandled rejection을 경고→크래시로 바꿈).
- **타입 분열(type split).** 이제 모든 함수가 "값" 또는 "값의 프로미스"를 반환. 동기 함수에 DB 호출 하나 추가하면 비동기가 되고, 모든 호출자가 값 대신 프로미스를 다뤄야 함. → 다음 파도가 더 키울 **컬러링 문제**의 약한 버전.

### 3파도 — Async/Await

프로미스 체인도 여전히 개발자가 쓰는 일반 순차 코드와 안 닮았다. async/await(2012 C#이 개척, JS ES2017/Python 3.5/Rust 1.39/Kotlin/Swift/Dart 채택)가 바로 그걸 줬다.

```js
// 프로미스 체인
function loadDashboard(userId) {
    return getUser(userId)
        .then(user => getOrders(user.id)
            .then(orders => [user, orders]))
        .then(([user, orders]) => render(user, orders));
}

// async/await — 순차 코드처럼 읽힘
async function loadDashboard(userId) {
    const user = await getUser(userId);
    const orders = await getOrders(user.id);
    return render(user, orders);
}
```

변수가 자연스럽게 바인딩되고, `.catch()` 대신 `try/catch`를 쓰고, 루프 안에서 `await`이 먹는다. **선형(linear) 비동기 시퀀스엔 명백한 ergonomics 승리.** 업계가 빠르게 채택해서 몇 년 만에 대부분 주류 언어의 동시 i/o 기본 작성법이 됐다.

### 함수 컬러링 세금 (Function Coloring Tax)

2015년 Bob Nystrom의 [`"What Color is Your Function?"`](https://journal.stuffwithstuff.com/2015/02/01/what-color-is-your-function/). 모든 함수가 "빨강" 아니면 "파랑"인 언어를 상상한다. 빨강은 파랑을 부를 수 있지만, **파랑이 빨강을 부르려면 특별한 의식이 필요**하고, 빨강을 부른 파랑은 자기도 빨강이 돼야 해서 **코드베이스 전체로 바이러스처럼 퍼진다.**

이게 async/await 비유다. **async = 빨강, sync = 파랑.** sync 함수에서 async를 부르려면 스레드를 블록하거나 코드를 재구성해야 하고, 그 색 선택이 모든 호출자로 전파된다. 비용은 여러 스케일에서 나타난다:

- **함수 레벨:** 동기 함수에 i/o 호출 하나 추가 → 시그니처·반환 타입·호출 규약이 바뀜 → 모든 호출자, 그 호출자의 호출자까지 수정. 한 줄 DB 조회가 수십 파일 수정을 부른다.
- **라이브러리 레벨:** 저자는 sync 라이브러리(async 유저 배제) vs async 라이브러리(sync 유저에 런타임 의존성 강요) 중 선택. 많이들 "둘 다"를 골라 API 표면·테스트 매트릭스·유지보수 부담을 2배로. 파이썬 `requests`(sync) vs `aiohttp`(async)가 다른 저자가 같은 일 하는 별개 프로젝트. `httpx`가 둘 다 제공하지만 이 분열 때문에 필요해진 것.
- **생태계 레벨:** Rust async가 경쟁 런타임(Tokio/async-std/smol)으로 파편화. TCP 스트림·타이머 같은 기본 타입조차 호환 안 됨. `reqwest`는 그냥 Tokio를 요구. **Tokio의 지배 = 생태계 규모의 함수 컬러링.**

비용은 로지스틱뿐 아니다. async/await는 스레드엔 없던 새 버그 종류를 만들었다. O'Connor가 기록한 **"futurelock"** — 한 future가 락을 잡은 채 폴링이 멈추고, 다른 future가 같은 락을 잡으려 함. 스레드는 락을 쥔 스레드가 항상 해제 쪽으로 전진하지만, async Rust는 `select!`·버퍼드 스트림·`FuturesUnordered`가 리소스를 쥔 future의 폴링을 일상적으로 멈춘다. Oxide의 최초 futurelock은 코어 덤프와 디스어셈블러로 진단해야 했다.

### 순차의 함정 (A Sequential Trap)

덜 주목받는 더 미묘한 비용. **async/await의 최대 강점(비동기를 순차처럼 보이게)이 동시에 인지적 함정이다.**

```js
async function loadDashboard(userId) {
    const user = await getUser(userId);
    const orders = await getOrders(user.id);
    const recommendations = await getRecommendations(user.id);  // orders 끝날 때까지 시작 안 함
    return render(user, orders, recommendations);
}
```

`orders`와 `recommendations`는 서로 독립인데도 순차로 실행된다. 코드는 깔끔하고 올바라 보이지만 **성능을 테이블에 흘리고 있다.** 병렬로 만들려면 프로그래머가 명시적으로 순차 스타일을 깨야 한다:

```js
async function loadDashboard(userId) {
    const user = await getUser(userId);
    const [orders, recommendations] = await Promise.all([
        getOrders(user.id),
        getRecommendations(user.id)
    ]);
    return render(user, orders, recommendations);
}
```

수십 개 async 호출이 있는 실제 앱에선 "뭐가 독립이라 병렬 가능한지"를 사람이 수동으로 의존성 분석해 재구성해야 한다. **순차 문법이 오히려 의존 구조(병렬 가능 여부를 알려주는 바로 그 정보)를 가려버린다.** 비동기를 쉽게 쓰려고 도입한 async/await가, "뭐가 동시에 돌 수 있나"를 사람이 수동 판단해 순차 흐름을 깨는 콤비네이터로 표현하게 만든 셈.

### async가 잘한 것 + 다른 길을 택한 언어들

공정하게, async/await는 분명 개선했다. 선형 시퀀스 ergonomics는 콜백·프로미스 체인보다 낫고, i/o가 섞인 본질적 순차 코드의 구문 잡음을 진짜로 줄였다.

근데 어떤 언어 설계자들은 다른 길을 택했다:
- **Go** — goroutine. 무거운 런타임을 감수하고 함수 컬러링 자체를 없앰. (단, `context.Context`가 취소 전파로 일종의 컬러링을 도입하긴 함.)
- **Java Project Loom** — 가상 스레드(Java 21). 일반 스레드처럼 보이고 동작해서 어떤 코드도 색을 바꿀 필요 없음. Loom 팀이 함수 컬러링을 피하고 싶은 문제로 명시.
- **Zig** — 컴파일러 레벨 async/await를 아예 제거하고, i/o 작업이 받는 `Io` 인터페이스 파라미터로 재구축. 런타임(스레드든 이벤트루프든 유저가 공급)이 인터페이스를 충족. 시그니처가 스케줄 방식에 안 바뀌고 async/await가 키워드가 아닌 라이브러리 함수가 됨. (다만 Io 파라미터 자체가 일종의 컬러링이란 반론도.)

### 누적되는 비용 (Accumulating Costs)

| 파도 | 푼 것 | 도입한 것 |
|---|---|---|
| **Callbacks** | 커넥션당 스레드 리소스 고갈 | 제어 흐름 역전, 파편화된 에러 처리, callback hell |
| **Promises** | 중첩 해소, 에러 통합, 콜백 대신 값 | one-shot 한계, 조용한 에러 삼킴, 약한 타입 분열 |
| **Async/Await** | 선형 비동기 시퀀스 ergonomics | 함수 컬러링, 생태계 파편화, 새 데드락(futurelock), 순차의 함정 |

각 파도는 **로컬 경험(한 함수 짜기)은 더 즐겁게, 글로벌 경험(대형 코드베이스 유지)은 더 복잡하게** 만들었다. 한 async 함수를 쓰는 개발자는 역대 최고지만, sync/async 섞인 대형 코드베이스를 유지하고 런타임 호환성을 관리하고 순차 `await` 체인 뒤에 숨은 병렬 기회를 찾는 팀은 예전엔 없던 부담을 진다.

이건 나쁜 엔지니어링 얘기가 아니다. 콜백·프로미스·async/await를 설계한 사람들은 진짜 문제를 풀었고, 각 단계는 직전 단계 실패에 대한 합리적 대응이었다. 다만 15년, 여러 반복 끝에 누적된 세금이 상당하고, 패턴이 보인다: **각 수정은 증상을 다루면서 구조는 그대로 둔다.**

### 📌 정리
`async의 진화는 직전 문제를 고치며 새 구조적 비용을 누적해왔다`

#### 핵심
> 동시성을 다루는 방식은 callbacks → promises → async/await로 진화했고, 각 파도가 직전의 최악 문제를 풀면서 새 문제를 만들었다. 콜백은 스레드 고갈을 풀고 callback hell을 낳았고, 프로미스는 중첩을 풀고 one-shot·silent error·타입 분열을 낳았고, async/await는 선형 ergonomics를 주고 **함수 컬러링·생태계 파편화·새 데드락·순차의 함정**을 낳았다. 로컬(한 함수)은 좋아졌지만 글로벌(대형 코드베이스)은 복잡해졌다. Go/Loom/Zig는 컬러링 비용이 이득보다 크다고 보고 다른 길을 택했다.

#### ⭐️ 앞으로 기억할 것
- 1. **함수 컬러링 = async가 바이러스처럼 전파된다**
  동기 함수에 `await` 하나 추가 → 시그니처 바뀜 → 모든 호출자가 async가 돼야 함. "한 줄 DB 조회가 수십 파일 수정."
- 2. **순차처럼 보이는 게 함정이다 — 독립 호출은 `Promise.all`로**
  ```js
  // ❌ 독립인데 순차로 실행 (느림)
  const orders = await getOrders(id);
  const recs = await getRecommendations(id);
  // ✅ 독립 작업은 병렬로
  const [orders, recs] = await Promise.all([getOrders(id), getRecommendations(id)]);
  ```
  `await`을 줄줄이 쓰기 전에 "이거 앞 결과에 진짜 의존하나?"를 항상 자문.
- 3. **프로미스는 one-shot — 스트림엔 안 맞다**
  반복 메시지/이벤트(WebSocket 등)는 프로미스 말고 이벤트 에미터·옵저버블·async iterator.
- 4. **unhandled rejection을 방치하지 마라**
  `.catch()` 없는 reject는 조용히 사라진다(과거). 항상 에러 경로를 닫기.
- 5. **각 추상화는 "증상"을 고치고 "구조"는 남긴다**
  더 나은 문법이 근본 문제(동시성을 명령형으로 표현하는 것)를 없애주진 않는다. 도구의 한계를 알고 쓰기.
- 6. **컬러링 없는 대안 존재**: Go goroutine, Java 가상 스레드(Loom), Zig Io 인터페이스. 언어 선택 시 참고.

📌 결론
▎ callbacks/promises/async-await는 "어떻게 동시 실행을 관리하나?"라는 질문이 모든 추상화 레벨에서 새 문제를 만들어내는 과정의 가장 선명한 사례다.
▎ async/await의 최대 강점(순차처럼 보임)이 동시에 최대 약점(병렬 기회를 가림 + 컬러링 전파).
▎ ⭐️ 실무 적용 포인트
▎ → JS 짤 때: `await` 줄세우기 전에 의존성 점검, 독립이면 `Promise.all`.
▎ → 라이브러리 고를 때: sync/async 색이 우리 코드베이스와 맞는지 확인(특히 Rust 런타임).
▎ → 스트림성 데이터는 프로미스가 아니라 async iterator/옵저버블.
