솔직히 나도 패키지 고를 때 주간 다운로드 수랑 GitHub 스타만 흘끗 보고 `npm install` 치는 편이다. 이 글은 그 두 숫자가 안전성, 유지보수 여부, 정직성 어느 것도 말해주지 않는다고 하면서 5~10분짜리 반복 가능한 체크 절차를 제안한다. JavaScript Weekly와 Node Weekly에 소개된 글이라 읽어봤고, 체크리스트로 쓰려고 정리해둔다.

### 왜 다운로드 수와 스타로는 부족한가

`npm install` 한 번은 "한 번도 만난 적 없는 사람이 쓴 코드를 내 프로세스 권한 그대로 프로덕션에서 실행하겠다"는 뜻이다. 파일시스템, 네트워크, 환경변수 전부 접근 가능하다.

공급망(supply chain) 공격은 이걸 더 나쁘게 만들었다. `event-stream`, `ua-parser-js`, `node-ipc`, `xz utils` 전부 패턴이 같다. 멀쩡히 잘 쓰이던 패키지가 메인테이너 사회공학, 타이포스쿼팅, 또는 세 단계 아래 묻힌 전이 의존성을 통해 침해된다. npm은 작은 패키지를 조합하는 문화와 깊은 전이 트리 때문에 특히 매력적인 표적이다. 내가 다 잘해도 직접 설치한 적 없는 것 때문에 당할 수 있다.

#### 새 변종: 슬롭스쿼팅(slopsquatting)

AI 코딩 도구가 존재하지 않는 패키지 이름을 환각으로 만들어낸다. 공격자는 그 환각 이름을 감시하다가 실제로 등록해버린다. 개발자가 확인 없이 제안을 따르면 악성 코드를 설치하게 된다. LLM이 처음 들어보는 패키지를 제안하면 설치 전에 **실제로 존재하는지, 이력이 있는지, 출처 증명이 있는지** 확인해야 한다.

에이전트 모드로 돌리면 패키지 선택 → 설치가 사람 확인 없이 연달아 일어나서 위험이 더 커진다. 이럴 땐 "먼저 확인해"라는 프롬프트 문구가 아니라 **툴체인 안의 강제 수단**(미검증 패키지를 차단하는 설치 훅이나 래퍼)에 의존해야 한다.

그렇다고 오픈소스를 끊으라는 얘기는 아니다. 그러면 생산성만 떨어지고 딱히 안전해지지도 않는다. 요지는 패키지 선택이 5초짜리 스타 확인보다는 가치 있는 일이라는 것.

### 📌 0단계: 정말 이 패키지가 필요한가?

감사하기 전에 제일 단순한 질문부터. 이 의존성이 애초에 존재해야 하나?

npm 사고가 심각해지는 이유는 패키지 하나가 치명적이어서가 아니라, 작고 편리한 패키지가 수십 개 서비스에 복사돼서 어디에나 있게 되기 때문이다. 그게 침해되거나 방치되거나 갑자기 unpublish되면 피해 범위가 더는 작지 않다.

#### 확인할 것
- **제거 테스트**: 이 패키지가 내일 사라지면 대체 난이도가 어느 정도인가? "코드베이스 절반 리팩터링"이면 고위험으로 보고 더 엄격하게 본다.
- **작은 유틸이면 직접 짤 수 있나?** 헬퍼 함수 하나 때문에 의존성을 끌어오는 건 장기 위험 대비 손해일 때가 많다.
- **의존성 발자국**: 런타임 의존성 0이 자동으로 안전은 아니지만, 적을수록 공격 표면과 전이 의외성이 줄어든다.
- **어디에 쓸 건가**: 격리된 내부 도구 하나 vs 모든 서비스에 import. 위험 프로필이 다르다.

```ts
// ❌ 두 줄짜리를 위해 의존성 추가
import isEmpty from 'is-empty-obj'

// ✅ 그냥 직접 쓴다
const isEmpty = (o: object) => Object.keys(o).length === 0
```

### 📌 1단계: 활발하게 유지보수되고 있나?

방치된 패키지는 복리로 불어나는 부채다. 취약점이 패치 안 되고, 새 Node 버전과 조용히 깨지고, 결국 옛 버전에 pin된 채 통째로 교체해야 하는 날이 온다.

최근 커밋이 명백한 신호지만 커밋 빈도만 보면 속기 쉽다. 지난주 커밋이 CI 액션 버전업뿐일 수 있다. 보고 싶은 건 **저자가 아직 실제 소프트웨어에 관여하는가**다.

#### 확인할 것
- **Issues 탭의 가장 오래된 열린 이슈**: 인지는 되고 있나? 18개월 전 버그 리포트에 답이 없다면, 문제 생겼을 때 어떤 관계가 될지 알 수 있다.
- **Commits 탭에서 봇·CI 잡음 걸러내기**: 사람이 소스 코드에 의미 있는 변경을 한 게 언제인가?
- **누가 하고 있나**: 커밋·릴리스·이슈 답변이 거의 한 사람이면 `버스 팩터` 1. 자동으로 나쁜 건 아니지만 내 운영 위험이 한 사람의 가용성에 묶인다는 뜻.
- **npm Versions 탭의 릴리스 리듬**: 알아볼 만한 주기가 있나, 아니면 2년 공백 뒤 몰아치기? 긴 공백 뒤 갑작스런 활동은 그 자체로 경고 신호일 수 있다. 계정 탈취는 실제로 일어난다.
- **CHANGELOG 품질**: 커밋 해시만 나열하면 쓸모없다. "무엇이 왜 바뀌었는지" 적힌 체인지로그는 사용자를 신경 쓰는 사람이 쓴 것이다.
- **마이그레이션 가이드**: 호환성 깨는 변경을 문서화하는 저자는 하류 비용을 생각하는 저자다.

### 📌 2단계: npm에 올라간 게 진짜 저자가 올린 건가?

1단계가 미래 얘기라면 이건 지금 당장의 얘기다. 레지스트리에 있는 바이트가 GitHub에서 읽은 소스와 같다고 믿을 근거가 있나?

npm 레지스트리는 기본적으로 검증이 없다. 소스와 게시를 잇는 고리는 `NPM_TOKEN`이고, 이건 CI 시크릿이나 개발자 노트북에 있는 **공격자가 딱 노리는 종류의 자격 증명**이다. 2018년 event-stream 사건이 이거다. GitHub도 npm 인프라도 안 뚫렸다. 그냥 자격 증명이 넘어갔을 뿐이다.

#### 출처 증명(Provenance)

현대적인 답은 [출처 증명][provenance]이다. 출처 증명과 함께 게시하면 npm이 **특정 타르볼 ↔ 특정 저장소의 특정 커밋 ↔ 특정 GitHub Actions 워크플로우 실행**을 묶는 암호학적 증명(GitHub OIDC 서명)을 받는다. 공개되어 있고 검증 가능하다. 저장소 출신이라고 주장하는데 어테스테이션이 안 맞으면 탐지된다.

#### 확인할 것

npm 패키지 페이지에서 버전 옆 초록색 "Provenance" 배지를 본다.

![npm provenance badge](https://blog.kakaocdn.net/dna/SCPVY/dJMcaiRPPqm/AAAAAAAAAAAAAAAAAAAAALxoBfnCESOJ74_1K9PkngVfzXY56hoAl7Z15uepZoXV/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1793458799&allow_ip=&allow_referer=&signature=JRZNGwse1CIYQdBP2yTlJFbwmhg%3D)

클릭해서 "View more details"로 들어가면 저장소 URL, 커밋 SHA, 게시한 워크플로우 실행이 보인다. 전부 클릭해서 실재하고 말이 되는지 확인할 수 있다.

![npm provenance details](https://blog.kakaocdn.net/dna/dekDx9/dJMcabSEBzf/AAAAAAAAAAAAAAAAAAAAAPk2lQ61sXPKrPTubKFrniKlgv_2AE2ERjpBHwEJuU1G/img.png?credential=yqXZFxpELC7KVnFOS48ylbz2pIh7yKj8&expires=1793458799&allow_ip=&allow_referer=&signature=2x5bKS4P2pVQ70pXIQ5ZpyvoP0A%3D)

배지가 없으면 출처 증명 없이 게시된 것. 자동으로 의심스러운 건 아니지만(대부분 패키지가 이 기능보다 오래됐다) 소스→게시 고리를 검증할 수 없다는 뜻이다.

CLI로도 된다. 패키지가 설치된 프로젝트에서:

```bash
npm audit signatures
# 설치된 모든 패키지의 서명을 검증하고 유효한 출처 증명이 있는 것을 보고
```

게시 워크플로우(`.github/workflows/`)를 열어 세 가지를 본다.

```yaml
# ✅ Trusted Publishing(OIDC). 훔칠 장기 토큰이 없다
permissions:
  id-token: write # npm과 OIDC 토큰 교환 허용
steps:
  - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # 전체 SHA로 고정
  - run: npm publish --provenance # 어테스테이션 생성

# ❌ 수명 긴 토큰 + 변경 가능한 태그
# - uses: actions/checkout@v4   ← 액션 저자가 태그를 바꾸면 조용히 다른 코드 실행
# - run: npm publish
#   env:
#     NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

| 확인 항목 | 의미 |
|---|---|
| `npm publish --provenance` | 어테스테이션을 생성하는 바로 그 플래그 |
| `id-token: write` | npm과의 OIDC 토큰 교환 허용 |
| `NPM_TOKEN` 시크릿 **없음** | Trusted Publishing이면 훔칠 장기 토큰이 없다 |
| 액션을 SHA로 pin | `@v4`, `@main`은 변경 가능. SHA는 워크플로우 파일을 고치지 않는 한 못 바꾼다 |

#### 설치 스크립트

검토하기도 전에 내 기계에서 코드를 실행하는 게 하나 더 있다. `package.json`의 `preinstall` / `install` / `postinstall` 훅은 `npm install` 치는 순간 돈다. 정당한 패키지 대부분은 이게 필요 없다. C++ 바인딩을 컴파일하는 네이티브 애드온 정도가 진짜 필요한 경우. 명백한 이유 없는 설치 스크립트를 보면 **이해하고 넘어가야 한다**.

### 📌 3단계: CI가 실재하나, 장식인가?

README의 초록 배지는 큰 의미 없이도 얻기 쉽다. 정상 경로 하나에서 테스트 세 개 돌리고 100% 통과를 보고하면 된다. 기술적으로 정확하면서 완전히 쓸모없는 배지.

알고 싶은 건 **CI가 실제로 코드베이스를 보호하는가**, 즉 회귀·타입 오류·엣지 케이스를 출시 전에 잡는가다.

#### 확인할 것
- **Actions 탭**: `pull_request` 이벤트에서도 도나, `main` 푸시에서만 도나? 머지 후에만 도는 파이프라인은 아무것도 보호하지 않는다. 이미 일어난 일의 기록일 뿐.
- **최근 머지된 PR 하나 열기**: CI가 돌았나? 누군가 통과를 기다렸나? 열린 지 30초 만에 CI 없이 머지됐으면 장식이다.
- **테스트 설정의 커버리지 임계값**:

```ts
// vitest.config.ts
// ✅ 임계값이 있으면 커버리지가 떨어질 때 CI가 실패한다
coverage: {
  thresholds: { lines: 90, functions: 90, branches: 90 },
}
// 없으면 보고만 될 뿐 강제되지 않는다. 테스트 절반을 지워도 빌드는 통과
```

- **테스트가 뭘 다루나**: `src/` 구조를 따라가는 `test/` 디렉터리나 소스 옆 단위 테스트는 좋은 신호. 스모크 테스트 몇 개 든 `index.test.ts` 하나는 완전히 다른 얘기.

### 📌 4단계: 코드 품질이 눈에 보이나?

모든 패키지의 코드 전체를 감사하진 않는다. 비현실적이다. 대신 품질과 상관관계 있는, 한눈에 보이는 신호를 본다.

#### 확인할 것
- **린팅 설정**: `eslint.config.js` 등이 존재하고 비어 있지 않나? 린팅은 기본 중의 기본이라 부재 자체가 신호.
- **`exports` 필드**: 현대적 패키지는 명명된 익스포트 조건을 지정한다. `main`만 있으면 이게 표준이 되기 전에 작성된 것. 자격 미달은 아니지만 저자 관행의 최신성을 알려준다.

```json
// ✅ 조건부 익스포트
"exports": {
  ".": {
    "types": "./dist/index.d.ts",
    "import": "./dist/index.mjs",
    "require": "./dist/index.cjs"
  }
}
```

- **`prepublishOnly`**: 깨진 빌드나 테스트 건너뛴 빌드를 실수로 게시하는 걸 막는다. 악의적 게시는 못 막지만 저자가 실수 게시를 고민했다는 건 알 수 있다.

```json
"prepublishOnly": "npm run build && npm run test:ci"
```

- **`tsconfig.json`의 `strict: true`**: null 검사, 엄격한 함수 타입, no-implicit-any. 한 부류의 버그 전체를 컴파일 타임에 잡는다. 꺼둔 저자는 그 버그들을 용인하기로 한 것.
- **`any`와 `@ts-ignore` 검색**: 어색한 interop에서 몇 번은 정상. 소스 곳곳에 수십 개면 타입이 겉치레다. `.ts` 확장자만 있고 타입 안전성은 없는 패키지.

### 📌 5단계: 뭔가 잘못되면 어떻게 되나?

사소하지 않은 패키지는 결국 취약점을 갖는다. 문제는 그때 저자가 어떻게 대응하느냐다. 빠르게? 책임감 있게(먼저 비공개, 수정과 함께 공개)? 내 버전이 영향받는지 판단할 수 있게 문서화하나?

#### 확인할 것
- **`SECURITY.md`** 또는 `github.com/<owner>/<repo>/security/policy`: 비공개 보고 방법, 연락 수단, 응답 일정. 없다고 안전하지 않은 건 아니지만, 내가 뭔가 발견했을 때 실수로 공개해버리지 않고 보고할 경로가 없다는 뜻.
- **Security 탭의 Advisories<strong>: 게시된 게 있나? 조율된 공개였나, 공개 시점에 수정이 준비돼 있었나, 영향 버전 범위가 명확했나? </strong>잘 처리된 과거 권고는 오히려 긍정 신호**다.
- **[osv.dev][osv] / [snyk.io][snyk]**: CVE와 GitHub Security Advisories 집계. 알려졌는데 패치 안 된 취약점은 설치 전에 알아야 한다.
- **[Socket.dev][socket]**: CVE 목록을 기다리는 대신 행위 분석. 네트워크 접근? 예상 밖 파일시스템 접근? 난독화 코드? 설치 스크립트? PR에서 새 의존성을 표시해주는 GitHub 앱도 있다.
- **[Socket Firewall][socket-firewall]**: 검토 시점 경고가 아니라 설치 시점에 정책을 강제하고 알려진 악성 패키지를 차단. 취미 프로젝트엔 과하지만 규제·보안 민감 시스템엔 강력한 통제.
- **과거 보안 이슈 해결 속도**: 며칠 안에 고친 치명적 취약점과 석 달 방치는 다르다. 보안 응답 시간은 저자가 책임을 얼마나 진지하게 보는지의 가장 명확한 신호 중 하나.

### 체크리스트

모든 항목이 같은 무게는 아니다. 세 가지만 할 시간이면:

1. **정말 필요한가?** 대체하거나 피할 수 있으면 위험을 관리하는 게 아니라 제거하는 것.
2. **출처 증명이 있는가?** 게시된 게 저자가 의도한 그것이라는 가장 명확한 신호.
3. **설명 안 된 설치 스크립트가 있는가?** `npm install` 순간 내 기계에서 코드가 돈다.

프로덕션에 결정적인 패키지면 네 번째: **메인테이너가 반응하는가?** 문제 생겼을 때 고칠 수 있는 사람이 실제로 고쳐줄지 알아야 한다.

#### 보안에 결정적인 신호

| 신호 | 어디서 | ✅ 초록 | ❌ 빨강 |
|---|---|---|---|
| 출처 증명 | npm 버전 페이지 | Provenance 섹션이 있고 저장소와 일치 | 없음, 또는 알 수 없는 출처의 버전 |
| Trusted publishing | `.github/workflows/publish.yml` | OIDC + `--provenance`, `NPM_TOKEN` 없음 | `NPM_TOKEN` 시크릿, 수동 게시 |
| 설치 스크립트 | `package.json` scripts | 없음, 또는 명백한 네이티브 애드온 사유 | 정당성 없는 `preinstall`/`postinstall` |
| 고정된 CI 액션 | `.github/workflows/*.yml` | SHA로 pin된 서드파티 액션 | `@v3`, `@latest`, `@main` |

#### 운영 성숙도 신호

| 신호 | 어디서 | ✅ 초록 | ❌ 빨강 |
|---|---|---|---|
| 활발한 유지보수 | 커밋 + 열린 이슈 | 최근 3개월 내 커밋, 인지된 이슈 | 마지막 커밋 2년+, 방치된 이슈 |
| 의존성 발자국 | npm 페이지 + 락파일 | 범위 대비 적은 의존성 | 사소한 유틸에 큰 전이 트리 |
| 메인테이너 집중도 | 커밋·릴리스·이슈 응답 | 여러 명에게 분산 | 한 명이 거의 전부 |
| 강제된 커버리지 | vitest/jest 설정 | 80% 이상 임계값 | 임계값 없음, 절대 안 바뀌는 배지 |
| 보안 정책 | `SECURITY.md` / Security 탭 | 명확한 공개 프로세스와 연락처 | 없음, 또는 연락처 없는 템플릿 |

보안 신호는 깨끗한데 운영 성숙도가 약하면 **계산된 위험**이다. 보안 신호에서 실패하면 **다른 범주의 문제**다.

### 위험은 이분법이 아니다

합격/불합격 테스트가 아니라 위험 평가고, 위험은 맥락에 따라 다르다. UI 날짜 포맷 유틸과 정부 API 사이에 앉은 HTTP 클라이언트는 위험 프로필이 다르다. 주간 5천만 다운로드는 5백보다 보는 눈이 많다. 보안팀 있는 조직의 패키지와 개인이 여가에 유지보수하는 건 다르다. 어느 것도 단독으로 자격 미달은 아니다. 생태계에서 가장 믿을 만한 패키지 일부는 개인이 유지보수한다. 다만 얼마나 면밀히 봐야 하는지에는 영향을 준다.

목표는 만점 패키지를 찾는 게 아니다. 추가할 때 **내가 뭘 받아들이는지 이해하고, 기본값으로 흘려보내는 대신 의도적으로 결정**하는 것이다.

### 📌 정리
`다운로드 수 말고 출처 증명·설치 스크립트·메인테이너 반응을 본다`

#### 핵심
> `npm install`은 모르는 사람 코드를 내 권한으로 실행하는 결정이다. 다운로드 수와 스타는 안전성을 말해주지 않는다. 시간이 없으면 세 가지만 본다. **정말 필요한가, 출처 증명(Provenance)이 있는가, 설명 안 된 설치 스크립트가 있는가.** 프로덕션 핵심이면 메인테이너 반응 속도까지. 나머지(CI 실재 여부, strict 타입, 커버리지 임계값, SECURITY.md)는 위험 부담이 클수록 추가로 본다. 그리고 AI 에이전트가 설치까지 하는 환경이면 프롬프트가 아니라 설치 훅 같은 툴체인 강제 수단에 의존한다.

#### ⭐️ 앞으로 기억할 것
1. 0단계가 제일 중요하다
감사 전에 "직접 짜면 몇 줄인가?"를 먼저 묻는다. 의존성은 관리하는 것보다 안 만드는 게 싸다. 제거 테스트로 "내일 사라지면?"을 상상해본다.
2. Provenance 배지와 `npm audit signatures`
npm 페이지에서 초록 Provenance 배지 → 저장소·커밋·워크플로우 실행이 실재하는지 클릭해본다. 이미 설치된 프로젝트면 CLI 한 줄로 전수 확인.
```bash
npm audit signatures
```
3. 설치 스크립트는 리뷰 전에 실행된다
`preinstall`/`postinstall`은 네이티브 애드온 아니면 거의 필요 없다. 이유 없는 설치 스크립트는 멈추고 읽는다. 팀 환경이면 `ignore-scripts`를 기본으로 두는 것도 방법.
```ini
# .npmrc
ignore-scripts=true
```
4. 게시 워크플로우에서 세 가지
`--provenance`, `id-token: write`, 그리고 `NPM_TOKEN`의 **부재**. 액션은 `@v4`가 아니라 전체 SHA로 pin. 내 패키지 배포 워크플로우에도 똑같이 적용할 것.
5. 초록 CI 배지는 장식일 수 있다
`pull_request`에서 도는지, 최근 PR이 CI를 기다렸는지, 커버리지 `thresholds`가 있는지. 셋 다 없으면 배지는 기록일 뿐 보호가 아니다.
6. 슬롭스쿼팅
LLM이 제안한 처음 보는 패키지는 설치 전에 npm 페이지부터 연다. 존재 여부, 이력, Provenance. 에이전트 모드면 이걸 사람 말고 툴체인이 강제하게 한다.
7. 잘 처리된 과거 Advisory는 긍정 신호
취약점이 있었다는 사실보다 조율된 공개·즉시 수정·명확한 영향 범위 문서화가 있었는지가 중요하다. 응답 속도가 책임감의 척도.

> 📌 결론  
> ▎ 다운로드 수와 스타는 인기 지표지 안전 지표가 아니다.  
> ▎ 시간 없으면 세 가지: 정말 필요한가 / Provenance 있나 / 설명 없는 설치 스크립트 있나.  
> ▎ 보안 신호 실패와 운영 성숙도 약함은 다른 범주다. 전자는 거의 탈락, 후자는 계산된 위험.  
> ▎ 위험은 맥락이다. 날짜 포맷 유틸과 핵심 HTTP 클라이언트를 같은 잣대로 보지 않는다.  
> ▎ ⭐️ 실무: PR에 새 의존성이 추가되면 리뷰 코멘트에 "직접 짜면 몇 줄?"과 "Provenance 확인했나?"를 습관처럼 남긴다.  
> ▎ ⭐️ 실무: 내가 배포하는 패키지는 Trusted Publishing(OIDC) + `--provenance` + SHA pin으로 전환한다. 남을 평가하는 기준을 나한테 먼저 적용.
