# 이제 웹팩과 작별할 때일까?

> **출처**: https://velog.io/@sehyunny/is-it-time-to-say-goodbye-to-webpack (velog @sehyunny, 황세현 번역) / 원문: https://javascript.plainenglish.io/time-to-say-goodbye-to-webpack-5bf06ff48823

요즘 새 프로젝트 깔 때 `CRA` 안 쓰고 `Vite`로 시작하는 글을 자주 본다. 솔직히 "웹팩 잘 돌아가는데 굳이?" 싶었는데, 왜 다들 넘어가는지 한 번 제대로 짚으려고 정리했다. 본론 들어가기 전에, 애초에 왜 이 고민을 하게 됐는지부터.

2021 bestofJS 데이터를 보면 빌드 도구 인기도에서 웹팩(Webpack)을 제치고 `Vite`가 확 치고 올라왔다. 더 자세한 건 [`2021 JavaScript Rising Stars`][rising-stars]에서.

![bestofJS build tools ranking](https://miro.medium.com/max/1400/1*8qh2O6sg9qIYWsEXH9HRXA.png)

### Vite가 뭔데?

> Vite("빠르다"는 뜻의 프랑스어, /vit/ "비트"처럼 발음)는 더 빠르고 가벼운 **개발** 경험을 목표로 하는 빌드 도구다.

여기서 **개발**을 굵게 강조한 게 핵심이다. Vite는 "프로덕션 번들이 더 작아진다", "런타임이 더 최적화된다" 같은 걸 보장하지 않는다. 그러니까 Vite 깔았다고 프로덕션 번들 사이즈가 확 줄거라 기대하면 안 된다. **개발 경험(DX)** 을 빠르게 만드는 도구라고 보면 된다.

#### 그럼 개발 경험을 위해 Vite는 뭘 하나

크게 두 가지다.

- **개발 서버 역할** — 네이티브 ES 모듈 기반으로, 매우 빠른 HMR(핫 모듈 리플레이스먼트) 같은 향상된 기능을 얹어 제공한다.
- **빌드 명령어 역할** — 프로덕션에 최적화된 정적 에셋을 뽑도록 미리 설정된 `Rollup`으로 번들링한다.

Vite는 다소 독단적(opinionated)으로 합리적인 기본값을 주지만, 타입 지원되는 JS API와 플러그인 API로 다양하게 확장할 수 있다.

### 왜 이게 문제였나 — 번들러의 숙명

ES6 모듈이 나온 뒤로 우리는 꽤 오래 JS를 모듈 단위로 짜왔다. 근데 **모든 브라우저가 ES6 모듈 로딩을 기본 지원하는 게 아니라서**, 모듈을 찾고 처리해서 브라우저가 실행할 수 있는 형태로 엮어주는 도구가 늘 필요했다. 웹팩, Parcel, Rollup이 다 이 역할.

문제는 프로젝트 초반엔 모듈 크기·개수가 별것 아닌 것 같다가, 코드가 쌓이고 규모가 커지면 **개발 서버가 점점 느려진다**는 것. 서버 띄우려면 코드를 변환하고 브라우저가 읽을 수 있게 다 엮어야 하니까. 이 느린 피드백이 반복되면 생산성·만족도가 바닥을 친다.

> Vite는 이 문제를 **브라우저의 네이티브 ES 모듈** + **네이티브 언어(Go 등)로 짠 JS 도구**(esbuild 같은) 같은 새 기술로 푼다.

Vite는 번들을 두 갈래로 나눈다.

- **외부 의존성(벤더 코드)** — 개발 중엔 거의 안 바뀌는 일반 JS. ➡️ **esbuild로 미리 번들링(pre-bundle)** 한다. esbuild는 JS 기반 번들러보다 **10~100배 빠르게** 의존성을 미리 묶는다.
- **내부 프로젝트 코드(ES 모듈)** — ➡️ **네이티브 ESM 그대로** 브라우저에 넘긴다. 본질적으로 번들러 작업 일부를 브라우저에 떠넘기는 것. Vite는 브라우저가 요청할 때마다 그 소스만 변환·제공하면 된다.

여기서 Vite는 "너 로컬에서 개발할 땐 ES6 모듈 지원하는 최신 브라우저 쓰지?"를 전제로 깐다.

#### 핵심: 서버 시작 전에 번들링하는 시간이 0이다

❌ **웹팩** — 서버 켜기 전에 전체를 다 번들링 → 규모 클수록 시작이 느려짐

![webpack bundle based dev server](https://miro.medium.com/max/1400/1*EcVlu5OOebUL06xnZWVaTg.png)

✅ **Vite** — 번들링 없이 서버부터 띄우고, 브라우저 요청 시 그 모듈만 변환

![vite native ESM dev server](https://miro.medium.com/max/1400/1*qKT6c5NA8iq80saCyFcByw.png)

### 그럼 프로덕션은 왜 굳이 번들링하나?

개발은 ESM 그대로 던진다며, 프로덕션도 그러면 안 되나? 안 된다.

- 대부분 브라우저가 ESM 로딩을 지원해도, **모든 유저가 최신 브라우저는 아니다** → 번들링이 여전히 필요.
- 번들링 안 하면 모듈 하나하나 가져오느라 **네트워크 요청이 폭증**한다. 프로덕션급 로딩 성능을 내려면 **트리 쉐이킹 / 지연 로딩(lazy loading) / 청크 스플리팅(캐싱 최적화)** 으로 묶는 게 맞다.

그래서 Vite도 프로덕션 빌드는 Rollup으로 제대로 번들링한다.

### Vite 시작하기

개발 의존성은 정말 최소다.

```json
"devDependencies": {
  "@vitejs/plugin-react": "^1.1.4",
  "vite": "^2.7.10"
}
```

아래가 가장 기본적인 `vite.config.js`.

```javascript
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()] // 끝. 설정 거의 없음
});
```

명령어도 단순하다 — `vite`로 개발 서버, `vite build`로 프로덕션 빌드.

Vite는 루트 디렉터리의 `index.html`을 엔트리로 찾아서, 거기서 root/index 모듈을 로드한다.

![project structure](https://miro.medium.com/max/604/1*shWk1GS1bxlmqFbgAMz11g.png)

- **`index.html`** — `<script type="module">` 이 포인트. 번들 파일이 아니라 ESM 엔트리를 직접 가리킨다.

```html
<!DOCTYPE html>
<html>
<head></head>
<body>
  <div id="root"></div>
  <script type="module" src="./index.jsx"></script>
</body>
</html>
```

- **`index.jsx`**

```jsx
import React from 'react';
import ReactDOM from 'react-dom';
import App from './src/app';

ReactDOM.render(
  <React.StrictMode>
    <App />
  </React.StrictMode>,
  document.querySelector('#root')
);
```

- **`src/app.jsx`**

```jsx
import React from 'react';

const App = () => {
  return <>
    <div>Hello There</div>
    <div>Time right now: {new Date().toTimeString()}</div>
  </>;
};

export default App;
```

번들링을 안 하니 서버는 **1초도 안 돼서** 뜬다.

![dev server starts in milliseconds](https://miro.medium.com/max/938/1*iaxVFIg0QToJZkxAIJozlQ.png)

브라우저 네트워크 탭 보면 `app.jsx`가 **네이티브 ES 모듈로** 로드된 게 보인다.

![app.jsx loaded as native ES module](https://miro.medium.com/max/1400/1*Dy6_4_nzpYujyj4019HOgw.png)

### 핫 모듈 리플레이스먼트 (HMR)

개발자는 코드 바꾸면 바로 보고 싶다. 전체 다시 번들링하고 페이지 풀 리로드(상태·흐름 다 날아감) 끝날 때까지 못 기다린다. 그래서 번들러들이 HMR을 지원하는 거다 — **나머지 페이지 안 건드리고 바뀐 모듈만 "핫 교체"**.

근데 웹팩 같은 번들러는 프로젝트가 커질수록 HMR 시간도 같이 길어진다. 이게 생산성을 갉아먹는다.

Vite는 **네이티브 ESM 기반 HMR**이라 여기서 우위에 선다. 파일이 바뀌면 Vite는 **바뀐 모듈과 가장 가까운 HMR 경계(보통 그 모듈 자신) 사이 연결만 정확히 무효화**하면 된다. 그래서 앱이 아무리 커져도 **HMR 속도가 일정하게 빠르다.**

거기에 HTTP 헤더로 풀 리로드도 가속한다.

| 요청 대상 | 캐싱 방식 | 효과 |
|---|---|---|
| 소스 코드 모듈 | `304 Not Modified` 조건부 요청 | 안 바뀐 건 다시 안 받음 |
| 외부 의존성 모듈 | `Cache-Control: max-age=31536000` (강력 캐시) | 한 번 캐싱되면 서버에 다시 요청 안 함 |

### 서버 사이드 렌더링

Vite는 빌드를 범용 앱(SSR)으로도 쓸 수 있게 미리 설정돼 있다. HTML을 미리 렌더링할 수 있어서 **크롤러가 JS 실행 없이도 콘텐츠를 긁어갈 수 있다.** 자세한 건 [Vite SSR 가이드][vite-ssr].

### 그래서 웹팩 버리고 Vite로 갈아타야 하나?

처음 질문으로 돌아왔다. 위 장점들 보면 앞으로 Vite 쓰는 건 꽤 괜찮아 보인다. 근데 한 가지 원칙을 기억해야 한다.

> 추상화와 의견이 많이 들어간 더 간단한 API는, 정작 세밀하게 설정하긴 어려운 경우가 많다.

즉,

- ❌ 웹팩에서 **아주 디테일한 롱테일 설정**을 빡세게 쓰고 있다 → 지금 당장 Vite 전환은 별로다. (그 추상화가 오히려 발목 잡는다)
- ✅ 웹팩 **기본 설정 위주**로 쓰고 있다 → 더 나은 DX 위해 Vite 가는 게 좋다.
- ✅ **새 프로젝트 시작** → 고민할 것 없이 Vite.

### 📌 정리
`Vite = 개발 중엔 번들링을 "안 해서" 빠르다 — 네이티브 ESM + esbuild`

#### 핵심
> 기존 번들러(웹팩)는 **서버를 켜기 전에 전부 번들링**해서 규모가 커질수록 시작·HMR이 느려진다. Vite는 발상을 뒤집어 ① 자주 안 바뀌는 **의존성은 esbuild로 미리 번들링(10~100배 빠름)**, ② 내 소스 코드는 **네이티브 ESM 그대로 브라우저에 넘겨** 요청 온 모듈만 변환한다. 그래서 서버가 1초 안에 뜨고 HMR이 앱 크기와 무관하게 일정하게 빠르다. 단 이건 **개발 경험(DX) 한정** 이야기고, 프로덕션은 여전히 Rollup으로 트리쉐이킹·청크스플리팅해서 번들링한다.

#### ⭐️ 앞으로 기억할 것
- 1. **"번들 vs 언번들"이 핵심 차이**
  웹팩 = 시작 전 전체 번들링(bundle-based). Vite = 번들 없이 서버부터 띄우고 요청 시 변환(native ESM). 그래서 시작 속도가 앱 규모에 안 묶인다.
- 2. **의존성은 esbuild로 pre-bundle**
  `node_modules` 같은 안 바뀌는 코드는 Go로 짠 esbuild가 미리 묶음 → JS 번들러보다 10~100배 빠름. CommonJS를 ESM으로 변환 + 요청 수 줄이는 역할도 겸함.
- 3. **HMR이 앱 크기와 무관하게 빠른 이유**
  바뀐 모듈 ↔ 가장 가까운 HMR 경계 사이 연결만 무효화하면 끝. 전체를 다시 안 묶음.
- 4. **HTTP 캐싱까지 활용**
  소스 모듈은 `304`, 의존성은 `Cache-Control: max-age=31536000` 강력 캐시.
- 5. **"개발은 ESM, 프로덕션은 번들"인 이유**
  구형 브라우저 대응 + 번들 안 하면 모듈마다 네트워크 요청 폭증. 그래서 프로덕션은 Rollup으로 트리쉐이킹/lazy load/chunk split.
- 6. **전환 판단 기준**
  웹팩 롱테일 설정 빡센 곳은 보류, 기본 설정·신규 프로젝트는 Vite. "간단한 API는 세밀 설정이 어렵다"는 트레이드오프를 기억.

📌 결론
▎ 웹팩이 느렸던 근본 원인은 "서버 켜기 전에 다 번들링한다"는 구조였다.
▎ Vite는 의존성=esbuild pre-bundle, 소스=네이티브 ESM으로 그 번들링 단계를 개발 중엔 통째로 생략한다.
▎ 단 이건 DX 최적화지 프로덕션 번들 최적화가 아니다 — 프로덕션은 여전히 Rollup.
▎ ⭐️ 실무 적용 포인트
▎ - 새 프로젝트 / CRA 졸업 → 고민 없이 Vite.
▎ - 기존 웹팩 프로젝트가 기본 설정 위주면 → 전환 이득(특히 개발 서버·HMR).
▎ - 웹팩 커스텀 로더/플러그인 빡세게 박아둔 레거시 → 마이그레이션 비용 먼저 계산하고 보류.
