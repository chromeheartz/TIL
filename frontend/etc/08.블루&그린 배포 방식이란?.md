# [AWS] 블루/그린(Blue/Green) 배포 방식이란?

서버를 운영하다 보면 결국 마주치는 게 "배포할 때 서비스 안 끊기게 하는 법"이다. 처음엔 그냥 서버 내려서 새 코드 올리고 다시 켜면 되는 줄 알았는데, 그 짧은 다운타임 동안 들어오는 요청은 전부 에러가 난다. 사용자 입장에서는 "서비스 죽었네" 하는 순간인 거다. 그래서 등장하는 게 **무중단 배포(Zero-downtime Deployment)** 고, 그중 대표적인 방식이 블루/그린이다. 솔직히 이름만 들으면 뭔 색깔 얘기인가 싶은데, 알고 보면 개념은 단순하다.

### 무중단 배포가 왜 필요한가

기존 서버가 v1.0.1로 돌아가는 중에 v1.0.2를 올려야 한다고 해보자. 가장 순진한 방법:

```
1. 서버 끈다
2. 새 코드 배포한다
3. 서버 켠다
```

❌ 이 사이에 들어온 요청은 전부 실패한다. 빌드/부팅에 30초만 걸려도 그 30초는 장애다.

✅ 무중단 배포의 핵심 아이디어는 **"새 버전을 띄워놓고, 준비가 다 됐을 때 트래픽만 옮긴다"** 는 것. 사용자는 언제 배포가 일어났는지도 모르게 넘어간다.

---

### 블루/그린 배포란?

이름 그대로 **두 개의 동일한 운영 환경**을 두는 방식이다.

| 그룹 | 의미 |
|------|------|
| **Blue** | 현재 운영 중인(라이브) 환경 — 실사용자 트래픽을 받고 있음 |
| **Green** | 새 버전을 배포해 둔 대기 환경 — 검증용 |

배포는 Green에다 새 버전을 올리고, 검증이 끝나면 로드밸런서가 가리키는 대상을 Blue → Green으로 **한 번에 스위칭**하는 식으로 진행된다. 문제가 생기면? 로드밸런서를 다시 Blue로 돌리면 끝. 이게 블루/그린의 가장 큰 매력인 **즉시 롤백**이다.

#### 서버 단위 배포 프로세스

1. **Blue 그룹(v1.0.1)** — 서버 2대로 요청을 정상 처리 중
   ![blue group](https://user-images.githubusercontent.com/45676906/114496127-43001280-9c5a-11eb-9342-36891c636bcb.jpeg)

2. **Green 그룹 생성** — Blue와 **동일한 인스턴스 수**로 v1.0.2를 배포
   ![create green](https://user-images.githubusercontent.com/45676906/114496156-4f846b00-9c5a-11eb-9df0-99c9e9c2777a.jpeg)

3. **로드밸런서에 Green 연결** — 잠깐 Blue/Green 둘 다 트래픽을 받는 구간 (검증 타이밍)
   ![attach green](https://user-images.githubusercontent.com/45676906/114496301-9b371480-9c5a-11eb-8a83-e1cc0cf2066d.jpeg)

4. **Blue 그룹 종료** — Green만 요청을 처리. 배포 완료
   ![terminate blue](https://user-images.githubusercontent.com/45676906/114496353-b73ab600-9c5a-11eb-9de2-a0eb8266d4c6.jpeg)

여기서 포인트는 **인스턴스 수가 배포 도중에도 줄지 않는다**는 것. Blue 2대가 살아있는 채로 Green 2대를 띄우니까, 전환 순간에도 처리 용량이 그대로 유지된다.

---

### 블루/그린의 장점

- **구버전·신버전 동시 운영 시간 최소화** — 트래픽 스위칭이 순간적으로 일어나서, 두 버전이 함께 떠 있는 애매한 구간이 짧다.
- **빠른 롤백** — 새 버전에 문제 발견 시, 아직 살아있는(혹은 방금 내린) Blue로 즉시 되돌릴 수 있다.
- **안정적인 처리량** — 배포 중에도 인스턴스 수가 감소하지 않아서 요청 처리 능력에 구멍이 안 생긴다.

❌ 단점도 솔직히 있다: 배포 순간 **서버를 2배로 띄워야** 하니 그만큼 비용이 든다. (Green 환경 띄우는 동안 Blue도 살아있으니까.)

### 📌 AWS Auto Scaling으로 실제 굴리기

이론은 위와 같고, AWS에서 실무로 할 땐 **AMI + 시작 템플릿(Launch Template) + Auto Scaling Group(ASG)** 조합으로 돌린다. 단계는 이렇다.

📌 **1단계: AMI 만들기**
배포할 최신 소스코드가 들어있는 EC2 인스턴스로 **AMI(Amazon Machine Image)** 를 만든다.
> AMI = "이 시점의 서버 상태를 그대로 떠놓은 스냅샷". 이걸로 새 인스턴스를 찍어내면 매번 동일한 환경이 보장된다.

원문에서도 AMI 제작용 EC2 한 대를 따로 두는 패턴을 소개한다. 평소엔 꺼둔(stopped) 상태로 있다가, 소스코드 업데이트가 생기면 그때 켜서 새 이미지를 굽는 식이다.

📌 **2단계: 새 시작 템플릿 생성**
> "새로운 시작 템플릿에 새로운 버전의 AMI를 넣고 만들어야 합니다."

새 버전이 나올 때마다 **새 AMI → 새 시작 템플릿**을 만든다. 시작 템플릿은 "Auto Scaling이 인스턴스를 새로 띄울 때 어떤 AMI/인스턴스 타입/보안그룹으로 띄울지" 정의해 둔 설계도다.

📌 **3단계: 새 ASG(Green) 띄우기**
새 시작 템플릿을 적용한 Auto Scaling Group을 Blue와 **동일한 인스턴스 수**로 생성한다.
   ![asg green](https://user-images.githubusercontent.com/45676906/114496500-0e408b00-9c5b-11eb-8c99-2ad1446aa1ad.jpeg)

📌 **4단계: 로드밸런서(타깃 그룹)에 Green 연결 후 검증**
Green을 로드밸런서에 붙여서 Blue/Green이 같이 트래픽을 받게 한 뒤, 새 버전이 정상인지 확인한다.
   ![attach lb](https://user-images.githubusercontent.com/45676906/114496670-7000f500-9c5b-11eb-998d-253d74e943c7.jpeg)
   ![verify](https://user-images.githubusercontent.com/45676906/114496777-a3dc1a80-9c5b-11eb-8404-920ece10a168.jpeg)

📌 **5단계: Blue 제외**
검증이 끝나면 기존 Blue 그룹을 로드밸런서에서 빼고 종료. 이제 Green이 라이브가 된다.
   ![remove blue](https://user-images.githubusercontent.com/45676906/114496974-0b926580-9c5c-11eb-89d4-0e3d7cc1c18b.jpeg)

> AWS는 이걸 **CodeDeploy**로 자동화할 수 있다. 배포 그룹을 Blue/Green 타입으로 설정하면 위 단계(새 ASG 생성 → 트래픽 재라우팅 → 기존 인스턴스 종료)를 알아서 처리해준다. 손으로 ASG 만들고 LB 붙이는 건 개념 이해용이고, 실무는 CodeDeploy를 많이 쓴다.

### 다른 무중단 배포 방식과 비교 (내가 더 붙인 파트)

블루/그린만 알면 반쪽이다. 면접이나 실무에서 "왜 롤링 말고 블루/그린?" 같은 질문이 나오기 때문에 세 가지를 같이 정리한다.

#### 1) 롤링(Rolling) 배포
서버를 **한 대씩(또는 일부씩) 순차적으로** 새 버전으로 교체한다.

```
[v1][v1][v1][v1]   ← 시작
[v2][v1][v1][v1]   ← 1대씩 교체
[v2][v2][v1][v1]
[v2][v2][v2][v2]   ← 완료
```

- ✅ 추가 서버가 거의 필요 없어 **비용 효율적**
- ❌ 교체 중엔 v1·v2가 **섞여서** 돌아간다 (호환성 문제 주의)
- ❌ 교체되는 동안 처리 가능한 인스턴스 수가 잠깐 줄어든다
- ❌ 롤백이 느리다 (다시 하나씩 되돌려야 함)

#### 2) 블루/그린(Blue/Green) 배포
위에서 본 방식. 환경을 통째로 복제해 트래픽을 한 번에 스위칭.

- ✅ **즉시 롤백**, 버전 혼재 없음, 처리량 유지
- ❌ 순간적으로 인프라 **2배 비용**

#### 3) 카나리(Canary) 배포
새 버전에 **소량의 트래픽(예: 5%)만** 먼저 흘려보내 반응을 본 뒤, 문제없으면 점진적으로 비율을 올린다. (광부들이 유독가스 탐지에 카나리아를 쓰던 데서 유래한 이름이다.)

```
v2에 5% → 모니터링 OK → 25% → 50% → 100%
```

- ✅ **실사용자 일부**로 실전 검증 → 리스크 최소화, A/B 테스트도 가능
- ❌ 모니터링·트래픽 분배 설정이 복잡, 전환이 느림

| 방식 | 추가 비용 | 롤백 속도 | 버전 혼재 | 리스크 |
|------|-----------|-----------|-----------|--------|
| 롤링 | 낮음 | 느림 | 있음 | 중 |
| 블루/그린 | 높음(2배) | **즉시** | 없음 | 낮음 |
| 카나리 | 중 | 빠름 | 있음(소량) | **가장 낮음** |

---

### 📌 정리
`블루/그린 = 환경 통째로 복제 후 트래픽 스위칭, 즉시 롤백이 핵심`

#### 핵심
> 무중단 배포는 "새 버전을 미리 띄워놓고 트래픽만 옮긴다"가 본질이다.
> 블루/그린은 운영 환경(Blue)과 동일한 새 환경(Green)을 띄워, 검증 후 로드밸런서를 한 번에 Green으로 전환하고 Blue를 내린다.
> AWS에서는 **AMI → 시작 템플릿 → Auto Scaling Group → 로드밸런서 재연결** 흐름으로 구현하며, CodeDeploy로 자동화한다.
> 가장 큰 장점은 **즉시 롤백**과 **버전 혼재 없음**, 단점은 **2배의 인프라 비용**이다.

#### ⭐️ 앞으로 기억할 것
- 1. **블루/그린의 본질은 "환경 복제 + 스위칭"**
  Blue는 현재 라이브, Green은 새 버전 대기. 로드밸런서 타깃을 바꾸는 순간이 곧 배포다.
  ```
  LB → Blue(v1)   // 배포 전
  LB → Green(v2)  // 스위칭 후, Blue는 종료(또는 롤백 대비 잠시 유지)
  ```

- 2. **AMI는 "서버 상태 스냅샷"**
  새 버전마다 새 AMI를 굽고, 그 AMI를 담은 새 시작 템플릿으로 Green ASG를 띄운다. 이래야 매 배포가 동일한 환경에서 재현된다.

- 3. **배포 중에도 처리 용량이 안 줄어든다**
  Blue가 살아있는 채로 Green을 띄우기 때문. 그래서 트래픽 많은 서비스에 유리하다. 대신 그 순간 비용은 2배.

- 4. **롤링 vs 블루/그린 vs 카나리 구분**
  - 비용 아껴야 → **롤링** (단, 버전 혼재·느린 롤백 감수)
  - 빠른 롤백·깔끔한 전환 → **블루/그린**
  - 실사용자로 리스크 최소화 → **카나리**

- 5. **블루/그린에서 주의할 것: DB 마이그레이션**
  Blue와 Green이 보통 **같은 DB**를 본다. v2에서 스키마를 바꾸면 아직 살아있는 Blue(v1)가 깨질 수 있다. 그래서 DB 변경은 양쪽 버전이 모두 동작하도록 **하위 호환되게(backward-compatible)** 단계적으로 해야 한다. (컬럼 삭제 대신 "추가 → 코드 전환 → 나중에 제거" 식)

📌 결론
▎ 무중단 배포의 핵심은 "트래픽을 옮기는 시점을 내가 통제한다"는 것.
▎ 블루/그린은 환경을 통째로 복제해 한 번에 전환 → 즉시 롤백이 가능한 게 최대 강점.
▎ AWS에선 AMI·시작 템플릿·Auto Scaling·로드밸런서(또는 CodeDeploy)로 구현한다.
▎ ⭐️ 실무 적용 포인트
  - 트래픽 큰 서비스 + 빠른 롤백이 중요하면 블루/그린이 1순위 후보.
  - 단, **인프라 2배 비용**과 **DB 하위 호환**은 반드시 같이 설계할 것.
  - 비용이 빠듯하면 롤링, 신중한 검증이 필요하면 카나리로 선택지를 넓혀라.
