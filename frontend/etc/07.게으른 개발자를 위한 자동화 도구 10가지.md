# 게으른 개발자를 위한 자동화 도구 10가지

> **원문**: [10 Automation Tools Every Lazy Developer Should Use](https://javascript.plainenglish.io/10-automation-tools-every-lazy-developer-should-use-f0e9a734c755) — Ram Milan (JavaScript in Plain English)
> **번역 출처**: [게으른 개발자가 꼭 써야 할 10가지 도구](https://siosio3103.medium.com/%EA%B2%8C%EC%9C%BC%EB%A5%B8-%EA%B0%9C%EB%B0%9C%EC%9E%90%EA%B0%80-%EA%BC%AD-%EC%8D%A8%EC%95%BC-%ED%95%A0-10%EA%B0%80%EC%A7%80-%EB%8F%84%EA%B5%AC-afce720a78ae) — 조영제

"두 번 짜증 나면 자동화하고, 20초 넘게 걸리면 스크립트로 만들고, 반복되면 손으로 하길 거부한다." 이 문장 하나 때문에 읽었다. 개발자는 게으른 게 아니라 효율적인 거라는 얘기인데, 솔직히 나도 매일 아침 터미널 탭 네 개를 손으로 여는 사람이라 뜨끔했다. 10개 중 몇 개는 이미 쓰고 있고 몇 개는 처음 들었다. 목록 자체보다 "어디서 마찰이 생기는가"를 기준으로 도구를 고른다는 관점이 남는다.

### 1. Taskfile — 프로젝트 공통 명령어 모음

![Taskfile](https://miro.medium.com/v2/resize:fit:1400/0*hb7itrDfo3pg3WV0.png)

Makefile의 현대적 대체품. YAML로 작업을 정의하고 `task dev` 한 줄로 실행한다.

```yaml
# Taskfile.yml
tasks:
  build:
    cmds:
      - npm run build
  dev:
    cmds:
      - npm run dev
```

긴 명령어를 복붙할 필요도, 복잡한 스크립트를 기억할 필요도 없다. Go, Node, Python, Docker 어디서나 같은 방식으로 동작하니 멀티 언어 레포에서 특히 좋다. `package.json`의 scripts로 충분한 프로젝트면 굳이 안 써도 되지만, 프런트·백엔드·인프라 명령이 섞이기 시작하면 하나로 모을 곳이 필요하다.

### 2. Watchman — 파일이 바뀌면 명령 실행

![Watchman](https://miro.medium.com/v2/resize:fit:1400/0*mnxUWmGc_xf40Gdl.png)

페이스북이 대규모 파일 변경 감시용으로 만든 도구.

```bash
# *.js 저장할 때마다 테스트 실행
watchman-make -p '*.js' --run 'npm test'
```

테스트를 수동으로 돌리지 않고, 빌드 실행을 잊지 않는다. 다만 요즘 프런트엔드는 Vite HMR이나 `vitest --watch`가 이미 이 역할을 하니까, 나한테 Watchman이 필요한 건 빌드 도구 밖의 파일들(예: 스키마 파일 바뀌면 코드젠 실행)이다.

### 3. tmux — 터미널 세션 자동 구성

![tmux](https://miro.medium.com/v2/resize:fit:1400/0*9-yIbtPc-f6m04B-.png)

탭 여러 개, 화면 분할, 세션 분리 후 재개. 저자의 구성은 이렇다.

| 탭 | 용도 |
|---|---|
| 1 | 백엔드 |
| 2 | 프런트엔드 |
| 3 | 로그 |
| 4 | 데이터베이스 |

`.tmux.conf`로 이 구성을 자동 로드하면 매일 아침 터미널을 손으로 열 일이 없다. 세션이 살아 있으니 SSH가 끊겨도 작업이 유지되는 게 진짜 장점이다.

### 4. Renovate — 의존성 업데이트 PR 자동 생성

![Renovate](https://miro.medium.com/v2/resize:fit:1400/0*yaleljZQUkackEWR.png)

`package.json`, `requirements.txt`, Dockerfile, GitHub Actions 버전까지 보고 자동으로 PR을 만든다. "Update lodash from 4.17.19 → 4.17.21" 같은 식. 직접 관리하지 않아도 안전한 최신 버전이 유지된다. Dependabot과 비슷한데 그룹핑·스케줄 설정이 훨씬 세밀하다.

### 5. pre-commit — 커밋 전 검사 자동화

커밋 전에 린트, 포맷팅, 시크릿 탐지, 타입 체크, 유닛 테스트를 돌린다.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/psf/black
    rev: 23.9b0
    hooks:
      - id: black
```

역자는 lefthook도 추천했다. JS 프로젝트면 나도 lefthook이나 husky + lint-staged 쪽이 더 자연스럽다. 도구가 뭐든 핵심은 **Git에 들어가기 전에 자동으로 걸러진다**는 것.

### 6. GitHub Actions — CI/CD

테스트, 빌드, 배포, 코드 품질 검사, 크론잡 전부.

```yaml
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - run: npm test
```

직접 테스트하고 빌드할 필요 없이 클라우드가 대신 한다. 이건 이미 안 쓰는 팀이 드물 테니 설명 생략.

### 7. Ansible — 인프라 설정 자동화

![Ansible](https://miro.medium.com/v2/resize:fit:1400/0*SK2wsbwc3m2kCaow.png)

서버를 관리한다면 "한 번 설정하고 잊어버리는" 도구.

```yaml
- hosts: server
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
```

서버에 직접 로그인할 필요도, 설정 파일을 손으로 만질 필요도 없고 실수도 막아준다. 프런트엔드 개발자한텐 거리가 있지만, 셀프호스팅 배포 서버 하나라도 있으면 값어치를 한다.

### 8. Zoxide — 학습하는 cd

`cd`의 개선판. 자주 가는 디렉터리를 학습해서 부분 이름만으로 이동한다.

```bash
z projects
z repo-name
```

긴 경로를 입력하지도, 폴더 이름을 정확히 기억하지도 않아도 된다. 이건 설치 5분에 매일 체감되는 종류의 도구다.

### 9. Cron + Bash — 자동화의 원조

![Cron](https://miro.medium.com/v2/resize:fit:1400/0*hxps3DRQRAulcmXZ.png)

GitHub 오픈소스는 아니지만 원조다. DB 백업, 로그 정리, API 스크립트, 이메일 알림 뭐든.

```bash
# 매일 새벽 2시 백업
0 2 * * * /home/user/backup.sh
```

자는 동안에도 돈다. 크론 표현식이 헷갈리면 [`crontab.guru`]에서 확인.

### 10. Espanso — 텍스트 확장

짧은 트리거를 긴 텍스트로 바꿔준다. `/sig`를 치면 서명이 나오고, `/uuid`를 치면 UUID가 생성되는 식.

반복 메시지, 자주 쓰는 커맨드, 보일러플레이트 코드, 이메일 답변 템플릿, 버그 리포트 템플릿에 쓴다. 에디터 스니펫과 다른 점은 **모든 앱에서** 동작한다는 것.

### 결론: 게으른 개발자가 효율적인 개발자다

생산성 높은 엔지니어의 비결은 더 열심히 일하는 게 아니라 **작은 마찰을 제거하는 것**이다. 반복 업무, 짜증 나는 터미널 명령, 수동 스크립트, 지루한 환경 설정, 시간 낭비하는 잡일. 워크플로우를 자동화하면 생각을 더 하고, 타이핑을 덜 하고, 빠르게 만들고, 안심하고 배포한다. 도구는 뒤에서 조용히 지루한 일을 한다.

### 📌 정리
`도구 목록이 아니라 "마찰이 두 번 생기면 자동화한다"는 기준을 가져간다`

#### 핵심
> 10개 도구는 각각 다른 마찰 지점을 없앤다. 명령어 기억(Taskfile), 저장 후 수동 실행(Watchman), 아침 터미널 세팅(tmux), 의존성 관리(Renovate), 커밋 전 검사(pre-commit), CI(Actions), 서버 설정(Ansible), 디렉터리 이동(Zoxide), 정기 작업(Cron), 반복 타이핑(Espanso). 전부 쓸 필요는 없고, 내가 하루에 몇 번씩 손으로 반복하는 게 뭔지부터 세어보는 게 먼저다.

#### ⭐️ 앞으로 기억할 것
- **1. 자동화 기준 세 가지**
두 번 짜증 나면 자동화, 20초 넘으면 스크립트, 반복되면 손으로 거부. 도구 선택보다 이 기준이 먼저다.

- **2. Taskfile은 멀티 언어 레포용**
JS만 있으면 `package.json` scripts로 충분. 프런트·백엔드·Docker 명령이 섞이면 그때 도입.
```yaml
tasks:
  dev:
    cmds:
      - docker compose up -d
      - npm run dev
```

- **3. 커밋 훅은 도구보다 존재 여부**
pre-commit, lefthook, husky 뭐든 상관없다. 린트·포맷·타입 체크가 커밋 전에 자동으로 도는지가 핵심.
```yaml
# lefthook.yml
pre-commit:
  commands:
    lint:
      run: npx eslint {staged_files}
```

- **4. Zoxide는 지금 당장**
설치 5분, 매일 체감. `brew install zoxide` 후 셸 init 한 줄.
```bash
eval "$(zoxide init zsh)"
```

- **5. Renovate는 그룹핑으로 PR 홍수 방지**
기본 설정으로 켜면 PR이 수십 개 열린다. minor·patch를 묶고 주간 스케줄로.
```json
{ "extends": ["config:recommended", "group:allNonMajor"], "schedule": ["before 6am on monday"] }
```

- **6. Espanso는 에디터 밖 반복에**
코드 스니펫은 에디터가 하고, Slack·이메일·이슈 템플릿처럼 앱을 가리지 않는 반복 텍스트는 Espanso.

> **📌 결론**
> ▎ 개발자는 게으른 게 아니라 효율적이다. 마찰을 제거하는 사람이 빠른 사람이다.
> ▎ 10개 도구는 각각 다른 마찰을 없앤다. 전부 쓰는 게 아니라 내 반복 작업에 맞는 걸 고른다.
> ▎ 도구 이름보다 "커밋 전 검사가 자동인가", "아침 세팅이 자동인가" 같은 질문이 남는다.
> ▎ ⭐️ 실무 적용 포인트 — 이번 주에 손으로 세 번 이상 한 작업을 하나 적고 그것부터 자동화한다. 나는 아침 터미널 세팅(tmux)과 디렉터리 이동(Zoxide)부터. 커밋 훅이 없는 프로젝트가 있으면 lefthook 하나 추가하는 게 가장 투자 대비 효과가 크다.
