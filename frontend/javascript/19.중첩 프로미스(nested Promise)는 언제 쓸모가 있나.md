# 중첩 프로미스(nested Promise)는 언제 쓸모가 있나

> 원문: [Uses for nested promises](https://blog.jcoglan.com/2026/03/23/uses-for-nested-promises/) — James Coglan

`Promise.then()`은 콜백이 일반 값을 반환하든 프로미스를 반환하든 알아서 "평탄화(flatten)"해준다. 그래서 우리는 `Promise<Promise<T>>` 같은 중첩 프로미스를 거의 만날 일이 없다. 이 글은 "그 자동 평탄화가 함수형 프로그래머들에겐 왜 골칫거리였는가"라는 옛날 JS 역사에서 출발해서, **저자가 동시성 제어 코드를 짜다 진짜로 중첩 프로미스가 필요해진 케이스**를 보여준다. 평소엔 안 보이던 개념인데 readers-writer lock 예제가 너무 깔끔해서 끝까지 읽게 됐다.

### 발단: Promises/A+ 스펙의 옛 논쟁

프로미스가 막 나왔을 때, 함수형 배경을 가진 사람들이 [모나드와 카테고리 이론을 도입하자](https://github.com/promises-aplus/promises-spec/issues/94)고 요청했다. 격렬한 논쟁이 벌어졌고, 저자는 역사적으로 스펙 저자(반대) 편이었다. 근데 최근 반대편이 맞았을 케이스를 만나서 입장을 재평가하게 됐다는 것.

### functor와 monad, 그리고 map vs flatMap

Haskell의 두 핵심 추상화:
- **functor** = `fmap`을 구현하는 컨테이너. `Functor<A>` + `(A -> B)` → `Functor<B>`. JS의 `Array.map()`이 예시.
  ```javascript
  ['category', 'theory'].map((word) => word.length)
  // -> [8, 6]
  ```
- **monad** = `>>=`("bind")를 구현. `Monad<A>` + `(A -> Monad<B>)` → `Monad<B>`. JS의 `Array.flatMap()`이 예시.
  ```javascript
  ['incorporate monads', 'and category theory'].flatMap((str) => str.split(' '))
  // -> ['incorporate', 'monads', 'and', 'category', 'theory']
  ```

핵심 차이 — 같은 함수를 `map`에 넘기면:
```javascript
['incorporate monads', 'and category theory'].map((str) => str.split(' '))
// -> [['incorporate', 'monads'], ['and', 'category', 'theory']]  // 중첩됨!
```
**`map`은 컨테이너를 중첩시키고(`Array<Array<String>>`), `flatMap`은 한 겹 평탄화한다.** 이게 functor `fmap`과 monad `>>=`의 결정적 차이.

### `then()`의 문제: functor도 monad도 아니다

함수형 진영의 불만: **`Promise.then()`은 이 둘을 동시에 한다.** 넘긴 함수가 일반 값을 반환하든 `Promise`를 반환하든 결과가 같다 — `then()`은 **임의 깊이의 중첩 프로미스를 평탄화**한다.

만약 `then()` 대신 `Promise.map()`/`Promise.flatMap()`이 따로 있었다면:
```javascript
// Promise<String> -> Promise<Number>  (값 반환이라 map)
pstr.map((str) => str.length)

// Promise<URL> -> Promise<Response>  (fetch가 Promise 반환이라 flatMap)
purl.flatMap((url) => fetch(url))

// 여기서 map을 쓰면 중첩됨
// Promise<URL> -> Promise<Promise<Response>>
let ppresp = purl.map((url) => fetch(url))
// 값 꺼내려면 두 겹 벗겨야 함
ppresp.map((presp) => presp.map((resp) => /* ... */))
```

**스펙 저자들의 입장:** 중첩 프로미스는 쓸 데가 거의 없다. 프로미스로 하고 싶은 건 결국 "안의 값 꺼내기"뿐. 중첩 Array는 유용한 자료구조지만, 중첩 프로미스는 "값 얻는 데 비동기 작업이 몇 번 필요했나"만 보존할 뿐 안 유용하다. 게다가 `map`/`flatMap` 구분은 API를 복잡하게 만들고(하나는 에러 케이스, 하나는 무의미). 그래서 `then()`이 다 암묵적으로 평탄화하는 게 압도적으로 편하다.

> 함수형 입장에서 `then()`이 문제인 이유: `A -> B`도 받고 `A -> Promise<B>`도 받고, 암묵적 평탄화로 무한 중첩 프로미스 반환 함수도 개념적으로 받는다. **타입이 잘 정의되지 않아서** functor로도 monad로도 신뢰성 있게 다룰 수 없고, 함수 합성 패턴이 깨진다. Haskell 같은 정적 타입 시스템에선 골칫거리(wart).

결국 함수형 진영이 논쟁에서 졌고 암묵적 평탄화가 채택됐다. **근데 만약 안 그랬다면? 중첩 프로미스를 만들 수 있게 둘 만한 진짜 유스케이스가 있을까?** 저자도 거의 필요 없었는데, 최근 동시성 제어 코드를 짜다 만났다.

### 진짜 유스케이스: Readers-Writer Lock

저자가 만드는 [EscoDB](https://github.com/escodb/core)(암호화 문서 저장소, 패스워드 매니저 백엔드용)는 동시성 패턴을 많이 써서 [readers-writer lock](https://en.wikipedia.org/wiki/Readers%E2%80%93writer_lock)이 필요했다.

**`Mutex`** 는 async 함수를 하나씩 순차 실행하지만, **`RWLock`** 은 **여러 reader가 동시에 OR 단일 writer만** 실행시킨다. 아무도 값을 수정 안 하면 누구나 읽을 수 있고, 한 명이라도 수정 중이면 나머지는 대기.

```javascript
// 전부 reader → 동시 실행
rwlock.read(logger('A')); rwlock.read(logger('B')); rwlock.read(logger('C'));
//  A start / B start / C start / A end / B end / C end

// 전부 writer → 순차 실행
rwlock.write(logger('A')); rwlock.write(logger('B')); rwlock.write(logger('C'));
//  A start / A end / B start / B end / C start / C end

// 섞이면 → reader 동시 실행, writer는 모든 reader 끝날 때까지 대기
rwlock.read(logger('A')); rwlock.read(logger('B')); rwlock.write(logger('C'));
//  A start / B start / A end / B end / C start / C end
```

`RWLock`은 동시 실행 개수 제한이 있는 `Queue` 위에 간단히 구현한다.
- `push(fn)`: `limit` 이하로만 동시 실행하며 `fn`을 실행, `fn()` 결과의 `Promise` 반환
- `onEmpty()`: 큐가 비어있으면 이미 resolve된, 아니면 다음에 비는 순간 resolve되는 `Promise` 반환

```javascript
class RWLock {
  constructor () {
    this._inbox = new Queue({ limit: 1 })
    this._read  = new Queue()
    this._write = new Queue({ limit: 1 })
  }

  read (fn)  { return this._exec(fn, this._read, this._write) }
  write (fn) { return this._exec(fn, this._write, this._read) }

  async _exec (fn, runner, blocker) {
    let { promise } = await this._inbox.push(async () => {
      await blocker.onEmpty()
      return { promise: runner.push(fn) }   // ← 일부러 중첩!
    })
    return promise
  }
}
```

`read()`는 `_write` 큐가 빌 때까지 기다렸다 `_read` 큐에 push, `write()`는 그 반대. **`_exec()`이 중첩 프로미스를 쓰는 건 그 값이 유용해서가 아니라, JS 실행 모델에서 올바르게 동작시키려면 필요해서다.** 왜 필요한지 보려면 잘못된 구현들과 비교해야 한다.

### 왜 일부러 `{ promise: ... }`로 감쌌나

`_inbox`는 limit 1 큐라 함수를 하나씩 실행한다. 제출된 각 `fn`은 `_inbox` 안에서 `onEmpty()` 호출을 실행 — 즉 **한 번에 하나의 `onEmpty()` 요청만 활성화.**

여기서 묘한 부분: `_inbox.push()`는 `Promise<{ promise: Promise<T> }>`를 반환한다. 만약 `{ promise: ... }` 래퍼를 제거하면 자동 평탄화 때문에 그냥 `Promise<T>`가 된다:

```javascript
// ❌ 평탄화돼서 mutex처럼 동작 (잘못됨)
async _exec (fn, runner, blocker) {
  return await this._inbox.push(async () => {
    await blocker.onEmpty()
    return runner.push(fn)
  })
}
```

이러면 limit-1인 `_inbox`가 **`runner.push(fn)`이 resolve될 때까지(즉 `fn()`이 끝날 때까지)** 다음 함수를 처리 안 한다. reader A를 제출하면 `_read`가 실행, 그 사이 reader B를 제출해도 `_inbox`가 막혀서 B를 `_read`에 못 넣는다(안전한데도). → **결국 mutex와 같은 완전 순차 실행이 돼버림.**

```
A start / A end / B start / B end / C start / C end  // 동시 읽기 능력 상실 = 잘못됨
```

> **그래서 프로미스를 명시적으로 중첩하면**, `fn`을 큐에 넣되 그 결과에 `_inbox`가 블록되지 않게 할 수 있다. **하나의 프로미스가 다른 프로미스의 결과를 기다리지 않게 하는 방법.** Array의 `map`이 내부 배열을 이어붙이지 않듯, 프로미스 중첩은 한 함수를 다른 함수 뒤에 강제로 줄세우지 않게 해준다 — **공간이 아니라 "시간 상의 concatenation"을 피하는 것.**

### 그럼 `_inbox`(mutex)는 왜 필요한가

`_inbox`를 빼면 같은 일을 하는 것처럼 보인다:
```javascript
// ❌ _inbox 제거
async _exec (fn, runner, blocker) {
  await blocker.onEmpty()
  return runner.push(fn)
}
```
근데 reader/writer 섞이면 틀린다:
```
rwlock.read(A); rwlock.read(B); rwlock.write(C);
//  A start / B start / C start / A end / B end / C end  // C가 A,B 끝나기 전에 시작됨!
```

이유: **`then()`/`await`으로 프로미스 내용에 접근하면 JS는 항상 다음 문장 전에 비동기 [microtask](https://jakearchibald.com/2015/tasks-microtasks-queues-and-schedules/) 지연을 넣는다.** 절대 다음 문장을 동기로 실행하지 않는다. 그래서 모든 `read()`/`write()` 호출이 `await blocker.onEmpty()` 후 지연을 겪고, **그 사이 전부 `blocker` 큐를 "비었다"고 보고** `fn`을 즉시 실행해버린다.

따라서 **"blocker가 비었나 확인 + runner에 fn push" 사이를 감싸는 mutex가 필요**하다. 다른 호출자가 큐 상태를 확인하기 전에 `fn`이 적절한 큐에 들어가도록. 그 mutex가 `_inbox`다. **단, `_inbox`가 `fn` 실행 자체엔 블록되면 안 된다**(블록되면 동시 읽기 상실) → 그래서 중첩 프로미스로 "어느 큐에 언제 넣을지 결정"만 보호하고, 실행은 기다리지 않게 한 것.

### 📌 정리
`중첩 프로미스 = "내부 함수를 호출하되 그 완료를 기다리지 않음"의 표현`

#### 핵심
> `Promise.then()`은 값이든 프로미스든 자동 평탄화해서 중첩 프로미스를 거의 못 만들게 한다(편의성 때문에 스펙이 그렇게 정함). 평탄화 = **"시간 상의 concatenation"(한 작업을 다른 작업 뒤에 줄세움)** 이고, 이게 보통 우리가 원하는 것. 근데 **동시성 제어**(RWLock처럼 뭘 병렬로/순차로 돌릴지 직접 조율)에선, "fn을 큐에 넣되 그 실행 완료엔 블록되지 않기"가 필요하고, 이때 **명시적 중첩 프로미스(`{ promise: ... }`로 한 겹 더 감싸기)** 가 "한 프로미스가 다른 프로미스를 기다리지 않게" 만드는 도구가 된다.

#### ⭐️ 앞으로 기억할 것
- 1. **`then()`은 functor(map)도 monad(flatMap)도 아니다**
  값(`A -> B`)도 프로미스(`A -> Promise<B>`)도 받고 임의 깊이를 평탄화. 편하지만 타입이 안 잡혀 정적 타입/함수합성엔 골칫거리.
  ```text
  map     → 컨테이너 중첩 유지 (Array<Array<T>>)
  flatMap → 한 겹 평탄화
  then    → 둘 다 + 무한 평탄화
  ```
- 2. **프로미스 평탄화 = "시간 상의 concatenation"**
  한 비동기 작업을 다른 작업 뒤에 강제로 줄세우는 것. 보통은 이게 원하는 동작.
- 3. **중첩 프로미스 = "호출하되 완료를 안 기다림"**
  `return { promise: runner.push(fn) }`처럼 한 겹 더 감싸면, 바깥 프로미스가 안쪽 `fn()` 완료에 블록되지 않는다. 동시성 조율의 핵심 트릭.
- 4. **`await`/`then`은 항상 microtask 지연을 넣는다 — 동기 실행 절대 안 함**
  ```javascript
  await blocker.onEmpty()   // 여기서 무조건 비동기 틈이 생김
  runner.push(fn)           // 그 사이 다른 호출자가 끼어들 수 있음
  ```
  그래서 "확인 → 행동" 사이에 경쟁 상태(race)가 생긴다.
- 5. **"check + act"는 mutex(limit-1 큐)로 원자적으로 묶어라**
  큐 상태 확인과 push 사이를 보호. 단, mutex가 fn "실행"까지 기다리게 하면 동시성을 잃으니, 실행은 중첩 프로미스로 분리.
- 6. **RWLock 구조 기억**
  limit-1 `_inbox`(결정 보호 mutex) + 무제한 `_read` + limit-1 `_write`. read는 write가 빌 때까지, write는 read가 빌 때까지 대기.

📌 결론
▎ 평소 프로미스는 "값 꺼내기"가 전부라 자동 평탄화가 압도적으로 편하고 옳다.
▎ 하지만 동시성을 직접 오케스트레이션할 땐, 중첩 프로미스가 "내부 작업을 시작시키되 그 완료엔 매이지 않는다"는 실제로 유용한 의미를 가진다.
▎ "확인→행동" 패턴엔 microtask 지연발 race가 숨어있으니 mutex로 묶되, 실행 대기는 중첩으로 떼어내라.
▎ ⭐️ 실무 적용 포인트
▎ → 일반 코드: 중첩 프로미스 만들지 말 것(`then`이 알아서 평탄화, 그게 맞음).
▎ → 큐/락/세마포어 같은 동시성 프리미티브 직접 구현 시: "결정"과 "실행 대기"를 분리해야 할 때 의도적 중첩이 답일 수 있음.
▎ → async에서 "확인 후 행동" 로직은 항상 microtask 틈을 의심하고 임계구역을 mutex로 보호.
