# 자바스크립트 엔진은 어떻게 이런 성능을 내는가

> **출처**: https://velog.io/@sehyunny/how-js-engine-achieve-great-performance (velog @sehyunny, 황세현 번역) / 원문: https://medium.com/bekk/how-javascript-engines-achieve-great-performance-fb0b36601557

JS는 사실 최적화하기에 끔찍한 언어다. 타입 정보가 없고, 객체는 런타임 내내 속성을 붙였다 뗐다 하고, falsy 값이 6종류나 되고, 모든 숫자가 64비트 실수다. 그런데도 빠르다. "이게 어떻게 가능하지?"가 이 글의 출발점이다. V8 같은 엔진이 뒤에서 쓰는 기법들 — **핫 코드 / 히든 클래스 / 인라인 캐시 / 인라이닝** — 을 따라가 본다.

> ⚠️ 원문도 강조하듯, 정확한 동작이 아니라 **이해를 위해 단순화한 모델**이다. 디테일 일부는 생략돼 있다.

### 실행 모델 — 왜 바로 기계어로 안 바꾸나

브라우저가 JS를 받으면 최우선 목표는 **최대한 빨리 실행 시작**이다. 그래서 코드를 **바이트코드(가상 기계 명령어)** 로 바꿔서 인터프리터/가상 기계에 넘긴다.

근데 왜 *진짜* 기계어가 아니라 *가상* 기계어로 바꿀까?

| | 가상 기계 명령어(바이트코드) | 실제 기계 명령어 |
|---|---|---|
| 컴파일 난이도 | 언어와 밀접 → **컴파일 쉽고 빠름** | 일반적 명령어 집합 → 변환 작업 많음, 느림 |
| `object.x` 처리 | 가상 명령어 1~2개면 됨 (객체를 "이해"함) | `.x`의 메모리 위치 파악에 명령어 多 |
| 실행 속도 | 런타임에 **해석**해야 해서 느림 | 바로 실행 → 빠름 |

핵심은 **빠른 컴파일 vs 빠른 런타임의 트레이드오프**다.

- 대부분의 경우 → **빠른 컴파일**이 이득. 버튼 클릭 반응이 20ms든 40ms든 사용자는 신경 안 쓴다. 특히 한 번 쓰는 버튼이면 더더욱. 빨리 컴파일해서 인터랙션을 빨리 시작하게 하는 게 낫다.
- 게임·구문 하이라이팅·무거운 연산처럼 **컴퓨팅 비용 큰 경우** → 컴파일 시간 + 기계어 실행 시간을 합쳐도 총 실행 시간이 줄어든다. ← 이걸 어떻게 처리하느냐가 다음 주제.

### 핫 코드 (hot code)

엔진은 **함수가 핫(hot) 상태 = 여러 번 실행됨**을 감지하면 그 함수를 **최적화 컴파일러**에 넘긴다. 이 컴파일러는

1. 가상 기계 명령어 → **실제 기계 명령어**로 변환하고,
2. 이미 여러 번 돌아간 함수라, **이전 실행에 근거해 추측(speculation)** 한 최적화를 건다.

추측이 틀리면? 엔진은 **잘못 최적화된 함수를 폐기(deoptimize)** 하고 최적화 안 된 버전으로 되돌린다. 함수가 몇 번 더 돌면, 갱신된 추측 정보와 함께 **다시 최적화 컴파일러로** 넘긴다.

> 즉 "자주 실행되는 함수일수록, 과거 실행 정보를 근거로 추측 최적화된다." 그럼 그 "정보"가 뭐냐 → 아래로 이어진다.

### 변환의 문제점 — 기계는 "객체"를 모른다

JS는 거의 모든 게 객체인데, 기계한테 JS 객체를 가르치는 건 까다롭다.

```javascript
function addFive(obj) {
  return obj.method() + 5;
}
```

간단해 보이지만 기계는 `객체`가 뭔지 모른다. `obj`가 어떤 형태인지 JS에선 **절대 확신할 수 없다** — 어떤 객체든 `method` 속성을 붙이거나 뗄 수 있고, 있더라도 그게 함수인지, 호출하면 뭘 반환하는지 보장이 없다.

객체 개념이 없는 JS로 위 코드를 풀어 쓰면 이렇게 된다. 먼저 객체를 배열로 표현하고(`[ [속성이름들], [속성값들] ]`), 조회 함수를 만든다.

```javascript
// { method: function() {} } 객체는 이렇게 표현 가능
// [ [ "method" ], [ function() {} ] ]  // [속성 이름, 속성 값]

function lookup(obj, name) {
  for (var i = 0; i < obj[0].length; i++) {
    if (obj[0][i] === name) return i;
  }
  return -1;
}
```

`addFive`를 이걸로 풀어 쓰면(반환값 타입 체크까지 넣으면):

```javascript
function addFive(obj) {
  var propertyIndex = lookup(obj, "method");
  var property = propertyIndex < 0 ? undefined : obj[1][propertyIndex];

  if (typeof(property) !== "function") {
    throw NotAFunction(obj, "method");
  }
  var callResult = property(/* this */ obj);

  if (typeof(callResult) === "string") {
    return stringConcat(callResult, "5");
  } else if (typeof(callResult) !== "number") {
    throw NotANumber(callResult);
  }
  return callResult + 5;
}
```

동작은 한다. 근데 이게 매번 이 모든 분기를 탄다. **미리 `obj` 구조랑 `method` 타입을 알면** 몇 단계를 건너뛰고 훨씬 빨라질 수 있다. ← 그래서 히든 클래스가 등장한다.

### 히든 클래스 (hidden classes)

모든 주요 엔진은 **객체의 "형태(shape)"를 추적**한다. 크롬에선 이걸 **히든 클래스**라고 부른다.

```javascript
var obj = {};  // 빈 객체
obj.x = 1;     // `x` 속성이 생기며 형태 변경
obj.toString = function() { return "TODO"; }; // 형태 변경
delete obj.x;  // 형태 또 변경
```

객체 형태가 바뀔 때마다 **새 히든 클래스로 전이**한다. 위를 배열 모델로 풀면, 형태가 바뀔 때마다 `obj[0]`(히든 클래스 포인터)이 갈아 끼워진다.

```javascript
var emptyObj__Class = [ null, [], [] ];  // 부모없음, 속성이름[], 속성타입[]
var obj = [ emptyObj__Class, [] ];       // [히든클래스, 속성값들]

var obj_X__Class = [
  emptyObj__Class, // 빈 객체에서 파생 (부모 = 이전 형태)
  ["x"],           // `x` 속성 추가
  ["number"]       // x는 number
];
obj[0] = obj_X__Class; // 형태 변경
obj[1].push(1);        // x의 값

var obj_X_ToString__Class = [ obj_X__Class, ["toString"], ["function"] ];
obj[0] = obj_X_ToString__Class;
obj[1].push(function() { return "TODO"; });

// delete 하면 처음부터 다시 시작 (부모 null)
var obj_ToString__Class = [ null, ["toString"], ["function"] ];
obj[0] = obj_ToString__Class;
obj[1] = [obj[1][1]];
```

이제 객체 형태를 추적할 수단은 생겼다. 근데 히든 클래스만으론 부족하다 — **이 정보를 의미 있는 곳에 저장**해야 한다. ← 인라인 캐시.

### 인라인 캐시 (inline caches)

JS 코드가 객체 속성에 접근할 때마다, 엔진은 **그 객체의 히든 클래스 + 조회 결과(속성이름→인덱스 매핑)** 를 캐시에 저장한다. 이게 **인라인 캐시(IC)** 이고, 두 가지 일을 한다.

- 바이트코드 실행 시, **객체의 히든 클래스가 캐시에 있으면 속성 접근이 빨라진다.** (lookup 루프 건너뜀)
- 속성 접근에 관여한 **타입 정보를 최적화에 제공** → 최적화 컴파일러가 그 타입에 딱 맞는 코드를 생성하게 돕는다.

IC가 저장하는 히든 클래스 개수에는 **제한**이 있다. (메모리 절약 + 캐시 조회를 빠르게 유지하기 위함. IC 조회가 히든 클래스 직접 조회보다 느리면 캐시가 무의미하니까.)

- 크롬 기준 IC는 히든 클래스를 **최대 4개**까지 추적.
- 그 이상이면 IC가 **비활성화**되고 전역 캐시로 넘어감. 전역 캐시도 크기 제한이 있어 꽉 차면 옛 항목을 덮어씀.

> ⭐️ **그래서 함수는 "단일 타입(단형/monomorphic) 객체"만 받도록 짜는 게 좋다.** 한 함수가 4종류 넘는 형태의 객체를 받으면(polymorphic/megamorphic) IC가 깨지고 최적화가 안 먹는다.

### 인라이닝 (inlining)

별개지만 중요한 최적화. **함수 호출을 그 함수의 구현으로 치환**한다.

```javascript
function map(fn, list) {
  var newList = [];
  for (var i = 0; i < list.length; i++) newList.push(fn(list[i]));
  return newList;
}
function incrementNumbers(list) {
  return map(function(n) { return n + 1; }, list);
}
incrementNumbers([1, 2, 3]); // [2, 3, 4]
```

`map`을 `incrementNumbers`에 인라이닝하면:

```javascript
function incrementNumbers(list) {
  var newList = [];
  var fn = function(n) { return n + 1; };
  for (var i = 0; i < list.length; i++) newList.push(fn(list[i]));
  return newList;
}
```

함수 호출이 사라졌고, 더 큰 이득은 **엔진이 함수 내부 사정을 더 많이 알게 됐다**는 것. 그래서 `fn`도 또 인라이닝:

```javascript
function incrementNumbers(list) {
  var newList = [];
  for (var i = 0; i < list.length; i++) newList.push(list[i] + 1);
  return newList;
}
```

이제 옵티마이저는 "`incrementNumbers`는 숫자 배열만 받는다"고 추측 가능. 심지어 호출부 `[1,2,3]`까지 인라이닝하고 `list.length === 3`을 알아채면:

```javascript
var list = [1, 2, 3];
var newList = [];
newList.push(list[0] + 1);
newList.push(list[1] + 1);
newList.push(list[2] + 1);
list = newList;
```

> 요약: **인라이닝은 함수 경계를 넘어서는 못 하던 최적화를 가능하게 한다.**

단, 제약이 있다.

- 코드 복사라 **함수 크기가 커진다** → 엔진은 "여기까지 커지면 인라이닝 안 함"이라는 **예산(budget)** 을 둔다.
- **인수로 전달된 함수 호출은 인라이닝이 어렵다.** 특히 **매번 같은 함수가 아니면** 더 어렵다. (역설적으로 인라이닝 자체 때문에 그렇게 될 수도)

### 📌 정리
`JS가 빠른 이유 = 핫 코드 추측 최적화 + 히든클래스/인라인캐시로 객체 형태를 추적 + 인라이닝`

#### 핵심
> JS는 타입도 없고 객체 형태가 런타임에 계속 바뀌어서 최적화하기 끔찍한 언어다. 엔진은 ① 일단 **바이트코드로 빨리 컴파일**해 인터랙션을 빠르게 시작시키고, ② **자주 실행되는 핫 함수**만 골라 **과거 실행 정보로 추측 최적화**해 실제 기계어로 변환한다(틀리면 deopt 후 복구). 그 "정보"의 정체는 **히든 클래스(객체 형태)** 인데, 속성 접근 시 형태→인덱스 매핑을 **인라인 캐시**에 저장해 lookup 루프를 건너뛰고 타입 맞춤 코드를 생성한다. 단 IC는 형태를 **최대 4개**만 추적하므로, 함수가 한 종류 형태(monomorphic)만 받게 짜야 최적화가 유지된다. 거기에 **인라이닝**으로 함수 경계를 허물어 추가 최적화를 푼다.

#### ⭐️ 앞으로 기억할 것
- 1. **컴파일 vs 런타임 트레이드오프**
  대부분은 "빨리 컴파일해서 빨리 시작"이 이득. 무거운 연산만 기계어 최적화로 총시간을 줄인다.
- 2. **핫 코드 = 추측 최적화 대상**
  여러 번 돈 함수만 최적화 컴파일러로. 추측 틀리면 deoptimize 후 비최적화 버전으로 폴백.
- 3. **히든 클래스 = 객체의 형태(shape)**
  속성 추가/삭제마다 새 히든 클래스로 전이. 그래서 **객체 형태를 일관되게 유지**(생성자에서 모든 속성 초기화, 나중에 속성 추가/delete 지양)하면 형태 전이가 줄어 유리.
- 4. **인라인 캐시는 형태 4개 한도(monomorphic이 최고)**
  한 함수에 여러 형태 객체가 들어오면 polymorphic/megamorphic → IC 깨지고 느려짐. ⭐ **함수는 단일 타입만 받게.**
- 5. **인라이닝은 함수 경계를 허문다**
  호출 제거 + 내부 정보 노출로 연쇄 최적화. 단 크기 예산 한도 안에서만, 그리고 **인수로 넘긴 함수(특히 매번 다른 함수)는 인라이닝 어려움.**

📌 결론
▎ JS가 빠른 건 언어가 잘 설계돼서가 아니라, 엔진이 핫 코드를 추측 최적화하고 객체 형태를 히든클래스/인라인캐시로 집요하게 추적하기 때문이다.
▎ 이 최적화는 "객체 형태가 일관되다 / 함수가 단일 타입을 받는다"는 전제 위에서만 잘 먹는다.
▎ ⭐️ 실무 적용 포인트
▎ - 객체는 **생성 시점에 모든 속성을 정해 형태를 고정**하라. 나중에 속성 추가·`delete`는 형태 전이를 유발해 최적화를 깬다.
▎ - 핫 패스 함수에는 **한 가지 형태의 객체만** 흘려보내라(monomorphic 유지). 배열도 원소 타입을 섞지 말 것.
▎ - 고차함수(map/filter 콜백)는 **매번 같은 함수 참조**를 넘기면 인라이닝 기회가 늘어난다.
▎ - "빠르게 만들기" 전에 **무엇이 핫 패스인지 프로파일링으로 먼저 식별**(원문 다음 편 주제이기도 함).
