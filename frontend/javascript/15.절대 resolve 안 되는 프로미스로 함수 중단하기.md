# 절대 resolve 안 되는 프로미스로 함수 중단하기

> 원문: [Hanging Promises for Control Flow](https://www.inngest.com/blog/hanging-promises-for-control-flow) — Inngest

**JS 프로미스는 취소할 수 없다.** `.cancel()`도 없고 `AbortController` 통합도 없다. TC39가 2016년에 [취소 기능을 검토](https://github.com/tc39/proposal-cancelable-promises)했지만 격론 끝에 철회됐다(실행 중인 코드를 중간에 취소하면 리소스가 더러운 상태로 남을 수 있어 협조적 cleanup이 필요한데, 그게 `.cancel()`의 단순함을 해친다).

근데 더 괴상한 걸 할 수 있다 — **절대 resolve 안 되는 프로미스를 반환하고 `await`한 뒤, 정지된 함수를 GC가 치우게 둔다.** 예외도, `try/catch`도, 특별한 반환값도 없다. 함수가 그냥 멈춘다. Inngest TS SDK가 async 워크플로 함수를 중단시키는 방식인데, 기법 자체가 범용적이고 그 뒤의 JS 시맨틱이 알아둘 가치가 있다.

### 왜 함수를 중단시키고 싶은가

가끔 **남의 async 함수를, 그 코드가 특별한 짓을 하지 않아도, 정확한 지점에서 멈춰야** 할 때가 있다. 함수 작성자는 평범한 `async`/`await`를 쓰고, 런타임이 언제·어디서 끊을지 결정한다.

구체적 케이스: **서버리스 인프라에서 워크플로 함수 실행 — 각 호출에 하드 타임아웃이 있음.** 워크플로는 수십 단계로 끝까지 몇 시간이 걸리지만, 한 번의 호출은 수 초~수 분만 돌 수 있다. 런타임(여기선 SDK)이 함수를 중단하고, 진행 상황을 저장하고, 나중에 재호출해 멈춘 데서 이어가야 한다 — 유저 코드는 그게 일어난 줄도 모르게. **그러려면 `await`를 throw 없이 중단해야 한다.**

### 시도 1 — 에러로 중단 (실패)

가장 뻔한 방법: 예외 throw.

```ts
class InterruptError extends Error {}

async function run(callback) {
  const result = await callback();
  // 결과 저장 후 중단
  throw new InterruptError();
}

async function myWorkflow() {
  const data = await run(() => fetchData());
  // run()이 throw하면 여기 도달 안 함
  await run(() => processData(data));
}
```

누군가 `try/catch`로 감싸기 전까지는 동작한다:

```ts
async function myWorkflow() {
  let data;
  try {
    data = await run(() => fetchData());
  } catch {
    console.log("Failed to fetch data, using default");
    data = defaultData;
  }
  // 중단하고 싶었는데도 여기가 실행됨 — catch가 InterruptError를 삼켰으니까
  await run(() => processData(data));
}
```

개발자는 그냥 fetch 실패 시 fallback을 원했을 뿐인데, `run`이 throw로 중단하니 **`catch`가 중단 신호까지 삼킨다.** 모든 유저 코드의 모든 `try/catch`가 내 제어 흐름을 조용히 깨뜨리는 잠재적 함정이 된다.

### 시도 2 — 제너레이터 (되지만 불편)

제너레이터는 중단을 위해 *태어났다.* `yield`마다 멈추고, 호출자가 재개 여부를 통제한다. 중단하려면 그냥 `.next()`를 안 부르면 된다.

```ts
function* myWorkflow() {
  let data;
  try {
    data = yield run(async () => fetchData());
  } catch {
    data = defaultData;
  }
  yield run(async () => processData(data));
}

const gen = myWorkflow();
const first = gen.next();   // 첫 yield까지 실행
// 중단: gen.next()를 다시 안 부름. catch도 안 돌고, 제너레이터가 yield에서 얼어붙음.
```

예외도, 삼켜진 중단도 없다. `yield`가 설계상 실행을 호출자에게 돌려주니 완전한 통제권을 가진다. (실제로 `async`/`await` 이전엔 제너레이터가 async 코드를 쓰는 표준 방식이었다 — `co` 같은 라이브러리가 yield된 프로미스를 resolve해 `.next(value)`로 다시 먹였다. ES2017이 그 패턴을 전용 문법으로 공식화하면서 **호출자의 재개 통제권을 맞바꿨다.**)

문제는 두 가지:
- **ergonomics.** 유저가 `async function` 대신 `function*`, `await` 대신 `yield`를 써야 함. 대다수 JS 개발자에겐 낯선 문법.
- **동시성에서 깨진다.** `await`는 `Promise.all`로 병렬이 자연스럽지만, `yield`는 정의상 순차다. 여러 값을 동시에 yield 못 함. 프로미스 배열을 yield하고 러너가 그걸 감지해 `Promise.all`하게 만들어야 하는데 → 언어 내장 동시성 프리미티브 대신 **자체 컨벤션을 발명**하게 되고 유저가 그걸 배워야 함.

> 그래서 질문: 유저가 평범한 `async`/`await`를 쓰게 두면서 제너레이터식 중단을 얻을 수 있나?

### 핵심 트릭 — 절대 resolve 안 되는 프로미스

throw 대신, **resolve 안 되는 프로미스를 반환**한다.

```ts
const start = Date.now();
process.on("exit", () => {
  const elapsed = Math.round((Date.now() - start) / 1000);
  console.log(`Exited after ${elapsed}s`);
});

async function interrupt() {
  return new Promise(() => {});   // 영원히 hang
}

async function main() {
  console.log("Before interrupt");
  await interrupt();
  console.log("After interrupt");   // 도달 불가
}
main();
```

출력:
```
Before interrupt
Exited after 0s
```

`After interrupt`는 안 찍힌다. 중단에 도달하면 **에러 없이 깔끔하게 종료.** 많은 사람이 "프로미스가 resolve 안 되니 영원히 hang하겠지"라고 예상하지만 아니다.

**왜 종료되나? 프로미스 단독으로는 Node 이벤트 루프를 살려두지 못한다.** 이벤트 루프는 active handle(타이머·소켓·I/O watcher)이 있을 때만 돈다. **미해결 프로미스는 그냥 메모리 속 객체일 뿐.** 기다릴 게 없으면 Node는 빈 이벤트 루프를 보고 종료한다.

진짜로 hang하는 게 맞는지(종료가 빨라서 resolve 기회가 없던 게 아니라) 증명하려면 타이머로 루프를 살려두면:
```ts
async function main() {
  setTimeout(() => {}, 2000);
  console.log("Before interrupt");
  await interrupt();
  console.log("After interrupt");   // 여전히 도달 불가
}
// → Before interrupt / Exited after 2s  (타이머가 2초 살려둠)
```

### 조립하기 — 단계별 실행 (메모이제이션)

깔끔한 종료만으론 안 쓸모 있다. 우리가 원하는 건 **함수를 여러 번 호출하되 각 단계 후 중단하고, 다음 호출에서 멈춘 데를 이어가기.** = 메모이제이션(이미 실행된 단계는 다시 안 돌리고 저장된 결과 반환).

유저가 쓰는 워크플로 함수 (Inngest SDK의 단순화 버전):
```ts
async function myWorkflow(step) {
  console.log("  Workflow: top");
  const data = await step.run("fetch", () => {
    console.log("  Step: fetch");
    return [1, 2, 3];
  });
  const processed = await step.run("process", () => {
    console.log("  Step: process");
    return data.map((n) => n * 2);
  });
  console.log("  Workflow: complete", processed);
}
```

런타임은 `myWorkflow`를 반복 호출하며 호출당 새 단계 하나씩 실행:
```
Run 0:  Workflow: top / Step: fetch
Run 1:  Workflow: top / Step: process
Run 2:  Workflow: top / Workflow: complete [2,4,6]
```
- `Workflow: top`이 3번 찍힘 → **매 호출마다 함수가 맨 위에서 재실행됨.**
- 각 `Step` 로그는 정확히 한 번 → 메모이즈된 단계는 즉시 반환, 새 단계만 실제 실행.

`execute` 구현 = ① 다음 새 `step.run` 찾기 ② 실행 ③ 결과 메모이즈 ④ 중단 ⑤ 끝날 때까지 반복:

```ts
async function execute(fn, stepState) {
  let newStep = null;

  // 유저 함수를 백그라운드에서 실행. 새 단계에서 hang함
  fn({
    run: async (id, callback) => {
      // 이미 실행된 단계면 메모이즈 결과 반환
      if (stepState.has(id)) {
        return stepState.get(id);
      }
      // 새 단계: 기록
      newStep = { id, callback };
      // 영원히 hang
      return new Promise(() => {});
    },
  });

  // 매크로태스크 예약. 메모이즈 단계의 resolve된 await(마이크로태스크)들이
  // 먼저 다 drain되어, 워크플로 함수가 완료된 단계들을 통과해 다음 새 단계에 도달할 시간을 줌.
  await new Promise((r) => setTimeout(r, 0));

  if (newStep) {
    const result = await newStep.callback();
    stepState.set(newStep.id, result);
    return false;   // 아직 안 끝남
  }
  return true;      // 끝남
}
```

**왜 `setTimeout(0)`?** 새 단계를 찾았는지 확인하기 전에, 함수가 메모이즈된 단계들을 다 통과해야 한다. `step.run`이 메모이즈 결과를 반환하면 그 `await`는 **마이크로태스크**로 resolve된다. 마이크로태스크는 매크로태스크보다 먼저 도니, 함수는 완료된 단계들을 마이크로태스크 체인으로 쭉 전진한다. 그 체인은 **새 단계(hang 프로미스는 아무것도 큐에 안 넣음)** 에 도달하거나 함수가 끝나면 멈춘다. `setTimeout`으로 매크로태스크를 예약하면 그 마이크로태스크들이 전부 먼저 drain되는 게 보장된다. (실제 SDK는 더 똑똑한 방식. 이벤트 루프 이해엔 Philip Roberts의 [What the heck is the event loop anyway?](https://www.youtube.com/watch?v=8aGhZQkoFbQ) 강추.)

### "근데 이거 메모리 누수 아냐?"

영원히 hang하는 프로미스를 계속 만드는데 누수 아닌가? **아무것도 참조하지 않으면 아니다.**

**JS GC는 프로미스가 settle됐는지 신경 안 쓴다. 무언가 그걸 *참조*하는지를 본다.** 프로미스를 만들고 함수 안에서 `await`한 뒤, 그 함수의 콜스택 전체가 도달 불가(unreachable)가 되면, GC가 전부 치운다 — 프로미스, 함수의 정지 상태까지 싹.

`FinalizationRegistry`(객체가 GC될 때 콜백 발화)로 증명:
```ts
const registry = new FinalizationRegistry((value) => {
  console.log("  GC", value);
});

async function myWorkflow(step) {
  const fetchP = step.run("fetch", () => { ...; return [1,2,3]; });
  registry.register(fetchP, "fetch");
  const data = await fetchP;
  const processP = step.run("process", () => { ...; return data.map(n => n*2); });
  registry.register(processP, "process");
  const processed = await processP;
}
// main() 끝에 globalThis.gc();  (--expose-gc 플래그로 실행)
```
출력 끝에:
```
  GC process / GC fetch / GC fetch / GC fetch / GC process
```
`GC fetch` 3번, `GC process` 2번 — 매 재호출마다 메모이즈 단계도 새 프로미스를 만들기 때문(`step.run`이 async라 매번 새 프로미스 반환). **영원히 hang한 것들 포함 5개 프로미스 전부 수거된다.**

### 함정 (The catch)

- **GC는 비결정적이다.** 정지된 함수가 *언제* 수거될지는 모른다. 우리 케이스엔 "수거된다는 것"만 알면 충분하고, 모던 엔진은 이걸 신뢰성 있게 한다.
- **진짜 위험은 참조 체인.** 무엇이든 hang 프로미스나 정지 함수의 클로저를 참조하면 GC가 못 건든다. **모든 참조를 의도적으로 끊어야만** 동작한다.

### 📌 정리
`throw도 generator도 아닌, "기다릴 게 없는 프로미스"로 async 함수를 멈춘다`

#### 핵심
> JS 프로미스는 취소 불가. async 함수를 유저 코드 수정 없이 정확한 지점에서 중단하려면 — ① **throw**는 유저의 `try/catch`가 삼켜서 깨지고 ② **generator**는 통제는 좋지만 `function*`/`yield` 문법 강요 + 동시성에서 깨진다. ③ **절대 resolve 안 되는 프로미스(`new Promise(() => {})`)를 반환**하면, 평범한 `async`/`await`를 유지하면서 함수를 그 자리에 멈출 수 있다. 미해결 프로미스는 이벤트 루프를 살려두지 않아 깔끔히 종료되고, 참조만 끊기면 정지된 함수째로 GC가 수거하므로 누수도 없다. 서버리스에서 워크플로를 단계별로 중단·메모이즈·재개하는 데 쓰인다.

#### ⭐️ 앞으로 기억할 것
- 1. **throw로 제어 흐름을 만들지 마라**
  유저의 `try/catch`가 네 InterruptError를 삼킨다. 모든 catch가 잠재적 함정.
- 2. **`new Promise(() => {})` = 영원히 hang하는 프로미스**
  `await`하면 그 지점에서 함수가 멈춤. 예외 없이 그냥 정지.
- 3. **미해결 프로미스는 이벤트 루프를 살려두지 않는다**
  active handle(타이머/소켓/IO)만 루프를 유지. 그래서 hang 프로미스만 있으면 Node는 깔끔히 종료(hang 안 함).
  ```ts
  await new Promise(() => {});  // 여기서 멈추지만, 다른 handle 없으면 프로세스는 exit
  ```
- 4. **GC는 settle 여부가 아니라 "참조 여부"로 수거한다**
  콜스택이 unreachable해지면 프로미스 + 정지 함수 상태까지 전부 수거. → 누수 아님.
- 5. **단, 참조 체인이 남으면 누수**
  hang 프로미스나 정지 함수 클로저를 누가 잡고 있으면 GC 못 함. 의도적으로 모든 참조 끊기.
- 6. **마이크로태스크 vs 매크로태스크로 "전진 후 확인" 타이밍 제어**
  메모이즈된 `await`는 마이크로태스크로 줄줄이 resolve → `setTimeout(0)`(매크로태스크)로 그게 다 drain된 뒤 새 단계를 확인.
- 7. **단계별 재개 = 맨 위 재실행 + 메모이제이션**
  매 호출마다 함수를 top부터 다시 돌리되, 완료된 단계는 저장값 즉시 반환, 새 단계 하나만 실제 실행 후 hang.

📌 결론
▎ 세 방법 비교: throw(async 유지하나 try/catch가 깨뜨림) / generator(통제 좋으나 문법·동시성 희생) / hang 프로미스(둘 다 — 네이티브 문법 + 신뢰성 있는 중단).
▎ "함수를 멈추는 가장 좋은 방법은 기다릴 것을 아무것도 주지 않는 것"이다.
▎ 핵심 시맨틱 3개: 미해결 프로미스 ≠ 이벤트 루프 유지 / GC는 참조 기반 / 마이크로·매크로태스크 순서.
▎ ⭐️ 실무 적용 포인트
▎ → 워크플로/스텝 러너, 서버리스 재개 로직 같은 런타임을 직접 만들 때의 강력한 패턴.
▎ → 단, 비결정적 GC라 "언제 수거"에 의존하지 말고 "수거된다"에만 의존. 참조 누수 철저히 점검.
▎ → 이벤트 루프/마이크로태스크 이해가 전제 — 헷갈리면 Philip Roberts 강의부터.
