# 자바스크립트에 타입 구문 도입 제안 (Types as Comments)

> **원문**: https://devblogs.microsoft.com/typescript/a-proposal-for-type-syntax-in-javascript/ (TypeScript 팀, Microsoft)
> **번역 출처**: https://velog.io/@eunbinn/A-Proposal-For-Type-Syntax-in-JavaScript

"빌드 없이 그냥 `.ts`를 바로 돌릴 순 없나?"라는 생각, 다들 한 번쯤 했을 거다. TypeScript 팀이 TC39에 낸 이 제안이 정확히 그 방향이다 — **JS 엔진은 타입 구문을 "주석처럼" 무시**하고, TS/Flow 같은 도구만 그 타입을 활용한다. 즉 타입 컴파일 단계를 없애는 게 목표. 개념이 흥미로워서 정리해둔다.

![thumbnail](https://velog.velcdn.com/images/eunbinn/post/f4206e0a-0670-43ad-bf46-947e24838aea/1_pc_OMTTFg9s0n_S2dqxudg.png)

### 제안 배경

JS 생태계는 점점 **반복 주기 단축 + 빌드 단계 단순화** 쪽으로 간다.
- 에버그린 브라우저 덕에 신버전 JS를 구버전으로 트랜스파일할 필요가 줄었다.
- 대부분 브라우저가 네이티브 모듈을 지원해서, 번들링은 이제 필수가 아니라 최적화 수단.

TypeScript가 나온 2012년은 달랐다. 브라우저 업데이트가 들쭉날쭉, IE 지원 불확실 → 번들러·컴파일러가 표준이었다. "어차피 JS를 컴파일하는데, 타입도 같이 컴파일하지 뭐"가 자연스러웠고 그래서 TS가 흥했다.

근데 지금 추세대로면 **타입 컴파일이 TS의 유일한 빌드 단계**로 남게 된다. 팀의 말: "우리는 좋은 개발 경험의 걸림돌이 되고 싶지 않다."

#### 지금의 우회책: JSDoc

TS는 JSDoc 주석으로 이 간극을 일부 메운다.

```javascript
/**
 * @param a {number}
 * @param b {number}
 */
function add(a, b) {
  return a + b;
}
```

주석이라 실행에 영향 없고, TS가 이걸로 자동완성·리팩토링을 제공한다. 파일 맨 위 `// @ts-check`나 `checkJs` 옵션이면 빌드 없이 타입 체크도 된다 — 작은 스크립트·간단한 페이지·Node 코드엔 충분.

하지만 보일러플레이트가 너무 많다. 그래서 제안: **TS 같은 구문을 JS가 그냥 무시하는 주석처럼 쓰면 어떨까?**

```javascript
function add(a: number, b: number) {
  return a + b;
}
```

이걸 TC39(ECMAScript 표준 위원회)에 제출했다.

### 어떻게 동작할까

그동안 "JS 타입"에 대한 의견은 갈렸다 — 런타임에서 완전히 무시하자 vs 의미를 갖게 하자(런타임 검증, 엔진 최적화 힌트). 최근 몇 년 사이 의견은 **TS 방향(런타임에서 완전히 무시·삭제 가능)** 으로 수렴했다.

#### 핵심 아이디어

JS는 **엔진이 완전히 무시하는** 타입 구문을 갖되, TS·Flow 같은 도구가 그걸 활용한다. 타입 체크의 이점은 유지하면서 빌드 단계는 제거.

**실행 방식 변화**: 기존(TS → 컴파일 → JS → 실행) → 제안(타입 구문 있는 JS를 바로 실행).

![실행 워크플로우](https://devblogs.microsoft.com/typescript/wp-content/uploads/sites/11/2022/03/tac-announcement-today-proposed.svg)

**타입 체크는 그대로**: 에디터 즉시 피드백, CLI로 TS 실행, CI 통합 다 유지. 차이는 "빌드 단계 제거"뿐.

![타입 체크 동작](https://devblogs.microsoft.com/typescript/wp-content/uploads/sites/11/2022/03/tac-announcement-checking-behavior.svg)

#### JS가 지원해야 할 구문

- 변수·함수의 타입 애너테이션
- 매개변수·클래스 멤버의 선택적 수정자 `?`
- 타입 선언 (`interface`, `type` 별칭)
- 타입 단언 연산자 (`as`, `!`)

이것들은 주변 코드 실행에 영향을 주지 않는다.

#### 선택적 요소 / 제외 요소

- 접근 제어자(`public`/`private`/`protected`)는 포함될 수 있다.
- 반면 **enum, namespace, 매개변수 프로퍼티**는 런타임 데이터를 관찰하므로 **제외**. (피드백 따라 별도 ECMAScript 제안이 될 수도)

목표는 "JS에 넣을 수 있는 TS의 최대 실현 가능한 부분집합". 엔진은 타입 정확성과 무관하게 코드를 실행하고, 타입 체커가 더 엄격한 규칙을 적용한다(커스터마이즈/완전 제거 가능).

### 이 제안이 포함하지 않는 것

명시적으로 **하지 않는** 것:
- 모든 브라우저/JS 런타임에 TS 타입 체크를 추가
- 브라우저에 새 타입 체커 도입

이런 접근은 런타임 성능 문제, TS 호환성 문제, 타입 체크 혁신 저해 위험이 있다. 대신 **TS가 발전시키는 구문을 도입하되, 어떤 타입 체커든 쓸 수 있고 JS 엔진은 건너뛴다.**

### 다음 단계

TC39 2022년 3월 회의에 Stage 1 제안 제출 예정 (Bloomberg의 Rob Palmer, Igalia의 Romulo Cintra 지원). Stage 1 도달 = 위원회가 "ECMAScript 타입 구문이 검토할 가치 있다"고 본다는 뜻(채택 보장 X). 회의론도 예상되고, 설계 변경·수년이 걸릴 수 있다. 하지만 성공하면 JS 생태계 최대 개선 중 하나가 될 것.

### 📌 정리
`타입을 "주석처럼" — 엔진은 무시, TS/Flow만 활용, 빌드 단계 제거`

#### 핵심
> TypeScript 팀이 TC39에 낸 "Types as Comments" 제안. JS 엔진이 **타입 구문을 완전히 무시(삭제 가능)** 하게 해서, `.ts`를 컴파일 없이 바로 실행하는 게 목표. 타입 체크는 여전히 에디터/CLI/CI에서 TS·Flow가 담당한다. 애너테이션·`?`·`interface`/`type`·`as`/`!`는 포함, 런타임 동작이 있는 **enum·namespace·매개변수 프로퍼티는 제외**. 브라우저에 타입 체커를 넣는 게 아니라 "무시되는 구문"만 추가하는 것.

#### ⭐️ 앞으로 기억할 것
- 1. 핵심은 "erasable(삭제 가능) 타입"
  엔진은 타입을 주석처럼 무시. 타입 정확성과 무관하게 실행됨.
  ```javascript
  function add(a: number, b: number) { return a + b; } // 엔진은 :number 무시
  ```
- 2. 타입 체크 책임은 여전히 도구(TS/Flow)
  브라우저가 체크하는 게 아님. 빌드 단계만 사라지고 체크는 에디터/CI에 그대로.
- 3. 런타임 동작 있는 건 제외된다
  enum, namespace, 파라미터 프로퍼티는 코드를 생성/관찰하므로 빠짐. (별도 제안 가능)
- 4. JSDoc의 진화형으로 보면 됨
  지금도 `// @ts-check` + JSDoc으로 빌드 없이 타입 체크 가능. 이 제안은 그 보일러플레이트를 TS 문법으로 대체.
- 5. 아직 제안 단계(당시 Stage 1 목표)
  수년 걸리거나 무산될 수도. 개념만 이해해두기.

📌 결론
▎ "타입 컴파일이 유일한 빌드 단계로 남는" 현실에서, 그 단계마저 없애려는 시도.
▎ 브라우저에 타입 체커를 넣는 게 아니라 "무시되는 타입 구문"을 표준화하는 것 — 혁신 여지를 도구에 남김.
▎ ⭐️ 실무 적용 포인트
  - 지금 당장은 영향 없음(제안 단계). 다만 Node가 `--experimental-strip-types`로 타입 제거 실행을 지원하기 시작한 게 이 흐름의 연장선.
  - 빌드 없이 타입을 쓰고 싶다면 현재는 `// @ts-check` + JSDoc이 현실적 대안.
