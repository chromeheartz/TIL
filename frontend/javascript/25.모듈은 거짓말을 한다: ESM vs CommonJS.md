"Your X Is Lying to You" 시리즈 중 모듈 편. `import`랑 `require`를 그냥 "파일 가져오는 문법 두 가지"로 생각하고 살았는데, 실제로는 리졸브 → 인스턴스 생성 → 평가 → 노출 각 단계에서 다른 결정을 내리는 다른 시스템이다. `.default`가 왜 튀어나오는지, 순환 참조가 왜 어떤 날은 되고 어떤 날은 안 되는지 평소 대충 넘겼던 것들이 전부 여기서 설명된다. JavaScript Weekly 799호에 소개된 글.

### 같은 코드, 다른 결과

출발점은 이 작은 모듈이다.

```js
// state.mjs
export let status = 'starting'

export function start() {
  status = 'ready'
}
```

ESM에서 named import로 가져와서 `start()`를 호출하면 가져온 `status`가 바뀐다.

```js
// app.mjs
import { status, start } from './state.mjs'

start()
console.log(status) // ready
```

CommonJS로 똑같이 짜보면 겉모습은 같다.

```js
// state.cjs
module.exports.status = 'starting'

module.exports.start = function () {
  module.exports.status = 'ready'
}
```

그런데 구조 분해로 가져오면 결과가 다르다.

```js
// ❌ 구조 분해 → 현재 값 복사
const { status, start } = require('./state.cjs')
start()
console.log(status) // starting

// ✅ 객체 자체를 유지 → 공유 참조
const state = require('./state.cjs')
state.start()
console.log(state.status) // ready
```

세 결과 모두 버그가 아니라 각 모듈 시스템의 계약이다. ESM의 named import는 **익스포트하는 모듈이 소유한 바인딩**을 가리킨다. CommonJS의 `require()`는 **`module.exports`라는 값**을 돌려줄 뿐이고, 그 다음은 평범한 JS 규칙이다. 구조 분해는 프로퍼티를 읽어서 로컬 변수에 저장하는 것뿐이니 당연히 스냅샷.

참고로 이 글의 예제는 전부 Node.js 네이티브 로더 기준이다. 브라우저는 ESM만 있고, 번들러·트랜스파일러는 자기만의 인터롭 래퍼를 만들어내서 Node가 보장하지 않는 동작을 보이기도 한다. 환경마다 따로 봐야 한다.

### 바인딩, 값, 객체

#### ESM 라이브 바인딩

임포트한 이름은 **읽기 전용**이다. 익스포트하는 쪽만 값을 할당하고, 임포트하는 쪽은 관찰만 한다.

```js
import { count } from './counter.mjs'
count = 10
// TypeError: Assignment to constant variable.
```

에러 메시지에 constant라고 나오는 이유가 이거다. 익스포트하는 쪽은 `let`으로 선언했어도 임포트한 쪽에서는 상수처럼 보인다.

단, 라이브 바인딩은 **객체 불변성과는 무관**하다. `export const settings = {...}`는 `settings`에 다른 객체를 재할당하지 못하게 막을 뿐, 객체 안의 프로퍼티는 누구나 바꾼다. 그리고 라이브 바인딩은 값이 바뀌었다고 알려주지 않는다. 그 이름을 읽는 표현식이 실행될 때 현재 값을 읽을 뿐이다. 익스포트된 바인딩을 앱 상태처럼 쓰면 전역 가변 상태와 똑같은 조율 문제가 생긴다.

#### CommonJS는 그냥 값이다

`module.exports`에 뭐든 할당하고, `require()`는 그 값을 돌려준다. 객체가 흔하지만 함수, 클래스, 문자열, 프로미스도 된다.

게터를 쓰면 라이브 바인딩 비슷하게 보이게 만들 수 있다.

```js
// counter.cjs
let count = 0
module.exports = {
  get count() { return count },
  increment() { count++ }
}
```

```js
const counter = require('./counter.cjs')
const { count, increment } = counter

increment()
console.log(counter.count) // 1 — 접근할 때마다 게터 호출
console.log(count)         // 0 — 구조 분해 시점에 게터 한 번 호출한 결과
```

ESM 라이브 바인딩처럼 보이지만 그냥 객체 문법의 결과다.

#### 변경(mutation) vs 대체(replacement)

```js
// mutation — 기존 객체를 바꿈. 이미 받아간 소비자도 본다
module.exports.status = 'ready'

// replacement — 다른 값을 익스포트. 이미 받아간 소비자는 못 본다
module.exports = { status: 'ready' }
```

이게 비동기 초기화에서 특히 위험하다.

```js
// ❌ client.cjs
module.exports = { ready: false }
initializeClient().then((client) => {
  module.exports = client // 이미 require한 쪽은 영원히 { ready: false }
})
```

초기화 전에 `require`한 소비자는 첫 객체를 들고 있고, 이후 소비자는 캐시에서 `client`를 받는다. 한 프로세스에 한 모듈에서 나온 객체가 두 개 돌아다니고, 첫 번째는 절대 ready가 안 된다.

비동기 초기화는 계약에 드러나야 한다. 프로미스 자체를 익스포트하자.

```js
// ✅ client.cjs
module.exports = initializeClient()

// app.cjs
const clientPromise = require('./client.cjs')
async function run() {
  const client = await clientPromise
  return client.query('SELECT 1')
}
```

### 평가 순서와 캐싱

#### 정적 import는 "줄 위치"를 무시한다

```js
// app.mjs
console.log('app: before import')
import './setup.mjs'
console.log('app: after import')
```

출력은 `setup` → `app: before import` → `app: after import`. import 문을 파일 맨 아래로 옮겨도 똑같다. Node는 엔트리 모듈 본문을 실행하기 전에 그래프 전체를 리졸브·링크하고 의존성부터 평가한다. 흔히 "import 호이스팅"이라고 부르지만, 선언을 위로 올리는 수준이 아니라 **그래프 단위 평가**다.

사이드 이펙트 import(`import './register-hooks.mjs'`)가 이걸 잘 드러낸다. 계측 설치나 레지스트리 채우기가 목적인데, 소스 위치로는 "이 두 문장 사이에 실행"을 못 만든다.

#### require는 소스 순서대로

```js
// app.cjs
console.log('app: before require')
require('./setup.cjs')
console.log('app: after require')
// app: before require → setup → app: after require
```

`require()`는 그냥 함수 호출이라 실행 흐름이 도달했을 때 동기적으로 평가한다. 처음 한 번 평가하고 `require.cache`에 넣은 뒤, 같은 파일로 리졸브되는 호출은 캐시된 exports를 돌려준다.

#### 캐시 키는 "리졸브된 정체성"

요청 문자열 표기가 아니라 리졸브된 파일이 키다. 같은 패키지 이름이라도 다른 파일로 리졸브되면 별도 인스턴스. 중첩 의존성, 심볼릭 링크, 조건부 엔트리 포인트, ESM·CJS 이중 배포 패키지에서 이게 중요해진다.

ESM은 `require.cache`가 아닌 자체 캐시를 쓰고, 정체성은 **리졸브된 URL**이다. 그래서 쿼리를 바꾸면 같은 파일이 두 번 평가된다.

```js
import './config.mjs?mode=one'
import './config.mjs?mode=two'
// config.mjs가 두 번 평가됨 — 테스트에선 유용, 실수면 상태가 갈라짐
```

#### 동적 import()와 top-level await

`import()`는 표현식이다. 실행이 도달해야 로드되고 네임스페이스 객체의 프로미스를 돌려준다. 조건문·함수 안에서 쓸 수 있으니 선택적 기능이나 무거운 코드에 적합하고, CJS에서 ESM으로 넘어가는 비동기 다리 역할도 한다.

top-level `await`는 비동기 평가를 그래프 전체로 퍼뜨린다. `configuration.mjs`가 top-level에서 `await fetch(...)`를 하면, 그걸 정적으로 임포트하는 모든 모듈이 자기 본문 실행 전에 그 완료를 기다린다. `await`를 한 줄도 안 쓴 모듈까지 붙잡힌다.

### 순환 의존성과 부분 초기화

#### CommonJS: 만들다 만 exports를 돌려준다

```js
// a.cjs
console.log('a: starting')
exports.ready = false
const b = require('./b.cjs')
console.log('a: b.ready =', b.ready)
exports.ready = true
console.log('a: finished')

// b.cjs
console.log('b: starting')
const a = require('./a.cjs')
console.log('b: a.ready =', a.ready)
exports.ready = true
console.log('b: finished')
```

`node a.cjs` 결과: `b: a.ready = false`. `b.cjs`가 `require('./a.cjs')`를 호출한 시점에 `a.cjs`는 아직 평가 중이라 Node는 **현재 상태 그대로의 exports 객체**를 돌려준다. 만약 `a.cjs`가 `require` 뒤에서 `ready`를 할당했다면 `b`는 `undefined`를 봤을 거다. 순환 안의 코드는 시작이 끝난 뒤엔 아무도 못 보는 상태를 관찰한다.

#### ESM: 바인딩은 있는데 초기화가 안 됐다

```js
// a.mjs
import { b } from './b.mjs'
export const a = 'a'
console.log('a: b =', b)

// b.mjs
import { a } from './a.mjs'
console.log('b: a =', a) // ReferenceError: Cannot access 'a' before initialization
export const b = 'b'
```

링커가 두 모듈 본문 실행 전에 바인딩을 만들어두지만, `b.mjs`를 먼저 평가하는 시점엔 `export const a`에 아직 도달하지 못했다. TDZ(temporal dead zone)를 건드려서 그래프 평가가 멈춘다.

읽기를 미루면(`setTimeout` 안에서 읽는 식으로) 동작은 한다. 선언 종류에 따라 증상도 다르다. `let`/`const`/`class`는 TDZ 에러, `var`는 `undefined`, 함수 선언은 이미 호출 가능. 선언 방식을 바꾸면 **순환은 그대로 두고 증상만 바뀐다.**

#### 진짜 해결은 그래프를 바꾸는 것

읽기를 미루면 오늘은 되지만, 초기화 순서가 파일 여러 개에 걸쳐 묶인 상태는 그대로다. 나중에 리팩터링이 접근 시점을 조금만 앞당기면 시작 시점 실패로 변한다.

- 공유 정의·상태는 양쪽이 의존하는 **더 낮은 레벨 모듈**로 내린다
- 밀접한 책임은 **한 모듈**에 합친다
- 한쪽이 다른 쪽의 런타임 동작이 필요하면 **함수/생성자 인자로 전달**해서 초기화 단계의 연결을 끊는다

### CommonJS ↔ ESM 경계 넘기

#### ESM에서 CJS 임포트

`module.exports`의 값이 **default export**로 노출된다. 이건 믿어도 된다.

named import도 되긴 하는데, Node가 평가 전에 CJS 소스를 **정적 분석**해서 인식 가능한 프로퍼티만 named export로 만든다. 그리고 그건 네임스페이스 구성 시점의 **복사본**이다.

```js
// status.cjs
exports.status = 'starting'
setTimeout(() => { exports.status = 'ready' }, 100)

// app.mjs
import statusModule, { status } from './status.cjs'
setTimeout(() => {
  console.log(statusModule.status) // ready — 객체 참조
  console.log(status)              // starting — 스냅샷
}, 200)
```

계산된 프로퍼티 이름이나 함수 결과로 exports를 대체하는 CJS는 정적 분석으로 못 잡는다. 어떤 패키지에선 되는 named import가 다른 패키지에선 런타임에 프로퍼티가 있는데도 실패한다. 그래서 **낯선 CJS 패키지는 default import로 받고 프로퍼티를 읽는 게** 안전하다.

```js
// ✅ CJS의 실제 익스포트 모델과 일치
import packageApi from 'commonjs-package'
packageApi.doWork()
```

#### CJS에서 ESM 로드

동적 `import()`는 어디서든 된다. 결과는 **네임스페이스 객체**. named export는 같은 이름 프로퍼티, default는 `.default`.

최신 Node는 `require(esm)`도 된다. 단 역시 네임스페이스 객체를 돌려주고 default를 풀어주지 않는다.

```js
// ❌ default가 함수라고 가정
const format = require('./formatter.mjs')
format('ok') // TypeError: format is not a function

// ✅
const formatter = require('./formatter.mjs')
formatter.default('ok')
```

그리고 그래프 어딘가에 top-level `await`가 하나라도 있으면 `require()`는 에러를 던진다. 그 경우 CJS 진입점은 `import()`뿐이다. 이 동작은 Node 버전마다 달라져 와서, 오래된 Node를 지원하는 라이브러리는 `require(esm)`을 전제로 못 짠다.

#### `.default`와 `__esModule`은 왜 있나

ESM의 default export도 사실 네임스페이스 안에서 `default`라는 이름을 쓰는 named 바인딩이다. CJS는 `module.exports` 하나뿐. 둘을 변환하려면 "이 CJS 값이 네임스페이스인가, default 값인가"를 정하는 규칙이 필요하다.

트랜스파일러들은 ESM에서 생성한 CJS 출력물에 `__esModule` 마커를 붙여 왔다.

```js
// ESM 원본
export default function format(value) { return String(value) }

// 단순화한 CJS 출력
Object.defineProperty(exports, '__esModule', { value: true })
exports.default = function format(value) { return String(value) }
```

컴파일러 헬퍼가 `__esModule`을 보고 객체를 그대로 쓸지 `{ default: value }`로 감쌀지 정한다. 문제는 컴파일러·번들러마다 헬퍼가 다르다는 것. **같은 import 문이 어떤 빌드에선 함수를, 어떤 빌드에선 `.default`를 가진 객체를 받는다.** `__esModule`은 언어 기능이 아니라 도구 관례이고, CJS 프로퍼티를 라이브 바인딩으로 바꿔주지도 않는다.

인터롭 버그는 보통 **개발과 프로덕션의 로더가 다를 때** 터진다. 테스트는 전부 CJS로 트랜스파일하거나 번들 결과물로 돌고, 프로덕션 Node는 게시된 파일을 직접 로드한다. 네이티브 경계가 배포 시점까지 테스트되지 않은 채 남는다.

### 두 시스템 모두에 배포하기

#### 파일 형식 결정 규칙

| 조건 | 형식 |
|---|---|
| `.mjs` | 항상 ESM |
| `.cjs` | 항상 CommonJS |
| `.js` + 가장 가까운 `package.json`의 `"type": "module"` | ESM |
| `.js` + `"type": "commonjs"` 또는 없음 | CommonJS |

`"type"` 하나 바꾸면 그 스코프의 모든 `.js` 해석이 바뀐다. 모노레포에서 소스 파일이 빌드 후 **다른 `package.json` 아래로 복사**되면, 소스에선 되던 문법이 `dist`에서 깨진다. 게시 파일은 패키징 이후에도 모호함 없는 확장자와 메타데이터를 가져야 한다.

상대 경로 ESM import는 확장자 필수다. Node는 `.js`를 붙여주지도, `index.js`를 찾아주지도 않는다.

```js
import { format } from './format.js' // 확장자 생략하면 ESM 리졸버가 못 찾음
```

#### 조건부 exports

```json
{
  "name": "formatter",
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./colors": {
      "import": "./dist/colors.js",
      "require": "./dist/colors.cjs"
    }
  }
}
```

ESM 소비자는 `import` 조건, `require()`는 `require` 조건을 탄다. 맵에 없는 파일은 비공개. 단 이 맵은 **가용성만 설명하지 대상을 검증하지 않는다.** `require` 쪽 파일이 빠져 있거나, 두 파일이 다른 이름을 익스포트하거나, 한쪽이 `"type"` 때문에 잘못된 형식으로 해석돼도 Node는 모른다. `src/index.js`를 직접 테스트하면 이 결정 과정을 통째로 건너뛴다.

#### 이중 패키지 인스턴스 위험 (dual package hazard)

`import`와 `require` 대상이 다른 파일이면 Node는 **별개 모듈, 별개 캐시**로 취급한다. 한 프로세스가 두 경로로 패키지에 도달하면 인스턴스가 두 개.

```js
// app.mjs
import { createRequire } from 'node:module'
import { Token as ImportedToken } from 'formatter'

const require = createRequire(import.meta.url)
const { Token: RequiredToken } = require('formatter')

const token = new ImportedToken('abc')
console.log(token instanceof ImportedToken) // true
console.log(token instanceof RequiredToken) // false — 소스는 같은데 정체성이 다름
```

ESM 앱이 쓰는 의존성 중 하나만 `require()`를 써도 이 상황이 된다. 클래스 정체성뿐 아니라 레지스트리, 모듈 수준 카운터, 설정 같은 공유 상태 전부 갈라진다. 번들러는 중복 제거나 조건 하나만 선택해서 이걸 **감춰주기 때문에** 번들 앱에서 멀쩡하던 패키지가 네이티브 Node에서 갈라진다.

대응 방법:
- 상태 있는 구현은 CJS 쪽에 두고, ESM 엔트리는 그걸 re-export
- 상태를 두 래퍼 바깥으로 빼고, 상태 없는 형식별 엔트리에 전달
- 한쪽 형식만 게시하고 다른 쪽은 Node 네이티브 인터롭에 맡기기 (지원 Node 버전이 허용할 때)

#### 설치된 패키지를 테스트하기

`npm pack`으로 타르볼을 만들고, **깨끗한 소비자 프로젝트에 설치해서** 패키지 이름으로 로드한다.

```js
// smoke.mjs
import { Token } from 'formatter'
console.log(new Token('esm'))

// smoke.cjs
const { Token } = require('formatter')
console.log(new Token('commonjs'))
```

워크스페이스 링크가 아니라 타르볼이어야 한다. 패킹을 거쳐야 빠진 빌드 파일이나 소스 트리를 가리키는 엔트리 포인트가 드러난다. 문서화된 하위 경로 전부 돌리고, 두 조건의 공개 API를 서로 비교한다. `require(esm)` 지원을 내세운다면 전이 의존성에 top-level `await`가 없는지도 테스트해야 한다.

### 모듈 경계 실전 규칙

- **새 Node 앱은 ESM.** 언어 표준이고 브라우저 모델과 같다. `"type": "module"` + 레거시는 `.cjs`로 명시적 경계. 기존 CJS 앱을 문법 때문에 마이그레이션할 필요는 없다.
- **라이브러리 공개 API는 named export.** 에디터·정적 분석에 노출되고, 인터롭에서 `.default` 모호함이 줄어든다.
- **가변 export는 공유 프로세스 상태로 취급.** 호출 쪽이 연산만 필요하면 상태는 비공개로.

```js
// ✅ 쓰기는 통제, 읽기는 명시적
let enabled = false
export function enable() { enabled = true }
export function isEnabled() { return enabled }
```

- **CJS 프로퍼티가 바뀔 거면 객체를 유지.** 구조 분해는 스냅샷.
- **낯선 CJS 패키지는 default import.** 합성된 named export는 정적 감지에 기대고 갱신을 못 받는다.
- **순환은 제거.** 평가 순서에 맞춰 코드를 재배치하는 건 숨은 의존성을 남기는 것.
- **동적 `import()`는 진짜 조건적·지연 로딩에만.**
- **패키지 경계에선 형식을 전부 명시.** `"type"` + 예외는 `.mjs`/`.cjs`, 상대 경로엔 확장자, 빌드 디렉터리는 자기 `package.json` 기준으로 확인.
- **다른 export 대상 = 다른 인스턴스로 가정.** 모듈 로컬 싱글턴은 양쪽이 같은 캐시를 받는다는 전제에 기대면 안 된다.
- **소스 경로가 아니라 패키지 이름을 테스트.**

### 디버깅 체크리스트

임포트한 값이 `undefined`거나, 오래됐거나, 예상 못 한 객체로 감싸져 있거나, 프로세스 다른 곳에서 본 값과 다를 때 이 순서로.

1. **임포트하는 파일의 형식** — 확장자 + 가장 가까운 `package.json`의 `"type"`. 소스에 `import()`가 있다고 로더를 추측하지 말 것.
2. **패키지 엔트리 포인트 리졸브** — `"exports"` 맵에서 현재 로더가 고르는 조건과 그 파일이 실제로 존재하는지.
3. **반환된 형태** — ESM 네임스페이스인지, CJS exports 객체인지, 컴파일러 래퍼인지. `.default`를 보기 전에 왜 래퍼가 있는지부터.
4. **로컬 변수가 담은 것** — 라이브 바인딩인지, 공유 객체인지, 구조 분해된 복사본인지.
5. **평가가 끝났는지** — ESM 의존성 사이드 이펙트는 임포트하는 쪽보다 먼저, CJS 순환은 부분 exports, ESM 바인딩은 미초기화 가능.
6. **전체 순환 추적** — 순환을 완성하는 모듈은 여러 파일 떨어져 있을 수 있다. 초기화 중 읽기(생성·등록 코드)를 찾아본다.
7. **모듈 정체성 비교** — 같은 파일/URL로 리졸브됐는지. import/require 혼용, URL 쿼리, 중복 설치, 별도 조건부 대상이 인스턴스를 갈라놓는다.
8. **한쪽 테스트 경로에서 변환 제거** — 지원 Node 버전에서 게시 파일을 직접 실행. 테스트 러너·번들러의 래퍼가 네이티브 실패를 가린다.
9. **패킹된 패키지로 재현** — 타르볼을 깨끗한 디렉터리에 설치하고 패키지 이름으로 로드.

### 📌 정리

`import와 require는 서로 바꿔 쓰는 표기법이 아니라, 코드를 연결하는 서로 다른 방식이다.`

#### 핵심

> ESM은 평가 전에 그래프 전체를 링크하고 **바인딩**을 넘긴다. CommonJS는 `require()`에 도달했을 때 평가하고 **값**을 넘긴다. 둘 다 캐시하지만 캐시도 정체성 규칙도 다르다. 순환 참조에서 CJS는 만들다 만 exports를, ESM은 초기화 안 된 바인딩을 노출한다. 경계를 넘을 때 CJS→ESM은 default가 `module.exports`고 named는 스냅샷, ESM→CJS는 네임스페이스 객체에 `.default`. 이중 배포 패키지는 두 조건이 별개 인스턴스가 되고, 번들러가 이걸 감추니 반드시 `npm pack` 결과물을 패키지 이름으로 테스트해야 한다.

#### ⭐️ 앞으로 기억할 것

- 1. ESM named import = 바인딩, CJS require = 값
`import { x }`는 익스포트 모듈의 변수 자체를 보는 창이고 읽기 전용. `const { x } = require()`는 그 순간의 값 복사. CJS에서 변할 프로퍼티를 볼 거면 객체를 들고 있어야 한다.
```js
// ❌ 바뀔 프로퍼티를 구조 분해
const { status } = require('./service.cjs')

// ✅ 객체 유지
const service = require('./service.cjs')
console.log(service.status)
```

- 2. `module.exports = ...` 재할당은 이미 받아간 소비자에게 안 보인다
비동기 초기화 후 exports를 교체하는 패턴은 "영원히 ready 안 되는 객체"를 만든다. 프로미스를 익스포트하거나 초기화 함수를 익스포트해서 비동기를 계약에 드러내자.

- 3. 정적 import는 줄 위치를 무시한다
사이드 이펙트 import를 "이 로그 다음에 실행"시키려고 중간에 끼워 넣어봐야 소용없다. 의존성이 먼저 전부 평가된다. 순서 제어가 필요하면 `import()`.

- 4. 순환은 미루지 말고 끊는다
`setTimeout`으로 읽기를 미루거나 `import()`로 바꾸면 오늘은 되지만 타이밍 의존성은 남는다. 공유 정의는 아래 레벨 모듈로, 밀접한 책임은 한 모듈로, 런타임 의존은 함수 인자로. ESLint `import/no-cycle` 같은 걸로 테스트 단계에서 먼저 터지게.

- 5. 낯선 CJS 패키지는 default import
Node가 정적 분석으로 named export를 합성해주지만 패키지마다 되거나 안 되고, 된다 해도 스냅샷이다.
```js
// ❌ 정적 감지 휴리스틱에 의존
import { doWork } from 'commonjs-package'

// ✅ CJS 모델 그대로
import pkg from 'commonjs-package'
pkg.doWork()
```

- 6. `require(esm)`은 default를 안 풀어준다
결과는 네임스페이스 객체. `.default`로 꺼내야 하고, 그래프에 top-level `await`가 있으면 에러. 오래된 Node 지원하는 라이브러리라면 아예 전제로 삼지 말 것.

- 7. `__esModule`은 도구 관례다
같은 import가 빌드 설정에 따라 함수를 주기도, `{ default }`를 주기도 한다. 테스트가 번들러/트랜스파일러를 거치고 프로덕션은 네이티브 로더면 그 경계는 배포 전까지 테스트 안 된 거다.

- 8. `.js`의 형식은 가장 가까운 `package.json`이 정한다
빌드가 파일을 다른 스코프로 복사하면 해석이 바뀐다. `dist`에 자체 `package.json`이 있는지, 상대 경로 import에 확장자가 붙어 있는지 확인.

- 9. `"import"`와 `"require"`가 다른 파일이면 인스턴스가 둘
`instanceof`가 깨지고 싱글턴·레지스트리가 갈라진다. 번들러가 감춰주니 네이티브 Node에서만 터진다. 상태는 한쪽에 두고 re-export하거나 아예 밖으로 빼자.

- 10. 테스트는 `npm pack` → 설치 → 패키지 이름으로
`src/` 직접 import나 워크스페이스 링크는 exports 맵 리졸브를 건너뛴다. ESM 스모크 + CJS 스모크를 타르볼 설치본에 대해 돌린다.

> **📌 결론**
> ▎ ESM은 바인딩을, CommonJS는 값을 넘긴다. 구조 분해 한 줄로 결과가 갈리는 이유다.
> ▎ 정적 import는 그래프 단위로 먼저 평가되고, require는 소스 순서대로 실행된다.
> ▎ 캐시 키는 리졸브된 파일/URL. 같은 소스라도 경로가 다르면 다른 인스턴스.
> ▎ 순환 참조는 타이밍 조정이 아니라 그래프 수정으로 해결한다.
> ▎ 인터롭에서 `.default`와 `__esModule`이 보이면 "어떤 로더가 어떤 형태를 만들었나"부터 따진다.
> ▎ 이중 배포 패키지는 번들러가 감춰주는 인스턴스 분리를 네이티브 Node에서 겪는다.
> ▎ ⭐️ 실무 적용 포인트: 라이브러리 배포 전 `npm pack` + 깨끗한 디렉터리 설치 + ESM/CJS 스모크 테스트를 CI에 넣자.
> ▎ ⭐️ 실무 적용 포인트: 모듈이 이상하게 굴면 import 문법을 만지지 말고 "리졸브된 파일 → 로더 → 반환 형태 → 평가 완료 여부 → 인스턴스 정체성" 순으로 본다.
