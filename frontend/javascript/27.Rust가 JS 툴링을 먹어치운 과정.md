# Rust가 JS 툴링을 먹어치운 과정

> **원문**: [Rust Is Eating JavaScript](https://leerob.com/rust) (Lee Robinson)  
> **번역 출처**: [(번역) Rust가 자바스크립트를 잠식하고 있습니다](https://velog.io/@sehyunny/rust-is-eating-js) (sehyunny)

요즘 프로젝트 `package.json`을 열어보면 번들러도 린터도 죄다 Rust 얘기다. 대체 언제 이렇게 된 건지 궁금했는데, 마침 2021년에 쓴 예측 글에 2023년, 2026년 업데이트를 덧붙인 글이 있어서 읽었다. 5년치 흐름이 한 번에 정리돼서 좋았다.

### 왜 Rust인가

JS는 안 쓰는 메모리를 가비지 컬렉터가 알아서 치워준다. Rust는 GC 없이 `소유권(ownership)`으로 해결한다. 누가 메모리를 읽고 쓰는지 컴파일러가 추적하고, 필요 없어지는 시점에 바로 해제한다. 규칙을 컴파일 타임에 강제하니까 런타임 메모리 버그가 거의 사라진다. C++처럼 손으로 관리하는 고통은 없으면서 메모리는 세밀하게 다룰 수 있다는 게 핵심이다.

Meta, Apple, Amazon, Microsoft, Google이 시스템 인프라에 이미 쓰고 있고, Dropbox는 복잡한 불변 조건을 타입으로 인코딩해서 컴파일러한테 검증시킨다고 한다. 성능보다 이쪽이 더 큰 수확이었다는 얘기가 흥미로웠다.

### JS로 짠 도구의 한계

지난 10년 동안 프론트 빌드는 전부 JS/TS로 만든 도구 위에 쌓였다.

| 역할 | 기존 도구 | 하는 일 |
| --- | --- | --- |
| 번들링 | `webpack` | 여러 파일을 하나로 묶는다 |
| 트랜스파일 | `Babel` | 최신 문법을 구형 브라우저용으로 바꾼다 |
| 압축 | `Terser` | 파일 크기를 최대한 줄인다 |
| 포맷팅 | `Prettier` | 코드 스타일을 통일한다 |
| 린팅 | `ESLint` | 배포 전에 문제를 찾는다 |

잘 돌아갔지만 JS로 짜낼 수 있는 최적화는 한계에 왔다. 그래서 나온 게 새 세대 도구들이다.

#### SWC

2017년에 나온 Rust 기반 플랫폼이다. 컴파일, 압축, 번들링을 다루고 Next.js, Parcel, Deno가 쓴다. 직접 쓰기보다 상위 도구 안에 라이브러리처럼 들어가는 형태다.

#### Deno

Node.js 원작자가 V8과 Rust로 다시 만든 런타임이다. 2018년에 시작했고 v1.0은 2020년 5월에 나왔다. 린터, 포매터, 문서 생성기가 전부 SWC 기반이다.

#### esbuild

2020년 1월에 나온 번들러로 기존 도구보다 10~100배 빠르다. 재밌는 건 이게 Rust가 아니라 Go라는 점이다. 제작자 Evan Wallace는 Rust로도 비슷한 속도는 낼 수 있겠지만 Go가 훨씬 즐거웠고, 사이드 프로젝트니까 재밌어야 계속한다고 했다. 사실 이 솔직함이 제일 좋았다.

글쓴이는 esbuild가 JS 도구에서 "빠르다"의 기준을 바꾼 사건이라고 본다. 그전까지 시스템 언어로 JS 툴링을 만드는 건 꽤 비주류였다.

#### Rome

Babel을 만든 Sebastian이 툴체인 전체를 하나로 합치겠다고 2020년에 시작했다. Babel 아키텍처가 2014년 초기 설계에 묶여 있어서 처음부터 다시 만들었다고 한다. TS로 시작해 Rust로 재작성에 들어갔는데, 프로젝트 자체는 2023년에 공식 종료되고 `Biome`로 포크됐다.

#### NAPI

Rust가 유독 Node와 잘 붙는 이유가 [`napi-rs`][napi-rs]다. `node-gyp`나 `postinstall` 없이 미리 컴파일한 네이티브 애드온을 npm에 올릴 수 있다. esbuild처럼 자식 프로세스를 띄우지 않고 Node에서 바로 호출할 수 있는 것도 장점이다.

### Rust + WebAssembly

Rust는 WASM으로도 컴파일되니까 브라우저까지 노릴 수 있다. 다만 WASM이 JS보다 빠르다고 네이티브 속도가 나오는 건 아니다. Parcel 팀 테스트에서는 WASM 빌드가 네이티브 바이너리보다 10~20배 느렸다고 한다.

Yew, Percy, Seed, Sycamore, Stork 같은 프레임워크가 있는데, JS를 대체하기보다 같이 돌아가는 쪽으로 설계됐다.

### 그래도 Rust를 고르면 안 되는 경우

- 학습 곡선이 가파르다. 웹 개발자가 평소 다루는 것보다 추상화 수준이 낮다.
- 네이티브로 내려가면 언어 선택보다 알고리즘과 자료구조가 더 중요하다.
- 인증, DB, 결제처럼 자주 쓰는 서비스용 라이브러리를 찾기 어렵다. 2021년 시점 얘기지만 웹 앱을 Rust로 짠다면 아직 고민할 대목이다.
- Rust로 쓰면 JS 개발자가 기여하기 어려워진다. 그런데 개발자들은 기여하기 어려워도 빠른 도구를 고르더라. 하하, 나도 그렇다.

### 2021년의 예측

글쓴이는 Next.js 12가 Babel과 Terser를 SWC로 갈아탄 이유를 네 가지로 들었다.

| 이유 | 내용 |
| --- | --- |
| 확장성 | 포크 없이 Next.js 내부에서 Crate로 쓸 수 있다 |
| 성능 | Fast Refresh 약 3배, 빌드 약 5배 빨라졌다 |
| WebAssembly | 모든 플랫폼에서 Next.js 개발이 가능해진다 |
| 커뮤니티 | Rust 생태계가 계속 성장 중이다 |

당시 남은 숙제는 플러그인, 번들링, WASM이었다. 플러그인이 제일 까다롭다. Rust로 짜라고 하면 JS 개발자가 못 쓰고, JS로 열어주면 성능 이점이 날아간다. 이건 지금도 깔끔한 답이 없는 문제 같다.

`swcpack`은 결국 안 나왔다. 그 자리는 Rspack과 Turbopack이 채웠다. 맞은 예측만 있는 건 아니어서 오히려 믿음이 갔다.

### 2026년 현재

2023년에 Biome, Rspack, Pacquet, Rolldown, Oxc, Turbopack, Lightning CSS가 언급됐고, 지금은 대부분 안정 버전이 나왔다.

| 도구 | 현황 | 글에 나온 수치 |
| --- | --- | --- |
| `Turbopack` | Next.js 16 기본 번들러 | 프로덕션 빌드 2~5배, Fast Refresh 최대 10배 |
| `Rolldown` | 2026년 5월 1.0, Vite 8 기본 번들러 | Rollup 대비 10~30배 |
| `Oxc` | Oxfmt 베타, Oxlint는 Shopify 등이 프로덕션 사용 | Oxfmt는 Prettier 호환에 30배 |
| `Biome v2` | `tsc` 없이 타입 인식 린팅 | - |
| `Rspack` | 2024년 8월 1.0, webpack API 호환 | - |
| `Tailwind CSS v4` | Oxide 엔진 + Lightning CSS | 전체 빌드 5배, 증분 8배 |
| `Deno 2.0` | Node/npm 하위 호환 | - |

패키지 매니저도 넘어가는 중이다. pnpm 11.2에 실험적 Rust 설치 엔진 `pacquet`이 들어갔다. Python 쪽도 `uv`, `Ruff`가 빠르게 자리를 잡았으니 JS만의 일은 아니다.

사람 얘기도 재밌다. Evan Wallace가 Go를 고른 반면, Vite를 만든 Evan You는 Rust 쪽에 베팅해서 VoidZero를 세웠다. Vite, Vitest, Rolldown, Oxc가 전부 그 밑에 있고, 2026년 6월에 Cloudflare에 인수됐다.

#### 코딩 에이전트라는 변수

마지막 대목이 제일 2026년스럽다. 엄격한 컴파일러가 AI 생성 코드와 궁합이 좋다는 주장이다. 컴파일이 통과하면 다른 언어보다 정답에 훨씬 가깝다는 것이다. 글쓴이는 에이전트만으로 런타임 의존성 없는 Rust 이미지 압축기 3만 8천 줄을 만들었고, Bun은 2026년 5월에 에이전트를 써서 코어 전체를 Zig에서 Rust로 옮겼다고 한다. 백만 줄 이상 변경이다.

배우기 어렵다는 Rust의 최대 약점을 에이전트가 깎아주고 있는 셈이다.

### 📌 정리
`JS 툴링의 승자는 Rust보다 네이티브 코드다`

#### 핵심
> JS로 짠 빌드 도구가 최적화 한계에 닿자 네이티브로 다시 짜는 흐름이 시작됐고, 2026년에는 주요 도구 대부분이 Rust로 넘어왔다.  
> 불을 붙인 esbuild는 Go였다. 판을 바꾼 건 언어 하나가 아니라 "빌드는 이 정도로 빨라야 한다"는 기대치다.

#### ⭐️ 앞으로 기억할 것
1. 도구를 바꾸기 전에 커스텀 Babel 설정부터 찾는다
Next.js는 Babel 설정 파일이 있으면 SWC 대신 Babel로 돌아간다. 설정 파일 하나 때문에 빌드 속도 이점을 통째로 놓칠 수 있다.
```js
// ❌ .babelrc: 이 파일이 있으면 Babel로 폴백한다
// { "presets": ["next/babel"], "plugins": ["styled-components"] }

// ✅ next.config.js: 컴파일러 옵션으로 옮기고 .babelrc는 지운다
module.exports = {
  compiler: { styledComponents: true },
}
```
2. 플러그인이 있는지가 마이그레이션 비용을 정한다
벤치마크 숫자보다 먼저 볼 건 우리 프로젝트의 커스텀 플러그인이다. 새 도구에 대응 기능이 없으면 Rust로 다시 짜거나 JS 플러그인으로 돌려서 속도를 일부 포기해야 한다.
3. 네이티브 패키지는 설치 경로가 달라진다
Rust 도구는 보통 플랫폼별 바이너리를 `optionalDependencies`로 배포한다. CI나 Docker에서 "모듈을 못 찾는다"는 에러가 나면 코드보다 설치 옵션과 lockfile을 먼저 본다.
```bash
# ❌ 플랫폼별 바이너리까지 같이 빠진다
npm ci --omit=optional

# ✅ 빌드 환경에서는 optional 의존성을 유지한다
npm ci
```
4. WASM 빌드는 네이티브와 다른 도구로 취급한다
바이너리가 없는 환경의 대안으로는 좋은데 속도까지 같다고 기대하면 안 된다. 빌드가 이상하게 느려지면 WASM 폴백으로 돌고 있는 건 아닌지 확인한다.
5. 컴파일 통과는 메모리와 타입에 대한 보증이다
에이전트가 짠 Rust가 컴파일됐다고 비즈니스 로직까지 맞는 건 아니다. 엄격한 컴파일러는 검증의 일부를 가져갈 뿐이고, 동작 확인은 여전히 테스트 몫이다.

> 📌 결론  
> ▎ JS 도구가 한계에 닿자 네이티브 재작성이 시작됐고, 2021년의 예측은 대부분 현실이 됐다.  
> ▎ esbuild(Go)가 기대치를 바꿨고, Rust는 `napi-rs`와 WASM 덕분에 JS 생태계에 잘 붙었다.  
> ▎ 언어보다 알고리즘과 자료구조가 먼저다. Rust로 짰다고 저절로 빨라지지는 않는다.  
> ▎ 플러그인 문제는 아직 깔끔한 답이 없다.  
> ▎ ⭐️ 실무: 번들러를 바꾸기 전에 커스텀 Babel, webpack 플러그인 목록부터 뽑는다.  
> ▎ ⭐️ 실무: CI에서 네이티브 모듈 에러가 나면 lockfile과 optional 의존성부터 확인한다.
