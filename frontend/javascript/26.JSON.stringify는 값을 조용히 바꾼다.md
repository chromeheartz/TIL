# JSON.stringify는 값을 조용히 바꾼다

> **원문**: [Your JSON Is Lying to You][ref-src] - Gabor Koos  
> **번역 출처**: [[번역] 당신의 JSON은 거짓말하고 있습니다][ref-tr] - 한정 (Han Jung)

`JSON.parse(JSON.stringify(obj))`는 "깊은 복사 한 줄"로 너무 익숙하다. 근데 이게 복사가 아니라 <strong>변환</strong>이라는 걸 예제로 하나하나 짚어주는 글이라 정리해 둔다.

### 일단 콘솔에서 이것부터

```js
const payload = { id: 9007199254740993 };

console.log(JSON.stringify(payload));
// {"id":9007199254740992}  ← 3으로 끝나야 하는데 2
```

에러도 없고 결과는 멀쩡한 JSON이다. 큰 페이로드 안에 묻힌 ID라면 알아채기 어렵다.

```js
const original = {
  id: 9007199254740993,
  missing: undefined,
  createdAt: new Date("2026-07-21T12:00:00Z"),
  score: NaN,
};

const copy = JSON.parse(JSON.stringify(original));
console.log(copy);
// {
//   id: 9007199254740992,              ← 숫자 바뀜
//   createdAt: "2026-07-21T12:00:00.000Z", ← Date가 문자열로
//   score: null                         ← NaN이 null로
// }
// missing은 아예 사라짐
```

가장 익숙한 왕복 한 번에 데이터도 타입도 다 달라졌다.

### 왜 이렇게 됐나

JSON은 2001년쯤 브라우저와 서버 사이에서 구조화된 데이터를 가볍게 주고받으려고 나왔다. 더글러스 크록퍼드가 이름 짓고 퍼뜨렸고, [`RFC 4627`][ref-rfc4627](2006)로 명세화됐고, 지금 표준은 [`RFC 8259`][ref-rfc8259](2017)다. 당시 XML 대신 JS 객체/배열 리터럴 문법을 빌려서 훨씬 작은 문법을 제공한 게 매력이었다.

JSON이 아는 타입은 딱 이것뿐이다.

| JSON이 아는 것 | JS에만 있는 것 |
|---|---|
| 문자열, 숫자, 불리언, `null`, 배열, 객체 | `undefined`, `BigInt`, `Symbol`, `NaN`/`Infinity`, 프로토타입 가진 객체, `Map`/`Set` 같은 내장 컬렉션 |

JSON의 설계 목표는 "JS 값을 정확히 보존"이 아니라 <strong>최소한의, 이식 가능한 와이어 포맷(wire format)</strong>이다. 그러니 `stringify`는 표현 못 하는 걸 바꾸거나 거부할 수밖에 없고, `parse`는 원래 타입을 복원할 정보가 없다. 이 차이는 값이 캐시, DB, 다른 서비스, 다른 언어로 넘어갈 때 비로소 드러난다.

### 숫자는 JSON이 보기도 전에 이미 틀린다

사실 위 예제의 반올림은 `stringify` 탓이 아니다. <strong>숫자 리터럴을 평가하는 순간</strong> 이미 반올림된다.

```js
const id = 9007199254740993;
console.log(id);
// 9007199254740992
```

JS `Number`는 IEEE 754 binary64라서 `Number.MIN_SAFE_INTEGER`(-(2^53 - 1)) ~ `Number.MAX_SAFE_INTEGER`(2^53 - 1)만 정확하다. 근데 JSON의 [`숫자 문법`][ref-rfc-num]은 10진 텍스트 표기만 정할 뿐 메모리 타입은 안 정한다. 그래서 더 큰 정수 타입을 쓰는 백엔드는 JS가 못 담는 숫자를 유효한 JSON으로 보낼 수 있다.

```js
const parsed = JSON.parse('{"id":9007199254740993}');
console.log(parsed.id);
// 9007199254740992  ← 텍스트는 정확했는데 parse 순간 손실
```

DB ID, 계좌 번호, 최소 단위(원, 센트) 금액에서 진짜 문제가 된다. 파싱 후 검증으로는 못 고친다. 구분이 이미 사라졌으니까.

`BigInt`는 아예 직렬화를 거부한다.

```js
JSON.stringify({ id: 9007199254740993n });
// TypeError: Do not know how to serialize a BigInt
```

```js
// ❌ 큰 정수를 숫자로
{ "id": 9007199254740993 }

// ✅ 10진 문자열로 합의 (스키마에 명시), 연산 필요하면 BigInt로 변환
{ "id": "9007199254740993" }
```

### undefined는 여러 의미를 뭉갠다

JS는 "프로퍼티가 없음"과 "값이 `undefined`"를 구분한다.

```js
const value = { present: undefined };

value.present;        // undefined
value.missing;        // undefined
"present" in value;   // true
"missing" in value;   // false
```

근데 직렬화하면 이 구분이 사라진다. 부분 업데이트(PATCH)에서 특히 위험하다. 예를 들어 "생략 = 그대로 두기, `null` = 지우기"인 API라면,

```js
JSON.stringify({});                       // {}
JSON.stringify({ nickname: null });       // {"nickname":null}
JSON.stringify({ nickname: undefined });  // {}  ← "그대로 두기"와 똑같아짐
```

위치에 따라 규칙도 다르다. 함수와 심벌도 똑같은 패턴이다.

| 위치 | `undefined` / 함수 / `Symbol` |
|---|---|
| 객체 프로퍼티 | 키째로 생략 |
| 배열 원소 | `null` (인덱스 밀림 방지) |
| 최상위 | 문자열이 아니라 JS `undefined` 반환 |

```js
JSON.stringify(["first", undefined, "third"]); // ["first",null,"third"]
JSON.stringify(undefined);                     // undefined (typeof "undefined")
JSON.stringify({ fn: () => 42 });              // {}
JSON.stringify([() => 42]);                    // [null]
```

API 계약은 JSON이 실을 수 있는 두 상태, <strong>생략과 `null`</strong>로 정의해야 한다. 그 이상이 필요하면 직렬화 전에 명시적으로 인코딩한다.

### 객체 키 순서는 경계를 넘으면 보장 안 된다

JS 안에서는 순서가 안정적이다. [`ECMAScript 명세`][ref-ecma-stringify]상 `Object.keys()`와 같은 규칙이다. 정수 인덱스 키가 오름차순으로 먼저, 나머지 문자열 키는 생성 순서.

```js
const value = {};
value.b = "second";
value[10] = "ten";
value[2] = "two";
value.a = "first";

JSON.stringify(value);
// {"2":"two","10":"ten","b":"second","a":"first"}
```

근데 [`RFC 8259는 객체를 순서 없는 컬렉션으로 정의`][ref-rfc-obj]한다. 예를 들어 Go 서비스가 `map[string]any`로 디코딩하면 [`Go 명세`][ref-go]상 맵 순회 순서는 보장이 없다.

```json
// ❌ 순서에 의미를 담음 (첫 번째 키가 최우선 같은 규칙)
{ "z": 1, "a": 2, "m": 3 }

// ✅ 순서가 중요하면 배열 (명세상 순서 보존)
[
  { "name": "z", "value": 1 },
  { "name": "a", "value": 2 },
  { "name": "m", "value": 3 }
]
```

해시, 서명, 캐시 키는 또 다른 문제다. 같은 객체라도 키 순서나 공백이 다르면 바이트가 다르다.

```js
'{"a":1,"b":2}' === '{ "b": 2, "a": 1 }'; // false
```

이런 데는 바이트 계산 전에 합의된 <strong>정규화(canonicalization)</strong>가 필요하다. 원본 JSON 문자열끼리 비교하는 테스트도 같은 함정이다.

### JSON은 타입을 지운다

#### Date

`Date`는 `toJSON()`으로 ISO 문자열이 된다. 파싱하면 그냥 문자열이다.

```js
const json = JSON.stringify({ createdAt: new Date("2026-07-21T12:00:00Z") });
// {"createdAt":"2026-07-21T12:00:00.000Z"}

const copy = JSON.parse(json);
typeof copy.createdAt;           // "string"
copy.createdAt instanceof Date;  // false
```

`parse`가 자동 복원을 못 하는 이유가 있다. 타임스탬프처럼 생긴 문자열이 원래 `Date`였는지 문자열이었는지 알 방법이 없다.

타임존 맥락도 날아간다. 가리키는 순간은 같지만 원래 벽시계 시각과 오프셋은 사라진다. 이건 같은 저자의 [`당신의 JS Date는 거짓말하고 있습니다`][ref-date]에서 더 자세히 다룬다.

```js
JSON.stringify({ scheduledAt: new Date("2026-07-21T09:00:00-04:00") });
// {"scheduledAt":"2026-07-21T13:00:00.000Z"}  ← -04:00 정보 소실
```

#### 나머지 내장 타입들

```js
const copy = JSON.parse(JSON.stringify({
  tags: new Set(["json", "js"]),
  lookup: new Map([["answer", 42]]),
  pattern: /json/i,
  error: new Error("failed"),
}));
// { tags: {}, lookup: {}, pattern: {}, error: {} }  ← 내용도 타입 정보도 없음
```

| 원래 값 | JSON 결과 | 잃는 것 |
|---|---|---|
| `Date` | ISO 문자열 (UTC) | 타입, 타임존 오프셋 |
| `Map` / `Set` / `RegExp` / `Error` | `{}` | 내용 전부 |
| `NaN` / `Infinity` / `-Infinity` | `null` | "값 없음"과 구분 불가 |
| `Uint8Array` | `{ 0: 10, 1: 20, ... }` | 타입, 이진 해석 |
| 클래스 인스턴스 | 열거 가능한 필드만 | 프로토타입, 메서드, `#private` |

`NaN`이 `null`이 되는 게 특히 놓치기 쉽다. `null`은 유효한 JSON이라 파싱도 잘 되고, 이후 코드는 "측정값 없음"과 "계산 결과가 NaN"을 구분 못 한다.

```js
class User {
  #role = "admin";
  constructor(name) { this.name = name; }
  greet() { return `Hello, ${this.name}`; }
}

const copy = JSON.parse(JSON.stringify(new User("Alice")));
// { name: "Alice" }
copy instanceof User;  // false
typeof copy.greet;     // "undefined"
```

이런 변환은 실제로 값을 쓰기 전까진 안 보인다. 그럴듯한 문자열, 느슨한 검사를 통과하는 빈 객체, 여러 계층을 조용히 지나가는 `null`. 답은 <strong>JSON이 아닌 타입의 직렬화 형태를 명시적으로 정의</strong>하는 거다.

### 직렬화는 코드를 실행한다

`stringify`는 값을 들여다보기만 하는 게 아니라 훅을 호출하고 프로퍼티를 읽는다.

#### toJSON()

```js
const user = {
  name: "Alice",
  password: "secret",
  toJSON() {
    return { name: this.name };  // password 제외
  },
};
JSON.stringify(user); // {"name":"Alice"}
```

공개 표현 정의엔 유용하지만, 호출부에서 객체만 보고는 출력을 예측하기 어렵다. `Date`도 이 메커니즘이다. `Date.prototype.toJSON()`이 `toISOString()`을 부른다. 그리고 `toJSON()`은 일반 함수라서 상태 변경, 외부 접근, 예외까지 다 가능하다.

```js
let serializations = 0;
const report = {
  value: 42,
  toJSON() {
    serializations += 1;  // 부수 효과
    return { value: this.value };
  },
};
JSON.stringify(report);
JSON.stringify(report);
serializations; // 2
```

#### 게터

```js
const invoice = {
  subtotal: 100,
  get total() {
    console.log("calculating total");  // stringify 중에 실행됨
    return this.subtotal * 1.2;
  },
};
JSON.stringify(invoice); // {"subtotal":100,"total":120}

const value = {
  get secret() { throw new Error("secret is unavailable"); },
};
JSON.stringify(value); // Error: secret is unavailable
```

게터가 던지면 `stringify`도 던진다. 로깅이나 에러 리포팅이 또 다른 실패 지점이 될 수 있다.

#### replacer

두 번째 인자. 함수면 루트에 한 번, 이후 프로퍼티마다 호출된다. 배열이면 허용 목록(allowlist)이다.

```js
const user = {
  name: "Alice",
  password: "secret",
  lastLogin: new Date("2026-07-21T12:00:00Z"),
};

// 함수: undefined 반환하면 키 제거
JSON.stringify(user, (key, value) => (key === "password" ? undefined : value));
// {"name":"Alice","lastLogin":"2026-07-21T12:00:00.000Z"}
// 주의: replacer는 toJSON() 실행 후의 값을 받음 → lastLogin은 이미 문자열

// 배열: 허용 목록
JSON.stringify({ name: "Alice", email: "a@x.com", password: "s", role: "admin" }, ["name", "role"]);
// {"name":"Alice","role":"admin"}
```

의존성 패키지나 다른 곳에서 온 객체를 직렬화한다면, 이건 <strong>실행되는 동작</strong>이라고 보고 값 변형이나 예외를 예상해야 한다.

### 아예 못 넘어가는 객체도 있다

#### 객체 정체성(identity)

JSON은 참조가 아니라 값을 기록한다.

```js
const shared = { name: "Alice" };
const original = { owner: shared, reviewer: shared };
const copy = JSON.parse(JSON.stringify(original));

original.owner === original.reviewer; // true
copy.owner === copy.reviewer;         // false  ← 별개의 두 객체
```

#### 순환 참조

```js
const value = { name: "loop" };
value.self = value;
JSON.stringify(value);
// TypeError: Converting circular structure to JSON
```

부모 링크, 그래프, 캐시, 프레임워크 객체에서 자연스럽게 생긴다. 직렬화는 로깅, 저장, HTTP 응답에서 늦게 일어나서 <strong>순환을 만든 코드와 먼 곳에서</strong> 에러가 터진다. replacer로 끊을 순 있지만 데이터 모델이 바뀐다. 정체성이 필요하면 ID와 ID 참조 필드 같은 명시적 참조 포맷을 쓴다.

#### 안 보이는 프로퍼티

`stringify`는 <strong>열거 가능한 자체 문자열 키</strong>만 본다.

```js
const value = Object.create({ inherited: "from prototype" }); // 상속 ❌
value.visible = "included";                                    // ✅
Object.defineProperty(value, "hidden", {
  value: "non-enumerable",
  enumerable: false,                                           // 열거 불가 ❌
});
value[Symbol("internal")] = "symbol value";                    // 심벌 키 ❌

JSON.stringify(value); // {"visible":"included"}
```

그래서 도메인 객체를 그대로 응답으로 보내는 건 취약하다. 경계에서 전송용 객체를 따로 만든다.

```js
// ❌ 클래스 인스턴스를 그대로 직렬화 (열거성·프로토타입 바뀌면 응답도 조용히 바뀜)
res.json(user);

// ✅ 전송용 객체를 명시적으로 구성
function toUserResponse(user) {
  return { name: user.name };
}
res.json(toUserResponse(user));
```

### 파싱은 안전한데, 그다음이 문제다

#### 프로토타입 오염

[`프로토타입 오염(prototype pollution)`][ref-mdn-pp]은 페이로드가 보통 JSON으로 와서 `JSON.parse` 문제로 오해받는다. 근데 파싱만으로는 `Object.prototype`이 안 바뀐다. `"__proto__"`는 그 이름의 자체 데이터 프로퍼티가 될 뿐이다.

```js
const value = JSON.parse('{"__proto__":{"admin":true}}');

Object.hasOwn(value, "__proto__"); // true
value.__proto__;                   // { admin: true }
({}).admin;                        // undefined  ← 다른 객체는 멀쩡
```

위험은 그 뒤, <strong>재귀 병합 헬퍼</strong>가 `__proto__`나 `constructor` 같은 키를 따라 프로토타입까지 내려가서 할당할 때 생긴다.

```text
신뢰할 수 없는 JSON
    ↓
파싱된 객체의 자체 프로퍼티 (여기까진 안전)
    ↓
안전하지 않은 재귀 병합
    ↓
프로토타입 변경 💥
```

그래서 방어는 키를 받아서 복사하는 지점에 있어야 한다. 스키마 검증으로 예상한 필드만 허용하는 게 좋고, 병합 유틸은 오염 방어를 문서화해야 한다.

객체 스프레드는 레거시 `__proto__` 세터를 안 부르고 자체 프로퍼티로 만든다.

```js
const parsed = JSON.parse('{"__proto__":{"admin":true}}');
const copy = { ...parsed };

Object.hasOwn(copy, "__proto__");                  // true
Object.getPrototypeOf(copy) === Object.prototype;  // true
```

그렇다고 스프레드면 다 안전한 건 아니다. 예상 못 한 키가 앱 로직에 영향 줄 수 있으니 검증은 여전히 필요하다.

#### 리소스 고갈

```js
// 유효한 JSON이지만 메모리·CPU를 많이 먹음
const deeplyNested = "[".repeat(100_000) + "]".repeat(100_000);
JSON.parse(deeplyNested);
```

파싱은 앱 레벨 검증보다 먼저 일어난다. 서버는 큰 본문을 <strong>파싱 전에</strong> 거부해야 하고, 필요하면 중첩 깊이, 컬렉션 크기, 처리 시간도 제한한다. reviver도 값마다 호출되니 콜백은 작고 예측 가능하게.

### reviver가 타입을 알아서 복원해주진 않는다

`JSON.parse`의 두 번째 인자. 자식 값이 부모보다 먼저 오고, 마지막에 빈 문자열 키로 루트가 온다. `undefined`를 반환하면 프로퍼티가 제거된다(배열이면 구멍).

```js
// ❌ ISO처럼 생긴 문자열은 전부 Date로
const parsed = JSON.parse(json, (key, value) => {
  if (typeof value === "string" && /^\d{4}-\d{2}-\d{2}T/.test(value)) {
    return new Date(value);
  }
  return value;
});
parsed.createdAt instanceof Date;   // true
parsed.searchQuery instanceof Date; // true  ← 검색어인데 Date가 됨

// ✅ 생산자가 타입 태그를 붙이고, 소비자가 태그만 보고 복원
const json = JSON.stringify({
  createdAt: { $type: "Date", value: "2026-07-21T12:00:00.000Z" },
});
const parsed = JSON.parse(json, (key, value) =>
  value?.$type === "Date" ? new Date(value.value) : value
);
```

replacer와 reviver를 <strong>같은 계약</strong>으로 짝지으면 BigInt도 안전하게 왕복한다.

```js
const json = JSON.stringify({ requestId: 9007199254740993n }, (key, value) =>
  typeof value === "bigint" ? { $type: "BigInt", value: value.toString() } : value
);

const copy = JSON.parse(json, (key, value) =>
  value?.$type === "BigInt" ? BigInt(value.value) : value
);
copy.requestId; // 9007199254740993n
```

reviver는 신뢰할 수 없는 데이터 전체에 대해 코드를 실행한다. 알려진 태그만 받고 페이로드도 검증할 것. 계약이 커지면 조건문 뭉치보다 전용 코덱이나 스키마 변환이 테스트하기 쉽다.

### JSON 경계를 위한 실전 규칙

모든 문제의 원인은 하나, <strong>암묵적인 계약</strong>이다. 보내는 쪽은 가진 객체를 그대로 직렬화하고, 받는 쪽은 같은 의미일 거라고 가정한다.

📌 1단계: 와이어 형태를 정의한다

```js
function toUserResponse(user) {
  return {
    id: user.id.toString(),                  // 큰 ID → 10진 문자열
    name: user.name,
    createdAt: user.createdAt.toISOString(), // Date → UTC 타임스탬프
    roles: [...user.roles],                  // Set → 순서 있는 배열
  };
}
```

`User` 클래스가 바뀌어도 이 함수가 안 바뀌면 응답도 안 바뀐다.

📌 2단계: 파싱 후 런타임 검증한다

`JSON.parse`는 문법만 본다. 타입스크립트 타입은 컴파일 때 지워지니 런타임 검사를 못 한다.

```js
JSON.parse('{"name":42,"createdAt":"yesterday"}');
// 유효한 JSON, 유효하지 않은 사용자 데이터
```

[`Zod`][ref-zod], [`Valibot`][ref-valibot], [`TypeBox`][ref-typebox] 같은 스키마 라이브러리를 쓴다.

```js
import { z } from "zod";

const UserResponse = z.object({
  id: z.string().regex(/^\d+$/),
  name: z.string(),
  createdAt: z.iso.datetime(),
  roles: z.array(z.string()),
});
const user = UserResponse.parse(JSON.parse(text));
```

단, 검증은 이미 잃은 정보를 못 살린다. 큰 정수가 숫자로 들어왔으면 스키마는 반올림된 값을 본다. <strong>보존은 와이어 표현의 몫</strong>, 검증은 그다음이다.

📌 3단계: 예외적인 값엔 명시적 표현을 준다

```json
{
  "requestId": "9007199254740993",
  "createdAt": { "$type": "Date", "value": "2026-07-21T12:00:00.000Z" },
  "avatarBase64": "iVBORw0KGgoAAAANSUhEUgAA..."
}
```

문자열 모양으로 추측하지 말고 필드 이름이나 타입 태그로.

📌 4단계: 순서가 중요하면 배열, 바이트 비교엔 정규화

```json
{
  "steps": [
    { "name": "validate" },
    { "name": "charge" },
    { "name": "confirm" },
    { "name": "notify" }
  ]
}
```

📌 5단계: 신뢰할 수 없는 입력을 제한한다

큰 본문은 `JSON.parse` 전에 거부. 깊은 중첩은 깊이와 크기 제한.

📌 6단계: 받는 쪽에서 테스트한다

직렬화기 테스트는 생산자 출력만 증명한다. 예를 들어 JS 클라이언트와 Go 서비스라면 큰 ID가 두 런타임을 다 거쳐도 살아남는지, 서명된 JSON이면 키 순서가 다른 동등한 객체가 정규화 후 같은 바이트가 되는지 확인한다.

📌 7단계: 필요하면 다른 포맷

[`MessagePack`][ref-msgpack]은 압축 바이너리와 확장 타입, [`CBOR`][ref-cbor]은 텍스트/바이트 문자열 구분, 태그, 넓은 숫자 표현을 지원한다. 그래도 계약이 필요하다는 사실은 안 바뀐다. 어휘만 넓어질 뿐.

### 마치며

도입부의 변화는 전부 정해진 규칙대로였다. 큰 정수는 리터럴 평가 때 반올림됐고, `undefined`는 JSON 표현이 없고, `Date`는 `toJSON()`으로 문자열이 됐고, `NaN`은 `null`이 됐다. JSON이 고장 난 게 아니라, 의도적으로 작게 만든 교환 포맷을 <strong>JS 상태의 무손실 스냅샷</strong>처럼 쓴 게 문제다.

같은 저자의 "거짓말하고 있습니다" 시리즈도 같은 패턴(도구가 보장한다고 믿는 것과 실제 동작 사이의 간극)을 다룬다. [`JS Date`][ref-date], [`console.log`][ref-console], [`Debounce`][ref-debounce], [`스로틀링`][ref-throttle], [`HTTP 클라이언트`][ref-http], [`재귀`][ref-recursion], [`패키지 매니저`][ref-pkg], [`모듈`][ref-modules].

### 📌 정리
`JSON.parse(JSON.stringify(x))는 복제가 아니라 변환이다`

#### 핵심
> JSON은 문자열·숫자·불리언·null·배열·객체만 아는 작은 와이어 포맷이다. 그 밖의 JS 값은 조용히 바뀌거나, 사라지거나, 에러를 낸다.  
> 큰 정수는 parse 순간 반올림되고, undefined는 생략되고, Date는 문자열, NaN은 null, Map/Set은 `{}`, 클래스는 평범한 객체가 된다. 키 순서와 객체 정체성도 경계를 넘으면 보장이 없다.  
> 해결책은 하나다. 경계에서 와이어 형태를 명시적으로 정의하고(전송용 객체, 타입 태그, 10진 문자열), 받는 쪽에서 스키마로 검증하고, 수신 측까지 테스트한다.

#### ⭐️ 앞으로 기억할 것

1. 깊은 복사는 `structuredClone`
`JSON.parse(JSON.stringify())`는 Date, Map, Set, undefined를 망가뜨린다. 같은 프로세스 안 복사라면 `structuredClone`이 Date·Map·Set·순환 참조까지 보존한다 (원문 내용은 아님). 함수와 클래스 프로토타입은 이것도 못 옮긴다.
```js
// ❌ 타입 다 날아감
const copy = JSON.parse(JSON.stringify(state));

// ✅ Date, Map, Set, 순환 참조 보존
const copy = structuredClone(state);
```

2. 안전 범위를 넘는 ID는 문자열로 받는다
백엔드가 64비트 정수 ID를 숫자로 내려주면 FE에서 이미 망가진다. API 계약 단계에서 문자열로 합의한다.
```js
Number.isSafeInteger(9007199254740993); // false → 문자열로 받아야 함
```

3. PATCH는 `undefined` 말고 생략 / `null`로 설계
폼 상태를 그대로 보내면 `undefined` 필드는 사라진다. "안 바꿈"과 "지움"을 생략과 `null`로 명확히 구분한다.
```ts
// ✅ 의도가 드러나게
const body = isCleared ? { nickname: null } : {};
```

4. `res.json(entity)` 대신 응답 매퍼
클래스나 ORM 엔티티를 그대로 직렬화하지 않는다. `toXxxResponse()`로 필드를 명시하면 비밀번호 같은 필드가 실수로 나가는 일도 막는다.

5. `as User`는 검증이 아니다
`JSON.parse(text) as User`는 컴파일러만 속인다. 외부 응답은 Zod 같은 스키마로 런타임 검증한다.
```ts
// ❌
const user = (await res.json()) as User;

// ✅
const user = UserSchema.parse(await res.json());
```

6. 재귀 merge 유틸에 외부 JSON을 바로 넣지 않는다
`__proto__`, `constructor` 키를 걸러주는지 확인하거나, 스키마로 허용 키만 통과시킨 뒤 병합한다.

> 📌 결론  
> ▎ JSON은 JS 값의 스냅샷이 아니라 작게 설계된 교환 포맷이다  
> ▎ 큰 정수, undefined, Date, NaN, Map/Set, 클래스는 경계에서 조용히 바뀐다  
> ▎ 키 순서와 객체 참조는 경계를 넘으면 보장되지 않는다  
> ▎ toJSON, 게터, replacer 때문에 직렬화는 코드를 실행한다  
> ▎ parse 자체는 안전하지만, 그 결과를 재귀 병합하면 프로토타입 오염이 생긴다  
> ▎ ⭐️ 실무 적용 포인트: 응답은 매퍼로 와이어 형태를 명시하고, 큰 ID는 문자열로, 받은 JSON은 Zod로 검증하고, 깊은 복사는 structuredClone을 쓴다
