# fetch 스트림으로 진행률 재면 안 되는 이유

> **원문**: [Fetch streams are great, but not for measuring upload/download progress][ref-1] — Jake Archibald (2025.09.15)
> **번역 출처**: [[번역] Fetch 스트림은 훌륭하지만, 업로드/다운로드 진행 상황 측정에는 적합하지 않습니다][ref-2] — devowen

지난번 [`베이스라인 노트`][ref-3]에서 "fetch는 업로드 진행률이 없어서 axios를 남길 이유가 된다"는 걸 봤는데, 그럼 **스트림으로 직접 세면 되지 않나?** 싶었다. 딱 그 생각을 반박하는 글이라 정리해둠. 글쓴이는 Mozilla에서 요청 스트림 기능 우선순위를 검토하다가, 개발자들한테 어디 쓸 거냐고 물어보니 1위 답변이 "업로드 진행률"이라서 이 글을 썼다고 한다.

### 응답 스트림 복습

응답 스트리밍은 이미 모든 브라우저에서 된다. `response.body`가 `ReadableStream`이라 받는 대로 청크를 처리할 수 있다.

```js
const res = await fetch('/api/logs')
const reader = res.body.getReader()

while (true) {
  const { done, value } = await reader.read()  // value는 Uint8Array
  if (done) break
  appendChunk(value)
}
```

`for await`로 쓰면 훨씬 깔끔한데… **사파리가 아직 `ReadableStream` async 이터레이션을 지원 안 한다.** (글쓴이가 Interop 2026 후보로 제안해둠)

```js
// 사파리 미지원 주의
for await (const chunk of res.body) {
  appendChunk(chunk)
}
```

바이트 말고 텍스트로 받고 싶으면 `TextDecoderStream`을 끼운다.

```js
const textStream = res.body.pipeThrough(new TextDecoderStream())
```

### 다운로드 진행률: 거의 맞는데 압축에서 깨진다

흔히 짜는 코드는 이런 모양이다.

```js
// ❌ 압축 응답이면 100%를 넘어간다
const res = await fetch('/files/report.json')
const total = Number(res.headers.get('Content-Length')) || 0
let received = 0

for await (const chunk of res.body) {
  received += chunk.length
  if (total) setProgress(received / total)
}
```

다운로드 쪽은 "데이터가 **내 손에 들어온 시점**"을 재는 거라 방향 자체는 맞다. 택배 받을 때 상자가 도착할 때마다 세는 것과 같다.

문제는 `Content-Encoding`(gzip, brotli)이 붙었을 때다.

| 값 | 기준 |
|------|------|
| `Content-Length` 헤더 | **압축된** 크기 |
| `chunk.length` 합계 | **압축 해제된** 크기 |

단위가 다른 두 숫자를 나누고 있으니 `received`가 `total`을 쉽게 넘어선다. 사실 이게 텍스트 리소스는 거의 다 압축돼서 오니까 꽤 흔하게 터지는 버그다. 글쓴이가 예전에 브라우저별로 압축 리소스 진행률을 어떻게 처리하는지 조사했을 때도 결과가 제각각이었다고.

압축 풀기 전 원본 바이트를 받는 기능은 [`whatwg/fetch 이슈`][ref-4]로 요청만 올라와 있는 상태.

### 요청 스트림: 업로드도 스트림으로

요청 body에도 `ReadableStream`을 넣을 수 있다. 영상을 트랜스코딩하면서 동시에 업로드하는 식으로 쓸 수 있다. 전통적인 방식은 처리를 다 끝내고 업로드를 시작하니 그만큼 느리다.

```js
const source = getCameraStream()                          // 원본 스트림
const encoded = source.pipeThrough(new MyEncoderStream()) // 처리하면서

await fetch('/upload', {
  method: 'POST',
  body: encoded,          // 바로 흘려보내기
  duplex: 'half',         // 스트림 body면 필수
  headers: { 'Content-Type': 'video/mp4' },
})
```

크롬은 꽤 전부터 지원했지만 **파이어폭스·사파리는 아직 미지원.**

#### 제약 사항

| 항목 | 내용 |
|------|------|
| `duplex: 'half'` | 요청이 끝나야 응답을 읽을 수 있다. 나중에 양방향 동시 처리(`full`)를 넣을 자리를 비워둔 것 |
| 동시 송수신이 필요하면 | fetch를 두 번 — 하나는 업로드 스트림, 하나는 다운로드 스트림 |
| 프로토콜 | 요청 길이를 미리 모르니 청크 전송이 자연스러운 **HTTP/2 이상**에서만 동작 |

### 업로드 진행률: 이건 아예 틀린 걸 잰다

글쓴이는 코드 예시조차 안 보여줄 정도로 비추한다. 하하.

요청 스트림에서 잴 수 있는 건 "**fetch가 스트림에서 데이터를 가져간 시점**"이다. 택배 비유로 하면 기사님이 상자를 **수거해 간 시점**이지, 상대방에게 **배달된 시점**이 아니다.

- fetch(택배 기사)는 청크를 일단 가져가서 내부에 쌓아둔다
- 실제 네트워크 전송은 그 뒤에 일어나고, 실패할 수도 있다
- 각 스트림엔 적정 버퍼량인 **하이 워터 마크(high water mark)**가 있어서, 파이프 구간별 속도 차이를 흡수한다 — 스트림의 정상 동작이다

그러니 "읽어간 바이트 / 전체"는 전송량이 아니라 **버퍼로 옮겨간 양**일 뿐이다.

#### 더 큰 문제: 브라우저 발목을 잡는다

이 부분이 제일 인상 깊었다. 부정확한 것에서 끝나지 않는다는 얘기.

1. 어떤 브라우저가 버퍼를 작게 잡고 출시 → 스트림 기반 진행률이 "대충 맞아 보임"
2. 많은 사이트가 그걸로 업로드 진행률을 구현
3. 나중에 브라우저가 "버퍼를 크게 잡으면 성능이 좋아진다"는 걸 발견
4. 선택지: 성능 개선을 출시해서 그 사이트들 진행률을 망가뜨리거나, 개선을 포기하거나

개발자가 구현 디테일에 기대는 순간, 그 디테일이 사실상 스펙처럼 굳어버린다. 웹 호환성 얘기에서 늘 나오는 패턴이다.

### 📌 지금 당장 진행률이 필요하면: XHR

아쉽지만 현재 정답은 `XMLHttpRequest`다. 업로드/다운로드 둘 다 진짜 progress 이벤트를 준다.

```js
function uploadWithProgress(url, file, onProgress) {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest()

    // 업로드 진행률 — xhr.upload에 건다
    xhr.upload.addEventListener('progress', (e) => {
      if (e.lengthComputable) onProgress(e.loaded / e.total)
    })

    xhr.addEventListener('load', () =>
      xhr.status >= 200 && xhr.status < 300 ? resolve(xhr.response) : reject(new Error(`HTTP ${xhr.status}`)),
    )
    xhr.addEventListener('error', () => reject(new Error('네트워크 오류')))

    xhr.open('POST', url)
    xhr.send(file)
  })
}
```

| 이벤트 대상 | 의미 |
|------|------|
| `xhr.upload.onprogress` | 요청 body 전송 진행률 |
| `xhr.onprogress` | 응답 body 수신 진행률 |
| `event.lengthComputable` | 전체 크기를 알 수 있는지 — `false`면 퍼센트 계산 불가 |

### 앞으로: fetch에 observer가 들어올 예정

Igalia의 Luke Warlow가 fetch에 진행 이벤트를 넣는 [`스펙 PR`][ref-5]을 작업 중이다. 출시 전에 바뀔 수 있지만 지금 초안은 대략 이런 모양.

```js
// 🚧 제안 단계 API — 모양 바뀔 수 있음
await fetch('/upload', {
  method: 'POST',
  body: file,
  observer(requestObserver, responseObserver) {
    requestObserver.onprogress = (e) => {
      if (e.lengthComputable) setUploadProgress(e.loaded / e.total)
    }
    responseObserver.onprogress = (e) => {
      if (e.lengthComputable) setDownloadProgress(e.loaded / e.total)
    }
  },
})
```

이게 들어오면 XHR로 돌아갈 이유가 사라진다. 진행률 말고 다른 용도로 요청 스트림이 필요하면 [`Interop 2026 제안`][ref-6]에 의견을 남기면 된다.

### 📌 정리
`스트림이 읽힌 시점 ≠ 네트워크로 전송된 시점`

#### 핵심
> fetch 스트림은 데이터를 **흘려 처리**하는 도구지 **진행률 측정** 도구가 아니다.
> 다운로드는 압축 때문에 `Content-Length`와 청크 크기 단위가 어긋나고, 업로드는 버퍼로 옮겨간 시점만 잴 수 있어서 아예 틀린 값이 나온다.
> 지금은 XHR progress 이벤트가 정답이고, fetch `observer` 제안이 들어오면 그걸로 옮긴다.

#### ⭐️ 앞으로 기억할 것
- 1. `Content-Length`는 압축된 크기다
응답 청크는 압축 해제된 바이트라서 둘을 나누면 100%를 넘을 수 있다. 굳이 스트림으로 다운로드 진행률을 보여줘야 하면 최소한 상한은 막아두자.
```js
// 임시 방편 — 정확하진 않지만 UI가 110% 찍히는 건 막는다
setProgress(Math.min(received / total, 1))
```

- 2. 업로드 진행률은 요청 스트림으로 만들지 않는다
읽어간 양 ≠ 보낸 양. 게다가 크롬만 지원한다. 업로드 진행률 바가 필요한 화면은 XHR(또는 XHR 기반 axios)을 쓴다.
```js
// ❌ 스트림 pull 횟수로 진행률 계산
// ✅ xhr.upload.onprogress
```

- 3. `lengthComputable` 체크를 빼먹지 말 것
전체 크기를 모르면 `total`이 0이라 `NaN`/`Infinity`가 나온다. 그땐 퍼센트 대신 불확정(indeterminate) 로딩 UI로.

- 4. 요청 스트림 쓸 땐 `duplex: 'half'` + HTTP/2
빠뜨리면 에러. HTTP/1.1 서버에선 동작 안 한다는 것도 같이 기억.

- 5. 구현 디테일에 기대는 코드는 플랫폼을 굳게 만든다
"대충 맞아 보이니까 쓰자"가 브라우저 성능 개선을 막을 수 있다. 스펙이 보장하는 동작인지 먼저 확인하는 습관.

> **📌 결론**
> ▎ fetch 응답 스트림은 전 브라우저 지원, `for await` 순회는 사파리 미지원
> ▎ 다운로드 진행률은 압축(`Content-Encoding`) 때문에 스트림으로 정확히 못 잰다
> ▎ 업로드 진행률은 스트림으로 재면 "수거 시점"만 잡혀서 틀린 값 + 브라우저 최적화까지 방해한다
> ▎ 현재 정답은 XHR progress 이벤트, 미래엔 fetch `observer`
> ▎ ⭐️ 실무 적용 포인트: 파일 업로드 컴포넌트는 axios/XHR 유지 — 베이스라인 점검에서 axios 걷어낼 때도 업로드 진행률 쓰는 곳은 예외로 남겨두기
