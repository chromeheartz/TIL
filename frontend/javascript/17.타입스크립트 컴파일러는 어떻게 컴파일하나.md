# 타입스크립트 컴파일러는 어떻게 컴파일하나

> **출처**: https://velog.io/@sehyunny/how-ts-compiler-compiles (velog @sehyunny, 황세현 번역) / 원문: https://www.huy.rocks/everyday/04-01-2022-typescript-how-the-compiler-compiles

매일 `tsc` 돌리고 빨간 줄 보고 고치면서도, 정작 그 안에서 무슨 일이 벌어지는지는 블랙박스로 두고 있었다. "타입 에러"랑 "문법 에러"가 왜 다른 단계에서 나오는지, `.d.ts`랑 `.js.map`은 누가 뽑는지 — 이걸 알면 에러 메시지도 더 잘 읽힌다. tsc 내부 파이프라인을 단계별로 따라가 본다.

> 한 줄 정의: **TS 컴파일러는 TS 코드를 분석해서 JS(`*.js`) + 타입 정의(`*.d.ts`) 또는 소스맵(`*.js.map`)으로 컴파일하는 도구다.**

### 1. 컴파일 과정

`tsc`를 실행하면 전체 흐름은 이렇게 흘러간다.

![tsc 전체 과정](https://raw.githubusercontent.com/huytd/everyday/master/_meta/tsc-overview.png)

#### 시작 — tsconfig.json 읽기

`tsc`는 먼저 `tsconfig.json`을 읽어서 **컴파일러 옵션**과 **입력 파일**을 파악한다.

```json
{
  "files": ["src/*.ts"],
  "compilerOptions": {
    // ...
  }
}
```

#### Program → Parser → AST

- **Program** (`src/compiler/program.ts`) — 컴파일 **컨텍스트**를 만든다. 모든 입력 파일과 import를 로드한 뒤, **Parser**를 호출한다.
- **Parser** (`src/compiler/parser.ts`) — 각 파일을 **AST(추상 구문 트리)** 로 변환한다.

![Program이 파일을 AST로](https://raw.githubusercontent.com/huytd/everyday/master/_meta/tsc-program-to-ast.png)

#### Scanner (Parser 내부)

Parser는 내부적으로 **Scanner** (`src/compiler/scanner.ts`)를 만든다. Scanner는 소스 코드를 훑어서 **`SyntaxKind` 토큰 스트림**을 만든다. (= 어휘 분석/토크나이징 단계)

> 흐름: 소스 텍스트 → **Scanner**(토큰화) → **Parser**(토큰 → AST)

#### Binder → Symbol Table

- **Binder** (`src/compiler/binder.ts`) — AST를 받아서 **AST 노드 ↔ Symbol** 사이의 맵을 만든다.
- **Symbol** — 각 노드의 **타입 정보 등 부가 메타데이터**를 담는다.
- 그 결과물이 **Symbol Table** → 이후 타입 체크 같은 단계에서 쓰인다.

![Symbol Table](https://raw.githubusercontent.com/huytd/everyday/master/_meta/tsc-binder-symbols.png)

#### Emit — JS 만들기

`Program.emit`이 호출되면 **Emit Worker**가 AST를 JS 소스 문자열로 변환한다. 이미터는 두 종류.

| 이미터 | 파일 | 산출물 |
|---|---|---|
| **JavaScript Emitter** | `src/compiler/emitter.ts` | JS 소스 + 소스맵(`.js.map`) |
| **Type Definition Emitter** | `src/compiler/definitionEmitter.ts` | 타입 정의 파일(`.d.ts`) |

emit 도중 `getDiagnostics()`가 **Type Checker** (`src/compiler/checker.ts`)를 만든다. 그리고 Emitter가 AST를 순회하면서 **Symbol Table의 타입 정보**를 이용해 각 노드를 처리한다.

![JS 소스 생성](https://raw.githubusercontent.com/huytd/everyday/master/_meta/tsc-emitter.png)

> 전체 파이프라인 한 줄 요약:
> **tsconfig → Program → Scanner → Parser(AST) → Binder(Symbol Table) → Type Checker → Emitter(JS / .d.ts / .map)**

### 2. 에러 보고

컴파일 **단계**에 따라 다른 종류의 에러가 나온다. tsc 내부엔 결과 플래그가 비트마스크로 정의돼 있다.

```typescript
enum BuildResultFlags {
  None = 0,
  Success = 1 << 0,
  DeclarationOutputUnchanged = 1 << 1,

  ConfigFileErrors = 1 << 2,
  SyntaxErrors = 1 << 3,
  TypeErrors = 1 << 4,
  DeclarationEmitErrors = 1 << 5,
  EmitErrors = 1 << 6,

  AnyErrors = ConfigFileErrors | SyntaxErrors | TypeErrors
            | DeclarationEmitErrors | EmitErrors
}
```

어디서 나는 에러인지가 단계와 직결된다.

| 에러 | 발생 단계/주체 |
|---|---|
| `ConfigFileErrors` | `tsconfig.json` 문제 |
| `SyntaxErrors` | **Scanner**가 감지 (문법 자체가 깨짐) |
| `TypeErrors` | **Parser / Type Checker**가 감지 (의미상 틀림) |

#### 타입 에러 예시

```typescript
let a: number = "hello";
```

이건 **문법은 멀쩡하다**(Scanner 통과). 근데 number 변수에 string을 넣어서 **의미상 틀렸으므로** Type Checker 단계에서 `TypeError`가 난다. ← "문법 OK인데 타입 에러"가 왜 별도 단계인지가 여기서 드러난다.

### 3. 결론

tsc는 결국 **Scanner → Parser → Binder → Checker → Emitter**로 이어지는 파이프라인이고, 각 단계가 자기 책임의 에러를 보고한다. 더 깊게 보려면 [`TypeScript Compiler Internals`](https://basarat.gitbook.io/typescript/overview)에서 실제 코드 위치와 호출 관계를 볼 수 있다.

### 📌 정리
`tsc = Scanner→Parser(AST)→Binder(Symbol Table)→Type Checker→Emitter(JS/.d.ts/.map) 파이프라인`

#### 핵심
> `tsc`는 단일 변환이 아니라 여러 단계의 파이프라인이다. ① `tsconfig.json`을 읽어 **Program**이 컨텍스트·파일을 로드하고, ② **Scanner**가 소스를 토큰(`SyntaxKind`)으로 쪼개고, ③ **Parser**가 토큰을 **AST**로 만들고, ④ **Binder**가 노드↔**Symbol**(타입 메타데이터)을 묶어 **Symbol Table**을 만들고, ⑤ **Emitter**가 AST를 순회하며 **Type Checker** + Symbol Table을 이용해 JS·`.d.ts`·소스맵을 뽑는다. 에러도 단계별로 나뉜다 — 문법 깨짐은 **Scanner(SyntaxError)**, 의미 틀림은 **Type Checker(TypeError)**. 그래서 `let a: number = "hello"`는 문법은 통과하지만 타입 체크에서 걸린다.

#### ⭐️ 앞으로 기억할 것
- 1. **파이프라인 순서**
  Program(컨텍스트) → Scanner(토큰화) → Parser(AST) → Binder(Symbol Table) → Type Checker → Emitter. 각 단계 파일까지 외우면 소스 읽을 때 길잡이.
- 2. **Scanner vs Parser**
  Scanner = 텍스트를 `SyntaxKind` 토큰으로(어휘 분석). Parser = 토큰을 AST로(구문 분석). Scanner는 Parser 내부에서 생성됨.
- 3. **Binder/Symbol = 타입 정보의 저장소**
  노드↔Symbol 매핑이 Symbol Table. Type Checker가 이걸 보고 타입을 검증하고, Emitter도 이걸 보고 코드를 생성.
- 4. **산출물 3종은 이미터가 나눠 뽑는다**
  JS Emitter → `.js` + `.js.map`, Definition Emitter → `.d.ts`.
- 5. **에러 종류 = 발생 단계**
  ConfigFileErrors(tsconfig), SyntaxErrors(Scanner, 문법), TypeErrors(Checker, 의미). "문법은 맞는데 타입 에러"가 별개인 이유.

📌 결론
▎ tsc는 Scanner→Parser→Binder→Checker→Emitter로 이어지는 다단계 컴파일러다.
▎ 각 단계가 자기 책임 영역의 에러를 보고하기 때문에, 에러 종류만 봐도 어디서 막혔는지 짐작할 수 있다.
▎ ⭐️ 실무 적용 포인트
▎ - 빨간 줄을 볼 때 "이게 SyntaxError냐 TypeError냐"를 구분하면 원인 추적이 빨라진다(문법 깨짐 vs 타입 불일치).
▎ - `tsc --noEmit`이 타입 체크만 하고 JS를 안 뽑는 이유 = Emitter 단계를 건너뛰는 것 → CI 타입 검증에 적합.
▎ - `.d.ts`/`.js.map`은 Emitter 산출물 → `declaration`, `sourceMap` 옵션이 그 이미터를 켜고 끄는 스위치.
▎ - 더 깊게 → basarat의 TypeScript Compiler Internals로 실제 코드 위치 추적.
