# NEXT.JS의 이미지 최적화는 어떻게 동작하는가?

> **원문**: [NEXT.JS의 이미지 최적화는 어떻게 동작하는가?](https://oliveyoung.tech/2023-06-09/nextjs-image-optimization/) — 코난 (올리브영 Front-end Engineer)

Next.js 쓰면서 `next/image`를 그냥 "알아서 잘해주는 img 태그" 정도로만 알고 썼는데, 사실 안에서 무슨 일이 벌어지는지 전혀 모르고 있었다. 왜 어떤 이미지는 최적화가 안 되는지, sharp를 설치하라는 경고는 왜 뜨는지 — 이 글 보고 정리해둔다.

### NEXT.JS의 이미지 최적화

`next/image`가 기본으로 해주는 것들부터.

- 디바이스 크기에 맞는 이미지 사이즈 + 최신 포맷(WebP, AVIF) 지원
- Web Vitals의 `CLS`(Cumulative Layout Shift) 발생 방지
- 기본 레이지 로드, 옵션으로 블러 플레이스홀더
- 이미지 리사이징 — 외부(remote) 이미지도 포함

말로만 보면 감이 안 오는데, 저자가 3G 환경에서 돌린 비교가 꽤 충격적이다.

![next image 01](https://oliveyoung.tech/static/e832a859a35918e9c3ac68be689a89d3/024a7/next-image-01.png)

| | 파일 크기 | 다운로드 시간 |
|---|---|---|
| `<img>` | 1.9MB | 11.5s |
| `next/image` | 16.9KB | 862ms |

같은 이미지인데 100배 넘게 차이난다. 3G 기준이라 극단적이긴 해도, 이 정도면 그냥 안 쓸 이유가 없다.

![next image 02](https://oliveyoung.tech/static/b76a29bee8e19a9f0b4529fced2239d8/8e749/next-image-02.png)

![next image 03](https://oliveyoung.tech/static/5b72a17e04e9a6e326638df1b41a2c30/1b718/next-image-03.png)

#### Next/image는 어떻게 동작하나

핵심은 이거다. `next/image`로 렌더링된 이미지는 원본 경로를 그대로 요청하지 않는다. **`/_next/image` 라는 자체 엔드포인트로 요청을 돌린다.**

```
/_next/image?url=%2Fimages%2Fsample.png&w=1080&q=75
```

쿼리스트링에 담기는 값은 세 개.

| 파라미터 | 의미 |
|---|---|
| `url` | 원본 이미지 경로 (인코딩됨) |
| `w` | 디바이스에 맞춘 너비값 |
| `q` | 품질값, 기본 `75` |

즉 브라우저가 "나 이 이미지를 이 너비로, 이 품질로 줘"라고 요청하면 Next.js 서버가 그때 만들어서 내려주는 구조다. 이 변환을 담당하는 게 **Default Loader**.

![next image 04](https://oliveyoung.tech/static/ce1a04edd95bbfa2e83d983175b82dee/e8cbb/next-image-04.png)

#### 최적화 시점과 캐싱

여기가 제일 중요한 포인트다. 빌드 타임이 아니라 **런타임**이다.

> 요청이 들어왔을 때, dist 폴더 밑에 `cache/images` 폴더에 최적화한 이미지를 동적으로 만들고, 이후에 동일한 요청에 대해서는 이미 만들어 놓은 최적화한 이미지를 캐시로서 재사용합니다.

그래서 **첫 요청은 느리다.** 캐시 상태는 응답 헤더로 확인할 수 있다.

```
X-Nextjs-Cache: MISS   # 캐시 없음 — 지금 만드는 중
X-Nextjs-Cache: HIT    # 만들어둔 거 재사용
```

응답 시간 차이:

| | 응답 시간 |
|---|---|
| 첫 요청 (`MISS`) | 64ms |
| 캐시 히트 (`HIT`) | 5ms |

![next image 05](https://oliveyoung.tech/static/6740ba08b2a1695b376a47130103634d/ac7a9/next-image-05.png)

![next image 06](https://oliveyoung.tech/static/6d63dc59c3c91470f114b2f08b9f45cc/1235c/next-image-06.png)

![next image 07](https://oliveyoung.tech/static/ecb97d61ba67cc7293b38712c8ae80ba/e76f9/next-image-07.png)

`cache/images`에 쌓이는 구조라는 건, 배포할 때마다 캐시가 날아간다는 뜻이기도 하다. 배포 직후 첫 사용자들은 매번 `MISS`를 맞는다.

#### 최적화되지 않는 이미지

전부 다 최적화해주는 건 아니다. NEXT.JS가 **의도적으로** 건드리지 않는 포맷이 있다.

- ❌ `SVG` — 벡터라서 리사이징 의미 없음, 게다가 SVG는 스크립트를 품을 수 있어 보안 이슈도 있다
- ❌ `GIF` — 애니메이션이 복잡해서 변환 비용 대비 이득이 적음

![next image 08](https://oliveyoung.tech/static/4b3102a4c69e5120e74c74ef491f7202/ac7a9/next-image-08.png)

이런 이미지는 `unoptimized` props를 주거나, loader를 직접 오버라이드해야 한다.

```jsx
// ✅ SVG/GIF는 최적화 파이프라인 태우지 말고 그대로
<Image src="/logo.svg" width={120} height={40} alt="로고" unoptimized />
```

### Sharp vs Squoosh

`next/image`가 실제로 이미지를 변환할 때 쓰는 엔진 얘기. Next.js는 **sharp가 설치돼 있으면 sharp를, 없으면 Squoosh를** 쓴다.

![sharp 01](https://oliveyoung.tech/static/761b330637a8fdb6711ee66fe8a36933/698d8/sharp-01.png)

#### Sharp

> 다양한 크기의 JPEG, PNG, WebP, GIF, AVIF와 같은 이미지들을 더 작은 크기로, 그리고 웹에 진화적으로 변환해 주는 매우 빠른 속도의 모듈

내부적으로 `libvips` 기반 네이티브 모듈이라 빠르다.

![sharp 02](https://oliveyoung.tech/static/b72d514ecf8b847955976468fd184360/9c0ca/sharp-02.png)

#### Squoosh

Google Chrome Labs에서 만든 이미지 압축 라이브러리. WASM 기반이라 설치가 필요 없다는 장점이 있는데, 그만큼 **느리다.** 개발 환경용이라고 보면 된다.

![sharp 03](https://oliveyoung.tech/static/3349943825e682215c9fa45b2385b28d/b9f8c/sharp-03.png)

#### 성능 비교

**PNG → WebP**

| | 결과 크기 | 소요 시간 |
|---|---|---|
| Squoosh | 17.1KB | 228ms |
| Sharp | 16.9KB | **64ms** |

약 3~4배 차이.

![sharp 04](https://oliveyoung.tech/static/8945e225b27afa9728c54d1e385fc38d/7fe1f/sharp-04.png)

**PNG → AVIF**

| | 결과 크기 | 소요 시간 |
|---|---|---|
| Squoosh | 10.8KB | 1.24s |
| Sharp | 13.1KB | **202ms** |

약 6배 차이. AVIF는 인코딩 자체가 무거워서 격차가 더 벌어진다. (대신 Squoosh 쪽이 용량은 더 작게 뽑는다 — 근데 1.24초를 감수할 만한 차이는 아니다.)

![sharp 05](https://oliveyoung.tech/static/1bb07c1fbfc6e6ffbd088be9829810eb/4a768/sharp-05.png)

결론은 명확하다. **프로덕션이면 sharp 깔아라.**

```bash
npm install sharp
```

#### AVIF 호환성은 어떻게 처리되나

AVIF가 압축률은 좋은데 지원 안 하는 브라우저가 있지 않나? 하는 걱정이 드는데, 이건 NEXT.JS가 알아서 해준다.

브라우저는 요청할 때 `Accept` 헤더에 **자기가 처리할 수 있는 이미지 포맷을 실어 보낸다.**

```
# Chrome
Accept: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8

# Edge
Accept: image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8
```

NEXT.JS는 이 헤더를 읽고 **그 브라우저가 소화 가능한 포맷으로 변환해서** 내려준다. 그러니까 설정에 AVIF를 켜놔도, AVIF를 못 받는 브라우저에는 WebP가 간다.

![sharp 06](https://oliveyoung.tech/static/61871248109b5ca4ba4bb26af99c9f67/c3ac1/sharp-06.png)

![sharp 07](https://oliveyoung.tech/static/1e5a061b660b19df5b63d74b1e5239c8/66227/sharp-07.png)

![sharp 08](https://oliveyoung.tech/static/4e9413c4af9fb823d808a9696c477191/a4f00/sharp-08.png)

![sharp 09](https://oliveyoung.tech/static/8830e1e582a78d64f2ac89e8f673f256/934f0/sharp-09.png)

```js
// next.config.js — 호환성 걱정 없이 AVIF 켜도 된다
module.exports = {
  images: {
    formats: ['image/avif', 'image/webp'], // 앞에 있는 것부터 시도
  },
}
```

### 📌 정리

`next/image는 런타임에 sharp로 이미지를 변환하고 캐시한다`

#### 핵심

> `next/image`는 `/_next/image?url=...&w=...&q=...` 엔드포인트로 요청을 우회시켜, **요청 시점에** 디바이스 크기·품질·브라우저 지원 포맷에 맞춰 이미지를 변환한다. 변환 결과는 `cache/images`에 저장돼 이후 요청에서 재사용된다. 변환 엔진은 sharp가 있으면 sharp, 없으면 Squoosh인데 성능 차이가 3~6배라 프로덕션에선 sharp가 사실상 필수다.

#### ⭐️ 앞으로 기억할 것

- 1. 최적화는 빌드 타임이 아니라 런타임이다
첫 요청은 이미지를 실시간으로 만들기 때문에 느리다(`X-Nextjs-Cache: MISS`). 두 번째부터 `HIT`. 배포하면 캐시가 날아가므로 배포 직후엔 다시 느려진다.
```
X-Nextjs-Cache: MISS  → 64ms
X-Nextjs-Cache: HIT   → 5ms
```

- 2. 프로덕션이면 sharp를 반드시 설치한다
Squoosh는 WASM 기반이라 설치 없이 동작하지만 느리다. AVIF 변환은 1.24s vs 202ms로 6배 차이. 런타임 변환이라는 걸 감안하면 이 차이가 그대로 사용자 대기 시간이 된다.
```bash
npm install sharp
```

- 3. AVIF는 호환성 걱정 없이 켜도 된다
브라우저가 `Accept` 헤더로 지원 포맷을 알려주고, NEXT.JS가 그에 맞춰 변환한다. AVIF 못 받는 브라우저엔 자동으로 WebP가 나간다.
```js
images: { formats: ['image/avif', 'image/webp'] }
```

- 4. SVG와 GIF는 최적화 대상이 아니다
벡터라 리사이징 의미가 없고(SVG), 애니메이션 변환 비용이 크다(GIF). `unoptimized`를 붙이거나 커스텀 loader를 쓴다.
```jsx
<Image src="/icon.svg" width={24} height={24} alt="" unoptimized />
```

- 5. `w`와 `q`는 내가 통제하는 값이다
`w`는 `sizes`/`deviceSizes` 설정에서, `q`는 `quality` prop에서 결정된다(기본 75). 캐시 키가 이 조합이라, 불필요하게 많은 사이즈를 열어두면 캐시 히트율이 떨어진다.

> **📌 결론**
> ▎ `next/image`는 `<img>` 대비 3G 환경에서 1.9MB/11.5s → 16.9KB/862ms 수준의 차이를 만든다.
> ▎ 최적화는 런타임에 일어나고 결과는 `cache/images`에 캐시된다 — 첫 요청은 느린 게 정상.
> ▎ 변환 엔진은 sharp(빠름) / Squoosh(느림, 폴백) 두 갈래. 성능 차 3~6배.
> ▎ `Accept` 헤더 기반 자동 포맷 협상 덕에 AVIF를 켜도 호환성 문제가 없다.
> ▎ SVG·GIF는 의도적으로 최적화 제외 — `unoptimized`로 처리.
> ▎ ⭐️ 실무 적용 포인트: ① 프로덕션 Dockerfile/의존성에 `sharp` 포함됐는지 확인 ② `formats: ['image/avif', 'image/webp']` 설정 ③ 배포 직후 이미지 응답이 느린 건 캐시 워밍업 문제이므로, CDN을 앞에 두거나 주요 이미지 프리워밍 고려 ④ `deviceSizes`를 무분별하게 늘리지 말 것 — 캐시 파편화.
