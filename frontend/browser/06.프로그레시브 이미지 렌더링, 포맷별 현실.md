# 프로그레시브 이미지 렌더링, 포맷별 현실

> **원문**: [The present and potential future of progressive image rendering][ref-1] — Jake Archibald (2025.10.15)
> **번역 출처**: [[번역] 프로그레시브 이미지 렌더링의 현재와 잠재적 미래][ref-2] — devowen

"JPEG XL 쓰면 프로그레시브 렌더링 되니까 좋다"는 말을 몇 번 들었는데, 막상 브라우저에서 진짜 그런지는 확인해본 적이 없었다. 지난번 [`fetch 스트림 노트`][ref-3]에 이어서 Jake Archibald 글을 하나 더 읽고 정리해둠. 결론부터 말하면 **기대보다 훨씬 복잡하고, 생각보다 덜 중요하다.**

### 프로그레시브 렌더링이란

파일을 다 받기 전에, 받은 만큼으로 **저해상도·저품질 버전이나 일부분**을 먼저 그려주는 것. 느린 네트워크에서 빈 박스 대신 뭔가 보여줄 수 있다는 게 장점이다.

실험 대상은 이 여우 사진. 1598×1753에 디테일이 많아서 AVIF로도 155kB나 된다. 이 이미지를 포맷별로 비슷한 용량으로 만들어서 "언제부터 그려지나 / 언제 여우인지 알아보나"를 비교했다.

![겨울 풀밭에 서 있는 여우 사진](https://jakearchibald.com/c/fox-DSbxk4jA.avif)

### 포맷별 현황 한눈에

| 포맷 | 프로그레시브 여부 | 렌더링 시작 시점 | 비고 |
|------|------|------|------|
| JPEG (프로그레시브) | ✅ 전 브라우저 | 약 1.2kB, 첫 패스 완료 약 33kB(21%) | 사실상 공짜. 디코딩 약 40% ↑ (그래도 ~1.3ms) |
| PNG | 위→아래 순차 | - | 인터레이스 모드는 용량이 커져서 비추 |
| WebP | 파폭·크롬만 위→아래 | 약 43kB(28%) | **사파리는 다 받을 때까지 아무것도 안 그림** |
| AVIF (일반) | ❌ | 완료 시 한 번에 | - |
| AVIF (`--layered`) | 크로미엄만 | 약 5.8kB(4%) | 실험 기능, 제약 많음 |
| JPEG XL | 사파리 지원하지만 **프로그레시브 안 함** | - | 사파리 디코딩 느림 |

#### JPEG — 오래됐지만 제일 믿음직
[`Squoosh`][ref-4]는 기본값이 프로그레시브 JPEG다. 재밌는 건 브라우저마다 초기 렌더링 모양이 다르다는 것.

![부분 로드된 여우 이미지 — 사파리는 블록, 파폭/크로미엄은 부드러움](https://jakearchibald.com/c/jpeg-safari-vs-Br8Dbgrp.avif)

사파리는 깍두기 블록, 파이어폭스·크로미엄은 부드럽게 뭉개서 보여준다. 둘 다 알아볼 순 있지만 부드러운 쪽이 확실히 낫다.

#### WebP — 사파리가 발목
파폭·크롬에선 색상 데이터가 파일 앞부분에 있어서 루마 채널이 들어오기 시작해야 그리기 시작한다(28% 시점). 사파리는 아예 프로그레시브를 안 한다.

#### AVIF — 숨겨진 `--layered`
일반 AVIF는 전혀 안 된다. 근데 libavif에 실험적인 **레이어 인코딩**이 있다. 직접 컴파일해야 쓸 수 있음.

```bash
# 레이어 2개: 1/8 해상도 최저 품질 + 원본 해상도 좋은 품질
avifenc -s 0 -y 420 --layered \
  --scaling-mode:u 1/8 -q:u 0 fox.png \
  --scaling-mode:u 1 -q:u 16 fox.png \
  fox-progressive.avif
```

두 번째 레이어가 첫 번째 레이어 데이터를 참조한다 — 동영상의 P-프레임 같은 구조. 크로미엄에서 5.8kB 시점에 흐릿한 초기 렌더링이 나오는데, 이 용량치고는 꽤 괜찮다.

단점이 많다.
- `--layered`에선 품질 수치가 일반 인코딩과 다르게 동작
- 파일 크기 오버헤드 약 5~6kB (초기 패스만큼)
- 스케일은 정해진 값만, 최소 1/8
- 레이어 늘리면 인코더 에러 or 용량 ~400kB 폭증
- 크롬 디코딩 약 40% ↑ (첫 레이어 건너뛰는 최적화가 아직 없는 듯). 파폭·사파리는 1~2%

#### JPEG XL — 기대와 제일 다른 결과
개발자들이 JPEG XL을 원하는 이유 1위가 프로그레시브 렌더링인데, 정작 **유일하게 지원하는 사파리가 프로그레시브를 안 한다.** 솔직히 이게 제일 의외였다.

더 놀라운 건 디코딩 속도.

| 비교 | 결과 |
|------|------|
| 사파리 JPEG XL vs 같은 이미지 AVIF | 약 2.5배 느림 (M4 Pro에서 +17ms) |
| 크로미엄 플래그 JPEG XL vs AVIF | 6배 이상 느림 |
| 파폭 플래그 JPEG XL | 사파리와 비슷 |

사파리의 JPEG XL 지원은 브라우저가 아니라 OS에서 온다. 단일 코어로 돈다는 얘기도 있어서 개선 여지는 있을 수 있다. 그래도 "JPEG XL은 디코딩이 빠르다"는 통념은 현재 구현 기준으론 안 맞는다는 것.

크로미엄 플래그 구현은 프로그레시브를 하긴 했지만 60kB(39%)까지 아무것도 안 그렸다. 이건 포맷 한계가 아니라 **디코더 한계**다.

### 근데 프로그레시브 렌더링, 진짜 중요한가?

![언덕을 달리는 오래된 윌리엄스 F1 자동차](https://jakearchibald.com/c/f1-DK8ANwoR.avif)

이 F1 사진은 HD 넘는데 AVIF로 56.4kB다. 여우처럼 디테일 빽빽한 사진이 오히려 예외고, 요즘 포맷이면 대부분 이미지가 작다.

그리고 Kornel이 짚은 포인트가 핵심이다. 실제 느린 네트워크에서 데이터는 **졸졸 흐르는 게 아니라 뚝뚝 끊겨서** 들어온다(혼잡, 버퍼블로트, 약한 신호). 5초 걸리는 이미지라도 5초에 걸쳐 고르게 들어오는 게 아니라 대부분 시간은 아무것도 안 오다가 한꺼번에 온다.

그러니 프로그레시브 렌더링이 보이려면 운이 묘하게 맞아야 한다.
- 나쁜 운: 네트워크가 느려서 전체를 받는 데 오래 걸림
- 좋은 운: 그 와중에 일부는 먼저 도착함

그래서 글쓴이 입장은 이렇다.
- 프로그레시브 지원을 위한 **파일 크기 오버헤드는 최소**여야 하고
- 프로그레시브가 필요 없을 땐(파일 다 받았을 때) **디코딩 오버헤드도 거의 0**이어야 한다

처음엔 프로그레시브 렌더링을 강하게 옹호하려고 글을 시작했는데, 파볼수록 확신이 줄었다고. 이 솔직함이 좋았다.

### "프로그레시브로 반응형 이미지 대체" — 안 된다

JPEG XL 최대 해상도 파일 하나만 두고, 브라우저가 필요한 해상도만큼 받으면 끊으면 되지 않냐는 아이디어.

1. 일부 받음 → 2. 부분 디코딩 → 3. "이 정도면 충분" 판단 → 4. 서버에 중단 요청 → 5. 서버가 전송 중단

문제는 **단계마다 지연**이 있어서, 실제로 끊기기 전에 이미지당 수 MB를 쓸데없이 받게 된다는 것.

바이트 범위를 미리 지정하는 가상의 기능이 생긴다면 모를까.

```html
<!-- ❌ 존재하지 않는 가상의 문법 -->
<img srcset="photo.jxl#range=0-20000 400w, photo.jxl#range=0-80000 1200w" sizes="..." />

<!-- ✅ 지금 쓰는 반응형 이미지 -->
<img
  srcset="photo-400.avif 400w, photo-1200.avif 1200w"
  sizes="(max-width: 600px) 100vw, 50vw"
  src="photo-1200.avif"
  alt="..."
/>
```

이것도 CORS 문제로 무산될 수 있고, 된다 해도 복잡도는 지금 `srcset`이랑 비슷하다. 썸네일 → 전체화면 전환 시 이어받기가 된다는 장점은 있지만, 해상도를 세밀하게 제어할 수 있는 **기존 반응형 이미지가 여전히 더 유연하다.**

### JPEG XL의 잠재력 (디코더만 따라온다면)

포맷 자체는 가능성이 있다.

| 도구 | 포인트 |
|------|------|
| `cjxl --progressive` (0.11.1) | 39%까지 안 그려짐 |
| `cjxl --progressive_dc 1` | 훨씬 일찍 렌더링. **`--help`에 안 나오고 `--help -v -v`로만 보임** 하하. 용량 영향 거의 없음 |
| `djxl` | 조기 렌더링 미지원 |
| [`jxl-oxide`][ref-5] (Rust) | 조기 렌더링 지원, wasm 데모 있음. 브라우저용으론 느림 |
| `jxl-rs` (Rust) | 파이어폭스용 개발 중 |

jxl-oxide로 보면 6kB쯤에서 뭔지 감이 오고, 46kB면 꽤 선명하다. 60kB 이후엔 디테일이 사각 블록 단위로 채워지는데, **블록 순서를 자유롭게** 정할 수 있다. 중심점을 지정하거나, 똑똑한 인코더면 얼굴부터 선명하게 할 수도 있다.

AVIF 5.8kB 렌더링과 비교하면:
- 6kB 근처에서 끊기면 → AVIF가 나음
- 50kB쯤 받은 상태면 → 패스가 여러 단계인 JPEG XL이 훨씬 나음

다만 브라우저에서 쓸 만큼 빨라지기 전까진 전부 이론.

### AVIF에 바라는 것: 블러 미리보기 내장

글쓴이 경험상 AVIF가 웹 품질 기준으로 JPEG XL보다 **작고, 현재 구현 기준 디코딩도 훨씬 빠르다.** 부족한 건 프로그레시브 기능 하나.

제안하는 아이디어가 흥미롭다.
- 원본을 축소 → 최저 품질 AVIF로 압축 → **후처리 블러** → 약 2kB짜리 미리보기
- 이걸 전체 이미지 파일 **앞부분에 별도 이미지로** 넣는다

| 장점 | 설명 |
|------|------|
| 품질 조절 가능 | 개발자가 허용할 오버헤드(2kB, 10kB…)를 직접 정함 |
| 디코딩 오버헤드 0 | 파일을 다 갖고 있으면 미리보기를 그냥 건너뜀 |
| 블러를 포맷에 포함 | CSS `filter`로 하면 렌더링 비용 큼 → 포맷이 싼 블러를 쓰도록 |

용량만 보면 미리보기만큼 100% 오버헤드지만, 그 크기를 개발자가 통제한다는 게 포인트. 2020년에 [`AVIF 이슈`][ref-6]로 처음 제안했던 아이디어라고 한다.

사실 이게 우리가 지금 손으로 하고 있는 **LQIP(Low Quality Image Placeholder)**, BlurHash 같은 걸 포맷 레벨로 내린 거라서 실무자 입장에서 제일 공감됐다.

### 📌 정리
`프로그레시브 렌더링 < 이미지 용량 줄이기`

#### 핵심
> 브라우저의 프로그레시브 렌더링 지원은 포맷·브라우저마다 제각각이고, 제대로 되는 건 사실상 **프로그레시브 JPEG** 정도다.
> JPEG XL은 유일 지원 브라우저인 사파리에서 프로그레시브도 안 되고 디코딩도 느리다. AVIF는 실험적인 `--layered`만 있다.
> 실제 네트워크는 끊기듯 들어와서 프로그레시브 렌더링을 볼 확률 자체가 낮다. **용량 최적화와 반응형 이미지가 먼저**다.

#### ⭐️ 앞으로 기억할 것
- 1. JPEG를 쓴다면 프로그레시브로 인코딩
용량 차이는 사실상 없고 디코딩 비용도 ms 단위. Squoosh 기본값이기도 하다.

- 2. "JPEG XL = 프로그레시브 + 빠른 디코딩"은 현재 구현 기준 틀린 말
사파리만 지원, 프로그레시브 안 함, AVIF보다 2.5배 느린 디코딩. 도입 검토할 땐 스펙이 아니라 **실제 브라우저 구현**을 기준으로.

- 3. WebP도 사파리에선 다 받을 때까지 빈칸
WebP면 알아서 점진적으로 보이겠지 하고 믿지 말 것.

- 4. 프로그레시브로 반응형 이미지를 대체할 수 없다
중단 요청 지연 때문에 불필요한 데이터를 대량으로 받는다. `srcset` + `sizes`는 계속 필수.
```html
<!-- ❌ 고해상도 한 장으로 퉁치기 -->
<img src="hero-3200.jxl" alt="..." />

<!-- ✅ 뷰포트에 맞는 해상도를 브라우저가 고르게 -->
<img srcset="hero-800.avif 800w, hero-1600.avif 1600w, hero-3200.avif 3200w"
sizes="100vw" src="hero-1600.avif" width="1600" height="900" alt="..." />
```

- 5. 로딩 중 경험은 지금은 플레이스홀더로 직접
포맷 레벨 블러 미리보기는 아직 제안 단계. 당장은 `width`/`height`로 CLS 막고, 작은 블러 이미지나 배경색 플레이스홀더를 두는 게 현실적.
```css
/* 흐린 미리보기를 배경으로 깔고, 원본이 로드되면 덮어씀 */
.thumb {
  aspect-ratio: 16 / 9;
  background: url('hero-blur-20px.avif') center / cover;
}
```

- 6. 느린 네트워크는 "고르게 느린" 게 아니다
혼잡·버퍼블로트 때문에 데이터가 몰아서 온다. 점진적 로딩 UX를 설계할 때 이 가정을 깔고 가자.

> **📌 결론**
> ▎ 프로그레시브 렌더링 지원은 포맷 × 브라우저 조합마다 다르고, 확실한 건 프로그레시브 JPEG뿐
> ▎ JPEG XL의 장점(프로그레시브, 빠른 디코딩)은 현재 브라우저 구현에선 아직 실현 안 됨
> ▎ AVIF는 작고 빠르지만 프로그레시브는 실험 단계 — 블러 미리보기 내장 같은 개선이 필요
> ▎ 실제 네트워크 특성상 프로그레시브 렌더링을 볼 기회 자체가 적어서 용량 최적화를 대신할 수 없다
> ▎ ⭐️ 실무 적용 포인트: 포맷 욕심보다 AVIF + `srcset`/`sizes` + 명시적 크기 + 가벼운 플레이스홀더 조합을 기본으로 가져가기
