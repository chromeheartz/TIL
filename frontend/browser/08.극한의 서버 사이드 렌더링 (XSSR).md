# 극한의 서버 사이드 렌더링 (XSSR)

> **원문**: [EXTREME SERVER SIDE RENDERING](https://www.scd31.com/posts/extreme-server-side-rendering) — Sophie (The Cat House)
> **번역 출처**: [극한의 서버 사이드 렌더링](https://www.yeongseo-blog.site/blog/extreme-server-side-rendering) — yeongseo-blog

제목부터 장난스러운데 내용은 꽤 진지한 글이다. "JS 없이 HTTP 응답을 안 끝내고 계속 흘려보내면, 그게 곧 실시간 UI 아니야?"라는 발상 하나로 플래피 버드까지 만들어버렸다. 실무에 그대로 쓸 일은 없겠지만, 브라우저가 HTML을 **스트리밍으로 파싱·렌더링한다**는 사실을 이렇게 극단적으로 보여주는 글은 처음이라 정리해둔다.

### 보통의 SSR은 뭐였더라

저자는 SSR을 두 갈래로 나눈다.

#### 올드스쿨 SSR

`/users/39` 같은 요청이 오면 서버가 그때그때 HTML을 만들어서 준다. 디스크에 정적 파일은 없다. 대신 한 번 내려주면 끝이다. JS가 없으니 페이지는 로드 이후 절대 안 바뀐다.

#### 뉴스쿨 SSR

구조는 같은데, 프론트에 JS가 붙어서 사용자가 뭔가 하면 백엔드에 요청하고 돌려받은 HTML 조각을 페이지에 끼워 넣는다. `htmx`나 Hotwire 같은 방식을 떠올리면 된다. 동적이긴 한데 결국 **프론트 로직을 또 관리해야 한다.**

저자의 질문은 이거다. "JS 없이 동적인 페이지를 만들 수는 없을까?"

### 아주 느린 HTTP 서버

핵심은 HTTP 응답이 그냥 텍스트라는 점이다. 헤더가 오고, 빈 줄, 그 다음 HTML. 그리고 이건 **한 번에 다 올 필요가 없다.**

저자는 `netcat`으로 사람이 직접 서버 역할을 하는 실험을 했다. 브라우저로 접속해두고 터미널에 HTML을 한 줄씩 손으로 타이핑하면, 브라우저가 그 줄이 도착할 때마다 화면에 그린다. Firefox, Chromium 둘 다 된다고.

```bash
# 사람이 서버가 되는 실험 — 8080 포트를 열고 대기
nc -l 8080

# 브라우저로 http://localhost:8080 접속 후 터미널에 직접 입력
HTTP/1.1 200 OK
Content-Type: text/html

<h1>안녕</h1>
<p>한 줄 칠 때마다 브라우저에 바로 뜬다</p>
```

여기서 발상이 튄다. 연결을 **안 닫고** 계속 열어두면, 서버가 원할 때마다 HTML을 더 밀어 넣을 수 있다. 그리고 그게 `<style>` 태그면? 이미 그려진 요소를 옮기고, 숨기고, 새로 추가하는 것까지 전부 CSS만으로 된다. JS 한 줄 없이.

저자는 이걸 **extreme server side rendering**, 줄여서 `XSSR`이라고 부른다. 하하.

### 사용자 입력은 어떻게 받나

출력은 해결됐는데 입력이 문제다. 일반 `<form>`을 제출하면 페이지가 새로 로드되면서 열어둔 스트림이 끊긴다. 그럼 XSSR의 의미가 없어진다.

해법은 (DJ Chase가 알려줬다는) **숨겨진 iframe 트릭**이다. 폼의 `target`을 숨긴 iframe으로 지정하면, 제출할 때 iframe만 새로고침되고 본 페이지는 그대로 스트림을 받고 있다.

```html
<!-- 화면에 안 보이는 iframe: 폼 제출 결과가 여기로 간다 -->
<iframe name="transFrame" id="transFrame" style="display: none;"></iframe>

<!-- target을 iframe으로 → 메인 페이지는 리로드 안 됨 -->
<form target="transFrame" method="POST" action="/action">
  <!-- 첫 로드 때 서버가 발급한 UUID: 어느 페이지(세션)의 입력인지 구분 -->
  <input type="hidden" name="uuid" value="USER-UUID-GOES-HERE" />
  <input type="submit" value="" />
</form>
```

여기서 `uuid`가 중요하다. 서버 입장에선 "이 POST가 지금 열려 있는 수많은 스트림 중 어느 것에 대한 입력인지"를 알아야 한다. 그래서 첫 응답을 만들 때 UUID를 하나 발급해서 폼에 박아두고, `/action`으로 들어온 요청을 그 UUID의 스트림에 연결한다.

| 구성 요소 | 역할 |
|---|---|
| 열려 있는 HTTP 응답 | 서버 → 브라우저 출력 채널 (HTML/CSS를 계속 추가) |
| `form target="iframe"` | 브라우저 → 서버 입력 채널 (메인 페이지 리로드 없이) |
| hidden `uuid` | 입력과 출력 스트림을 짝지어주는 키 |

### 진짜로 뭘 만들어보자: 플래피 버드

증명용으로 저자는 [플래피 버드 클론][flappy]을 만들었다.

- 점수 텍스트가 바뀌고
- 파이프가 움직이고
- 클릭하면 새가 점프한다

클릭은 화면 전체를 덮는 투명 submit 버튼 + 위의 iframe 트릭으로 처리한다. 버튼에 포커스가 가면 스페이스/엔터도 먹는다.

물리 연산은 **전부 서버**에서 돈다. 서버가 60FPS로 새 위치를 계산해서 CSS를 계속 흘려보내는 구조라, 브라우저 탭은 영원히 "로딩 중" 상태다. JS를 꺼도 동작한다. `curl`로 찔러보면 CSS가 끝없이 쏟아지는 걸 볼 수 있다고.

원리를 내 식대로 줄여보면 대충 이런 느낌이다. (원문은 Rust, 아래는 이해용 Node 스케치)

```js
import http from 'node:http'

http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' })
  // 첫 화면: 새 한 마리
  res.write('<div id="bird" style="position:absolute;width:20px;height:20px;background:gold"></div>')

  let y = 0
  const timer = setInterval(() => {
    y = (y + 2) % 300
    // ✅ 응답을 끝내지 않고 <style>을 계속 덧붙인다 → 뒤에 온 규칙이 이긴다
    res.write(`<style>#bird{top:${y}px}</style>`)
  }, 1000 / 60)

  req.on('close', () => clearInterval(timer)) // 탭 닫으면 정리
}).listen(8080)
```

뒤에 온 `<style>`이 같은 선택자를 덮어쓰니까 "애니메이션"이 된다. 대신 DOM에 `<style>` 태그가 끝없이 쌓인다. 몇 분 지나면 버벅인다는 게 이것 때문일 거다.

### 생각보다 나쁘지 않다? (트레이드오프)

#### 성능

- **클라이언트**: 몇 분 플레이하면 Firefox, Chromium 둘 다 느려진다. 다만 이건 60FPS로 계속 쏘니까 그런 거고, 사용자 액션이 있을 때만 업데이트하는 페이지라면 별 문제 없을 수도 있다.
- **서버<strong>: 오래된 홈랩 머신에서 단순한 Rust 서버가 </strong>코어당 동시 게임 약 500개**를 처리했다. 저자는 "적당히 복잡한 Rails 앱보다 낫다"고 비교한다.

#### 대역폭

- 게임 하나당 약 **20 KiB/s**.
- 1MB짜리 JS 앱을 받는 것과 같아지려면 약 49초를 플레이해야 한다.
- 프레임레이트만 낮춰도 확 줄어든다.

#### 레이턴시

이게 진짜 약점이다. 클릭 한 번마다 서버까지 왕복해야 반응이 온다.

| 위치 (서버는 캐나다 대서양 연안) | 체감 |
|---|---|
| 캐나다 대서양 연안 | 플레이 가능 |
| 미국 동부 | 티가 남 |
| 미국 서부 | 거슬림 |
| 지구 반대편 | 플레이 불가 |

저자는 "엣지에 올리면 되겠네"라고 반쯤 비꼬듯 말하고, 그냥 [소스][source]를 받아 로컬에서 돌려보라고 한다. 솔직히 이게 XSSR의 본질적 한계다. **입력 → 화면 반영 사이에 반드시 네트워크가 끼어 있다.**

### 덤: 페디버스를 터뜨린 이야기

저자가 이 데모 링크를 Pleroma(페디버스 서버)에 올렸더니, 글이 퍼지는 동안 서버가 3~4번 죽었다 살아났다.

원인은 **링크 미리보기**였다. Pleroma가 서버 측에서 링크 미리보기를 만들려고 URL에 접속하는데, 이 페이지는 응답이 영원히 안 끝난다. 끝없이 조금씩 흘러들어오는 연결을 제대로 처리하지 못하는 앱들이 있는 거다. 친구 Olivia가 Pleroma 소스에서 원인을 찾았고, DoS 벡터로 보안 버그 제보를 해서 패치됐다.

이 부분이 오히려 실무적으로 제일 와닿았다. 남의 URL을 서버에서 fetch하는 기능(미리보기, 웹훅, 크롤러)은 **응답이 안 끝나는 경우**를 반드시 가정해야 한다.

### 앞으로 해볼 만한 것

- **서버에서 도는 React**: 가상 DOM을 통째로 서버에서 돌리고, diff만 XSSR로 브라우저에 쏘는 것. 저자도 비현실적이라고 인정하지만 재밌는 아이디어.
- **구형 기기용 프록시**: 헤드리스 브라우저가 최신 사이트를 렌더링해서 DOM을 만들고, 그걸 XSSR로 스트리밍. JS를 못 돌리는 오래된 기기에서도 최신 사이트를 볼 수 있게.

### 📌 정리

`HTTP 응답은 끝내지 않아도 된다. 브라우저는 도착하는 대로 그린다. 이걸 극단까지 밀면 JS 없는 실시간 UI가 된다.`

#### 핵심

> HTTP 응답을 닫지 않고 HTML/`<style>`을 계속 흘려보내면, 브라우저가 스트리밍 파싱으로 도착하는 즉시 반영한다. 입력은 `target`을 숨긴 iframe으로 지정한 폼 + UUID로 받아서 리로드 없이 서버에 전달한다. 이걸로 서버가 물리를 돌리는 60FPS 플래피 버드를 JS 없이 만들었다. 서버 효율은 의외로 괜찮지만(코어당 500게임, 20KiB/s), 모든 입력이 왕복해야 해서 레이턴시가 치명적이다. 덤으로, 끝나지 않는 응답은 링크 미리보기 같은 서버 측 fetch를 DoS시킬 수 있다.

#### ⭐️ 앞으로 기억할 것

1. 브라우저는 HTML을 "스트리밍으로" 그린다
응답이 다 와야 그리는 게 아니다. React 18의 `renderToPipeableStream`, Next.js의 `loading.tsx`/Suspense 스트리밍이 다 이 성질 위에 서 있다. "먼저 보낼 수 있는 건 먼저 보낸다"가 TTFB·FCP 최적화의 기본기다.
```js
// ✅ 셸(head, 레이아웃)을 먼저 flush → 브라우저가 CSS/폰트 다운로드를 일찍 시작
res.write('<!doctype html><html><head><link rel="stylesheet" href="/app.css"></head><body>')
const data = await slowQuery() // 느린 데이터는 그 다음
res.end(`<main>${render(data)}</main></body></html>`)
```

2. 같은 선택자의 CSS는 나중 것이 이긴다
XSSR 애니메이션의 원리가 결국 캐스케이드다. 명시도가 같으면 문서 순서상 뒤에 온 규칙이 적용된다. 디버깅할 때 "왜 이 스타일이 안 먹지?"의 단골 원인이기도 하다.

3. `form target`으로 리로드 없는 제출이 된다
`fetch`가 없던 시절의 고전 트릭인데, JS 없이 동작해야 하는 환경(점진적 향상, JS 로드 전 폼)에서 여전히 쓸모 있다.
```html
<!-- ❌ 제출하면 페이지 전체가 이동 -->
<form action="/action" method="POST">...</form>

<!-- ✅ 결과는 숨긴 iframe으로, 현재 페이지는 유지 -->
<iframe name="sink" hidden></iframe>
<form action="/action" method="POST" target="sink">...</form>
```

4. 서버 상태 UI의 진짜 비용은 레이턴시
대역폭·서버 CPU는 생각보다 싸다. 문제는 모든 상호작용이 네트워크 왕복이라는 것. Phoenix LiveView, Blazor Server, htmx 같은 서버 주도 UI를 고를 때도 "사용자와 서버 사이 거리"와 "즉각 반응이 필요한 인터랙션"부터 따져야 한다. 그런 인터랙션은 결국 클라이언트에서 낙관적으로 처리하게 된다.

5. 서버에서 남의 URL을 fetch할 땐 타임아웃과 크기 제한 필수
링크 미리보기, 웹훅, OG 이미지 수집 같은 기능은 응답이 끝나지 않거나 무한히 큰 경우를 반드시 막아야 한다.
```js
// ✅ 시간 제한 + 바이트 제한
const res = await fetch(url, { signal: AbortSignal.timeout(5000) })
const reader = res.body.getReader()
let size = 0
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  size += value.length
  if (size > 1_000_000) { await reader.cancel(); break } // 1MB 넘으면 중단
}
```

> 📌 결론  
> ▎ HTTP 응답을 열어둔 채 HTML/CSS를 흘려보내면 JS 없이도 화면이 계속 바뀐다. 이게 XSSR.  
> ▎ 입력은 숨긴 iframe을 target으로 한 폼 + UUID로 리로드 없이 받는다.  
> ▎ 서버 처리량과 대역폭은 의외로 감당 가능하지만, 레이턴시는 구조적으로 못 피한다.  
> ▎ 끝나지 않는 응답은 서버 측 fetch를 쓰는 서비스에 DoS 벡터가 될 수 있다.  
> ▎ ⭐️ 실무 적용 포인트: SSR 응답에서 셸을 먼저 flush하고 있는지 확인해보자. 스트리밍 SSR의 이득은 거기서 나온다.  
> ▎ ⭐️ 실무 적용 포인트: 서버에서 외부 URL을 가져오는 코드가 있다면 `AbortSignal.timeout`과 응답 크기 제한부터 걸자.
