# innerHTML 대신 setHTML — 브라우저 기본 XSS 방어

> **원문**: [Goodbye innerHTML, Hello setHTML: Stronger XSS Protection in Firefox 148](https://hacks.mozilla.org/2026/02/goodbye-innerhtml-hello-sethtml-stronger-xss-protection-in-firefox-148/) — Tom Schuster, Frederik Braun, Christoph Kerschbaumer (Mozilla)
> **번역 출처**: [[번역] 굿바이 innerHTML, 반가워 setHTML: Firefox 148에서 한층 강화된 XSS 방어](https://velog.io/@superlipbalm/goodbye-innerhtml-hello-sethtml-stronger-xss-protection-in-firefox-148) — Chanhee Kim

`innerHTML`에 사용자 입력 넣을 때마다 "DOMPurify 붙였나?" 한 번씩 확인하는 게 습관이 됐는데, 이제 브라우저가 그걸 기본으로 해준다고 해서 읽어봤다. Firefox 148이 표준 [`Sanitizer API`][sanitizer-spec]를 처음으로 출시했다는 소식.

### XSS는 여전히 현역이다

[`XSS`][xss](Cross-Site Scripting)는 공격자가 웹사이트에 임의의 HTML/JS를 심는 공격이다. 심어진 스크립트는 그 사이트의 권한으로 돌아가니까 사용자 세션, 쿠키, 화면에 보이는 데이터까지 다 노출될 수 있다.

솔직히 오래된 취약점이라 다 해결된 줄 알았는데, 거의 10년째 웹 취약점 Top 3(CWE-79) 안에 계속 들어가 있다고 한다. 하하... 아직도 다들 당하고 있다는 얘기.

#### CSP가 있긴 한데

Mozilla는 2009년에 이미 [`CSP`][csp](Content-Security-Policy)를 만들었다. 페이지에서 어떤 스크립트·리소스를 불러올 수 있는지 서버가 제한하는 방식인데, 문제는 **설정이 어렵다**는 것.

- 기존 사이트에 적용하려면 구조를 꽤 뜯어고쳐야 함
- 정책을 계속 리뷰·관리해줄 보안 담당자가 사실상 필요함

그래서 강력한 것에 비해 실제로 제대로 쓰는 곳이 많지 않았다. 이 빈틈을 메우려고 나온 게 `Sanitizer API`다.

### Sanitizer API와 setHTML()

핵심 아이디어는 단순하다. **신뢰할 수 없는 HTML을 DOM에 넣기 전에, 브라우저가 위험한 부분을 걸러준다.**

![Sanitizer 동작 다이어그램](https://hacks.mozilla.org/wp-content/uploads/2026/02/sanitizer-diagram-optimized-2.svg)

그 진입점이 [`setHTML()`][sethtml]이다. 삽입과 정제(sanitize)가 하나의 메서드에 합쳐져 있어서, 따로 정제 함수를 호출하는 걸 까먹을 일이 없다. 이게 "기본값이 안전하다(safe by default)"의 의미.

```js
// 사용자 입력이라고 가정
document.body.setHTML(`<h1>Hello my name is <img src="x" onclick="alert('XSS')">`);
```

결과 DOM:

```html
<h1>Hello my name is</h1>
```

`<h1>`은 남기고, 이벤트 핸들러가 달린 `<img>`는 통째로 날아갔다.

#### ❌ / ✅ 비교

```js
// ❌ 문자열 그대로 파싱 → onclick, <script> 등 전부 살아남음
el.innerHTML = userInput;

// ✅ 파싱 + 정제를 한 번에
el.setHTML(userInput);
```

마이그레이션도 대부분 이 한 줄 바꾸기로 끝난다. 이게 제일 큰 장점 같다.

#### 기본 설정이 부족하거나 과할 때

기본 설정은 위험한 요소·속성을 알아서 제거해주는데, 서비스 특성상 더 열거나 더 막고 싶으면 config를 넘기면 된다. 어떤 요소/속성을 남길지, 뺄지 지정할 수 있다.

```js
// 허용할 요소만 지정 (예: 댓글에서 기본 서식만 허용)
el.setHTML(userInput, {
  sanitizer: { elements: ['p', 'b', 'i', 'a'] },
});

// 또는 특정 요소만 제거
el.setHTML(userInput, {
  sanitizer: { removeElements: ['img'] },
});
```

원문에서는 config를 바꿔가며 결과를 바로 확인해볼 수 있는 [`Sanitizer API Playground`][playground]도 소개한다. 설정 짜기 전에 여기서 먼저 돌려보면 좋을 듯.

### Trusted Types랑 같이 쓰면

여기서 한 단계 더 가는 방법이 [`Trusted Types`][trusted-types]와의 조합이다. Trusted Types는 `innerHTML` 같은 위험한 삽입 지점(sink)에 그냥 문자열을 넣지 못하게 막는 API다.

| 조합 | 효과 |
|------|------|
| `setHTML()`만 | 바꾼 곳은 안전, 남아있는 `innerHTML`은 여전히 위험 |
| `setHTML()` + Trusted Types | `setHTML()`은 허용, 정제 안 된 HTML 삽입은 **정책 차원에서 차단** |

```http
# CSP 헤더로 Trusted Types 강제
Content-Security-Policy: require-trusted-types-for 'script'
```

즉 "setHTML로 다 바꿨겠지?"를 사람이 믿는 게 아니라, 브라우저가 강제하게 만드는 것. 복잡한 커스텀 정책 없이도 꽤 엄격한 방어선이 생긴다.

---

### 📌 정리

`innerHTML → setHTML, 정제는 브라우저에게`

#### 핵심

> XSS는 10년째 Top 3 취약점이고, CSP는 강력하지만 도입이 어렵다.
> `Sanitizer API`의 `setHTML()`은 HTML 삽입과 정제를 합쳐서 기본값으로 안전하게 만든다.
> Firefox 148이 첫 구현. Trusted Types와 조합하면 안전하지 않은 삽입 자체를 막을 수 있다.

#### ⭐️ 앞으로 기억할 것

- 1. 신뢰 못 하는 HTML은 `setHTML()`
`innerHTML`에 외부 입력 넣는 코드는 일단 의심하자. 대부분 한 줄 교체로 끝난다.
```js
// ❌
el.innerHTML = comment.body;
// ✅
el.setHTML(comment.body);
```

- 2. 아직은 기능 감지 필수
2026년 2월 기준 Firefox 148이 첫 구현이다. 다른 브라우저 지원 전까지는 폴백(DOMPurify 등)을 같이 둔다.
```js
if ('setHTML' in Element.prototype) {
  el.setHTML(html);
} else {
  el.innerHTML = DOMPurify.sanitize(html); // 폴백
}
```

- 3. 기본 config로 시작, 필요할 때만 커스텀
처음부터 허용 목록을 직접 짜지 말고, 기본값으로 쓰다가 부족한 부분만 `sanitizer` 옵션으로 조정한다. 조정 전엔 Playground에서 확인.

- 4. 끝판왕은 Trusted Types 강제
`require-trusted-types-for 'script'`로 남은 `innerHTML`을 브라우저가 막게 하면, 실수로 남긴 구멍까지 잡힌다.

- 5. React라면 `dangerouslySetInnerHTML`이 같은 위험 지점
이름부터 위험하다고 말하고 있는 그곳. 외부 HTML을 넣는다면 정제는 여전히 필수다.

> **📌 결론**
> ▎ XSS는 아직도 현역, 오래된 취약점이라고 방심 금지
> ▎ `setHTML()` = 삽입 + 정제, 기본값이 안전하다
> ▎ config로 허용/제거 요소 조정 가능
> ▎ Trusted Types까지 붙이면 정책 차원의 차단
> ▎ ⭐️ 실무 적용 포인트: 외부 HTML 넣는 `innerHTML`을 찾아 `setHTML()` + 폴백으로 바꾸고, 지원 범위 넓어지면 Trusted Types 강제
