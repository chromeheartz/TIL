# 새로운 HTTP 메서드 QUERY

> **원문**: https://kreya.app/blog/new-http-query-method-explained/
> **번역 출처**: https://velog.io/@lgwk0642/새로운-HTTP-메서드-QUERY (김건우)

RFC 10008이 발행됐다는 얘기를 보고 정리해봤다. "검색은 GET인데 필터가 많으면 URL이 터지고, 그렇다고 POST 쓰자니 캐싱도 멱등성도 없고..." 이 애매함을 프론트에서 한 번쯤 겪어봤다면 이 글이 반가울 거다. 2026년 6월, 드디어 `QUERY`라는 조회 전용 메서드가 공식 문서로 나왔다. 아직 Proposed Standard 단계다.

### 왜 이게 필요했나

솔직히 그동안 조회 요청 하나 보내는 것도 은근 신경 쓰였다. 상황을 나눠보면 이렇다.

#### GET의 한계

`GET`은 조회의 정석이지만, 쿼리 파라미터에 다 때려박는 구조라 필터가 많아질수록 URL이 감당이 안 된다.

- URL 길이 제한 넘으면 `414 URI Too Long` 뜬다
- 한글 같은 비-ASCII 문자는 인코딩되면서 요청 크기가 확 커진다
- 쿼리 파라미터가 서버 로그에 그대로 남아서 보안 이슈가 생긴다
- 배열이나 중첩 구조를 어떻게 표현할지 표준이 없다 (`tags[]=a&tags[]=b`? `tags=a,b`? 제각각이다)

#### "그럼 GET에 바디 넣으면 되잖아?"

이게 함정이다. 기술적으로 못 담는 건 아닌데, HTTP RFC가 권고하지 않는다. 그래서 클라이언트·웹서버·프록시마다 처리가 제각각이다. 어떤 프록시는 바디를 그냥 버리기도 한다. 신뢰할 수가 없다.

#### POST로 도망친 결과

결국 바디가 필요하면 다들 `POST`를 썼다. 근데 `POST`는 원래 조회용이 아니다.

- 데이터 생성·처리용 메서드다
- 멱등(idempotent)하지 않다 → 두 번 보내면 두 번 처리될 수 있다
- 자동 재시도할 때 중복 생성 위험이 있다
- 캐싱이 안 된다

읽기만 하는데 캐싱을 못 쓰는 게 제일 아프다.

### 그래서 나온 QUERY

`QUERY`는 딱 이 빈틈을 메우는 메서드다.

- `GET`처럼 데이터 **조회용**
- `POST`처럼 **바디 포함 가능**
- **Safe**하고 **idempotent**하도록 정의됨

즉 "바디를 쓸 수 있는 GET"이라고 보면 편하다.

#### 요청 예시

```http
QUERY /posts HTTP/1.1
Content-Type: application/json

{
  "title": "검색어",
  "tags": ["notice", "event"],
  "filters": { "createdAfter": "2026-01-01" }
}
```

`POST` → `QUERY` 이 한 단어 차이로 "이건 읽기 전용이고 재시도해도 안전함"이라는 의미가 클라이언트·서버·프록시·CDN 전부에 전달된다. 메서드 이름 하나에 의미가 담기는 거라, 이게 생각보다 크다.

#### 캐싱은 어떻게?

`QUERY` 응답도 캐시할 수 있다. 근데 조회 조건이 URL이 아니라 **바디**에 있으니까, 캐시 키에 요청 바디를 포함시켜야 한다.

여기서 주의할 점 — 바디가 JSON이면 정규화가 필요하다.

```js
// ❌ 이 둘은 의미가 같은데 문자열이 달라서 캐시 미스
{"a":1,"b":2}
{ "b": 2, "a": 1 }

// ✅ 키 정렬 + 공백 제거로 정규화한 뒤 캐시 키로 사용
JSON.stringify(obj, Object.keys(obj).sort())
```

키 순서, 공백 같은 걸 정규화 안 하면 같은 조회인데 캐시가 계속 빗나간다.

#### GraphQL 하는 사람이면 특히 반가울 듯

GraphQL은 조회 쿼리까지 전부 `POST`로 보내서 HTTP 레벨 캐싱을 못 누렸다. (이거 GraphQL의 오랜 아쉬움 중 하나였다.) `QUERY`로 이 문제를 풀 수 있는 길이 열린 셈이다.

### 📌 정리

`QUERY = 바디 쓸 수 있는 GET, 조회 전용 메서드`

#### 핵심
> `GET`은 URL이 터지고, `POST`는 멱등·캐싱이 안 된다. `QUERY`는 이 사이의 빈틈 — **바디를 담을 수 있으면서 Safe하고 idempotent한 조회 전용 메서드**다. RFC 10008로 2026년 6월 발행됐고, 아직 Proposed Standard 단계.

#### ⭐️ 앞으로 기억할 것
- 1. QUERY의 정체성
  "바디를 쓸 수 있는 GET". 조회용 + 바디 가능 + safe + idempotent.
- 2. 왜 POST로는 부족했나
  POST는 생성용이라 멱등하지 않고, 재시도 시 중복 위험 + 캐싱 불가.
  ```
  POST /search   → 두 번 보내면 두 번 처리될 수 있음, 캐시 X
  QUERY /search  → 재시도 안전, 캐시 O
  ```
- 3. 캐싱하려면 바디 정규화 필수
  조회 조건이 바디에 있으니 캐시 키에 바디를 넣어야 함. 단, JSON 키 정렬·공백 제거 안 하면 캐시가 계속 빗나감.
  ```js
  JSON.stringify(obj, Object.keys(obj).sort())
  ```
- 4. GraphQL 캐싱 돌파구
  조회까지 POST로 보내던 GraphQL이 HTTP 레벨 캐싱을 노려볼 수 있게 됨.

📌 결론
▎ HTTP 메서드는 결국 문자열이라, 임의 메서드를 허용하는 클라이언트는 지금도 `QUERY`를 보낼 수 있다.
▎ 다만 프록시·캐시·프레임워크 생태계에 자리잡으려면 2~3년은 걸릴 듯.
▎ RFC 저자에 Cloudflare, Akamai 같은 CDN 사업자가 들어가 있는 게 신호 — 인프라 쪽이 밀고 있다.
▎ `QUERY`가 만능은 아니다. URL 공유·북마크가 필요하면 여전히 `GET`이 맞다.
▎ ⭐️ 실무 적용 포인트
  - 지금 당장 바꿀 건 아니지만, 검색/필터 API 설계할 때 "이거 원래 QUERY로 갈 자리였구나"를 인지하고 있으면 앞으로 인프라가 받쳐줄 때 자연스럽게 넘어갈 수 있다.
