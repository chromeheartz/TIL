# GitHub Issues가 이슈 페이지를 즉시 띄우는 방법

> **원문**: [From latency to instant: Modernizing GitHub Issues navigation performance](https://github.blog/engineering/architecture-optimization/from-latency-to-instant-modernizing-github-issues-navigation-performance/) (Alexander Lelidis)  
> **번역 출처**: [(번역) 지연에서 즉시 반응으로, GitHub Issues 내비게이션 성능 개선하기](https://velog.io/@tap_kim/from-latency-to-instant-modernizing-github-issues-navigation-performance) (tap_kim)

성능 개선 글은 대개 번들을 줄였다거나 쿼리를 고쳤다는 얘기로 끝나는데, 이 글은 페이지가 로드되는 과정 자체를 바꿨다길래 읽었다. 데이터가 많은 앱에 그대로 가져다 쓸 만한 패턴이 많다.

문제 정의가 좋다. Issues가 느렸다기보다, 이미 본 데이터인데도 이동할 때마다 서버 렌더링, 네트워크, 클라이언트 시작 비용을 다시 치르고 있었다는 것이다. 그래서 백엔드를 조금씩 깎는 대신 로컬 데이터로 먼저 그리고 뒤에서 재검증하는 구조로 갔다.

### "빠르다"부터 정의했다

GitHub은 LCP와 비슷한 내부 지표 `HPC(Highest Priority Content)`를 쓴다. 페이지의 주요 콘텐츠가 처음 렌더링되는 시점이고, 이슈 페이지에서는 대개 제목이나 본문이다.

| 구간 | HPC 기준 | 의미 |
| --- | --- | --- |
| 즉시 반응 | 200ms 미만 | 실제 작업 중에 즉각적이라고 느낀다 |
| 빠름 | 1000ms 미만 | 괜찮지만 기다림을 인지하기 시작한다 |
| 느림 | 1000ms 이상 | - |

측정 철학을 바꾼 대목이 제일 인상적이었다. 예전에는 p90, p99 꼬리를 줄이는 데 힘을 썼는데, p99가 좋아져도 중앙값 사용자는 여전히 굼뜰 수 있다. 그래서 전체 내비게이션 중 몇 %가 빠름, 즉시 반응 구간에 들어가는지를 보기로 했다.

### 내비게이션은 세 종류다

`issues#show`에 들어오는 경로를 먼저 나눴다.

| 유형 | 동작 | 치르는 비용 |
| --- | --- | --- |
| 하드 | 브라우저가 페이지 전체를 로드 | 네트워크, SSR, 에셋, JS 시작, 하이드레이션 전부 |
| Turbo | Rails Turbo로 일부 영역만 갱신 | 일부를 피하지만 서버 응답에 크게 의존 |
| 소프트 (React) | 실행 중인 런타임 안에서 전환 | 페이지 초기화 비용을 대개 피함 |

![이슈 조회 라우트의 내비게이션 비중을 보여주는 그래프. 하드 57.6%, 리액트 37.5%.](https://github.blog/wp-content/uploads/2026/05/trafficDistro.png?resize=1024%2C336)

![내비게이션 유형별 HPC 분포를 보여주는 그래프. 하드 2.05, Turbo 1.76, 리액트 1.04.](https://github.blog/wp-content/uploads/2026/05/trafficPerf.png?resize=1024%2C335)

제일 많이 쓰는 경로가 제일 느린 경로였다. 하드가 많은 이유는 GitHub이 아직 Rails에서 React로 옮기는 중이라, 두 세계의 경계를 넘을 때마다 콜드 부팅이 일어나서다. 마이그레이션이 끝나길 기다릴 수는 없으니 효과가 빨리 나는 소프트 내비게이션부터 시작했다.

### 1단계: IndexedDB 캐시와 SWR

소프트 내비게이션은 런타임이 이미 떠 있으니 데이터 가져오는 시간이 가장 큰 비용이다. 사용자가 같은 이슈를 자주 다시 여는 패턴을 보고 캐시 적중률을 약 30%로 추정한 뒤 시작했다.

![클라이언트 캐시 계층을 보여주는 아키텍처 다이어그램.](https://github.blog/wp-content/uploads/2026/05/softNavFlow.png?resize=1024%2C443)

기존 인메모리 스토어에 IndexedDB를 영구 캐시로 붙였다. 고른 이유는 탭을 닫아도 남고, 키로 조회하기 좋고, `localStorage`보다 실제로 쓸 수 있는 용량이 커서다.

| 경로 | 동작 |
| --- | --- |
| 읽기 | 로컬 캐시로 먼저 채워서 즉시 렌더링 |
| 재검증 | 백그라운드 요청으로 확인하고 바뀌었으면 스토어에 반영 |
| 장애 시 | 네트워크가 나빠도 캐시로 페이지를 보여주고, 복구되면 최신화 |

캐시냐 정확성이냐의 양자택일이 아니라, 같은 내비게이션 안에서 먼저 그리고 나서 맞춘다는 점이 핵심이다.

![캐시 배포 후 HPC 분포를 보여주는 그래프.](https://github.blog/wp-content/uploads/2026/05/softNavIncrease.png?resize=1024%2C592)

React 내비게이션의 즉시 반응 비율은 4%에서 약 22%로 올랐다. 적중률은 약 33%로 사전 분석과 맞았다. 서버와 캐시의 불일치는 약 4.7%였는데, 이걸 운영 허용 범위로 명시한 게 좋았다. "가끔 오래된 데이터가 보일 수 있음"을 숫자로 합의한 셈이다.

### 2단계: 사전 예열

적중률 3분의 1이면 대부분의 이동이 데이터보다 먼저 도착한다는 뜻이다. 그렇다고 목록의 이슈를 전부 프리페치하면 요청량이 늘고 N+1 패턴이 생긴다. 안 열 페이지에 서버 자원을 쓰는 꼴이다.

그래서 목표를 바꿨다. 항상 최신으로 유지하는 대신, 클릭하는 순간 쓸 만한 데이터가 로컬에 있기만 하면 된다.

![사전 예열 과정 흐름도. 이슈 목록을 보고 각 이슈의 예열 요청을 실행합니다. 캐시에 데이터가 있으면 IndexedDB에 추가하고, 없으면 데이터를 가져온 뒤 IndexedDB에 추가합니다.](https://github.blog/wp-content/uploads/2026/05/preheatFlow.png?resize=1024%2C237)

`사전 예열(preheating)`은 열 가능성이 높은 이슈를 미리 돌되, 캐시에 없을 때만 네트워크를 쓴다. 최신 상태를 강제하는 로직이 아니라 캐시를 채우는 로직이라는 점이 프리로딩과 다르다. 최신화는 어차피 이슈를 열 때 재검증이 해준다.

여기에 IndexedDB 앞단의 인메모리 캐시도 넣었다. IndexedDB는 비동기라서 임계 경로에서 비용이 드는데, 자주 쓰는 페이로드를 메모리에서 동기로 주면 비동기 경계가 하나 사라진다.

![인메모리 캐시 계층을 보여주는 다이어그램.](https://github.blog/wp-content/uploads/2026/05/hotcacheArch.png?resize=1024%2C389)

예열은 이슈 목록, 대시보드, 프로젝트, 의존성 보기에서 돈다. 낮은 우선순위 워커에서 처리하고, 빈도를 제한하고, 서킷 브레이커로 부하가 커지면 물러난다. 사용자가 직접 시작한 요청이 항상 먼저다.

![사전 예열 배포 후 HPC 분포를 보여주는 그래프.](https://github.blog/wp-content/uploads/2026/05/preheatResults.png?resize=1024%2C593)

결과는 `issues#show` 전체의 즉시 반응 비율 약 30%, React 내비게이션만 보면 최대 약 70%. 적중률은 33%에서 약 96%로 뛰었다.

### 3단계: 서비스 워커로 Turbo와 하드까지

새로고침, 새 탭, 직접 입력한 URL, 외부 링크로 들어오는 하드 내비게이션은 React로 다 옮겨도 남는다. 서비스 워커는 페이지 JS가 안 떠 있어도 요청을 가로챌 수 있어서 여기에 맞는 도구다.

![서비스 워커가 요청을 가로채는 흐름을 보여주는 다이어그램.](https://github.blog/wp-content/uploads/2026/05/swFlow.png?resize=1024%2C189)

이슈 데이터가 로컬에 있으면 요청에 헤더를 붙여 서버에 알린다. 캐시를 응답으로 돌려주는 게 아니라 서버 일을 줄여주는 신호라는 점이 재밌다.

| 경로 | 서버 응답 |
| --- | --- |
| 캐시 적중 | 가벼운 HTML 셸을 주고, React가 로컬 페이로드로 렌더링 |
| 캐시 미적중 | 평소처럼 데이터를 로드해서 SSR |

순수 최적화라서 캐시가 비었거나 서비스 워커를 못 쓰면 기존 서버 렌더링으로 돌아간다.

![서비스 워커 배포 후 Turbo 내비게이션의 HPC 분포를 보여주는 그래프.](https://github.blog/wp-content/uploads/2026/05/swTurboImpact.png?resize=1024%2C332)

Turbo는 서버 응답 시간에 묶여 있어서 효과가 바로 나왔다. 하드는 SSR 시간이 줄어든 대신 CSR 비용을 치르니 임계 경로가 JS 다운로드와 실행으로 옮겨간다. 그래서 `React.lazy`와 라우트 프리로딩으로 코드를 나누고, 이슈 편집기 번들은 편집 모드에 들어갈 때만 가져오고, 호버 같은 의도 신호로 프리페치했다.

![하드 내비게이션의 HPC 분포.](https://github.blog/wp-content/uploads/2026/05/hardNavImpact.png?resize=1024%2C448)

### 📌 정리
`서버를 빠르게 하는 대신 서버에 안 가는 경로를 넓혔다`

#### 핵심
> 이미 본 데이터를 매번 다시 받는 비용을 없애려고 메모리, IndexedDB, 사전 예열, 서비스 워커를 차례로 쌓았다.  
> 조금 오래된 데이터를 먼저 보여주고 뒤에서 맞추는 대신, 불일치 약 4.7%를 허용 범위로 명시했다.

#### ⭐️ 앞으로 기억할 것
아래 코드는 원문이 아니라 이해용으로 내가 줄여 쓴 의사코드다.

1. SWR은 렌더링 순서를 바꾸는 일이다
서버를 빠르게 하지 않아도 체감이 바뀐다. 재검증은 빼면 안 된다.
```ts
// ❌ 캐시가 있어도 응답을 기다린다
const issue = await fetchIssue(id)
render(issue)

// ✅ 로컬로 먼저 그리고 뒤에서 맞춘다
const cached = memory.get(id) ?? (await idb.get(id))
if (cached) render(cached)

const fresh = await fetchIssue(id)
await idb.set(id, fresh)
render(fresh)
```
2. 프리페치 전에 "없을 때만"을 먼저 넣는다
적중률을 올리려다 서버를 터뜨리면 의미가 없다. 사용자 요청보다 뒤로 밀고 제한을 건다.
```ts
// ❌ 있든 없든 목록 전체를 요청한다. N+1이 된다
issues.forEach(({ id }) => fetchIssue(id))

// ✅ 캐시에 없는 것만, 낮은 우선순위로, 제한을 걸어서
for (const { id } of issues) {
  if (await idb.has(id)) continue
  await limiter.run(async () => {
    await idb.set(id, await fetchIssue(id, { priority: 'low' }))
  })
}
```
3. 백분위 말고 구간 비중도 본다
p99만 보면 대다수 사용자의 경험이 안 보인다. "200ms 안에 끝난 이동이 몇 %인가"처럼 사람이 느끼는 구간으로 목표를 잡는다.
4. 내비게이션 유형별로 쪼개서 잰다
한 숫자로 합치면 병목이 가려진다. 이 글에서도 유형별로 나누고서야 가장 많이 쓰는 경로가 가장 느리다는 게 보였다.
5. 오래된 데이터 허용치를 숫자로 합의한다
"캐시라서 가끔 달라요"는 합의가 아니다. 불일치율을 재서 허용 범위를 정하고, 권한이나 결제처럼 틀리면 안 되는 화면은 처음부터 캐시 대상에서 뺀다.
6. 헤더로 응답이 갈리면 캐시에 알린다
같은 URL이 헤더에 따라 셸이나 완성된 HTML을 주면, CDN이나 HTTP 캐시가 섞어 줄 수 있다. 원문에는 없는 내용이고 헤더 이름은 예시다.
```http
# ✅ 이 헤더 값에 따라 응답이 달라진다고 캐시에 알린다
Vary: X-Issue-Cached
```
7. 영구 캐시는 로그아웃까지 설계한다
IndexedDB는 탭을 닫아도 남는다. 비공개 저장소의 이슈 내용이 공용 PC에 남을 수 있으니 로그아웃이나 계정 전환 때 지운다. 이것도 원문에는 없다.
```ts
// ✅ 로그아웃 시 사용자 데이터를 함께 지운다
indexedDB.deleteDatabase('issues-cache')
```

> 📌 결론  
> ▎ 느린 원인은 기능이 아니라 이미 본 데이터를 다시 받는 요청 생명주기였다.  
> ▎ IndexedDB + SWR로 React 즉시 반응 비율을 4%에서 약 22%로 올렸다.  
> ▎ 없을 때만 받는 사전 예열로 적중률이 약 96%가 됐다.  
> ▎ 서비스 워커는 응답을 대신하지 않고, 서버에 일을 줄이라고 알려준다.  
> ▎ 하드 내비게이션의 병목은 SSR에서 JS 시작으로 옮겨갔을 뿐 끝나지 않았다.  
> ▎ ⭐️ 실무: 성능 작업 전에 내비게이션 유형별 비중과 구간별 비율부터 잰다.  
> ▎ ⭐️ 실무: 클라이언트 캐시를 넣을 때는 불일치 허용치와 로그아웃 시 삭제를 같이 정한다.
