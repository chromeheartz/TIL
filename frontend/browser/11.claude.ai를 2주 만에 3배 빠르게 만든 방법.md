# claude.ai를 2주 만에 3배 빠르게 만든 방법

> **원문**: [How we made claude.ai faster](https://claude.dev/blog/how-we-made-claude-ai-faster/) — Anthropic
> **번역 출처**: [2주 만에 claude.ai를 3배 빠르게 만든 방법](https://siosio3103.medium.com/2%EC%A3%BC-%EB%A7%8C%EC%97%90-claude-ai%EB%A5%BC-3%EB%B0%B0-%EB%B9%A0%EB%A5%B4%EA%B2%8C-%EB%A7%8C%EB%93%A0-%EB%B0%A9%EB%B2%95-408898c0e52c) — 조영제

Anthropic이 claude.ai와 데스크톱 앱을 2주 스프린트로 약 3배 빠르게 만든 회고다. "AI가 코드를 짰다" 류의 글인가 싶었는데, 읽어보니 진짜 알맹이는 **성능을 어떻게 측정 가능한 숫자로 바꾸고, 그 숫자를 CI로 지켰는가**였다. 프론트 성능 작업하는 사람이면 AI 얘기를 빼고 봐도 건질 게 많다.

### 결과부터

사용자 활동의 95%를 차지하는 네 가지 여정에 집중했다. 기준은 p75.

| 여정 | 이전 | 이후 |
|---|---|---|
| claude.ai 첫 로드 → 입력 가능 | 3.1초 | 0.55초 |
| 새 Claude Code 세션 시작 | 0.8초 | 0.3초 |
| Cowork 클라우드 세션 로드 | 2.6초 | 0.73초 |

> `p75`는 사용자 측정값을 빠른 순으로 줄 세웠을 때 75% 지점의 값이다. 평균과 달리 극단적으로 느린 값에 덜 휘둘려서 Core Web Vitals도 p75를 쓴다. `p95`는 가장 느린 5%가 겪는 경험.

![핵심 사용자 여정 p75, 8월 13일 대비 8월 27일](https://miro.medium.com/v2/resize:fit:1400/1*9JAUqC8Guf-kfPUjbu8taA.png)

네 여정, 13개 측정값 기준으로 기하 평균 3.1배. 2주 동안 머지한 변경이 3천 건이 넘는데 **고객 영향 장애나 롤백은 0건**이었다고 한다. 솔직히 이게 제일 놀랍다.

작업은 슬랙 채널 하나에서 Claude Tag(베타)로 돌렸다. Claude가 병목 찾기, 벤치마크 만들기, 배포, 배포 모니터링을 하고, 사람은 목표 설정·트레이드오프 판단·변경 승인을 맡는 구조.

### 과제 설정

#### 상시 지침부터 깔고 시작

채널을 만들고 Claude에게 "성능 관련 모든 일이 네 책임"이라는 상시 지침을 남겼다. 배포마다 회귀 모니터링, 기존 성능 데이터가 정확한지 평가, 대시보드 유지, 쉬운 문제는 먼저 해결, 프로젝트 제안까지.

#### 측정 기준을 먼저 맞춘다

Datadog MCP 서버를 붙여서 사용 데이터를 분석하게 했고, 영향이 큰 여정 네 개가 나왔다.

- 앱 실행
- 대화 시작
- 기존 대화 로드
- 메시지 전송

이걸 웹/데스크톱, 제품별로 쪼개니 측정값이 13개. 여기서 중요한 건 **모든 측정이 "사용자 인터랙션 시작 → 결과 렌더링 끝"으로 통일**되고, 클라이언트 작업과 서버 작업을 분리했다는 점이다. 측정값끼리 그대로 비교할 수 있을 때까지 계측을 더했다.

#### 20개 프로젝트, 사흘 만에 12/13 달성

직접 고른 20개쯤의 프로젝트로 시작했고, Claude가 프로젝트별 효과를 ms 단위로 추정해서 합산한 값을 목표로 잡았다. 결과는 13개 목표 중 12개를 **사흘 만에** 달성. 초기에 한 것들:

- 정적 입력창(composer)을 HTML에 미리 박아서 React 초기화 중에도 타이핑 가능하게
- V8 코드 캐시를 미리 컴파일해서 데스크톱 셸 메인 프로세스가 재컴파일 안 하게
- 대화 전환 시 입력창을 언마운트하지 않고 유지
- 세션에 마우스 hover 시 프리페치
- 사이드바 리렌더링 90% 감소

목표를 일찍 넘겨서 "아직 탐색 안 한 건 뭐지? 엉뚱한 아이디어도 환영"으로 목록을 다시 짰다.

### 측정하는 순간 개선할 수 있다

#### 벽시계 시간 대신 뭘 잴까

배포를 기다리지 않고 테스트 환경에서 반복하려면, 노이즈 많은 실제 경과 시간(wall clock) 말고 **결정적인(deterministic) 지표**가 필요했다. Sam이 "JS 인스트럭션 수를 셀 수 있나?"라고 물었고 Claude 답은 이랬다.

| 대상 | 결정적 지표 |
|---|---|
| 순수 JS 핫 패스 (Node) | `node --predictable` + Valgrind로 인스트럭션 수(`Ir`) |
| 브라우저 경로 | 인터랙션당 React 커밋 수 |
| | V8 정밀 커버리지로 얻는 함수 호출 수 |
| | 레이아웃·스타일 재계산 횟수 |
| | DOM 변경 횟수 |

11분 뒤 이 다섯 지표별로 스레드 다섯 개가 돌고 있었다고. 하하.

#### 벤치마크는 의심부터

새 벤치마크는 두 조건을 통과해야 살아남았다.

1. Claude가 테스트 환경에서 **움직일 수 있는** 지표일 것
2. CI에서 **내려가기만 하는** 가드레일 역할을 할 수 있을 것

그리고 "이 지표를 개선하면 실제 경과 시간이 줄어든다는 걸 증명해. 못 하면 뺀다." 결정적인 숫자라도 사용자가 체감하는 시간과 상관관계가 없으면 엉뚱한 걸 최적화하게 되니까.

#### 메가모픽 조회 하나로 4.6배

검증용으로 두 핫 패스(메시지 트리 조립, Claude Code 출력의 상태 줄 스캐너)를 골랐다. Valgrind로 보니 첫 번째 경로 인스트럭션의 4분의 1이 **메가모픽 딕셔너리 조회**였고, 같은 메시지 ID를 세 번 따로 찾고 있었다.

> `megamorphic`: V8 인라인 캐시 상태 중 하나. 한 코드 지점에 너무 다양한 shape의 객체가 들어오면 V8이 인라인 캐시를 포기하고 매번 느린 범용 조회를 한다.

| 경로 | 변경 | 인스트럭션 | 실제 시간 | 속도 |
|---|---|---|---|---|
| 메시지 트리 조립 | ID를 세 번 → 한 번만 조회 | −48% | −78% | 4.6배 |
| 상태 줄 스캐너 | 정규식 전에 싼 첫 글자 검사 | −31% | −44% | 1.8배 |

인스트럭션 수가 줄면 실제 시간도 줄어든다는 게 증명됐고, 바로 **래칫(ratchet) 검사** 두 개를 저장소에 추가했다. 인스트럭션 수를 늘리는 PR은 CI에서 실패하고, 매일 도는 작업이 수치가 줄 때마다 상한선을 낮춘다.

> `ratchet`: 한 방향으로만 도는 톱니바퀴. 수치가 좋아지는 방향으로만 움직이게 막는 CI 검사다.

여기서 이 글의 핵심 문장이 나온다. **"측정하는 순간 손쓸 수 있는 문제가 된다."** 예전엔 측정이 본 작업 전 준비 단계였는데, 이제는 넘어설 숫자가 생기는 즉시 최적화가 시작된다. 그러니 가장 레버리지 큰 일은 **측정할 대상을 더 찾는 것**.

### 스레드 단위로 도는 루프

스프린트는 자연스럽게 하나의 루프로 굳었다.

📌 1단계: 누군가 느린 구간에 대한 스레드를 연다 (스크린샷/화면 녹화 첨부)

📌 2단계: Claude가 흐름을 추적하고 문제를 드러내는 벤치마크를 찾거나 만든다

📌 3단계: 테스트 환경에서 유망하면 PR을 올린다. 위험도·리뷰 부담에 맞춰 여러 개로 쪼개고, 사용자 눈에 보이는 변경은 전부 기능 플래그로 감싼다

📌 4단계: 배포 후 Claude가 실서비스 데이터를 읽는다

📌 5단계: 빨라졌으면 래칫을 낮춰 고정, 아니면 플래그 끄고 다시

📌 6단계: 같은 여정의 다음 느린 지점으로

#### 예시: CLS로는 안 잡히던 사이드바 덜컹거림

페이지 로드 후 사이드바의 Chat 행과 Cowork 행이 서로 다른 타이밍에 자리를 잡으면서 덜컹거리는 녹화가 올라왔다. 그런데 기존 지표엔 안 잡혔다. CLS로 보면 이동 한 번이 약 0.008점이라 "좋음" 기준인 0.1에 한참 못 미친다. **지표상 멀쩡한데 눈으로 보면 거슬리는** 전형적인 케이스.

그래서 CLS의 바탕인 [Layout Instability API][layout-instability]를 직접 썼다. `layout-shift` 엔트리의 `sources`를 보고 **어느 영역(사이드바, 대화 내용…)에서, 어느 시점(첫 페인트 전, 입력 가능해진 뒤…)에** 이동했는지 기록하는 RUM 이벤트를 만들었다. 대충 이런 느낌일 거다.

```js
// 이동이 "어디서" 났는지까지 기록하는 layout-shift 수집 (이해용 스케치)
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.hadRecentInput) continue // 사용자 입력 직후 이동은 제외
    for (const src of entry.sources ?? []) {
      // data-region 같은 이름표로 영역 식별
      const region = src.node?.closest?.('[data-region]')?.dataset.region ?? 'unknown'
      sendToRUM({ region, value: entry.value, time: entry.startTime })
    }
  }
}).observe({ type: 'layout-shift', buffered: true })
```

동시에 통합 테스트도 추가했다. 사이드바 데이터를 첫 페인트 끝날 때까지 붙잡아뒀다가 풀어주고, 이름 붙은 영역 중 하나라도 움직이면 실패. main에선 20/20 빨간불, PR에선 20/20 초록불로 수정을 증명했다.

배포 후 데이터를 보니 <strong>웹 페이지 로드의 31%</strong>에서 사용자 입력 없이 무언가 움직이고 있었다. 늦게 도착하는 헤더 행, 사용자 이름이 로드되면 옆으로 밀리는 캐럿, 스크롤바가 생기면서 밀리는 목록 등을 이름 붙여 하나씩 잡았다.

### 수평 확장

루프가 스레드 하나에서 돌면, 확장은 스레드를 여는 것뿐이다. 스레드 하나에서 PR이 50~100개씩 나왔고, 나중엔 새 스레드를 여는 쪽도 Claude였다. 측정할 때마다 거리가 나왔다.

| 측정 방법 | 찾은 것 |
|---|---|
| React 훅 전수 조사 | 입력창 타이핑 경로에서 키 입력마다 리렌더되는 훅 6,900개, 스토어 구독 900개 |
| 스타일 재계산 횟수 | `:root:has()` 선택자 하나가 DOM 변경마다 24ms 추가 |
| 첫 페인트 이후 코드 경로 추적 | 어떤 로드 지표에도 안 잡히던 하루 50만 번의 `location.reload()` |
| 유휴 탭 프로파일러 샘플 | 같은 캐시 스냅샷을 1분에 두 번 IndexedDB에 복제, 그것도 메인 스레드에서 |

#### 범인은 em 대시였다

제일 재밌었던 건 이거다. 완성된 코드 블록에 구문 강조를 걸면 페이지가 1초 가까이 멈추는 경우가 있었는데, 원인이 <strong>긴 줄표(—)</strong>였다.

V8은 문자열을 내부적으로 두 가지로 저장한다. Latin-1 범위 문자만 있으면 글자당 1바이트(one-byte), 그 밖의 문자가 **하나라도** 있으면 문자열 전체를 글자당 2바이트(UTF-16, two-byte)로. 응답 마크다운에 `—`나 `“ ”` 하나만 있어도 전체가 two-byte가 되고, 그걸 잘라 쓴 코드 블록에 돌린 구문 강조 정규식이 전부 느린 two-byte 경로로 돌았다.

수정은 20줄. 구문 강조 전에 코드 블록을 one-byte 문자열로 **복사**하는 것.

```js
// ❌ two-byte인 원본 마크다운에서 잘라낸 문자열 → 정규식이 느린 경로
const code = markdown.slice(start, end)
highlight(code)

// ✅ 코드 블록만 새 문자열로 만들어 one-byte 표현을 받게 한다 (이해용 스케치)
// 코드 블록 안이 전부 Latin-1이면 V8이 1바이트 문자열로 저장할 수 있다
const code = markdown.slice(start, end)
highlight(/^[\x00-\xff]*$/.test(code) ? Buffer.from(code, 'latin1').toString('latin1') : code)
```

(실제 구현은 원문에 안 나온다. 위는 원리를 이해하려고 내가 짠 스케치다. 브라우저면 `Buffer` 대신 다른 복사 방법을 써야 한다.)

### 가드레일

성능에 민감한 핵심 경로(첫 페인트, 입력창, 대화 내용)만 건드리니까 안전장치를 처음부터 깔았다.

- 모든 PR은 자동 리뷰 + 최소 1명 사람 승인
- 최적화보다 **단위 테스트가 항상 먼저**
- 사용자에게 보일 수 있는 변경은 수명 짧은 기능 플래그로

#### 플래그도 관리 대상

2주간 플래그가 200개 가까이 생겼다. 플래그를 **킬 스위치<strong>(문제 생기면 즉시 끄기)와 </strong>램프**(단계적 공개)로 나누고, 안전해지는 즉시 지웠다. 스프린트 끝날 때 절반 이상이 이미 정리돼 있었다.

#### 정적 입력창을 지키는 법

빠르게 움직이는 코드베이스에선 성능 개선이 금방 사라진다. 그래서 효과가 증명된 프로젝트엔 **지키는 비용**도 투자했다. 정적 입력창은 HTML 사본을 먼저 보여주고 그 위에 React가 그리는 구조라, 렌더 결과가 1px만 어긋나도 티가 난다.

- 정적 마크업은 **실제 React 컴포넌트를 jsdom에서 렌더해서 생성**, 둘이 어긋나지 않음을 테스트로 보장
- 14가지 뷰포트에서 정적 페이지와 React 렌더 결과 정렬 오차 1px 이내 검증
- 전환 시점에 걸쳐 계속 타이핑해서, 키가 하나라도 사라지거나 순서가 바뀌면 실패하는 테스트
- 실서비스에서 전환마다 화면 이동량을 0.1px 단위로 기록, 조금이라도 움직이면 Claude가 스레드를 연다

#### 크롬 새 탭 푸터가 범인

그래도 테스트로 다 못 잡으니 점진적 배포(사내 → 1% → 전체)를 썼다. 사내 배포 4시간 만에 "새 탭에서 claude.ai 열면 가끔 입력창이 15~20px 툭 내려간다"는 제보가 왔다. 측정해보니 전환 이동량은 0px. 원인은 우리 코드가 아니라 **크롬**이었다.

- 조직이 관리하는 크롬은 새 탭 페이지 아래에 56px 푸터("anthropic.com에서 관리 · Chrome 맞춤설정")를 그린다
- 주소창에 입력하는 동안 크롬이 [추측성 로딩][speculative-loading]으로 페이지를 <strong>현재 탭 높이(푸터 때문에 56px 짧은)</strong>에 맞춰 미리 렌더한다
- Enter를 누르면 짧은 높이 기준 첫 프레임이 그려지고, 약 100ms 뒤 푸터가 사라지며 페이지가 56px 늘어난다
- `/new`는 인사말과 입력창을 높이의 18% 지점에 두니까 0.18 × 56 ≈ 10px 이동
- 예전엔 페이지가 이렇게 일찍 그려진 적이 없어서 안 보였을 뿐, 늘 잠재해 있던 문제. 헤드리스 크롬엔 걷어낼 브라우저 UI가 없어서 테스트로도 못 본다

Claude가 리사이즈 중에도 레이아웃이 안 움직이게 고정했고, 프리렌더 흐름을 재현하는 테스트를 추가했다. 이건 진짜 사람이 잡기 어려운 버그다.

### 방향 잡기: 사람이 한 일

루프가 알아서 굴러가진 않았다. 사람 몫은 세 가지.

#### 과감함

Claude는 기본적으로 보수적이다. 티켓으로 남기고, 장담 안 하고, 예상 시간을 넉넉히 잡는다. "이번 주 안에 PR 올리고, 수치는 며칠 기다려야 한다"는 Claude에게 Raymond가 "지금 올리면 내가 바로 머지·배포할게. 제발 더 용감해져"라고 했고, 한 시간 안에 PR이 올라왔다. 목표를 달성한 스레드들이 느슨해지자 Sam은 "목표에서 멈출 필요 없다, 다음은?"이라고 스레드마다 남겼다.

#### 안목

모든 스레드엔 사람 담당자가 있었고, 사용자가 체감하는 변경엔 전후 스크린샷/녹화가 붙었다. 판단은 사람 몫이다.

- 표는 셀 단위로 채울까, 행이 다 찰 때까지 기다릴까?
- 로딩 스켈레톤은 즉시 보일까, 0.5초 뒤에만 보일까?
- 스트리밍 텍스트의 단어 단위 페이드가 프레임 예산의 5분의 1을 쓸 가치가 있나?

#### 방향

스레드마다 범위를 일부러 좁혀서 벤치마크 하나, 여정 하나에만 집중시켰다. "박을 못을 찾아다니는 망치 150개"라는 표현이 와닿았다. 사람은 순서, 스레드 병합, 언제 닫을지를 정했다. 900줄짜리 PR에 달린 한 줄: "메시지당 2ms 아끼자고 이 빌드 플러그인 유지보수 부담을 질 가치는 없다."

### 프레임당 8밀리초

구문 강조 정규식 최적화를 보여주려고 Claude가 긴 답변 스트리밍 녹화에 `requestAnimationFrame` 타임스탬프 기반 FPS 표시를 붙여왔다. Raymond가 "60fps로 제한된 거야? 120까지 올려볼 수 있어?"라고 물었고, Claude는 헤드리스 크롬이 기본 60Hz라는 걸 확인한 뒤 **DevTools begin-frame 제어**로 결정적인 120Hz 프레임 스테핑을 만들었다. 8.33ms 간격 begin-frame 240번에 정확히 240프레임. "이 프레임이 120Hz에서 제시간에 그려졌나"를 노이즈 없이 읽을 수 있게 됐다.

그다음 긴 답변을 한 프레임씩 넘기며 느린 부분을 잡았다.

- 완성된 블록은 메모이제이션 → 청크마다 들던 `O(message length)` 작업 제거
- 길어지는 코드 펜스의 토큰화를 워커로
- 표는 셀 단위로 나타나게

```tsx
// ❌ 청크가 올 때마다 메시지 전체를 다시 파싱·렌더 → O(message length)
function Message({ markdown }: { markdown: string }) {
  return <>{parseBlocks(markdown).map((b, i) => <Block key={i} block={b} />)}</>
}

// ✅ 완성된 블록은 memo로 고정, 마지막(진행 중) 블록만 다시 그린다 (이해용 스케치)
const DoneBlock = memo(Block)
function Message({ blocks, streaming }: { blocks: BlockData[]; streaming: BlockData }) {
  return (
    <>
      {blocks.map((b) => <DoneBlock key={b.id} block={b} />)}
      <Block block={streaming} />
    </>
  )
}
```

그 스레드에서만 PR 60개 가까이 머지. 긴 답변의 메인 스레드 블로킹 합계는 약 750ms → 약 200ms, CPU 사용량 약 3분의 1, 120Hz MacBook에서 처음부터 끝까지 120fps. 120Hz 테스트 환경은 야간 작업이 되어 회귀를 감시 중이다. 공식 발표로는 느린 노트북에서 멈춤 횟수 9배 감소, 가장 긴 멈춤 4.5배 단축.

### 다음 단계

지금은 8월 초 대비 약 3배 빠르고, 래칫이 이걸 지킨다. 남은 건 p95, 다른 여정, 아주 긴 대화. Electron, Chromium, Node.js 업스트림에 기여한 작업은 별도 글로 나온다고.

### 📌 정리

`측정하는 순간 개선이 시작된다. 그러니 측정할 대상을 계속 찾고, 개선한 건 래칫으로 잠근다.`

#### 핵심

> Anthropic은 2주 스프린트로 claude.ai 핵심 여정을 p75 기준 약 3배 빠르게 만들었다. 핵심은 노이즈 많은 실제 시간 대신 결정적 지표(인스트럭션 수, React 커밋 수, 스타일 재계산, DOM 변경)를 찾고, 그 지표가 실제 시간과 상관있음을 증명한 뒤, CI 래칫으로 회귀를 막는 것이었다. "스레드 열기 → 벤치마크 → 쪼갠 PR + 기능 플래그 → 실데이터 확인 → 래칫 고정" 루프를 150개 넘게 병렬로 돌렸고, 사람은 과감함·안목·방향을 맡았다. CLS로 안 잡히는 덜컹거림, em 대시 하나로 two-byte가 된 V8 문자열, 크롬 새 탭 푸터 같은 버그는 전부 "새로 측정하기 시작한 뒤"에야 보였다.

#### ⭐️ 앞으로 기억할 것

1. 성능 회귀는 래칫으로 막는다
ms 단위 벽시계 시간은 CI 게이트로 쓰기엔 너무 흔들린다. 결정적인 카운트(인스트럭션 수, 렌더 횟수, 번들 크기)를 기준값 파일에 커밋해두고, 나빠지면 실패, 좋아지면 기준값을 갱신하자. 우리 프로젝트라면 번들 크기나 특정 컴포넌트 렌더 횟수부터 걸어볼 만하다.
```js
// scripts/ratchet.mjs — 수치가 기준보다 커지면 CI 실패, 줄었으면 기준 갱신
import fs from 'node:fs'
const baseline = JSON.parse(fs.readFileSync('perf-baseline.json', 'utf8'))
const current = await measure() // { 'message-tree': 120345, ... }
for (const [key, value] of Object.entries(current)) {
  if (value > baseline[key]) {
    console.error(`❌ ${key}: ${baseline[key]} → ${value} (회귀)`)
    process.exitCode = 1
  } else if (value < baseline[key]) {
    baseline[key] = value // ✅ 좋아진 만큼 상한을 내린다
  }
}
fs.writeFileSync('perf-baseline.json', JSON.stringify(baseline, null, 2))
```

2. 대리 지표는 실제 시간과 상관관계를 증명한 뒤에 쓴다
결정적이라는 이유만으로 지표를 고르면 엉뚱한 걸 최적화한다. "이 숫자를 줄였더니 실제로 X ms 줄었다"를 한 번은 보여야 벤치마크로 인정한다.

3. CLS 점수가 좋아도 눈에 거슬리는 이동은 있다
CLS 0.008은 "좋음"이지만 사용자는 덜컹거림을 느낀다. 점수만 보지 말고 `layout-shift` 엔트리의 `sources`로 **어디서** 움직였는지 기록하자. `data-region` 같은 이름표를 주요 영역에 달아두면 원인 추적이 쉬워진다.

4. V8 문자열은 one-byte / two-byte가 따로 있다
Latin-1 밖의 문자(`—`, `“ ”`, 한글, 이모지)가 하나라도 섞이면 문자열 전체가 two-byte가 되고 정규식 같은 처리가 느린 경로를 탈 수 있다. 큰 문자열에 무거운 정규식을 돌리다 이유 없이 느리면 의심해볼 것. 한글 서비스면 사실 대부분 two-byte라는 것도 기억해두자.

5. 선택자 하나가 스타일 재계산 비용을 키울 수 있다
`:root:has()`처럼 문서 최상단에서 하위를 보는 `:has()`는 DOM이 바뀔 때마다 넓은 범위를 다시 매칭하게 만들 수 있다. 편하다고 전역에 쓰지 말고, 범위를 좁힌 조상에 걸자.
```css
/* ❌ DOM 어디가 바뀌든 루트부터 다시 확인 */
:root:has(.modal-open) { overflow: hidden; }

/* ✅ 상태를 클래스로 직접 토글하거나, 범위를 좁힌 컨테이너에 */
html.modal-open { overflow: hidden; }
```

6. 정적 셸은 실제 컴포넌트에서 생성해야 안 깨진다
HTML에 미리 박은 UI(스켈레톤, 정적 입력창)를 손으로 따로 관리하면 언젠가 React 결과와 어긋난다. 같은 컴포넌트를 빌드 타임에 렌더해서 뽑고, 여러 뷰포트에서 픽셀 정렬을 테스트로 묶어두자.

7. 높이 비율로 배치한 UI는 뷰포트 변화에 민감하다
"위에서 18% 지점"처럼 뷰포트 높이에 비례한 배치는 프리렌더, 모바일 주소창 접힘처럼 첫 페인트 이후 높이가 바뀌는 상황에서 그대로 움직인다. 첫 화면 핵심 요소는 이런 변화에 흔들리지 않게 고정할 것.

8. 기능 플래그는 만드는 것만큼 지우는 것도 일이다
킬 스위치와 램프를 구분하고, 안전해지면 바로 지운다. 200개 만들어 절반 이상을 2주 안에 정리한 게 "롤백 0건"과 같이 갔다는 점이 인상적이다.

> 📌 결론  
> ▎ 측정이 준비 단계가 아니라 개선의 첫걸음이 됐다. 레버리지가 가장 큰 일은 측정할 대상을 더 찾는 것.  
> ▎ 벽시계 시간은 노이즈가 크니, 실제 시간과 상관관계가 증명된 결정적 지표를 CI 래칫으로 지킨다.  
> ▎ 루프(스레드 → 벤치마크 → 쪼갠 PR + 플래그 → 실데이터 → 래칫)가 하나에서 돌면 확장은 스레드를 늘리는 것뿐이다.  
> ▎ 가드레일(단위 테스트 우선, 기능 플래그, 점진적 배포)이 있어서 3천 건 머지에 롤백 0건이 가능했다.  
> ▎ 사람의 일은 과감하게 밀어주기, 트레이드오프 판단, 범위와 순서 정하기.  
> ▎ ⭐️ 실무 적용 포인트: 우리 앱의 핵심 여정 3~4개를 정하고 "인터랙션 시작 → 렌더 완료"로 측정 기준부터 통일하자.  
> ▎ ⭐️ 실무 적용 포인트: 번들 크기나 핵심 컴포넌트 렌더 횟수 하나라도 래칫 CI로 걸어두자. 개선은 잠가야 남는다.
