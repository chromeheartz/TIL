# SSE vs WebSocket vs 폴링, 프론트에서 실시간 전송 고르기

> **원문**: [SSE vs WebSockets (and polling): picking a real-time transport on the front end][origin] — Mario Sassine
> **번역 출처**: [(번역) SSE와 WebSocket(그리고 폴링): 프런트엔드에서 실시간 전송 방식 선택하기][translation] — ykss

"새로고침 없이 화면이 알아서 갱신되게 해주세요"라는 요구는 거의 모든 프로젝트에서 한 번은 나온다. 그런데 막상 고르려면 선택지가 "타이머로 다시 물어보기"부터 "세션 내내 소켓 열어두기"까지 폭이 넓다. 너무 무거운 걸 고르면 필요도 없는 소켓 인프라를 떠안고, 너무 가벼운 걸 고르면 UI가 느려지거나 API를 두들겨 패게 된다. 이 글은 그 선택을 클라이언트 입장에서 정리한 글이라 읽고 나도 정리해둔다.

### 선택지 네 가지

- `폴링(Polling)`: 일정 간격으로 fetch. 새 인프라 0, 어디서나 동작.
- `롱 폴링(Long polling)`: 서버가 데이터가 생길 때까지(혹은 타임아웃까지) 요청을 붙잡고 있는 방식. SSE가 있는 지금은 거의 레거시지만 아직 폴백 용도로 쓰인다.
- `SSE(Server-Sent Events)`: 하나의 긴 HTTP 응답에 서버가 계속 써내려가는 방식. 서버 → 클라이언트 단방향. 브라우저 API는 `EventSource`. 텍스트만 가능. 자동 재연결과 이어받기가 내장.
- `WebSocket`: HTTP 업그레이드 후 자체 프로토콜로 전환되는 전이중(full-duplex) 연결. 텍스트/바이너리 모두 가능. 대신 메시지 프로토콜, 재연결, 인증 흐름을 전부 직접 만든다.

참고로 Pusher, Ably, Supabase Realtime, Firebase 같은 매니지드 실시간 서비스와 GraphQL subscription은 거의 다 WebSocket 위에 올라가 있다. `WebTransport`(HTTP/3)도 있긴 한데 아직 프론트에서 꼭 필요한 경우는 드물다.

### SSE vs WebSocket 나란히 비교

| 항목 | SSE | WebSocket |
|---|---|---|
| 방향 | 서버 → 클라이언트 단방향 | 양방향 |
| 프로토콜 | 그냥 HTTP (1.1 또는 2) | ws/wss로 업그레이드, 별도 프로토콜 |
| 브라우저 API | `EventSource`, 작지만 알아서 많이 해줌 | `WebSocket`, 작고 그 위는 전부 내가 만듦 |
| 재연결 | 자동 | 직접 구현 |
| 끊긴 뒤 이어받기 | `Last-Event-ID` 헤더, 서버가 놓친 이벤트 재전송 가능 | 직접 설계 |
| 페이로드 | UTF-8 텍스트, `data:` / `event:` / `id:` 프레이밍 | 텍스트 또는 바이너리 프레임 |
| 브라우저에서 커스텀 인증 헤더 | 네이티브 `EventSource`로는 불가 | 핸드셰이크에서도 불가 |
| 인프라 | 평범한 HTTP, 단 버퍼링하는 프록시가 스트리밍을 깨뜨릴 수 있음 | ws를 아는 로드밸런서 필요, 때로 sticky session |
| HTTP/1.1 연결 제한 | 도메인당 브라우저 ~6개. HTTP/2 멀티플렉싱이면 해소 | 연결 1개, 6개 제한과 무관 |
| 스케일 모델 | 클라이언트당 HTTP 연결 1개 유지 | 클라이언트당 소켓 1개 + 보통 pub/sub 팬아웃 계층 추가 |

표만 봐도 느낌이 온다. SSE는 "브라우저가 대신 해주는 게 많은 대신 할 수 있는 게 적다", WebSocket은 "뭐든 할 수 있는 대신 뭐든 내가 만든다".

### 폴링은 아직도 자리가 있다

솔직히 폴링을 무시하기 쉬운데, 데이터가 천천히 혹은 불규칙하게 바뀌고 몇 초 정도 늦어도 괜찮다면 폴링이 정답이고 가장 싸다.

- 대시보드, "새 항목 N개" 뱃지, CI 상태, 1분에 한 번 갱신되는 IoT 패널.
- TanStack Query라면 `refetchInterval`, `refetchOnWindowFocus`만으로 끝. 엣지의 stale-while-revalidate 캐시와도 잘 어울린다.
- 적응형으로 만들기: 탭이 숨겨지면 간격을 늘리거나 멈추고, 사용자 액션 직후엔 더 자주.
- 간격에 지터(jitter)를 섞어서 클라이언트 천 개가 같은 초에 몰려 폴링하는 사태를 막는다.

```ts
// ✅ 탭 가시성 + 지터를 반영한 폴링 간격
function pollInterval(base: number): number | false {
  if (document.hidden) return false // 숨겨진 탭은 폴링 중단
  return base + Math.random() * 1000 // 최대 1초 지터
}

useQuery({
  queryKey: ['ci-status'],
  queryFn: fetchCiStatus,
  refetchInterval: () => pollInterval(10_000),
  refetchOnWindowFocus: true,
})
```

비용은 명확하다. 지연의 하한선이 폴링 간격이 되고, 아무것도 안 돌아오는 요청이 많이 생긴다.

### SSE가 맞는 경우

- 단방향 업데이트: 알림, 라이브 피드, 긴 작업의 진행률, 읽기만 하는 시세 티커, "다른 사람이 이 문서를 수정했어요" 류의 넛지.
- LLM 토큰 스트리밍. 어시스턴트 UI가 SSE를 쓰는 이유가 이거다. 서버는 텍스트를 흘려보내고, 클라이언트는 이어붙이고, 다음 프롬프트는 그냥 평범한 POST로 보낸다.
- 빌드/배포 로그를 패널에 스트리밍.
- 자동 재연결과 이벤트 리플레이를 직접 안 짜고 싶을 때.
- 인프라를 최소로 하고 싶을 때. 그냥 HTTP 응답이니까.

```ts
const es = new EventSource('/api/notifications', { withCredentials: true })

// 서버가 event: notification 으로 보낸 것만 받음
es.addEventListener('notification', (e) => {
  inbox.add(JSON.parse(e.data))
})

es.onopen = () => setStatus('live')
es.onerror = () => {
  // 재연결은 EventSource가 알아서 함. 여기선 상태만 반영
  setStatus('reconnecting')
}

// ⚠️ EventSource는 404여도 영원히 재시도한다.
// 언마운트 / 라우트 이동 시 반드시 es.close()
```

### WebSocket이 맞는 경우

- 진짜 양방향이면서 저지연: 채팅, 협업 편집(커서 위치, presence, CRDT/OT 연산), 멀티플레이 게임, 라이브 드로잉, 주문도 넣는 트레이딩 터미널.
- 바이너리 페이로드: 오디오/비디오 프레임, protobuf나 msgpack, 압축된 게임 상태.
- 클라이언트가 자주 보내서 메시지마다 POST 한 번씩은 낭비일 때.

```ts
class RealtimeSocket {
  private ws?: WebSocket
  private attempt = 0
  private heartbeat?: number

  connect() {
    this.ws = new WebSocket(`wss://api.example.com/realtime?token=${getToken()}`)

    this.ws.onopen = () => {
      this.attempt = 0 // 성공하면 백오프 카운터 리셋
      this.send({ type: 'subscribe', channels: currentChannels() }) // 서버는 날 기억 못 함, 매번 재구독
      this.heartbeat = window.setInterval(() => this.send({ type: 'ping' }), 25_000)
    }

    this.ws.onclose = () => {
      clearInterval(this.heartbeat)
      // 지수 백오프 + 지터, 최대 30초
      const delay = Math.min(1000 * 2 ** this.attempt++, 30_000) + Math.random() * 1000
      setTimeout(() => this.connect(), delay)
    }

    this.ws.onmessage = (e) => handleMessage(JSON.parse(e.data))
  }

  send(msg: unknown) {
    // 열려 있을 때만 전송. 끊긴 동안의 메시지 정책은 따로 정해야 함
    if (this.ws?.readyState === WebSocket.OPEN) this.ws.send(JSON.stringify(msg))
  }
}
```

이 코드가 WebSocket의 현실이다. "연결하고 메시지 받기"는 세 줄인데 재연결·하트비트·재구독이 나머지 전부다.

### 인증이 함정이다

브라우저는 `EventSource`에도, WebSocket 핸드셰이크에도 임의의 헤더를 못 붙이게 한다. 그러니까 `Authorization: Bearer ...`는 둘 다 못 쓴다. 보통 쓰는 우회법:

- `쿠키`: same-site면 둘 다 쿠키를 보낸다(SSE는 `withCredentials: true` 필요). `httpOnly` 세션 쿠키가 있으면 이게 제일 깔끔하다.
- `쿼리스트링에 짧은 토큰`: 둘 다 동작. 대신 서버 액세스 로그와 프록시 로그에 남으니, 몇 분 안에 만료되고 이 연결에만 스코프된 토큰을 발급해야 한다.
- `fetch 기반 SSE 클라이언트`: `@microsoft/fetch-event-source` 같은 라이브러리는 네이티브 `EventSource` 대신 fetch를 쓰니 헤더도 POST 바디도 보낼 수 있다. 대신 재연결은 직접 구현.
- `연결 직후 인증 메시지`: WebSocket 패턴. 연결하자마자 첫 메시지로 토큰을 보내고, 서버는 1~2초 안에 안 오거나 유효하지 않으면 소켓을 끊는다.

```ts
// ❌ 둘 다 안 됨 — 브라우저가 헤더 설정 자체를 막는다
new EventSource('/api/stream', { headers: { Authorization: 'Bearer ...' } })

// ✅ 쿠키 (same-site + httpOnly 세션)
new EventSource('/api/stream', { withCredentials: true })

// ✅ 연결 후 첫 메시지로 인증 (WebSocket)
ws.onopen = () => ws.send(JSON.stringify({ type: 'auth', token }))
```

### 재연결과 복원력, 클라이언트 쪽에서

#### SSE
- `EventSource`가 자동으로 재시도하고, 서버는 `retry:` 필드로 재시도 간격을 힌트할 수 있다.
- 그래도 내가 할 일: 리플레이 후 이벤트 중복 제거, 앱 상태 재구독, "재연결 중" 표시, 그리고 리소스가 사라졌을 때 재시도 멈추기. 안 그러면 `EventSource`는 404를 영원히 두들긴다.

#### WebSocket
- 지수 백오프 + 지터 + 재시도 상한으로 재연결 구현.
- 20~30초마다 하트비트 ping. 연결이 조용히 죽었을 때 브라우저가 `onclose`를 바로 안 쏴주는 경우가 있어서, 하트비트가 사실상 유일한 감지 수단이다.
- 재연결할 때마다 채널 재구독. 서버는 나를 기억하지 않는다.
- 끊겨 있는 동안 보낸 메시지를 어떻게 할지 정하기: 큐에 쌓거나, 버리고 재구독으로 상태를 다시 맞추거나.

#### 둘 다
- `document.hidden`이면 멈추거나 닫고, 포커스 돌아오면 재개.
- 컴포넌트 언마운트와 내비게이션 시 닫기.
- bfcache(back/forward cache)가 페이지를 얼렸다가 되살리는 경우 주의.

### 점진적 전략

클라이언트가 푸시할 필요가 없다면 그냥 `SSE + 폴링 폴백`으로 바로 간다. 이걸로 거의 다 커버되고 단순하다. socket.io가 하는 "WebSocket, 안 되면 SSE, 안 되면 롱 폴링" 사다리는 진짜 양방향이 필요하면서 험악한 프록시까지 지원해야 할 때만 꺼낸다.

### 프로젝트별로 뭘 고를까

| 프로젝트 | 선택 | 이유 |
|---|---|---|
| 채팅 / 메시징 | WebSocket | 클라이언트 전송 잦음, 저지연, presence |
| 협업 문서 편집기 | WebSocket | 양방향 연산, 커서, presence |
| 멀티플레이 게임 | WebSocket (+ 나중에 WebTransport) | 고빈도, 바이너리 많음, 클라이언트 입력 |
| LLM 채팅 스트리밍 | SSE | 서버가 토큰 스트림, 프롬프트는 일반 POST |
| 알림 벨 | SSE | 서버 → 클라이언트만, 자동 재연결 원함 |
| 라이브 피드 / 타임라인 | SSE | 단방향, 재연결 시 리플레이가 유용 |
| 긴 내보내기/가져오기 진행바 | SSE | 작업 하나, 스트림 하나, 끝 |
| CI/CD 파이프라인 상태 페이지 | SSE 또는 폴링 | 저빈도, 좀 늦어도 됨 |
| 읽기 전용 시세 / 스코어 티커 | SSE | 순수 서버 푸시. 클라이언트도 행동하면 WS |
| "새 글 있음" 뱃지 | 폴링 | 몇 초 늦어도 됨, 인프라 0 |
| IoT 대시보드 (분당 1회) | 폴링 또는 SSE | 클라이언트 수와 지연 요구에 따라 |
| 공유 커서 / presence | WebSocket | 작은 양방향 메시지가 끊임없이 |

### 📌 정리
`클라이언트가 보낼 게 없으면 SSE, 보낼 게 많으면 WebSocket, 몇 초 늦어도 되면 폴링`

#### 핵심
> 실시간 전송 선택의 기준은 "얼마나 실시간이냐"가 아니라 **방향과 빈도**다. 서버 → 클라이언트만 필요하면 SSE가 자동 재연결·리플레이까지 공짜로 주고 인프라도 그냥 HTTP다. 클라이언트가 자주 보내거나 바이너리가 필요할 때만 WebSocket을 꺼내고, 그 순간부터 재연결·하트비트·재구독·인증이 전부 내 몫이 된다. 그리고 둘 다 브라우저에서 커스텀 인증 헤더를 못 붙인다는 걸 처음부터 설계에 반영해야 한다.

#### ⭐️ 앞으로 기억할 것
1. 기본값은 SSE + 폴링 폴백
클라이언트 푸시가 필요 없으면 WebSocket을 고려할 이유가 없다. LLM 스트리밍도 응답은 SSE, 프롬프트는 POST로 충분하다.
2. EventSource는 404를 영원히 재시도한다
자동 재연결이 편하지만, 리소스가 사라졌을 때 멈추는 건 내가 해야 한다.
```ts
es.onerror = () => {
  // 서버가 닫았으면(CLOSED) 재시도 안 함. 그 외엔 브라우저가 알아서 재연결
  if (es.readyState === EventSource.CLOSED) cleanup()
}
```
3. Authorization 헤더는 둘 다 못 쓴다
`EventSource`도 WS 핸드셰이크도 헤더를 못 붙인다. same-site `httpOnly` 쿠키가 1순위, 안 되면 몇 분짜리 연결 스코프 토큰을 쿼리스트링에.
4. WebSocket은 하트비트 없으면 죽은 줄도 모른다
`onclose`가 안 올 수 있다. 20~30초 ping은 선택이 아니라 필수. 재연결 시 재구독도 매번.
5. 탭 숨김 / 언마운트 / bfcache를 다 처리한다
폴링이든 SSE든 WS든 `document.hidden`에서 멈추고, 언마운트에서 닫고, bfcache 복원을 고려한다. 연결 누수는 서버 비용이자 배터리 비용이다.
6. 폴링은 지터와 적응형 간격이 전부다
```ts
// ✅ 천 명이 같은 초에 몰리지 않게
refetchInterval: () => (document.hidden ? false : 10_000 + Math.random() * 1000)
```

> 📌 결론  
> ▎ 방향이 단방향이면 SSE, 양방향이고 잦으면 WebSocket, 몇 초 지연 OK면 폴링.  
> ▎ SSE는 재연결·리플레이·HTTP 인프라를 공짜로 준다. 단 텍스트만, 단방향만.  
> ▎ WebSocket은 뭐든 되지만 재연결·하트비트·재구독·인증을 전부 직접 짠다.  
> ▎ 브라우저는 둘 다 커스텀 인증 헤더를 못 보낸다. 쿠키 or 짧은 쿼리 토큰.  
> ▎ ⭐️ 실무: 새 기능 요구가 "서버가 알려주면 돼요"면 SSE부터. "WebSocket 써야죠"는 클라이언트가 뭘 얼마나 자주 보내는지 먼저 물어보고 결정.  
> ▎ ⭐️ 실무: 어떤 전송이든 `document.hidden` 처리와 언마운트 시 `close()`는 코드리뷰 체크리스트에 넣는다.
