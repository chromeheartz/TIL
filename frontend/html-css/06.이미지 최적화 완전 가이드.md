# 이미지 최적화 완전 가이드

> **출처**: https://velog.io/@sehyunny/the-definitive-guide-to-image-optimization (velog @sehyunny, 황세현 번역) / 원문: https://www.builder.io/blog/the-definitive-guide-to-image-optimization

이미지가 보통 페이지에서 가장 무거운 리소스다. LCP도 거의 히어로 이미지가 잡고, 레이아웃 시프트(CLS)도 이미지가 주범인 경우가 많다. `next/image`가 알아서 해주긴 하지만 **걔가 뒤에서 뭘 하는지**(srcset/sizes/lazy/aspect-ratio)를 알아야 직접 튜닝도 하고 프레임워크 밖에서도 써먹는다. 그래서 `<img>` 속성 레벨부터 정리.

### 이미지 최적화란?

**좋은 품질을 유지하면서 가능한 한 작은 파일 크기로** 이미지를 만들고 표시하는 것. 최적의 *형식 · 크기 · 해상도*로 내보내는 작업이다.

### 왜 신경 써야 하나

- **사용자 경험** — 이미지 다 로드될 때까지 기다리고 싶은 사람은 없다.
- **페이지 성능** — 크고 최적화 안 된 이미지 = 느린 로드.
- **가시성(SEO)** — 최적화된 이미지는 검색엔진에 맥락을 주고 이미지 검색 상단 노출에 유리. 페이지가 빠르면 구글이 더 잘 노출해준다.

### 모범 사례

#### 1) `<img>` 태그 쓰기 (vs CSS `background-image`)

둘 다 시각적으로 비슷해 보여도 **같지 않다.** 다음 경우엔 `<img>`가 맞다.

- 이미지가 장식이 아니라 **콘텐츠의 일부**일 때
- 사용자가 페이지를 **인쇄**할 때 이미지도 같이 인쇄돼야 할 때
- 경고 아이콘처럼 **의미가 있고**, 그 맥락이 스크린 리더에 전달돼야 할 때
- **SEO 이점**을 원할 때 → ⭐ 구글은 **배경 이미지를 자동 인덱싱하지 않는다.**
- 브라우저가 텍스트 크기에 맞춰 이미지를 확장·렌더링하게 할 때

게다가 `<img>`는 `srcset`, `sizes` 같은 최적화 속성을 줘서 로드를 빠르게 한다.

#### 2) 차세대 포맷 활용 (WebP)

WebP는 JPEG/PNG보다 파일이 최소 **25~30% 작다.** 페이스북 사례로는 JPEG→WebP 시 25~35%, PNG→WebP 시 **80%** 감소.

모든 브라우저가 WebP를 지원하진 않으니, `<picture>` + `<source>`로 **폴백**을 깐다.

```html
<picture>
  <source srcset="hero.webp" type="image/webp" />
  <img src="hero.jpg" alt="..." />  <!-- WebP 미지원 브라우저 폴백 -->
</picture>
```

#### 3) `alt` 텍스트로 접근성 ↑

대체 텍스트는 그래픽의 기능·모양에 대한 맥락을 준다. 접근성(스크린 리더)뿐 아니라 **SEO 순위·로드 지연 시 대체 표시**에도 중요하다.

단, 구분이 핵심이다.

- ✅ **콘텐츠성 이미지** → 구체적이고 잘 쓴 `alt`
- ✅ **순수 장식용 배경 이미지** → `role="presentation"` (또는 빈 `alt=""`)로 보조기구가 건너뛰게

#### 4) `srcset`으로 반응형 이미지

아이콘·로고 빼면 대부분 화면 크기에 맞춰 리사이즈돼야 한다. 고정 크기 대신 `srcset`으로 **단말기 화면 너비에 따라 다른 이미지**를 준다.

```html
<img srcset="small.jpg 500w, medium.jpg 1000w, large.jpg 2000w"
     src="medium.jpg" alt="...">
```

> ⭐ **`x`보다 `w` 단위를 써라.** `x`는 픽셀 밀도(DPR)용이라 고정 크기 이미지에 적합하고, `w`는 화면 너비에 맞는 이미지를 가져오게 해준다.

#### 5) `sizes`로 슬롯 너비 알려주기

브라우저는 **첫 프리로드 시점에 이미지가 화면에서 얼마나 클지 모른다.** `sizes`가 없으면 **이미지가 페이지 전체 너비를 차지한다고 가정** → 필요 이상으로 큰 이미지를 받아온다.

`sizes`는 "이 조건이면 이미지 슬롯이 이만큼"을 미리 알려준다. 절대 px 대신 `vw`로 **화면에서 차지할 비율**을 줄 수도 있다.

```html
<img srcset="small.jpg 500w, medium.jpg 1000w, large.jpg 2000w"
     sizes="(max-width: 600px) 100vw, 50vw"
     src="medium.jpg" alt="...">
```

#### 6) 가로세로 비율(aspect ratio) 보존 → CLS 방지

리사이즈할 때 비율을 안 지키면 **레이아웃 시프트**가 난다 (이미지가 늦게 로드되며 주변 콘텐츠를 밀어냄).

> **[역주] 레이아웃 시프트** — 느린 이미지 로딩으로 레이아웃이 갑자기 변경·이동되는 현상.

해결: **HTML에 `width`/`height`를 명시** + CSS에서 `height: auto`. 그럼 브라우저가 비율로 자리를 미리 잡아 CLS를 최소화한다. `object-fit`(fill/cover/contain/scale-down)으로 채움 방식도 지정.

```html
<img src="hero.jpg" width="1600" height="900" alt="..."
     style="height:auto; object-fit:cover;">
```

| `object-fit` | 동작 |
|---|---|
| `fill` (기본) | 슬롯 채움, 비율 무시(찌그러짐) |
| `cover` | 비율 유지하며 슬롯 꽉 채움(넘침 잘림) |
| `contain` | 비율 유지하며 슬롯 안에 다 들어오게 |
| `scale-down` | `none`/`contain` 중 더 작은 쪽 |

#### 7) 중요 이미지는 `fetchpriority="high"`

히어로 이미지처럼 **LCP에 해당하는 이미지**는 바로 보여야 임팩트가 있다. `fetchpriority="high"`로 "이거 먼저 처리해"라고 브라우저에 알리면, 하단 이미지 같은 데 자원을 먼저 안 쓴다.

#### 8) 하단 이미지는 lazy loading + async decoding

- `loading="lazy"` — **뷰포트 밖 이미지**는 스크롤 전까지 로드 안 함. ⭐ **단 LCP 이미지/상단 이미지엔 쓰면 안 됨**(오히려 느려짐). 하단 + 비-LCP 이미지에만.
- `decoding="async"` — 이미지 디코딩이 성능에 영향을 주는데, 하단 비-LCP 이미지는 먼저 디코딩할 필요 없다고 지정.
- 거기에 `fetchpriority="low"`까지 묶어주면 좋다.

```html
<img src="footer.jpg" alt="..." loading="lazy" decoding="async" fetchpriority="low">
```

### 자동화 도구

손으로 sizes·포맷·리사이즈를 다 챙기는 건 지루하다. 대부분 빌드/CDN이 자동화해준다.

- **Cloudinary** — 단말 환경에 맞춰 포맷·성능 자동 최적화하는 DAM.
- **Next.js `<Image>`** — `<img>` 확장. 자동 리사이즈/최신 포맷 변환/CLS 방지/하단 lazy loading.
- **Nuxt Image** — Vue용. Next.js Image와 유사.
- **Gatsby Image Plugin** — 성능·SEO·접근성 챙긴 이미지 추가.
- **Builder.io** — 페이지 레이아웃 분석해 디바이스별 정확한 크기 → 최적 `sizes`를 자동 생성.

### 📌 정리
`이미지 최적화 = 작은 파일(WebP) + 딱 맞는 크기(srcset/sizes) + 자리 미리잡기(width/height) + 우선순위 제어(fetchpriority/lazy)`

#### 핵심
> 이미지는 페이지에서 제일 무겁고 LCP·CLS를 좌우한다. 핵심은 네 갈래다. ① **포맷** — WebP로 25~80% 절감, `<picture>`로 폴백. ② **크기** — `srcset`(w 단위)으로 화면 너비별 이미지 + `sizes`로 슬롯 너비를 알려줘 과다 다운로드 방지. ③ **CLS 방지** — HTML `width`/`height` 명시 + CSS `height:auto`로 비율 자리 선점. ④ **우선순위** — LCP 히어로는 `fetchpriority="high"`, 하단 비-LCP는 `loading="lazy"` + `decoding="async"` + `fetchpriority="low"`. 그리고 SEO·접근성 위해 콘텐츠 이미지는 `<img>` + 의미 있는 `alt`, 장식은 `role="presentation"`. 실무에선 next/image 같은 도구가 이걸 다 자동화하지만 원리를 알아야 튜닝한다.

#### ⭐️ 앞으로 기억할 것
- 1. **`<img>` vs `background-image`**
  콘텐츠·SEO·접근성·인쇄가 필요하면 `<img>`. ⭐ 구글은 **배경 이미지를 인덱싱 안 함** → SEO 노릴 이미지는 무조건 `<img>`.
- 2. **WebP + `<picture>` 폴백**
  JPEG 대비 25~35%, PNG 대비 80%까지 절감. 미지원 브라우저는 `<source type>` + `<img>` 폴백으로 커버.
- 3. **`srcset`은 `w`, `sizes`로 슬롯 알려주기**
  `w` = 화면 너비 기준(반응형), `x` = DPR(고정 크기). `sizes` 없으면 100vw로 가정해 과대 다운로드.
- 4. **width/height 명시로 CLS 잡기**
  HTML에 치수 박고 CSS `height:auto`. 비율 선점 → 레이아웃 시프트 최소화. `object-fit`으로 채움 방식 조절.
- 5. **우선순위는 위치 따라 정반대**
  ⭐ LCP/상단 = `fetchpriority="high"`, **lazy 금지**. 하단/비-LCP = `loading="lazy"` + `decoding="async"` + `fetchpriority="low"`.
- 6. **장식 이미지는 `role="presentation"`/`alt=""`**
  스크린 리더가 건너뛰게. 콘텐츠 이미지는 구체적 `alt`(SEO·접근성 둘 다).

📌 결론
▎ 이미지 최적화의 4축: 포맷(WebP) · 크기(srcset/sizes) · 자리선점(width·height) · 우선순위(fetchpriority/lazy).
▎ next/image가 다 해주지만, 그게 뒤에서 srcset/sizes/lazy/aspect-ratio를 처리하는 것뿐 — 원리를 알면 프레임워크 밖에서도 같은 효과를 낸다.
▎ ⭐️ 실무 적용 포인트
▎ - Next.js면 → `<Image>`에 `priority`(=fetchpriority high, lazy off)는 **LCP 히어로에만**, 나머진 기본 lazy 그대로.
▎ - `sizes` prop을 꼭 채워라(안 그러면 100vw로 과대 다운로드). 반응형 레이아웃이면 `(max-width: ...) ..vw` 형태로.
▎ - 직접 `<img>` 쓸 땐 width/height 항상 명시해 CLS부터 막기.
▎ - 콘텐츠 이미지에 의미 있는 alt → 접근성 + 이미지 검색 SEO 동시에.
