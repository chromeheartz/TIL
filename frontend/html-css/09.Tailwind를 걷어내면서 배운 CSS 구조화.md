# Tailwind를 걷어내면서 배운 CSS 구조화

> **원문**: [Moving away from Tailwind (and learning to structure my CSS)](https://jvns.ca/blog/2026/05/15/moving-away-from-tailwind--and-learning-to-structure-my-css-/) — Julia Evans
> **번역 출처**: [Tailwind에서 벗어나기 (그리고 CSS 구조화 배우기)](https://velog.io/@tap_kim/moving-away-from-tailwind-and-learning-to-structure-my-css-) — tap_kim

Julia Evans가 8년 전에 "Tailwind 발견했다, 신난다"는 글을 썼던 사람인데, 이번에 몇 개 사이트를 시맨틱 HTML + 바닐라 CSS로 다시 옮기면서 정리한 글이다. 나도 Tailwind 없이 CSS를 어떻게 "구조화"해야 하는지 막막했던 적이 있어서 흥미롭게 읽었다. 저자도 풀타임 FE가 아니라서 CSS를 띄엄띄엄 배웠다고 하는데, 그래서 오히려 관점이 솔직하다.

### 알고 보니 Tailwind가 많은 걸 가르쳐줬다

CSS 구조화를 처음 고민할 때 저자는 좀 위축됐다고 한다. 그런데 [`A whole cascade of layers`]나 [`How I write CSS in 2024`] 같은 글을 읽다 보니 세 가지가 보였다.

- 모든 CSS 코드베이스에는 여러 종류가 섞여 있다. 레이아웃, 폰트, 색상, 공통 컴포넌트.
- 이걸 관리할 시스템이나 가이드라인이 없으면 혼돈이 된다.
- **Tailwind는 이미 이 중 일부에 대한 시스템을 갖고 있고, 나는 그걸 이미 안다.** 좋아하는 것만 흉내 내면 된다.

예를 들면 리셋 스타일시트, 색상 팔레트, 폰트 스케일. Tailwind를 쓰면서 무의식적으로 익힌 시스템들이다.

### 다루는 시스템 9가지

리셋 → 컴포넌트 → 색상 → 폰트 크기 → 유틸리티 → 베이스 → 간격 → 반응형 → 빌드. 일부는 Tailwind에서 가져왔고 일부는 아니다.

#### 1. 리셋

`tailwind.css` 열어서 앞 200줄, 즉 [`preflight`] 스타일을 그대로 복사했다. Tailwind 리셋에 이미 "관계"가 형성돼 있었기 때문이다. 대표적으로 이거.

```css
/* width가 padding을 포함하도록 */
* {
  box-sizing: border-box;
}
```

이거 없이 CSS 쓰는 건 큰 적응이 필요하고, `html { line-height: 1.5; }`처럼 있는지도 몰랐는데 익숙해진 것들이 더 있을 거라는 얘기. 나도 그렇다. 리셋을 직접 쓰기보다 익숙한 걸 가져오는 게 맞다.

#### 2. 컴포넌트

CSS의 대부분이 여기 들어간다. Vue나 React 컴포넌트와 같은 멘탈 모델로 CSS를 컴포넌트 단위로 나누는 것. 사이트에 JS가 하나도 없어도 된다.

원칙은 세 가지.

- 각 컴포넌트는 고유한 클래스를 가진다
- 한 컴포넌트의 CSS는 다른 컴포넌트의 CSS를 **절대** 덮어쓰지 않는다
- 각 컴포넌트는 자기 CSS 파일을 가진다

이러면 한 컴포넌트를 고쳐도 다른 데가 알 수 없는 이유로 깨지지 않는다. 100줄짜리 컴포넌트를 편집할 때 그 100줄만 생각하면 된다.

```html
<figure class="zine horizontal">
  <img src="whatever.jpg">
</figure>
```

```css
/* 중첩 선택자로 변형과 상태를 한 블록에 */
.zine {
  ...
  &.horizontal { ... }
  &.vertical { ... }
  &:hover { ... }
}
```

웹 컴포넌트나 `@scope`처럼 컴포넌트 간 간섭을 프로그래밍적으로 막는 건 안 썼다. 그냥 컨벤션만으로도 충분히 큰 개선이었다고. 솔직히 이게 핵심인 것 같다. 도구보다 규칙.

#### 3. 색상

`colours.css` 하나에 변수를 전부 모은다. 규칙은 딱 하나, **사이트에서 쓰는 모든 색은 이 파일에 있어야 한다.**

```css
:root {
  --pink: #fea0c2;
  --pink-light: #F9B9B9;
  --red: #f91a55;
  --orange: rgb(222, 117, 31);
  ...
}
```

색상은 어려워서 이번 리팩터링에선 건드리지 않고 그대로 뒀다고 한다.

#### 4. 폰트 크기

Tailwind에서 좋았던 것 하나가 "글자 크게 하고 싶다 → `text-lg`" 끝이라는 점. 부족하면 `xl`, `2xl`. `em`/`px`/`rem` 중 뭘 쓸지 고민할 필요가 없다. 그래서 Tailwind 스케일을 변수로 옮겼다.

```css
--size-xs: 0.75rem;
--line-height-xs: 1rem;

--size-sm: 0.875rem;
--line-height-sm: 1.25rem;
```

```css
h3 {
  font-size: var(--size-lg);
  line-height: var(--line-height-lg);
}
```

Tailwind보다 장황하긴 한데 일단 만족한다고.

#### 5. 유틸리티

여러 컴포넌트에 걸쳐 나오는 버튼 같은 것들. Tailwind에서 `.sr-only` 같은 걸 복사해왔다. 이 섹션은 작게 유지하고, 바꿀 때 조심한다.

#### 6. 베이스

사이트 전체에 적용되는, 저자가 직접 고른 스타일. 전체에 많은 걸 강제할 자신이 없어서 **정말 작게** 유지한다. 지금은 두 개뿐.

```css
/* 각 <section> 가운데에 950px 컬럼 */
section {
  --inner-width: 950px;
  padding: 3rem max(1rem, (100% - var(--inner-width)) / 2);
}

a {
  color: var(--orange);
}
```

저 `padding` 트릭이 좋다. 좌우 패딩을 `max(최소 여백, 남는 공간의 절반)`으로 계산해서 미디어 쿼리 없이 컨테이너를 만든다.

베이스는 **바텀업**으로. 거의 빈 상태에서 시작해서, 컴포넌트를 만들다가 공통으로 쓰고 싶은 게 보이면 그때 베이스로 올린다.

#### 7. 간격

아직 완전히 정리 못 한 부분. Tailwind 쓸 때는 원하는 모양 나올 때까지 패딩·마진을 아무 데나 넣었다는 고백이 있는데, 하하, 나도 그랬다.

지금 원칙은 **가능한 한 바깥쪽 레이아웃 컴포넌트가 간격을 담당**하는 것. 자식들 사이 간격은 owl selector로.

```css
/* 첫 자식 빼고 모든 자식 위에 간격 */
section > * + * {
  margin-top: 1rem;
}
```

참고한 글은 [`the owl selector`]와 [`no outer margin`].

#### 8. 반응형 — 미디어 쿼리 대신 그리드

Tailwind에서는 `md:text-xl` 식으로 브레이크포인트를 잔뜩 썼다. 지금은 **브레이크포인트가 거의 필요 없는 유연한 그리드**를 시도 중이다. 어렵지만 Tailwind로는 안 되는 것의 좋은 예시이기도 하다.

```css
/* 넓으면 2열, 좁으면 1열. 미디어 쿼리 없음 */
display: grid;
grid-template-columns: repeat(auto-fit, minmax(min(100%, 400px), max-content));
justify-content: center;
```

| 조각 | 역할 |
|---|---|
| `auto-fit` | 들어갈 수 있는 만큼 컬럼을 만들고, 빈 트랙은 접는다 |
| `minmax(min(100%, 400px), max-content)` | 최소 400px, 단 컨테이너가 400px보다 좁으면 100%로 |
| `justify-content: center` | 남는 공간이 있으면 가운데 정렬 |

`grid-template-areas`도 많이 썼는데 Tailwind에서는 못 쓰는 기능이라고. 참고 글은 CSS Tricks의 [`A responsive grid layout with no media queries`].

#### 9. 빌드 — esbuild

개발 중에는 빌드가 필요 없다. CSS에 이미 `@import`와 중첩 선택자가 내장돼 있으니까.

```css
@import "reset.css";
@import "typography.css";
@import "colors.css";
```

```css
.page {
  h2 { ... }
}
```

프로덕션에서 번들링하고 싶으면 esbuild.

```bash
esbuild style.css --bundle --loader:.svg=dataurl --loader:.woff2=file --outfile=/tmp/out.css
```

평소엔 CSS/JS 빌드 시스템을 피하지만 esbuild는 괜찮다는 입장. 웹 표준 기반이고 정적 Go 바이너리라서.

### 왜 Tailwind에서 벗어나나

- Tailwind가 2018년 이후 빌드 시스템에 훨씬 더 의존하게 됐다. 최신 버전은 빌드 없이 못 쓰는 것 같아서 몇 년째 v2를 쓰고 있었다.
- 빌드 없이 쓰다 보니 프로젝트마다 2.8MB짜리 `tailwind.min.css`(gzip 270K)가 들어 있었다. 좀 어리석게 느껴졌다.
- CSS를 처음보다 훨씬 잘하게 됐다.
- Tailwind에는 한계가 있다. CSS로 이상한 걸 하고 싶을 때 항상 되는 건 아니다. 그 한계가 유용할 때도 있지만(이 글의 상당 부분이 그 한계 일부를 다시 구현하는 얘기다), 이제는 골라 쓰고 싶다.
- 바닐라 CSS와 Tailwind가 섞인 사이트들이 생겼고 유지보수가 즐겁지 않았다.
- 더 시맨틱한 HTML을 쓰면 어떤 느낌일지 궁금했다.

### 다음에 배우고 싶은 CSS

이번엔 안 썼지만 알게 된 것들. `@layer`, `@scope`, 컨테이너 쿼리, 서브그리드.

### 마지막 이유

3년 전에 읽은 [`Tailwind and the Femininity of CSS`]가 마음에 남았다고 한다. CSS가 "간단하다"고 들어서 쉬울 거라 가정하고, 안 되면 CSS를 탓하는 태도. 저자도 그렇게 시작했을 거라고.

그런데 지난 10년간 CSS를 기술로서 진지하게 받아들이기로 결심하고 나니 모든 게 바뀌었다. "센터링은 불가능해" 같은 좌절 대부분이 이미 오래전에 해결됐고, "센터링"이 뭘 의미하는지 자체가 항상 명확하지 않으니 방법이 여러 개인 게 말이 된다는 것도 알게 됐다. **CSS는 어려운 문제를 풀고 있어서 어렵다.**

그리고 Tailwind가 CSS 전문성의 평가절하에 기여한다는 느낌이 들었고, 개인적으로 유용했더라도 거기 동참하고 싶진 않았다는 것. LLM 시대에 인간의 전문성을 가치 있게 여기는 게 더 중요해진 지금은 특히.

### 📌 정리
`Tailwind를 버린 게 아니라 Tailwind가 가르쳐준 시스템만 남기고 나머지를 CSS로 되찾은 것`

#### 핵심
> CSS 구조화의 핵심은 도구가 아니라 **분류와 컨벤션**이다. 리셋·컴포넌트·색상·폰트 스케일·유틸리티·베이스·간격·반응형을 각각 파일과 규칙으로 나누고, 컴포넌트끼리 절대 서로 덮어쓰지 않는다. Tailwind에서 이미 익숙해진 리셋과 스케일은 그대로 변수로 가져오면 된다.

#### ⭐️ 앞으로 기억할 것
- **1. 컴포넌트 CSS 3원칙**
고유 클래스, 남의 CSS 덮어쓰기 금지, 파일 하나. `@scope` 같은 강제 장치 없이 컨벤션만으로도 충분히 효과가 있다.
```css
/* components/zine.css */
.zine {
  &.horizontal { ... }
  &:hover { ... }
}
```

- **2. 베이스는 바텀업, 그리고 작게**
처음부터 전역 스타일을 많이 잡지 말 것. 컴포넌트 만들다가 반복되는 게 보이면 그때 올린다.

- **3. 미디어 쿼리 없는 컨테이너**
`padding: 3rem max(1rem, (100% - 950px) / 2)` 한 줄이면 최소 여백 보장 + 가운데 정렬이 된다.

- **4. 간격은 부모가 담당, owl selector**
자식 컴포넌트에 바깥 마진을 두지 말고 레이아웃 컴포넌트가 간격을 준다.
```css
section > * + * {
  margin-top: 1rem;
}
```

- **5. 반응형은 `auto-fit` + `minmax(min(100%, N), ...)`**
브레이크포인트 대신 그리드가 스스로 접히게. `min(100%, 400px)`가 없으면 좁은 화면에서 오버플로가 난다.
```css
grid-template-columns: repeat(auto-fit, minmax(min(100%, 400px), max-content));
```

- **6. 빌드는 옵션이다**
`@import`와 중첩은 이미 네이티브. 개발 중엔 빌드 없이, 프로덕션만 esbuild로 번들.

> **📌 결론**
> ▎ Tailwind의 진짜 가치는 유틸리티 클래스가 아니라 리셋·색상·폰트 스케일 같은 **시스템**이었다. 그건 변수로 옮기면 그대로 남는다.
> ▎ CSS 구조화 = 종류별 파일 분리 + "컴포넌트는 서로 안 건드린다" 컨벤션. 도구 없이도 된다.
> ▎ 그리드와 `min()`/`max()`를 알면 미디어 쿼리 대부분이 사라진다.
> ▎ "CSS는 어렵다"에 대한 올바른 응답은 평가절하가 아니라 더 잘하게 되는 것이다.
> ▎ ⭐️ 실무 적용 포인트 — Tailwind를 쓰는 프로젝트라도 `tokens.css` 하나에 색상·폰트 스케일을 CSS 변수로 두고, 컴포넌트별 CSS 파일 컨벤션을 잡아두면 나중에 어느 쪽으로든 옮길 수 있다. 섞어 쓰는 상태가 제일 나쁘다.
