# 브레이크포인트 없이 반응형 UI 만들기

> **원문**: https://frontendmasters.com/blog/building-a-ui-without-breakpoints/ (Frontend Masters)
> **번역 출처**: https://velog.io/@tap_kim/building-a-ui-without-breakpoints

![post-thumbnail](https://velog.velcdn.com/images/tap_kim/post/0cfa113b-9824-496d-bb4a-233ee9016c0d/image.jpg)

`@media (min-width: 768px)`. 반응형 한다고 하면 거의 반사적으로 이 한 줄부터 쓰게 된다. 그만큼 브레이크포인트는 웹 초창기부터 반응형의 표준이었고, 친숙하고 배우기 쉽다. 근데 솔직히 컴포넌트가 수십 개로 늘어나면 미디어 쿼리가 여기저기 복붙되면서 CSS가 점점 지저분해지는 경험, 다들 해봤을 거다. 이 글은 "지금 시대 UI는 페이지가 아니라 컴포넌트 중심인데, **전역 뷰포트 너비**를 로컬 레이아웃 결정의 입력값으로 쓰는 게 애초에 잘못된 거 아니냐"는 문제 제기에서 출발한다. 그리고 현대 CSS 도구로 브레이크포인트를 거의 안 쓰고도 반응형을 만드는 법을 보여준다.

### 브레이크포인트가 해결한 것, 그리고 표준이 된 이유

브레이크포인트는 고정 데스크탑 레이아웃 시절에서 보면 엄청난 발전이었다. 폰/태블릿/데스크탑을 실용적으로 다 지원하게 해줬으니까. 기본 모델은 이렇다.

1. 중요한 뷰포트 너비를 고른다
2. 그 지점에서 레이아웃·크기 변화를 정의한다
3. 제품이 복잡해지면 규칙을 더 추가한다

이 단순함이 표준이 된 이유다. 전형적인 패턴은 이렇게 생겼다.

```css
.page {
  width: 90%;
  font-size: 16px;
}

.card-grid {
  display: grid;
  gap: 1em;
  grid-template-columns: 1fr;
}

@media (min-width: 768px) {
  .card-grid {
    grid-template-columns: repeat(2, 1fr);
  }
}

@media (min-width: 1024px) {
  .page {
    width: 920px;
    font-size: 18px;
  }
  .card-grid {
    grid-template-columns: repeat(3, 1fr);
  }
}

@media (min-width: 1280px) {
  .card-grid {
    grid-template-columns: repeat(4, 1fr);
  }
}
```

문제는 **규모**에서 터진다. 컴포넌트 수십 개가 각자 반복되는 뷰포트 분기를 들고 있으면 → CSS 덩치 증가, 오버라이드 꼬임, 부분 간 결합도 상승. 익숙한 그림이다.

### 왜 "브레이크포인트 우선" 사고가 낡아가는가

화면 종류·크기·픽셀 밀도가 폭발적으로 늘어나면서 근본적인 질문이 생긴다. **대체 어떤 너비를 브레이크포인트로 잡아야 하나?** 768, 1024 같은 기존 기준값이 지금도 유효한가? 명확한 답이 없다.

더 중요한 건 이거다.

> 레이아웃 로직이 항상 화면 너비랑 가장 잘 맞물리는 건 아니다. 보통은 **컴포넌트가 놓인 컨텍스트**랑 맞물릴 때 더 잘 작동한다.

같은 카드 컴포넌트라도 전체 너비 피드에 있을 때, 좁은 사이드바에 있을 때, 모달 안에 있을 때, 대시보드 타일일 때 전부 다르게 보여야 한다. 근데 화면 너비는 이걸 구분 못 한다.

![레이아웃 다양성 예시](https://i0.wp.com/master.dev/blog/wp-content/uploads/2026/04/s_124E0F4150208DDF98EE944AA8CF94692A7C4F345845A0771B8E6D5804D20A4E_1775563466437_image.png?w=1536&ssl=1)

그리고 실무에서 대부분의 반응형 변경은 사실 **진짜 구조적 전환이 아니다.** 공간 배분, 밀도, 타이포그래피, 리듬이 조금씩 점진적으로 바뀌는 거다. 근데 브레이크포인트 우선 사고는 이 연속적인 변화를 억지로 **불연속적인 도약(jump)**으로 만들어버린다. 그 결과 → 로직 중복, 긴 오버라이드 체인, 불안정한 상호작용.

다행히 현대 CSS는 더 나은 기본 도구들을 준다. 아래 4가지가 핵심이다.

---

### 📌 방법 1: 내재적(Intrinsic) 레이아웃을 먼저

적응 로직을 미디어 쿼리가 아니라 **레이아웃 원시 도구 자체**에 밀어 넣는다. "X 너비에서 N개 열을 강제하라"가 아니라, **제약 조건만 정의하고 브라우저가 알아서 연속적으로 유도하게** 두는 거다.

```css
.grid {
  display: grid;
  gap: 1em;
}

/* ❌ 전통적인 브레이크포인트 방식 */
.with-breakpoints {
  grid-template-columns: 1fr;

  @media (min-width: 720px) {
    grid-template-columns: repeat(2, 1fr);
  }
  @media (min-width: 1024px) {
    grid-template-columns: repeat(3, 1fr);
  }
  @media (min-width: 1360px) {
    grid-template-columns: repeat(4, 1fr);
  }
}

/* ✅ 내재적 그리드 — 브레이크포인트 0개 */
.with-auto-fit {
  grid-template-columns: repeat(auto-fit, minmax(320px, 1fr));
}
```

미디어 쿼리 4개로 하던 걸 **한 줄**로 끝낸다. 의도도 훨씬 명확하다 → "열을 최대한 많이 만들되, 절대 320px보다 좁아지지는 마." 라인 수 줄고, 오버라이드 복잡도 줄고, 읽기도 쉬워진다.

#### 2영역 유연 레이아웃 (사이드바 + 메인)

```css
body {
  display: flex;
  flex-wrap: wrap;
}

main {
  /* 메인 콘텐츠는 우선순위를 갖고, 최소 읽기 가능 너비 보장 */
  flex: calc(infinity) 1 360px;
}

aside {
  /* 사이드바 기본 크기 */
  flex: 1 1 240px;
}
```

`flex: calc(infinity) 1 360px` — grow를 무한대로 줘서 메인이 남는 공간을 다 먹게 하되, basis 360px·240px 덕분에 좁아지면 자연스럽게 위아래로 wrap 된다. 하드 스위치를 부드러운 레이아웃 흐름으로 대체하는 패턴.

### 📌 방법 2: 유동적(Fluid) 값 사용하기

반응형 규칙 중 상당수는 그냥 **스칼라 값 조정**이다. 타이포그래피, 간격, 반경(radius), 컴포넌트 크기 — 이런 건 단계적(stepped)이 아니라 연속적(continuous)으로 만들 수 있다. 여기서 `clamp()`가 빛난다. 안전한 최솟값·최댓값을 지켜주면서 그 사이를 유동적으로 스케일하니까.

```css
/* ❌ 브레이크포인트 — 단계적 값 */
.stepped-card {
  font-size: 20px;
  padding: 2em;

  @media (max-width: 720px) {
    font-size: 18px;
    padding: 1.5em;
  }
  @media (max-width: 380px) {
    font-size: 16px;
    padding: 1em;
  }
}

/* ✅ clamp() — 유동적 값 */
.fluid-card {
  font-size: clamp(16px, calc(11.529px + 1.176vi), 20px);
  padding: clamp(1em, calc(-0.118em + 4.706vi), 2em);
}
```

미디어 쿼리 여러 개를 규칙 한 줄로 압축하면서 스케일링은 더 부드러워진다. 가운데 `calc(...)` 값은 직접 계산하기 빡세니까 [clamp 계산기](https://clamp-calculator.netlify.app/)를 쓰면 된다. (`vi`는 viewport inline size = 가로쓰기에선 `vw`와 같음)

### 📌 방법 3: 로컬 반응성을 위한 컨테이너 유닛

지금까지의 값들은 죄다 **뷰포트에 절대적으로 묶여** 있었다. 근데 컴포넌트 시스템에선 이 컴포넌트가 어디에 렌더링될지, 실제로 공간을 얼마나 받을지 미리 알 수가 없다. 바로 여기서 **컨테이너 유닛**이 등장한다. (이제 브라우저 지원도 넓어서 자신 있게 써도 된다)

화면 너비가 아니라 **컴포넌트의 실제 렌더링 크기** 기준으로 값을 스케일하고 싶을 때 이상적이다.

```css
.card-container {
  container-type: inline-size;
}

.card {
  /* 뷰포트가 아니라, 카드 실제 너비 기준으로 폰트 크기가 스케일됨 */
  font-size: 5cqi;

  /* 폰트 크기가 정해지면, 이걸 기준 단위로 다른 속성에 활용 */
  gap: 1em;
  padding: 1.5em;

  /* 또는 카드 크기와 함께 스케일되는 clamp */
  border-radius: clamp(4px, calc(-16.87px + 6.522cqi), 64px);
}
```

내부 내재적 레이아웃 동작도 컨테이너 유닛으로 관리 가능하다.

```css
.card {
  display: flex;
  flex-wrap: wrap;
}

.card-content {
  /* 가능한 공간 다 차지하되, 40cqi 밑으로는 안 줄어듦 */
  flex: calc(infinity) 1 40cqi;
}
```

`cqi`는 컨테이너 인라인 크기의 1% — 뷰포트에서 `vi`가 하던 역할을 컨테이너로 옮겨온 거다. 똑같은 CSS인데 컨테이너 크기에 따라 완전히 다른 결과가 나온다. **컴포넌트가 어디 놓일지 미리 알 필요가 없어지니** 이식성·재사용성이 확 올라간다.

| 단위 | 기준 |
| --- | --- |
| `vi` / `vw` | 뷰포트의 인라인/가로 크기 1% |
| `cqi` | **컨테이너**의 인라인 크기 1% |
| `cqw` / `cqh` | 컨테이너의 가로 / 세로 크기 1% |

### 📌 방법 4: 진짜 구조적 변화엔 컨테이너 쿼리

유동 값·내재적 레이아웃으로 많은 게 해결되지만, 가끔은 진짜로 **구조 자체를 바꿔야** 할 때가 있다. 세로 → 가로 배치, 특정 요소 숨김 같은 거. 이때 쓰는 게 컨테이너 쿼리(`@container`).

핵심 전환은 질문이 바뀌는 거다.

> "화면이 얼마나 넓은가?" ❌
> "이 컴포넌트가 **지금 얼마나 많은 공간**을 갖고 있는가?" ✅

```css
.container {
  container-type: inline-size;
}

.group {
  display: flex;
  flex-direction: column;
  gap: 1em;

  @container (max-width: 32em) {
    flex-direction: row;
    gap: 0.5em;

    .icon {
      font-size: 1.5em;
    }
    p {
      display: none;
    }
  }
}
```

같은 컴포넌트인데 컨테이너 너비에 따라 동작이 달라진다. 임의의 뷰포트 브레이크포인트가 아니라, **그 컴포넌트에게 딱 맞는 순간**에 레이아웃이 바뀐다. 그래서 사이드바든 모달이든 카드든 풀페이지든 어디에 갖다 놔도 예측 가능하게 동작한다.

### 중간 정리: 브레이크포인트는 "기초"가 아니라 "선택지"가 된다

| 도구 | 담당 |
| --- | --- |
| 내재적 레이아웃 (`auto-fit`, `minmax`, `flex`) | **구조** |
| 유동 값 (`clamp`) | **크기** |
| 컨테이너 유닛 (`cqi`) | **국소적 크기 조정** |
| 컨테이너 쿼리 (`@container`) | **실질적 구조 전환** |

브레이크포인트가 사라지는 건 아니다. 다만 **모든 레이아웃 결정의 토대**에서 → 컴포넌트가 진짜로 동작을 바꿔야 할 명확한 이유가 있을 때만 꺼내 쓰는 **집중적·선택적 도구**로 강등된다.

### 그럼 `@media`는 언제 쓰나 — 기기 기능 & 사용자 환경설정

오해하면 안 되는 게, `@media`를 없애자는 게 아니다. **레이아웃을 위한 픽셀 측정 용도로 쓰던 걸 그만두고**, 대신 기기 기능과 사용자 환경을 파악하는 데 쓰자는 거다.

```css
/* hover 지원 감지 */
@media (hover: hover) {
  .link:hover {
    color: blue;
  }
}

/* 터치 디바이스 (coarse pointer) → 탭 영역 키우기 */
button {
  padding: 1em;
  @media (pointer: coarse) {
    padding: 2em;
  }
}

/* PIP 모드 */
@media (display-mode: picture-in-picture) {
  body {
    border: 2px solid white;
  }
}

/* 느린 화면 갱신 환경 → 무거운 blur 끄기 */
.glass-panel {
  backdrop-filter: blur(16px);
  @media (update: slow) {
    backdrop-filter: none;
    background: rgb(255 255 255 / 0.92);
  }
}

/* 스크립팅 없는 환경 */
.no-script-msg {
  display: none;
  @media (scripting: none) {
    display: block;
  }
}
```

그리고 딱 하나 카테고리를 우선시한다면 **사용자 환경설정(user preferences)**부터 챙겨라. 이건 미적 선택이 아니라 **실제 접근성 요구**에서 나오는 거다.

```css
/* 다크모드 */
:root {
  color-scheme: light;
  @media (prefers-color-scheme: dark) {
    color-scheme: dark;
  }
}

/* 높은 대비 */
.card {
  color: #333;
  background: #ccc;
  @media (prefers-contrast: more) {
    color: #000;
    background: #fff;
  }
}

/* 데이터 절약 모드 → 무거운 비디오 숨김 */
@media (prefers-reduced-data: reduce) {
  .hero-video {
    display: none;
  }
}

/* 모션 줄이기 — 설정 안 한 사람한테만 애니메이션 */
.element {
  @media (prefers-reduced-motion: no-preference) {
    animation: spin 4s linear infinite;
  }
}
```

정리하면: **레이아웃은 컨테이너 로직이 주도하고, `@media`는 기기 기능·제약·사용자 요구를 담당**한다. 역할 분담이 명확해진다.

### 📌 실용 마이그레이션 체크리스트

전면 재작성 필요 없다. 한 번에 한 컴포넌트씩 옮기면 변화는 쌓인다.

1. **기존 미디어 쿼리 감사** — 스칼라 변경(크기·간격·타이포)과 구조 변경(구성·레이아웃)을 분리
2. **스칼라 분기를 먼저 교체** — `clamp()`, `min()`, `max()`로
3. **레이아웃을 내재적 원시 도구로** — 고정 열 수 대신 `auto-fit` + `minmax()`
4. **동작을 컴포넌트에 스코프** — 필요한 곳에 `container-type` 추가, 컨테이너 유닛 도입
5. **구조가 진짜 바뀔 때만 컨테이너 쿼리 추가** — 임계값은 컴포넌트 로컬하게
6. **`@media`는 환경 의도용으로** — `hover`, `pointer`, `prefers-reduced-motion`, `update`
7. **실제 배치 환경에서 검증** — 사이드바·모달·풀콘텐츠에서 같은 컴포넌트 테스트

> 가장 중요한 건 **이 방법들을 앞으로의 기본 기준선(default baseline)으로 채택**하는 것.

### 📌 정리
`반응형의 입력값을 "화면 너비"에서 "컴포넌트가 가진 공간"으로 옮기기`

#### 핵심
> 브레이크포인트는 전역 뷰포트 너비를 기준으로 레이아웃을 불연속적으로 점프시킨다. 하지만 현대 UI는 컴포넌트 중심이고, 대부분의 반응형 변경은 사실 연속적인 스칼라 조정이다. **내재적 레이아웃(구조) + 유동 값(크기) + 컨테이너 유닛(국소 크기) + 컨테이너 쿼리(구조 전환)** 4종으로 브레이크포인트를 기초가 아닌 선택지로 강등시키고, `@media`는 레이아웃이 아니라 기기 기능·사용자 환경설정 담당으로 역할을 재정의한다.

#### ⭐️ 앞으로 기억할 것
- 1. **반응형 변경 = 거의 다 스칼라 조정**
  진짜 구조 전환은 생각보다 드물다. 크기/간격/타이포는 `clamp()`로 연속화하면 미디어 쿼리 여러 개가 한 줄로 사라진다.
  ```css
  font-size: clamp(16px, calc(11.529px + 1.176vi), 20px);
  ```
- 2. **그리드 열은 `auto-fit` + `minmax`로**
  "N개 열 강제" 대신 "최소 너비만 지키고 알아서 채워" 로 사고를 바꾼다.
  ```css
  grid-template-columns: repeat(auto-fit, minmax(320px, 1fr));
  ```
- 3. **`cqi` vs `vi` — 기준이 다르다**
  `vi`는 뷰포트, `cqi`는 컨테이너 인라인 크기의 1%. 컴포넌트가 어디 놓일지 모를 때 `container-type: inline-size` + `cqi`면 위치 독립적으로 스케일된다.
  ```css
  .wrap { container-type: inline-size; }
  .card { font-size: 5cqi; }
  ```
- 4. **구조를 진짜 바꿀 때만 `@container`**
  세로→가로, 요소 숨김처럼 배치 자체가 바뀔 때. "화면이 얼마나 넓냐"가 아니라 "이 컴포넌트가 지금 공간이 얼마냐"를 묻는다.
  ```css
  @container (max-width: 32em) { .group { flex-direction: row; } }
  ```
- 5. **`@media`는 레이아웃 말고 환경 파악용**
  `hover`, `pointer: coarse`, `prefers-reduced-motion`, `prefers-color-scheme`, `update: slow` 등. 특히 `prefers-*`는 접근성 필수 항목이라 우선 챙긴다.
- 6. **`flex: calc(infinity) 1 <basis>` 패턴**
  grow를 무한대로 줘서 우선순위 영역이 남는 공간을 독식하되, basis로 최소 너비 보장 + wrap 유도. 사이드바+메인 2영역에 유용.

📌 결론
▎ 브레이크포인트는 안 죽는다. 단지 "맨 처음 의존하는 도구"에서 "필요할 때만 꺼내는 정밀 도구"로 내려간다.
▎ 입력값을 전역 뷰포트 → 로컬 컴포넌트 컨텍스트로 옮기는 게 사고방식의 핵심 전환.
▎ 결과: CSS는 깔끔해지고, 회귀 버그는 줄고, 컴포넌트는 어디 놓여도 탄력적으로 동작한다.
▎ ⭐️ 실무 적용 포인트 — 전면 재작성 X. 지금 미디어 쿼리에 의존하는 컴포넌트 하나 골라서 이 패턴들로 재구축 → 배포 → 배운 거 반영 → 반복. "충분히 반응형"에서 "진짜 적응형"으로 가는 길.
