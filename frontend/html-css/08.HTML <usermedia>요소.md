# HTML `<usermedia>` 요소

> **원문**: [Introducing the `<usermedia>` HTML element][ref-1] — Mari Viana, Minh Le (Chrome for Developers, 2026.06.29)
> **번역 출처**: [HTML `<usermedia>` 요소를 소개합니다][ref-2] — 샛별(@typo)

카메라/마이크 권한 붙일 때마다 `getUserMedia()` 호출 타이밍이랑 거절당한 뒤 복구 UX 때문에 매번 골치였다. Chrome 151부터 이걸 **HTML 태그 하나**로 처리하는 `<usermedia>`가 들어왔다길래 정리해둠. 얼마 전 봤던 `<geolocation>` 요소랑 같은 계열이다.

### 권한 "관리"에서 기능 "전달"로

처음엔 범용 `<permission type="camera">` 같은 요소(PEPC 제안)로 시작했는데, 방향이 바뀌었다. 기능별로 전용 요소를 만드는 **Capability Elements** 쪽으로.

- 1호: `<geolocation>`
- 2호: `<usermedia>` ← 이번 글

차이가 꽤 크다. `<permission>`은 "권한 상태가 뭐냐"만 알려주는 역할이었다면, `<usermedia>`는 **권한 요청부터 `MediaStream` 전달까지 전 과정을 중개**한다. 즉 권한 받은 다음에 `getUserMedia()`를 따로 또 부를 필요가 없다. 요소가 스트림을 바로 쥐여준다.

### 실제로 효과가 있었나?

Origin Trial 결과가 숫자로 나와 있어서 설득력이 있다.

| 서비스 | 결과 |
|--------|------|
| Cisco | 한 번 거절한 사용자의 권한 복구율 약 10% → 65% 이상 |
| Zoom | 카메라/마이크 캡처 에러 46.9% 감소 |
| Google Meet | "마이크 안 돼요" 피드백 17% 감소, 권한 복구 성공 131% 증가 |

솔직히 복구율 10% → 65%는 좀 충격이다. 기존엔 한 번 "차단" 누르면 사용자가 주소창 자물쇠 → 사이트 설정까지 찾아 들어가야 했으니… 거의 다 이탈했던 거다.

### 왜 `<usermedia>`를 써야 하나

#### 1. 의도와 타이밍이 명확하다
브라우저가 통제하는 요소를 **사용자가 직접 클릭**해야 프롬프트가 뜬다. 페이지 로드하자마자 권한 팝업 띄우는 안티패턴이 구조적으로 막힌다.

#### 2. 거절 후 복구가 쉽다
이전에 차단했어도 요소를 다시 누르면 복구 흐름을 탈 수 있다. 브라우저 설정 뒤질 필요 없음.

#### 3. 스트림을 바로 받는다
권한 체크 → `getUserMedia()` → 에러 분기… 이 보일러플레이트가 이벤트 리스너 몇 개로 줄어든다.

### 📌 1단계: 기본 마크업

`<geolocation>`이랑 똑같이 선언적으로 쓴다. 안에 넣은 버튼은 폴백용 콘텐츠 역할도 한다.

```html
<!-- 클릭하면 카메라/마이크 권한 요청 + 스트림 전달 -->
<usermedia id="cam">
<button>카메라 켜기</button>
</usermedia>

<video id="preview" autoplay playsinline muted></video>
```

### 📌 2단계: JS로 제약 조건 + 이벤트 연결

```js
const cam = document.getElementById('cam')
const preview = document.getElementById('preview')

// 원하는 하드웨어 조건 지정 (getUserMedia의 constraints랑 같은 모양)
cam.setConstraints({
video: { width: 1280, height: 720 },
audio: { echoCancellation: true },
})

// 권한 OK → 스트림이 요소에 담겨서 옴
cam.addEventListener('stream', () => {
preview.srcObject = cam.stream
})

// 실패 → DOMException이 cam.error에
cam.addEventListener('error', () => {
showToast(`카메라 접근 실패: ${cam.error?.name}`)
})

// 사용자가 프롬프트를 그냥 닫음
cam.addEventListener('cancel', () => {
showToast('권한 요청이 취소됐어요')
})
```

API 표면이 작아서 외우기 편하다.

| 이름 | 종류 | 설명 |
|------|------|------|
| `stream` | 읽기 전용 속성 | 권한 획득 후 받은 `MediaStream` |
| `error` | 읽기 전용 속성 | 실패 시 `DOMException` |
| `setConstraints()` | 메서드 | 해상도, 에코 캔슬링 등 미디어 제약 조건 설정 |
| `onstream` / `onerror` / `oncancel` | 이벤트 | 성공 / 실패 / 사용자 취소 |

### 📌 3단계: 스타일링 — 마음대로는 안 된다

권한 요소라서 **클릭재킹이나 속임수 UI를 막으려고** 브라우저가 스타일을 강하게 제한한다. 디자인 시안 받을 때 미리 알고 있어야 하는 부분.

| 제약 | 내용 |
|------|------|
| 가독성 | 글자/배경 대비 최소 3:1, 색상 알파값은 반드시 `1` (반투명 ❌) |
| 크기·여백 | 브라우저가 최소/최대 크기를 강제, 음수 `margin` 무시 |
| 시각적 무결성 | `transform`은 2D 이동(translate)과 비율 유지 스케일만 허용 |
| 의사 클래스 | `:granted`, `:hover`, `:active` 지원 |

```css
/* ❌ 투명하게 숨기거나 찌그러뜨리기 → 적용 안 됨 */
usermedia {
opacity: 0.3;
transform: skewX(20deg);
margin-top: -40px;
}

/* ✅ 권한 상태에 따라 스타일 분기 */
usermedia {
background: #1a1a1a;
color: #fff;
}
usermedia:granted {
background: #0a7d38;
}
```

`:granted` 의사 클래스가 은근 유용할 듯. 권한 상태 JS로 체크해서 클래스 토글하던 코드가 CSS 한 줄로 끝난다.

### 📌 4단계: 점진적 향상 & 마이그레이션

Chrome 151+ 에서만 되니까 당연히 폴백이 필요하다. 기능 감지는 `HTMLUserMediaElement` 존재 여부로.

```html
<usermedia id="cam">
<!-- 미지원 브라우저에선 그냥 일반 버튼으로 렌더링됨 -->
<button id="cam-fallback">카메라 켜기</button>
</usermedia>
```

```js
function onStream(stream) {
preview.srcObject = stream
}

if ('HTMLUserMediaElement' in window) {
// ✅ 신규 요소 경로
const cam = document.getElementById('cam')
cam.addEventListener('stream', () => onStream(cam.stream))
} else {
// 기존 getUserMedia 경로 — 클릭 시점에만 요청하는 건 동일하게 유지
document.getElementById('cam-fallback').addEventListener('click', async () => {
const stream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true })
onStream(stream)
})
}
```

미지원 브라우저는 모르는 태그를 그냥 인라인 요소로 취급하고 안쪽 `<button>`만 보이니까, 마크업은 하나로 두고 JS만 분기하면 된다. 이 패턴 깔끔하다.

Origin Trial 때 `<permission>` 요소를 썼다면:

- `<permission type="camera microphone">` → `<usermedia>`로 태그 교체
- 기능 감지 `HTMLPermissionElement` → `HTMLUserMediaElement`로 변경

### 앞으로 나올 것

- `<camera>`: 비디오만 필요할 때
- `<microphone>`: 오디오만 필요할 때

`<usermedia>`는 둘 다 쓰는 화상회의 같은 케이스용이고, 용도별로 더 쪼갠 요소가 나올 예정이다.

---

### 📌 정리
`권한 요청 + 스트림 획득을 태그 하나로`

#### 핵심
> `<usermedia>`는 카메라/마이크 권한 요청을 **사용자 클릭 기반의 선언적 HTML 요소**로 바꾸고, 권한을 얻으면 `MediaStream`까지 직접 넘겨준다.
> 거절 후 복구가 쉬워져서 실제 서비스(Cisco, Zoom, Meet)에서 복구율·에러율이 크게 개선됐다.
> 대신 스타일은 브라우저가 강하게 제한하고, Chrome 151+ 전용이라 폴백은 필수.

#### ⭐️ 앞으로 기억할 것
- 1. 권한은 "사용자 행동 이후"에 요청한다
페이지 진입하자마자 팝업 띄우면 거절 → 복구 불가 루트. `<usermedia>`는 이걸 강제하지만, 폴백 경로에서도 똑같이 클릭 시점에 요청하도록 맞추자.
```js
// ❌ 로드 즉시 요청
window.addEventListener('load', () => navigator.mediaDevices.getUserMedia({ video: true }))

// ✅ 버튼 클릭 시 요청
button.addEventListener('click', () => navigator.mediaDevices.getUserMedia({ video: true }))
```
- 2. 기능 감지는 `HTMLUserMediaElement`
마크업은 `<usermedia>` 안에 `<button>` 넣어서 하나로 두고, JS에서만 분기.
```js
if ('HTMLUserMediaElement' in window) { /* stream 이벤트 */ } else { /* getUserMedia */ }
```
- 3. 이벤트 3종 세트: `stream` / `error` / `cancel`
`cancel`(사용자가 그냥 닫음)이 `error`랑 분리돼 있다는 것. 실패 안내 문구를 다르게 가져갈 수 있다.
- 4. 스타일 제약을 디자인 단계에서 공유
반투명, 음수 margin, 기울이기/회전 transform 안 됨. 대비 3:1 이상. 대신 `:granted`로 상태별 스타일은 CSS만으로 가능.
```css
usermedia:granted { background: #0a7d38; }
```
- 5. Capability Elements 흐름 자체를 기억
`<permission>`(범용) → `<geolocation>`, `<usermedia>`(기능별) → `<camera>`, `<microphone>`(더 세분화). 권한이 필요한 웹 API는 앞으로 "전용 HTML 요소" 방향으로 갈 가능성이 크다.

> **📌 결론**
> ▎ `<usermedia>` = 권한 요청 + `MediaStream` 전달을 한 번에 하는 선언적 요소
> ▎ 사용자 클릭 기반이라 타이밍 문제와 거절 후 복구 문제가 같이 해결된다
> ▎ 스타일은 브라우저가 신뢰성을 위해 강하게 제한한다 (대비 3:1, 불투명, 제한된 transform)
> ▎ Chrome 151+ 전용 → `HTMLUserMediaElement` 감지 + `getUserMedia()` 폴백은 필수
> ▎ ⭐️ 실무 적용 포인트: 화상 통화/녹화 기능의 "카메라 켜기" 버튼을 `<usermedia>`로 감싸고, 기존 로직은 폴백으로 남겨두는 점진적 도입부터
